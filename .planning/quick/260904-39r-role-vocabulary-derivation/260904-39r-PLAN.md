## Decisions recorded (these are the plan; implement them, do not re-litigate)

### D-1 — Rank FIRST, cluster the head only. Fixed N = 200, not a recurrence cutoff.

`build_portal_vocabulary` currently calls `cluster_titles(sorted(counts))` — all 2,045
titles — and then `rank_top_families` keeps 8. It pays to cluster the entire tail in order
to discard nearly all of it. Invert: rank by recurrence first, send only the head.

**Head = the 200 most-recurrent titles**, ordered `(-count, title)` so the selection is
deterministic and tie-breaks never depend on dict order. Exposed as `HEAD_N = 200` and a
`--head N` flag (the operator's one live acceptance run may want to raise it without editing
the file mid-sitting).

**Why 200, from the measured numbers.** The failing call sent 2,045 titles as 16,079 input
tokens — ~7.9 tokens per title including JSON scaffolding. Output must echo each member
verbatim, so output cost tracks input cost. 200 titles projects to ~1,600 input tokens and
~1,800 output tokens, against a new ceiling of 8,000 (D-2) — roughly 4x headroom, so a
worse-than-projected clustering still completes rather than truncating.

**Why fixed N and not "count >= 2".** The defect IS unbounded output growth. A recurrence
cutoff has an unknown head size (2,045 distinct over 3,772 titled contacts, mean 1.84 — we
cannot know offline how many recur, and no executor task may probe live), so it could
re-blow the same ceiling. A fixed N bounds the prompt deterministically. That is the whole
point of the fix.

**What is lost.** A title outside the head never joins a family, so it contributes no
recurrence to any family and cannot itself become one. Acceptable, on two grounds:
(a) only `TOP_N_FAMILIES = 8` families survive ranking anyway, and a family assembled purely
from count-1 tail titles could never out-rank a head family — the tail is discarded either
way, this just stops paying to cluster it first; (b) the tail is not wholly lost downstream:
`role_classify.classify_title` matches on contiguous token runs, so a tail title like
"Senior Track Manager" still classifies against a head-derived "Track Manager" member. The
tail is lost only where its wording shares no token run with any head member.

**Honesty requirement:** `build_portal_vocabulary` must PRINT the coverage the head actually
achieved — `head titles / distinct titles` and `contacts covered by head / titled contacts`
— so the operator's live acceptance run reports whether 200 was enough instead of assuming
it. This is a measured number, not an assertion.

### D-2 — Truncation raises by name. Repair-retry only for a COMPLETE-but-unparseable body.

`stop_reason == "max_tokens"` is a capacity failure, not a malformed one. Retrying it
identically truncates identically and spends a second call to learn nothing. So:

- `stop_reason == "max_tokens"` → raise `RoleVocabularyDerivationError` naming the
  stop_reason, the head size sent, and the `max_tokens` ceiling. No retry.
- otherwise parse with `src.web_research._extract_json` (reuse — the repo already has the
  fence-stripping + regex-object-scan parser; do not write a second copy).
- parse failure on a complete body → **one** repair retry (CLAUDE.md §26.3: "Haiku invalid
  JSON -> Retry once with repair prompt"), sending back the unparseable text and asking for
  the JSON object alone. The repair response is checked for `stop_reason == "max_tokens"`
  too — a repair call can truncate as well. A second failure raises
  `RoleVocabularyDerivationError`.

**New ceiling: `max_tokens` 2000 → 8000**, justified by D-1's ~1,800-token projection. The
bump is not the fix and is not load-bearing alone — it is headroom over a now-bounded input.

### D-3 — Normalise once, at count time. Junk rule: fewer than 2 alphabetic characters.

`rank_top_families` drops any returned member not found in `counts` by exact match, so
normalisation applied to the titles SENT must be the same normalisation behind the `counts`
used to rank the results back. The safe structure is to normalise at the single ingest point:

- `_normalize_title(raw)` = `html.unescape` then collapse internal whitespace then strip.
  Applied inside `sweep_all_jobtitles`, so `counts` KEYS are already the exact strings sent to
  the model. `'AV &amp; Broadcast Senior Executive'` and `'AV & Broadcast Senior Executive'`
  become one key with merged counts instead of two competing head slots.
- The SAME `_normalize_title` is applied to each returned member before the `in counts` check
  in `rank_top_families`. One line, and it kills the entire silent-drop class rather than the
  one instance the UAT happened to see.
- Nothing heavier. No `&`→`and`, no punctuation stripping, no case-folding — `role_classify`
  does that at match time, and doing it here would mangle the verbatim titles the model is
  required to echo.

**Junk rule (deliberately conservative):** drop a title with fewer than 2 alphabetic
characters — `sum(c.isalpha() for c in title) < 2`. That removes `'+61407 911 185'`, bare
numbers and punctuation-only values. **Divergence from the UAT, stated:** G-62-5 also names
bare `'AV'` as junk; this rule KEEPS it. `'AV'` has two letters and may be a real department
label, dropping a real title is worse than keeping a phone number, and an unrecurring 'AV'
never reaches the head anyway. No length cap either: a pasted blob occurs once and is ranked
out by construction, so a second rule would only add a way to lose a real long title.

**Ordering, decided rather than left emergent:** the `SPARSE_THRESHOLD` check runs on the
POST-unescape, POST-junk-drop counts. Junk is not evidence of a vocabulary. (On this portal
the difference is immaterial — 2,045 vs 20 — but the ordering must be deliberate.)

### D-4 — The shipped 17-family vocabulary is never overwritten (hard constraint 4)

`operator-claude-plugin/config/role_vocabulary.yaml` currently holds
`version: lv-role-vocabulary-v2`, `top_n: 17`, `evidenced: false` — 8 original families plus
the 9 governance families plan 62-09 added and proved live at 41/43 selected. A working
derivation writing 8 evidenced families over that would be a regression: a live-proven
vocabulary silently discarded.

**Chosen branch: write to a separate path; never merge; never auto-adopt.**

- Derived output goes to `operator-claude-plugin/config/role_vocabulary.derived.yaml`.
  `role_classify.DEFAULT_VOCABULARY_PATH` names the shipped file exactly, so a sibling file
  is inert to the plugin.
- **Not merged.** `load_families()` returns a DOCUMENT-level `evidenced` flag and
  `offer_block()` keys the D-62-07 disclosure sentence off it. A document that is half
  counted and half invented has no honest value for that flag. A document is evidenced or it
  is not.
- On write, print the shipped labels that do NOT appear in the derived output —
  "adopting this file would drop: Chair, President, …" — plus the exact `cp` command to adopt.
  That is the operator's compare aid and the actual discharge of this constraint.
- `VOCABULARY_VERSION` `v1` → `v2`, matching the schema version the shipped file already
  carries, so an adopted file is not a version regression.
- `TOP_N_FAMILIES` stays 8 (D-62-06). Raising it to 17 to match the curated file is an
  operator decision, not a side effect of a bug fix.
- `.gitignore` gains `operator-claude-plugin/config/role_vocabulary.derived.yaml`. The derived
  file is a **run artifact, not a deliverable** — the tracked ignore rule is what keeps it from
  being swept into a plugin release, and is the opposite of the untracked-stray problem
  (`scripts/uat62_*.py`) that motivated the git-tracking constraint.

<objective>
Let one company carry more than one known domain, so an organisation whose website and mail
live on different registrable domains (Roma Turf Club: site `romaturfclub.com.au`, mail
`@romaturfclub.org.au`) stops having every genuine staff email held as
`email_domain_mismatch`.

Purpose: the recorded domain is CORRECT — the round's own ladder fetched
`www.romaturfclub.com.au/sitemap.xml` and read the committee page from that host. The record
is INCOMPLETE, not incorrect. The fix is an alternate-domain SET, each member still matched by
the existing equality-or-subdomain rule applied per domain.

Output: `company_domains`'s VALUE widens from a domain string to a domain string *or* an
iterable of them; `email_domain_relation` accepts the same; the SKILL documents where the
extra domains come from and that they are operator-supplied only.

Non-goals, stated so they are not drifted into:
- NOT the wrong-domain bug (`.planning/todos/pending/2026-09-04-provenance-aware-manual-protected.md`).
  Nothing here "corrects" `.com.au` to `.org.au` — that would break the discovery ladder,
  which needs the website host.
- NOT a looser match rule. Accepting a shared registrable label across eTLDs
  (`romaturfclub.com.au` ~ `romaturfclub.org.au` because both are `romaturfclub`) is unsafe:
  `<label>.com.au` and `<label>.org.au` are separately registrable in Australia and can be
  different organisations. That is the failure the ruling exists to stop.
- NOT a change to `company_domains`'s required-ness, to `extraction.hold_emailless`, or to any
  n8n workflow.
</objective>

## Decisions

Recorded here because they are the plan's substance, not its packaging. Cite the ID in the
code docstring and in the SKILL prose so the reasoning survives the commit.

**D-ad2-01 — `company_domains`'s VALUE widens to `str | iterable-of-str`; its required-ness
does not.** The map is still `{company NAME: recorded domain(s)}`, still a REQUIRED second
positional parameter with no default. An optional argument there would be a one-keyword bypass
of the operator's ruling; that reasoning is unchanged by this plan and the test pinning it
(`test_partition_for_dispatch_requires_company_domains_with_no_default`) is not modified.

**D-ad2-02 — the per-domain rule is untouched; only the number of domains changes.** `related`
becomes `any(ed == cd or ed.endswith("." + cd) for cd in cds)`. No new comparator, no eTLD
awareness, no public-suffix dependency, no shared-label heuristic. A single-string value
behaves byte-identically to today: it cleans to a one-element set and `any()` over one element
is the old expression.

**D-ad2-03 — alternate domains are OPERATOR-SUPPLIED ONLY. Nothing is auto-learned.** The
brief offered three sources; this is the choice and why.

- *Rejected: harvest the domain from a `mailto:` on the company's own crawled contact page.*
  It is decent evidence in isolation, but the crawl ladder is bound to the RECORDED website
  host — and whether that host is right is exactly what the companion todo
  (`2026-09-04-provenance-aware-manual-protected.md`, Brisbane Lions) says is currently
  unreliable and cannot self-correct. Auto-adoption composes the two open bugs: a wrong
  recorded domain sends the ladder to a stranger's site, and any `mailto:` found there is
  silently adopted as this company's second domain — a wrong record widening its own send
  gate, with no human in the loop. Secondary reason, true even with a correct record: a
  `mailto:` on a page is not evidence the company controls that domain's mail; it can belong
  to a webmaster, an agency, a registrar, a sponsor, or a partner club.
- *Rejected for now: an explicit confirm step.* A propose-and-confirm surface is real
  machinery — a proposal store, a re-entry point, and a round that pauses. The todo's own
  immediate workaround (the operator names the alternate before the round) already delivers
  the outcome for the cost of one typed value.
- *Chosen: operator-supplied, at the `company_domains` map the round already builds.* The
  operator naming the domain IS the confirmation; there is nothing to propose and nothing to
  adopt silently. A widened send gate stays a deliberate human act.

Deferred, recorded so the path is not lost: a `mailto:`-observed domain may later be
PROPOSED — surfaced in the held pile beside the mismatch reason that already names both
domains — and adopted only after the operator confirms. Never adopted from the observation
alone. Not built here.

**D-ad2-04 — absent or unusable still means `company_domain_unknown`, never `mismatch`.** A
company missing from the map, a value that cleans to nothing, an empty list, and a list whose
every member is unusable (a LinkedIn URL, an empty string) all hold with
`reason_code: "company_domain_unknown"`. This matters mechanically, not just tidily:
`enrichment._clean_domain` does `str(raw)`, so a list reaching it becomes
`"['romaturfclub.com.au']"` — a string that contains a dot and would read as a *mismatch*
against a real email. The `isinstance(value, str)` branch in the new normaliser is the only
thing standing between a list and that path, and it is pinned from both directions.

The unusable test applies to the map VALUE as a whole, not to the recorded domain alone: a
company whose recorded value is unusable but which carries an operator-supplied alternate has
that alternate as its only domain, and its rows become sendable against it. That is consistent
with D-ad2-03 — the operator typed it — and near-moot in practice, since `discovery_plan` /
`url_fallback` refuse a host-less company, so such a company yields no rows to partition. No
test needed for it.

**D-ad2-05 — a held reason names every domain that was compared.** One domain yields today's
exact string (`email domain thehartford.com does not match romaturfclub.com.au`) — byte for
byte, which is why the join only engages at two or more. Two or more yields
`... does not match romaturfclub.com.au or romaturfclub.org.au`, so the operator can see what
was actually checked and whether an alternate is still missing.

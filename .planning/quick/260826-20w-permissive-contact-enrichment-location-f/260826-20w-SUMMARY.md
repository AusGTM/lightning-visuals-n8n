# Quick 260826-20w: Permissive contact enrichment + location fields — Summary

Contact `email` is reclassified `fill_blank_only` @ confidence 80 (was `manual_protected`
@ 95, which no real ingest-lane candidate ever cleared) in both engines. A discovered
email now promotes into a blank HubSpot contact record and is flagged
`lv_enrichment_needs_review` for a human to see in the triage queue — non-clobber is
unchanged, an existing email is never overwritten. Five HubSpot-native contact location
properties (`city`, `state`, `country`, `hs_state_code`, `hs_country_region_code`) join
the enriched field set, sourced from Lusha's `location` object and Apollo's flat
`person.{city,state,country}` fields; `hs_*` codes are derived only from already
code-shaped values, never a name→code lookup table. Live disarmed proof (execution
`11958`) shows both mechanisms firing together on a real HubSpot contact. Both suites
green throughout (3111 pytest / 725 node, up from the 3108/717 baseline). Nothing pushed.

## The calibration: 85 is a cliff, not a distribution

Task 1 pulled executions `11932`–`11956` off workflow `950HPb7a1GgSAIyZ` via plain
`urllib` (project memory: `executions_client.py`'s `requests` transport fails in this
environment). Every contact merge decision sampled — across 8 executions on the
enrichment workflow — carried the **identical** `confidence: 85, source_provider:
"waterfall"`. The CSV ingest lane's `80` and the `hubspot_native` lane's `85` are static
code facts (`scripts/build_cloud_workflows.py:293,2868,2888`), not live traffic in this
window; the merge boundary discards per-candidate provider accuracy and always passes one
of exactly three flat numbers, so there is no finer distribution to tune against.

The chosen threshold is **80** — the highest bar that still admits all three real
ingest-lane constants (waterfall 85, hubspot_native 85, csv 80). Every level from 85 down
to 80 promotes the one real candidate observed (Football NSW / John Tsatsimas,
`johnt@footballnsw.com.au`), so the Football NSW proof alone doesn't distinguish 85 from
80 — the lane-admission column is what carries information, and 85 silently excludes the
CSV upload lane forever. Full walk table, withholding inventory (RELAX/KEEP dispositions
across all five source files), and the pin inventory are in
[260826-20w-CALIBRATION.md](./260826-20w-CALIBRATION.md).

**Notable finding from Task 1's sample:** contact `347569451461` (John Tsatsimas, Football
NSW) is *simultaneously* the plan's named "known test record" and the blank-email contact
the plan expected to have to search for separately — its `existingRecord.email` was `None`

**`hs_state_code` / `hs_country_region_code` derivation:** ONLY from an already

no state field; Apollo's is a full name), and Apollo's `hs_country_region_code` also never
fires live (its `country` is a full name). Lusha's `hs_country_region_code` fires live
100% of the time (its `countryIso2` is a dedicated code field). The code-shaped path for
both hs_* fields is exercised with synthetic fixtures in
`tests/n8n/normalizeProviders.test.mjs` to prove the logic is correct even where live
traffic hasn't exercised it.

## BUG 19 note (documented, not fixed — explicitly out of scope)

AFTER the contact patch is built, so a `create` still overwrites a waterfall-discovered
email with the caller's own identity email. This predates this task, is unchanged by it,
and is intentional (it prevents unbounded re-creation from an unseeded record) — per the
plan's explicit instruction, noted here rather than "fixed."

**Refinement of the orchestrator's rule (a), stated openly rather than applied silently.**
The brief defines a real loss as "a `merge_fired_with_unfilled_input` entry whose unfilled
input's declared producers RAN and emitted >= 1 item (use runData)". That predicate
false-positives on the very recording this task must reproduce, twice:

1. On 12354, `Companies Absent Sentinel Gate` is a declared producer of `Decide Company
   Action Merge` input 1, ran carrying items, and run 1 has input 1 unfilled — flagged as a
   loss, when its items in fact landed in run 0.
2. `runData[ifNode]` records the node's PRE-SPLIT input (walkWorkflow.mjs line 643). An IF
   that ran 2 items and routed both true, whose FALSE branch feeds the Merge, reads as
   "emitted >= 1 item" while having delivered nothing.

Under the run-indexed pending model a delivery carrying items ALWAYS lands in some pending
run, so the only shape where items are genuinely lost is **a pending run that carries items
and never fires** — which is exactly what MN-01's one-run cap creates and names
(`merge_pending_runs_undrained`). `starvedWithData` is defined on that shape below. The
INTENT of rule (a) — "filter trace.stalled to what is actually a loss under v1, one shared
definition, not 30 copies" — is honoured exactly; only the predicate is corrected. The
signature is the one-arg `starvedWithData(trace)` rather than the brief's `(trace, runData,
wf)` example: the walker has runData, `wf` and `mergeState` all in scope at stall-pass time,
and one arg means the ~30 class-(a) sites that destructure only `{ trace }` need no widening.

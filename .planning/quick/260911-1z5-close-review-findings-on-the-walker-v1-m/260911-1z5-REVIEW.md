## 2. New findings introduced (or left standing) by the closure round

### Blocker

#### NF-BL-01: `starvedWithData` — the ONE loss predicate 30 sites now depend on — is blind to row *annihilation* at 23 of the enrichment graph's 33 Merges

**File:** `tests/n8n/lib/walkWorkflow.mjs:908-935` (the export), `:406-457` (`mergeBuffers`), and every
class-(a) consumer.

The export's docstring states the load-bearing claim:

> under the run-indexed pending model a delivery carrying items ALWAYS lands in SOME pending run,
> so that is the only shape where a real row went in and never came out.

The premise is true; the conclusion is false. A delivery landing in a pending run says nothing about
what the *merge maths* does to that run when it fires with an unfilled input. For `mode: "combine"` +
`combineByPosition`, `mergeBuffers` computes `n = Math.min(...counts)` with an absent input
contributing `[]` → `n = 0` → **zero items out**. `combineAll` is the same (`combos` collapses to
`[]`). Real rows enter the Merge and nothing leaves, and the reported shape is
`merge_fired_with_unfilled_input`, which `starvedWithData` excludes **by design**:

```
graph: Real -> M.input0 (2 rows) | Dead -> M.input1 (returns [])
       M = { mode: "combine", combineBy: "combineByPosition", numberInputs: 2 } -> Sink

runData.M    = [[]]                     <-- 2 rows in, 0 out
runData.Sink = undefined                <-- nothing downstream ran
stalled      = [{node:"M", reason:"merge_fired_with_unfilled_input", run:0, missingInputs:[1]}]
starvedWithData = []                    <-- "no row was lost"
```

Scale: `n8n/wf_enrichment_cloud.json` has 33 Merges — **22 `combine/combineByPosition` + 1
`combine/combineAll` + 10 `append`**. Every carry-merge in the repo is `combineByPosition` (e.g.
`HubSpot Search Carry Merge`). This is the G-70-2/G-70-3 shape the whole instrument exists to see:
an input a gated sentinel failed to fill, silently eating the lane's rows.

Latency, stated honestly: **no walk in the current suite triggers it.** I instrumented a mirrored
copy of the walker to print any `combine`-mode Merge that fired with an unfilled input while a
filled input carried items, ran `node --test tests/n8n/*.test.mjs` in the mirror, and got **zero
hits** (the instrument itself was verified to fire on the synthetic graph above). One file,
`fieldProducerMatrix.test.mjs`, fails at file level in the mirror for unrelated path reasons — it
contains zero `walkWorkflow` references (static jsCode analysis only), so it is not a gap in this
scan.

That is why this is a blocker and not bookkeeping: it is the same *kind* of defect BL-01 named — a
green suite that cannot see a loss — narrowed to the shape where rows are actively destroyed rather
than merely never delivered, and installed as the single shared definition behind 30 assertions.

**Fix (small, and provably no false positive on the recording):** record the fired run's output
count when the run is pushed (both fire sites already have `merged` in hand), and widen the filter:

```js
// walkWorkflow.mjs — at both fire sites
state.runs.push({ sources: {...}, itemCounts: {...}, outputCount: merged.length });

// starvedWithData, v1 branch — add, keeping the merge_pending_runs_undrained arm as-is:
if (s.reason === "merge_fired_with_unfilled_input") {
  const run = trace.merges[s.node].runs[s.run];
  const carried = Object.values(run.itemCounts).reduce((a, b) => a + b, 0);
  return carried >= 1 && run.outputCount === 0;   // rows in, nothing out — annihilation
}
```

Mode-agnostic, and it does **not** fire on 12354's `Decide Company Action Merge` run 1 (append, 1
item in / 1 item out) — the case the plan's narrowing was written to protect. Add the synthetic
graph above as the RED-first case.

### Major

#### NF-MJ-01: BL-02's grouping rule is an *inference* presented as an observation, and its interaction with MN-01's cap can synthesize a phantom loss on a shape 4 committed Merges carry

**File:** `tests/n8n/lib/walkWorkflow.mjs:516-529` (the comment), `:646-668` (the rule).

The comment reads:

> ONE producer node-run's deliveries to SEVERAL inputs of the SAME Merge land in ONE pending run
> (Gate 11, 12354/12355/12356: `Companies Absent Sentinel Gate`'s single node-run filled BOTH
> inputs of `Decide Company Action Merge`'s run 0).

The parenthetical is a true reading of the recording. The **rule** is not the only rule that
produces it: a plain per-input FIFO queue model (input *i*'s *k*-th delivery joins run *k*) also
yields `run0=[CA,CA]`, `run1=[RNR,null]` whenever `CA` reached input 0 before `RNR`. Gate 11 never
isolated the two, and this repo's own §13.0.3 discipline is that a `[documented]`/inferred rule must
not be written up as observed.

The two models diverge observably. On the *contested* shape — one producer feeding inputs 0 **and**
1 while another producer also feeds input 1, which is `Decide Company Action Merge`'s literal wiring
(`CA#0->0,1`, `RNR#0->0`, `Merge Company#0->1`, `Recompute Requested Sentinel Gate#0->1`,
pass-through`->0`) — I ran both arrival orders:

```
CA->[0,1] + X->[1], both delivering, either trigger order:
  walker: runs = [{0:CA, 1:CA}, {1:X}]      (arrival-order independent — that IS the grouping)
  per-input-queue model would give: run0 = (CA, X), run1 = (—, CA)
```

Attribution and pairing differ; **no loss either way**, so the divergence is benign here. It stops
being benign one input wider. With a 3-input Merge and two *overlapping* grouped producers — the
shape `Build Response Merge Stage 1` (6 inputs, 6 multi-input producers), `Build Response Merge
Stage 2` (7 inputs, 7), `Merge Winners Fan-In` and `Merge Company Fan-In` all carry — the atomic
"ALL of my inputs must be unfilled" rule forces a second pending run that MN-01's cap then refuses
to drain:

```
P -> M.inputs[0,1]   Q -> M.inputs[1,2]   (3-input append Merge, both deliver 1 row)
runData.M       = [[{id:'q'},{id:'q'}]]
starvedWithData = [{node:"M", reason:"merge_pending_runs_undrained", run:0,
                    filledInputs:[0,1], itemCounts:{"0":1,"1":1}}]   <-- P's row "lost"
```

Under the per-input-queue model run 0 would have been complete `(P,P,Q)` and nothing lost. So a
future batch that drives two overlapping sentinels turns a class-(a) site RED and points the reader
at a graph defect that may be a walker artifact. The scan behind the counts:
7 Merges in `wf_enrichment_cloud.json` (+2 in `wf_enrichment_local_live.json`) have at least one
producer feeding multiple inputs, and **every one of them** also has a second producer on one of
those inputs.

**Fix:** demote the comment to what was observed ("consistent with the recording; a per-input queue
model is equally consistent — not isolated by Gate 11"), append the divergence to
`.planning/todos/pending/2026-09-11-merge-input-contract-allows-many-producers-per-input.md` beside
the MN-01 question it already carries, and land the 3-input overlap graph as a pinned case so the
choice is visible rather than implicit. Do **not** change the rule offline — it reproduces the only
recording available.

## Answers to the orchestrator's four targeted questions

1. **Does the BL-02 producer-run grouping rule change any legacy behaviour?** No observable change,
   and the three legacy fidelity cases are zero-diff and green — but the comment's stated *reason*
   ("these edges are always enqueued directly adjacent to each other") is wrong: merge-targeted
   edges are now enqueued **after** all non-merge edges of the same `propagate` call, so they are not
   adjacent to their original neighbours. The correct reason is that legacy dequeues FIFO, which
   preserves the batch's relative order, and a producer's own merge delivery therefore still precedes
   anything its non-merge siblings enqueue — so legacy "first delivery to an input wins" cannot flip.
   Worth correcting in the comment; not a defect.
2. **Does it mis-attribute on `Decide Company Action Merge`'s actual shape (one producer → 0 and 1,
   another → 1)?** Not on that shape: `runs = [{0:CA,1:CA},{1:X}]` in **both** arrival orders, no loss.

   Gate 11 — NF-MJ-01. One input wider (overlapping grouped producers) the divergence becomes a
   phantom loss report.

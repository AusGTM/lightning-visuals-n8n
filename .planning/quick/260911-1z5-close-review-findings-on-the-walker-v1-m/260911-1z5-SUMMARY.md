## Deviations from Plan

### 1. [Rule 1 — design correction, recorded per the plan's own instruction] MN-02's guard scope widened from drain-only to shared main-loop+drain

- **Found during:** Task A, while implementing Step 8 (MN-02) exactly as the review's own snippet scoped it (a counter incremented only inside the drain's fire site).
- **Issue:** Once MN-01's per-Merge `drainedOnce` cap is in place, the number of times the DRAIN can fire is bounded by the number of Merge nodes in the graph — always strictly less than `nodes.length * 4`. A guard scoped only to the drain can therefore never throw; it would be provably dead code, and Task B's own requirement ("a guard never seen red is a comment") could not be satisfied by testing it.
- **Fix:** the fire-count guard (`recordV1Fire`/`FIRE_CAP`) is called from BOTH the main-loop arrival fire site (uncapped by count, correctly — `Decide Company Action Merge`'s own run 0 is a real double-complete-fire and must stay allowed) and the drain fire site, sharing one counter. This is the only shape that lets a genuine feedback cycle (a Merge whose own output re-completes its own input via the main loop) get caught.
- **Files modified:** `tests/n8n/lib/walkWorkflow.mjs` (`v1FiresCount`/`FIRE_CAP`/`recordV1Fire`, called from both fire sites).
- **Commit:** `747736fb`.

### 2. [Rule 1 — test-shape correction, recorded per the plan's own instruction] MN-02's guard test could not use the review's literal graph verbatim

- **Found during:** Task B, writing case (iii) exactly as the plan specified (`A -> M.input0, M -> Loop -> M.input1`, `assert.throws(..., /M/)`).
- **Issue:** Tracing that exact graph through the post-MN-01 walker: the drain fires `M` once (input 0 alone, via `drainedOnce`), the feedback delivery to input 1 opens a NEW pending run, and the outer `while (progressed)` loop simply skips `M` on the next pass because it is already in `drainedOnce` — no throw, no hang, the walk terminates cleanly with one `merge_pending_runs_undrained` entry. This is the CORRECT, intended consequence of MN-01's fix (it is in fact what stops the review's original infinite-refire finding), but it means the review's literal graph can no longer demonstrate the guard.
- **Fix:** landed TWO tests instead of one. `MN-02 graph` (`walkWorkflow.test.mjs:569`) uses the review's exact graph and asserts the terminating (non-throw) shape, documenting the deviation in-line. `MN-02 guard` (`walkWorkflow.test.mjs:596`) uses a genuine self-referential SINGLE-input Merge (`numberInputs: 1`, so any delivery is immediately "complete" and fires via the uncapped main-loop code) feeding back into its own input via a passthrough node — this DOES throw, proving the shared guard from deviation 1 is reachable.
- **Files modified:** `tests/n8n/walkWorkflow.test.mjs`.
- **Commit:** `205b9ffe`.

No other deviations. Every other Task A/B/C step landed exactly as the plan specified, including the "grouping alone reproduces the recording, stop here, do not touch `dequeue()`" branch of Step 6.

# Quick Task 260918-322: Fix F-S5 — verify_decision boolean false negative

A review approve that set a true/false field to `false` reported `failed` on a write that
had entirely landed; fixed with one shared value normaliser in the plugin's verifier plus a
boolean stringify in the backend's `reviewApply`, and the defect todo closed with the
verified root cause replacing its false original premise.

## What was built

**Task 1 — `_as_hubspot_text` in `operator-claude-plugin/scripts/review_decision.py`**
(`b95e38b2`). One module-level normaliser placed directly above `verify_decision`: a Python
`bool` maps to HubSpot's lowercase spelling, `None` maps to the empty string, everything
else goes through `str()`. The bool case is checked **first** because Python treats booleans
as an int subclass. Applied to **both sides of BOTH comparisons** — leg 1 (`would_write` vs
`intended`) and leg 2 (`properties` vs `expected`). A one-leg fix would have left the same
false negative reachable from the other. The leg 1 inline comment now names the normaliser
and says why lowercasing a boolean is required rather than incidental; the normaliser's own
docstring records its one narrow accepted consequence (a key whose intended value is already
blank and which is absent from `would_write` or the refetch now compares equal — both
patches originate in the same `clearPatch`, and HubSpot omits a blank property from a read).
No sentinel type was introduced to tell absent from blank apart.

Three tests added beside the existing read-back verification block, and the RED/GREEN split
came out exactly as the plan predicted:

| Test | Before | After |
|---|---|---|
| (a) live MRC shape: `False` intended, `"false"` refetched | **RED** (`'failed' != 'verified'`) | GREEN |
| (b) blank-is-not-false guard: `False` intended, `""` refetched | already GREEN | GREEN, now pinned |
| (c) `None` intended vs `""` refetched | **RED** (`'failed' != 'verified'`) | GREEN |

Plugin bumped `0.50.0` → `0.50.1` with its `## [0.50.1]` CHANGELOG section in the same
commit, per the release rule at the top of that file.

**Task 2 — boolean stringify in `n8n/code/reviewApply.js`** (`4c065964`). The map runs at
the `canonicalPatch` assignment, strictly **after** the enum check and the stale
compare-and-set, alongside the existing array-join, so neither gate can be bypassed by it.
Strings, numbers and null pass through untouched. The comment block now cites D-07 (43-01,
PIPE-01) as the precedent it completes — that stringify has only ever covered `clearPatch`,
and `canonicalPatch` was the missing half. Regenerated with
`scripts/build_cloud_workflows.py`; never hand-edited.

**Task 3 — the todo closed** (`e9f05e2b`). Rewritten in place and `git mv`'d to
`completed/`. Its original premise (HubSpot returning an unchecked `booleancheckbox` as an
empty string) was **never observed and is false for this record** — the rewrite says so
explicitly, replaces "What happened" with the real five-step chain, replaces "Fix (not
designed here)" with a "Fixed by" section, and records that blank still reads as a failure
and that the suggested false-equals-empty rule was deliberately not implemented. `kind`
stays `defect` — it was a real defect and it is fixed.

## The verified root cause

The plan's diagnosis held under test at every step:

1. `mergeCompanies.js` mints the candidate's `chosen_value` as the raw JS boolean `false`.
2. Neither `lv_is_hardware_vendor` nor `lv_produces_content` appears in
   `n8n/code/hubspotEnums.generated.js` (confirmed by grep: 0 hits), so both passed through
   `normalizeEnumValue` unchanged and reached `canonicalPatch` as bare booleans.
3. The PATCH body and the response's `would_write` therefore carried JSON `false`.
4. The plugin sets `intended = preview["would_write"]`, so Python saw `False`.
5. Leg 2 compared `str(False)` — `"False"` — against the refetched `"false"` and called it a
   mismatch, failing the whole approve. Leg 1 passed only because both of its sides were the
   same Python `False`.

The RED assertion in `reviewLoop.test.mjs` printed `false !== 'false'` before the fix,
confirming step 2 empirically rather than by reading alone.

<objective>
Fix F-S5: `verify_decision` reports a fully successful review approve as `failed` when an
approved field is a Python `bool`.

Purpose: an operator who sees `failed` on a clean write loses trust in the report and
re-attempts a write that already landed.

Output: a one-function normaliser in the plugin's verifier, a boolean-stringify in the
backend's `reviewApply`, and the defect todo closed.
</objective>

<verified_root_cause>
The todo's stated premise is FALSE and must not be implemented. Live evidence 2026-09-18
(operator curl on MRC company `9604614548` after the Stage E approve): HubSpot returns
`lv_is_gambling_operator` and `lv_is_hardware_vendor` as the string `false`. **The write
landed.** HubSpot did NOT return an empty string.

The real chain:

1. `n8n/code/mergeCompanies.js:495` mints the candidate's `chosen_value` as the raw JS
   boolean `false`.
2. `reviewApply` passes a non-enum-bound value through unchanged (`hubspotEnums.js:96`);
   D-07's stringify covers `clearPatch` only, never `canonicalPatch`. Confirmed: neither
   `lv_is_hardware_vendor` nor `lv_produces_content` appears in
   `n8n/code/hubspotEnums.generated.js`, so both reach `canonicalPatch` as bare booleans.
3. The PATCH body and the response's `would_write` therefore carry JSON `false`.
4. The plugin sets `intended = preview["would_write"]`, so Python sees `False`.
5. `verify_decision` leg 2 compares `str(False)` (`"False"`, capital F) against the
   refetched `"false"` and calls it a mismatch — so the whole approve reports `failed`.

Leg 1 passes because both of its sides are the same Python `False`. Only the two boolean
fields failed; every string field on the same record passed. Consistent with the evidence.

**Task 1 fixes this against the backend deployed today.** Task 2 is hygiene on the source
of the bare boolean; it is NOT a substitute for Task 1.
</verified_root_cause>

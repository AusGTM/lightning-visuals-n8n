Land the standing drift guard first, so every remaining plan in this phase has a named, runnable
assertion to turn green rather than a hand-rolled ad-hoc check. Per D-11 the harness is two layers:
a pytest module (`tests/test_scoring_parity.py`, fixtures parametrized from
`config/icp_scoring.yaml`, oracle `compute_icp_score`, live calls behind an opt-in env var) and a
thin `scripts/` wrapper that runs the sweep and writes a JSON verdict report. Per D-12 it has two
cadences: a cheap read-only recompute over the real-record sample for the unattended sweep, and the
full create/exercise/delete fixture run on demand. Per D-13 the F4/F7 veto regressions are proven
live end to end with no offline substitute.

Every defect this phase closes was invisible in the HubSpot UI and was found only by asserting live
behaviour against the oracle. That is what PARITY-01 and PARITY-02 exist to make permanent.

Expected state at the end of this plan: the offline tier is green, and the live tier is RED for
every defect not yet fixed. That is correct — each later plan's verify is the selector that turns
its own case green.

Purpose: a fix with no assertion is a fix that silently rots.
Output: one pytest module, one shared disposable-fixture helper, one report-writing wrapper.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test process -> HubSpot portal 22617666 | Live tier creates, patches and deletes disposable companies in a production CRM |
| scheduled sweep -> HubSpot portal | The wrapper reads real company records on an unattended cadence |
| harness verdict -> operator trust | The report is the artifact an operator acts on; a false green is worse than no report |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

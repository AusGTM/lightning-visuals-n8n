Two questions research could not settle without live credentials. The aggregator must handle
BOTH outcomes of each, degrade gracefully, and report what it actually found. It must never
fail on the unknown branch and never fabricate a number.

1. **Does `lv_closed_lost_reason` exist live on the Deal object at all?** It appears in zero
   repo code or config. `CLAUDE.md` §5.3 documents it as a *proposed* picklist. PROJECT.md's
   "0% filled" presupposes existence but has no confirmed live source. The report's message
   must differ between "this property does not exist in this portal" and "it exists and N of M
   closed-lost deals have it filled" — so the script must probe the deal property schema
   directly rather than inferring absence from empty reads. Also read HubSpot's native
   unprefixed `closed_lost_reason` alongside it and report both, since reps closing through
   the standard UI populate the native one.

2. **Does `hs_primary_associated_company` reliably join a closed-lost Deal to its Company?**
   No repo code reads that name. The aggregator's join must try it first and fall back to the
   Associations v4 endpoint for deals where it is empty, counting how many rows took each
   path and how many could not be joined at all. Unjoined deals appear in the report under an
   explicit unknown-tier bucket — never dropped silently, which would understate a tier.

43-04 Task 2 is where the operator runs this live and the answers get recorded.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Operator plugin -> backend repo | The plugin gains, for the first time, a documented path to execute backend code |
| Aggregator -> HubSpot Deal/Company API | Reads real revenue-outcome data; credentialed |
| Report artifact -> committed repo | A markdown file describing real customers and lost deals may be committed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-43-12 | Elevation of Privilege | Plugin credential surface | high | mitigate | The plugin holds no HubSpot token and gains none: the skill is SKILL.md only, shells out, and an acceptance criterion greps the example config for a token to prove none was added. `test_no_backend_imports.py` structurally blocks the import route (C3). |
| T-43-13 | Spoofing | The report's own claims | high | mitigate | Absent-property and empty-dataset are distinct, explicitly-worded outcomes; missing credentials exit non-zero rather than rendering a zero-findings report. A run that could not look must never read like a run that found nothing. |
| T-43-14 | Tampering | Aggregator write surface | medium | mitigate | Consumption only — an acceptance criterion greps the script for any HubSpot write helper and requires zero hits. No rubric file is opened for writing. |
| T-43-15 | Information Disclosure | Committed report | medium | mitigate | The report aggregates to counts per reason and tier; it names no individual contact and carries no provider payload. Deal/company identifiers appear only in the unjoined-rows diagnostic, which the operator reviews before committing. |
| T-43-16 | Repudiation | Skill shipped but not installable | medium | mitigate | The version bump and CHANGELOG cut are acceptance criteria here; the marketplace-clone refresh and post-install verification are operator steps in 43-04 (C5). |

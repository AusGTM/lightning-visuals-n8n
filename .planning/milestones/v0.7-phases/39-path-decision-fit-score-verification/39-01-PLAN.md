## Planner assumptions (unresolved edge coverage — surfaced, not dropped)

Two edge-coverage probes for DECIDE-01 came back unresolved. They are resolved here as
explicit planner assumptions, and pinned into plan 39-03's code so they become testable
facts rather than reader interpretation.

- **A-BOUNDARY (D-04 band edges).** The three D-04 outcome bands have no numeric boundary
  in CONTEXT.md. Assumed contract, implemented in `classify_latency_band`: band `a` is
  `median <= 600.0` seconds; band `b` is `600.0 < median <= 3600.0`; band `c` is
  `median > 3600.0`, or no observed score change before the poll timeout, or a change that
  only appears after a manual in-portal recalculation. Both boundaries are inclusive-upper
  (exactly 600.0 is `a`; exactly 3600.0 is `b`), and one step either side is asserted in
  the unit tests. Risk if wrong: a measurement landing exactly on a boundary is classified
  one band optimistically; mitigated because 39-DECISION.md records the raw median
  alongside the band, so a reader can re-band it.
- **A-PRECISION (latency measurement contract).** Elapsed time is measured with
  `time.monotonic()` — t0 taken immediately before the PATCH is dispatched, t1 immediately
  after the GET response that first shows the changed score value. HubSpot-side timestamps
  are never used (cross-clock skew). Poll interval is 5.0 s, so every reported latency is an
  **upper bound quantized up to the nearest poll** — resolution is ±5 s and the evidence JSON
  must say so. `statistics.median` of exactly 3 floats returns the middle sample verbatim (no
  averaging, no interpolation, no float tie-break). Raw floats go to the evidence JSON at
  full precision; only the human-readable summary rounds, to 1 decimal place. No overflow
  path exists — elapsed is bounded by the poll timeout. Risk if wrong: a sub-5-second recalc
  is reported as up to 5 s; harmless, because band `a` extends to 600 s.

## Summary

The genuine-event gap is real and the CONTEXT ground truth checks out on re-read (line numbers drifted by a handful of lines since 2026-07-28's first pass but every cited construct is present and semantically unchanged — see Ground-Truth Re-Verification below). The central design question — does fetch-by-id ADD, REPLACE, or reparametrize — resolves cleanly once one hard technical fact is established: **the n8n `n8n-nodes-base.hubspot` node's native `get` operation cannot be used for this job.** Sourced directly from `n8n-io/n8n`'s `HubspotV2.node.ts` (the code actually shipped for `typeVersion: 2.1`, the version this repo already pins), `contact:get` calls the sunset CRM v1 endpoint `/contacts/v1/contact/vid/{id}/profile` and `company:get` calls the legacy v2 endpoint `/companies/v2/companies/{id}` — and the company `get` branch never forwards a `properties` querystring at all (only `includeMergeAudits`), so it cannot even be asked for `lv_org_type` etc. Both legacy endpoints return properties as `{value, timestamp, source, ...}` objects, not the flat `propertyName: value` map every downstream Code node in this pipeline (`Adapt Search`, `Adapt Company Search`, `Enrichment Gate`, `mergeContacts.js`, `mergeCompanies.js`) already assumes. Wiring a native `get` node into this chain would silently corrupt every field it touches.

The fix: fetch-by-id must be a **second `n8n-nodes-base.hubspot` SEARCH node** (same `resource`/`operation: "search"` shape, same `typeVersion: 2.1`, same `onError: "continueRegularOutput"` idiom as the existing `HubSpot Search`/`HubSpot Company Search` nodes), filtered on `hs_object_id EQ {{ object_id }}` instead of `email`/`domain`. This hits the modern CRM v3 Search API (`/crm/v3/objects/{contacts|companies}/search`), returns the exact same flat-properties response shape `Adapt Search`/`Adapt Company Search` already parse, and needs zero new parsing logic invented — only a new filter value and a distinguishing failure-semantics tweak (below).

Given that, the ADD-vs-REPLACE question collapses to an ADD-with-conditional-bypass: a new `IF Bare Event` gate sits **after** `Build Identity`/`Build Company Identity` (not before — this is the load-bearing placement choice, see Architecture Patterns), routing a bare event (`object_id` present, no direct identity fields) through the new `HubSpot Fetch By Id` → `Adapt Fetch By Id` lane straight into `Enrichment Gate`/`Company Gate`, bypassing the redundant identity-field search entirely for that lane — while the existing direct-field/caller-envelope lane (`HubSpot Search`/`HubSpot Company Search` → `Adapt Search`/`Adapt Company Search`) is untouched, byte-for-byte, preserving every existing pinned test that asserts `Route By Object Type`'s edges and the two search nodes' filter shapes.

**Primary recommendation:** Add `IF Bare Event` / `IF Company Bare Event` gates immediately downstream of `Build Identity`/`Build Company Identity` (never upstream of them — that would break `test_object_type_router_sends_companies_events_to_the_company_branch`'s pinned edge assertions), each feeding a new `HubSpot Fetch By Id` search-by-`hs_object_id` node whose adapter (a NEW pure module, `n8n/code/adaptFetchById.js`, unit-testable) produces the exact `{existingRecord, lookup_failed}` contract `Adapt Search` already produces PLUS backfills `identity_keys` from the fetched record so `Enrichment Gate`/provider request bodies (which already read `identity_keys` by node name off `Enrichment Gate`/`Company Gate`, never `Build Identity` directly) work unmodified. Zero of the 7 frozen companies research/judge nodes are anywhere near this part of the graph; zero changes to `enrichmentGate.js`, `Enrichment Gate`, `Company Gate`, `Build Identity`, or `Build Company Identity` are required.

## Architecture Patterns

### Placement decision — resolves the central design question

**The gate goes AFTER the identity builders, not before them.** This is the one deviation from CONTEXT's literal Reasoned-Default wording worth flagging loudly, because it changes *which* existing test the plan must touch.

Two placements were evaluated:

| Placement | Pinned tests affected | Bare-event detection signal |
|---|---|---|
| A: `Route By Object Type` -> **new gate** -> `Build (Company) Identity` | Breaks `test_object_type_router_sends_companies_events_to_the_company_branch` (asserts the exact true/false-lane target node names) — this test WOULD need editing | Re-derive from raw event (`!$json.email && !$json.domain`) — redundant with what `Build Identity` computes one hop later |
| **B (recommended): `Build (Company) Identity` -> new gate -> {fetch lane / existing search lane} -> `Enrichment Gate`/`Company Gate`** | Zero existing pinned tests touched (`Route By Object Type`'s edges are unchanged; `HubSpot Search`/`HubSpot Company Search`'s own filter-shape assertions are unchanged since those nodes are untouched, just conditionally bypassed) | Reuse `identity_keys.email`/`identity_keys.domain` that `Build Identity` ALREADY computed — a bare event naturally produces `identity_keys.email = null` (since `normalizeEmailBasic(undefined) === null`) with zero new derivation logic |

Placement B is strictly cheaper (fewer new lines, zero test churn beyond additive assertions) and strictly safer (reuses computed state instead of re-deriving it). Recommended.

### Pattern 1: The `lookup_failed` extension — 0 results on a KNOWN id is NOT "confirmed absent"

**What:** `Adapt Search`'s existing contract treats a 0-result search as `existingRecord: {}` / `lookup_failed: false`, which `enrichmentGate.js`'s `decideAction({})` correctly reads as "create" — because for an email/domain search, 0 results legitimately means "this contact/company doesn't exist in HubSpot yet." For `Adapt Fetch By Id`, this is WRONG: a 0-result search on an `hs_object_id` that HubSpot itself just told us about via a live webhook event means the record was deleted (or merged, or the event is stale) between emission and processing — not "let's create a brand-new record" (you cannot even set `hs_object_id` on a HubSpot create call; it's server-assigned). `Adapt Fetch By Id` must map `results.length === 0` to `lookup_failed: true`, same as a network/auth error — reusing the EXISTING `create`->`skip` override in `ENRICH_GATE`/`ENRICH_CO_GATE` (`:836`, `:1560`) rather than inventing new vocabulary, exactly as CONTEXT's Reasoned Default 4 asks.

**When to use:** Every branch of `Adapt Fetch By Id`'s response handling (error item, malformed item, 0 results) maps to `lookup_failed: true`; only a genuine single/first match maps to `lookup_failed: false`.

**Example (proposed `adaptFetchById.js` shape):**
```javascript
// Source: pattern mirrors n8n/code's existing enrichmentGate.js purity conventions
// (this repo, tests/n8n/*.test.mjs proves every such module in isolation)
function adaptFetchByIdResult(searchItem) {
  const failed = !searchItem || searchItem.error || (searchItem.json && searchItem.json.error);
  if (failed) return { existingRecord: {}, lookup_failed: true };
  const res = searchItem.json || {};
  if (!Array.isArray(res.results) || res.results.length === 0) {
    // Known object_id, 0 results = deleted/merged since the event fired — NOT
    // confirmed-absent. Distinct REASON from Adapt Search's 0-results case,
    // SAME lookup_failed=true mechanism (Task 6 precedent, reused not reinvented).
    return { existingRecord: {}, lookup_failed: true };
  }
  const first = res.results[0];
  return { existingRecord: { ...(first.properties || {}), hs_object_id: first.id }, lookup_failed: false };
}
module.exports = { adaptFetchByIdResult, backfillIdentityKeys };
```

### Pattern 2: Node-name row recovery across the new HTTP hop (bd682a2 class)

**What:** `HubSpot Fetch By Id` is an HTTP-replacing node (native HubSpot node = HTTP request under the hood). `Adapt Fetch By Id` MUST recover the pre-hop row via `$('Build (Company) Identity').all()`, paired by index with `$('HubSpot (Company) Fetch By Id').all()` — never bare `$json` (which after the hop is the search response, not the row). This is the EXACT pattern `Adapt Search` already implements (`:973-975`) and the exact bug class `bd682a2` fixed on the research/judge chain. No new pattern is being invented here — it is a mechanical copy of an already-proven idiom, which is precisely why this hop is LOW risk if built this way and HIGH risk if a plan/executor free-hands it with `{...it.json}`.

**When to use:** Any Code node immediately downstream of any HTTP-replacing node in this file.

### Anti-Patterns to Avoid
- **Using the native HubSpot `get` operation for fetch-by-id:** Confirmed unusable — see Common Pitfalls.
- **Placing the bare-event gate before `Build Identity`/`Build Company Identity`:** Breaks a pinned edge test for no benefit (see Placement decision above).
- **A single object-type-conditional fetch node instead of two branch-specific nodes:** Every other stage in this file (Search, Adapt, Gate) is already branch-specific; a merged node would be the first exception and would need its own conditional property-list logic.
- **Reading `existingRecord`/`identity_keys` via bare `$json` anywhere after `HubSpot Fetch By Id`:** the bd682a2 bug class, verbatim.

## Common Pitfalls

### Pitfall 1: The native HubSpot `get` operation looks like the obvious answer and is wrong

**What goes wrong:** A plan/implementer reaches for `resource: contact, operation: get` (or `company`/`get`) because it is the most literally-named option and matches CONTEXT's own wording ("fetch the record fresh by object_id"). The built node imports cleanly, and — because n8n's UI resource-locator field for `contactId`/`companyId` accepts a plain numeric string too — it may even *look* like it will work when eyeballed in the n8n editor.

**Why it happens:** The n8n HubSpot node's V2 implementation (the version this repo pins, `typeVersion: 2.1`) was never fully ported off HubSpot's original v1 Contacts API / v2 Companies API for the `get`/`getAll`/`getRecentlyCreatedUpdated` operations — only `create`/`update`/`delete`/`search` were modernized to CRM v3 endpoints in places. This is visible directly in the source: `contact:get` -> `` `/contacts/v1/contact/vid/${contactId}/profile` `` (`HubspotV2.node.ts:1586`); `company:get` -> `` `/companies/v2/companies/${companyId}` `` (`:2198`), which never even sets a `properties` querystring param (compare to `company:getAll` at `:2211-2219`, which does).

**How to avoid:** Use `search` filtered on `hs_object_id`, per this document's recommendation.

**Warning signs:** If a plan's node JSON has `"operation": "get"` on a `n8n-nodes-base.hubspot` node anywhere in this graph, that is the signal this pitfall was not caught. A live smoke-test would eventually surface it as either (a) a 404/error if the legacy endpoint has actually been sunset in this HubSpot portal, or (b) — worse, silently — `existingRecord.domain` becoming `{value: "...", ...}` instead of a string, which would flow into `mergeCompanies.js`'s non-clobber comparisons as a truthy-but-wrong object and corrupt every field the fetch touched.

### Pitfall 2: Forgetting the identity_keys backfill means the provider waterfall silently gets nulls

**What goes wrong:** If `Adapt Fetch By Id` only produces `existingRecord`/`lookup_failed` (mirroring `Adapt Search` literally) and does NOT also backfill `identity_keys`, then for a bare event the row still carries `identity_keys.email = null` all the way to `Enrichment Gate` — and every provider request body (`Lusha Enrich`, `Apollo Match`, `Lusha Company`, `Apollo Org`, ZoomInfo) reads `identity_keys` **by node name off `Enrichment Gate`/`Company Gate`** (`:3265`, `:3272-3278`, `:3451`, `:3456` — confirmed, not `Build Identity`), not off the found record. Enrichment Gate would correctly compute `action: "enrich"` (since `existingRecord` is non-empty), but the provider waterfall would then fire with null email/domain — degrading every provider call to a guaranteed miss, silently.

**Why it happens:** It is easy to treat `Adapt Fetch By Id` as "just like Adapt Search" and stop at the existingRecord contract, missing that identity_keys serves a SECOND purpose downstream (provider matching) that `Adapt Search`'s branch never had to worry about because `Build Identity` already populated it correctly for that lane.

**How to avoid:** `Adapt Fetch By Id`'s output MUST include a re-derived `identity_keys` object, backfilled from the found record's own properties (email/firstname/lastname/company/`lv_linkedin_url` for contacts; domain/name for companies) — filling only currently-null keys, never overwriting a caller-envelope-provided value.

**Warning signs:** A functional/e2e test seeding a bare event should assert `identity_keys.email` (or `.domain`) is NON-NULL by the time it reaches `Enrichment Gate`/`Company Gate` — if this assertion is missing from the plan's test list, this pitfall is uncaught.

### Pitfall 3: Property-list mismatch — CLAUDE.md §18.4's aspirational list vs. what the portal actually has

**What goes wrong:** CLAUDE.md §18.4 specifies broad company/contact fetch property lists (including e.g. `lv_icp_fit_score`, `lv_named_account_priority`, `enrichment_lock_until`, etc.) that do NOT all exist as real custom properties in portal 22617666 yet — per this codebase's own comments (`:1495-1500`, `ENRICH_ADAPT_CO_SEARCH`'s header: "the 5 lv_* props that ACTUALLY exist in portal 22617666"). HubSpot silently drops unknown property names from a `properties` request and still returns 200 — so requesting the full §18.4 list would not error, but would waste request size and give a false impression of completeness.

**How to avoid:** `HubSpot Fetch By Id`'s `properties_csv` should be the SAME list `HubSpot Search`/`HubSpot Company Search` already request (proven live-compatible), reconciled per the table below — NOT a fresh transcription of CLAUDE.md §18.4.

**Reconciliation table (contacts):**

| Field | In existing `HubSpot Search` list? | Needed by | Recommendation |
|---|---|---|---|
| `email, firstname, lastname, jobtitle, phone, mobilephone, hs_object_id, lv_jobtitle_verified_at, lv_mobilephone_verified_at, seniority, lv_contact_enrichment_provenance` | Yes (all) | `Enrichment Gate`'s REQUIRED (`email,jobtitle,mobilephone`) + its stale-check cache keys + `Merge Winners`'s provenance read | Keep verbatim |
| `company` | No | `Build Identity`'s `identity_keys.companyName` fallback (`row.company \|\| row.companyName`) | ADD — needed for the backfill (Pitfall 2); HubSpot's default contact freetext-company property is literally named `company` |
| `lv_linkedin_url` | No | `Build Identity`'s `identity_keys.linkedin_url` (PN-1 rename, per `ENRICH_MERGE`'s own comment `:868-870`) | ADD — same reason |

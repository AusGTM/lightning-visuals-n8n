# Phase 16.4 — CONTEXT

**Domain**: Make the n8n Cloud enrichment webhook work against a GENUINE HubSpot private-app event. Such an event carries only `objectId` / `objectType` / `subscriptionType` / `propertyName` / `occurredAt` — no `email`, no `domain`, no name fields. Today both identity builders read those fields off the raw spread event, so on the live path they receive nothing and the whole run degrades to an empty identity. This phase closes the last structural gap before Track B can produce a meaningful live verification.

**Source**: User directive 2026-07-28 (`/goal`: "...before moving onto B2, plan, implement, and validate with tests, unit, integration and functional end to end testing"). Promoted from the Phase 16.2 Track-B follow-up list. Originally deferred in Phase 16 Task 6 as an explicit, documented budget carve-out — not an oversight.

**Why it blocks everything downstream**: Until this lands, a live run exercises only the synthetic caller-envelope path. That means the bd682a2 research-lane row-loss fix — the latent bug the Phase 16.2 cross-AI review caught in the *shipped* companies chain — still has never been verified under real conditions, and cannot be.

## Ground Truth (verified in-repo 2026-07-28)

**The shim being replaced**, `scripts/build_cloud_workflows.py:3033-3046`, inside `ENRICH_PARSE_EVENT_CLOUD`. Its own comment is an accurate confession:

```js
    // MINIMUM-scope shim (Task 6, documented per the plan's own budget carve-out):
    // Build Identity/Build Company Identity still read direct body fields (email/
    // domain/...) rather than fetching the record fresh by object_id — restructuring
    // them to fetch-by-id is a larger port than this task's budget. Spreading the raw
    // event here keeps that shim working for a direct-field test payload; a genuine
    // HubSpot event carries none of these fields, so on the real path Build Identity
    // sees only object_id/object_type until a follow-up phase adds the fetch-by-id.
    ...event,
```

`ENRICH_PARSE_EVENT_CLOUD` already emits a correct `object_id` (`event.objectId != null ? String(event.objectId) : null`) and a normalized `object_type`. The plumbing exists; nothing consumes it for retrieval.

**What consumes the spread today**:
- `ENRICH_BUILD_IDENTITY` (`:796-816`) reads `row.email`, `row.domain`, `row.linkedin_url`, `row.firstname`/`row.first_name`, `row.lastname`/`row.last_name`, `row.company`/`row.companyName` → builds `identity_keys`.
- `ENRICH_BUILD_CO_IDENTITY` (`:1476-1493`) reads `row.domain` / `row.website` / `row.company` / `row.name` → builds `identity_keys {domain, companyName}`.

**The non-obvious complication — a lookup already exists.** Immediately downstream of each identity builder there is ALREADY a credential-bound native HubSpot node:
- contacts: `HubSpot Search` (`:3204-3223`), `resource: contact, operation: search`, filtering `email EQ {{ $json.identity_keys.email }}`, requesting a specific property list including `hs_object_id`. `onError: continueRegularOutput`.
- companies: `HubSpot Company Search` (`:3426`), same shape anchored on `domain`.

So the webhook path currently does: event → (spread) → build identity from event fields → **search HubSpot by those fields**. With a real event, `identity_keys.email` is null, so the search filters on null.

This makes 16.4 a genuine design question rather than a drop-in insert, and the researcher must resolve it:

- **Does a fetch-by-id node ADD to the chain (before the identity builder), or REPLACE the search on the webhook path?** For a webhook event the record definitionally exists — HubSpot just emitted an event about it — so a search-by-email to discover a record you already have the id for is redundant. But the search is also load-bearing for the *scheduled/manual* entry paths and for the create-vs-enrich decision.
- **`Adapt Search` (`:3226`) already distinguishes confirmed-absent (200 + 0 results) from lookup-FAILED (non-200/malformed), tagging `lookup_failed=true`; the Gate wrapper overrides `action` create→skip on that flag** (Phase 16-01 precedent). A fetch-by-id has a different failure surface — a 404 on a known id means something else entirely (deleted between event and processing). The degrade path must be reasoned about, not inherited by assumption.
- **Back-compat is mandatory.** The direct-field / caller-envelope payload path is what the entire existing offline suite drives, plus the per-request `providers` selection resolution (16.1) rides on the same envelope. Breaking it would invalidate the suite rather than extend it.

**Row-flow hazard — the known-dangerous pattern in this codebase.** n8n HTTP/native nodes REPLACE `$json` with the response. This exact fact produced bd682a2 (the companies research-lane row-loss: post-HTTP Code nodes spread `{...it.json}` — i.e. the response — losing `existingRecord`/`scored`, so Merge Company returned `merge:null`). Adding a new HubSpot node hop means adding a new place this can happen. Every downstream read must recover by NODE NAME (`$('Parse HubSpot Event')`, `$('Build Identity')`, …), never bare `$json`. Phase 16.1 established this convention repo-wide for exactly this reason.

**The harness that proves it**: `tests/n8n/researchChainRowFlow.test.mjs` simulates n8n item-flow over the ACTUAL emitted node jsCode via `new Function`, modelling HTTP nodes as replacing the item json. Phase 16.3 extended the same mechanism to a single compiled node body. This is the substrate for the functional/e2e tier; it is not something to reinvent.

## Reasoned Defaults (the researcher should confirm or refute, not rubber-stamp)

1. **Additive, not a rewrite.** Prefer a new fetch node plus a narrow change at the identity builders over restructuring the branch topology. Phase 16.1's `Route By Object Type` precedent is instructive: an existing pinned node was left UNCHANGED and a new gate added upstream, rather than rewriting it, precisely because a test pinned its shape.
2. **Credential-bound native HubSpot node**, matching the existing `HubSpot Search` / `HubSpot Company Search` pattern (`n8n-nodes-base.hubspot`, typeVersion 2.1) — NOT a Code node reading a token. CLAUDE.md §18.1 / Phase 16-01 Criterion 5: zero `$env`/`$vars` may survive anywhere in the built Cloud workflow, and no secret literal may be committed.
3. **Identity derives from the FETCHED record.** After the fetch, `Build Identity` should read the record's properties (email/firstname/lastname/company) and `Build Company Identity` the company's `domain`/`name` — reached by node name, not `$json`.
4. **Fetch failure degrades safely** — no create, no clobber. Mirror the spirit of the `lookup_failed` create→skip precedent rather than inventing a new failure vocabulary, but reason explicitly about 404-on-known-id (record deleted post-event), 401 (credential/config error — stop, don't retry), and 429/5xx.
5. **Three test tiers, per the user's explicit instruction**: UNIT (identity extraction from a fetched record shape), INTEGRATION (Parse Event → fetch → identity builder over compiled node bodies), FUNCTIONAL/E2E (a bare-objectId event driven through the full compiled contacts AND companies chains to a patch payload). Plus a row-flow regression across the new hop in the bd682a2 style.

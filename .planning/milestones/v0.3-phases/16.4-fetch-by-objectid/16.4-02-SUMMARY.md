## Track B live checkpoint

**The entire fetch-by-objectId design rests on ONE unproven external fact:** that HubSpot's CRM v3 Search API accepts `hs_object_id` as a filterable property with the `EQ` operator, against portal `22617666`. This is corroborated by practitioner usage and by this repo's own search nodes already successfully REQUESTING `hs_object_id` as a returned property — but it has never been proven as a FILTER property against this specific portal, and this phase's fence explicitly forbids proving it (offline-only, no live calls).

**Verification command (run once, by an operator, before relying on this lane live):**

```bash
curl -s -X POST "https://api.hubapi.com/crm/v3/objects/contacts/search" \
  -H "Authorization: Bearer $HUBSPOT_PRIVATE_APP_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "filterGroups": [{
      "filters": [{ "propertyName": "hs_object_id", "operator": "EQ", "value": "<a known test contact id>" }]
    }],
    "properties": ["hs_object_id", "email"],
    "limit": 1
  }'
```

- **Pass condition:** HTTP 200 whose `results` array contains an object with `id` equal to `<a known test contact id>`.
- **Fail conditions:**
  - HTTP 400 whose error body names `hs_object_id` as an invalid/unfilterable property, OR
  - HTTP 200 with `results: []` for an id known to exist (the assumption is wrong: `hs_object_id` is not filterable this way, or requires a different operator/property name).

**In-flight diagnostic surface (if it fails live instead of at this one-shot check):** `Adapt (Company) Fetch By Id`'s `fetch_diagnostic` field distinguishes an errored response (carrying the actual error text, e.g. `"error: <HubSpot's 400 body text>"`) from a genuine zero-result response (`"zero-results: hs_object_id not found (deleted/merged/stale event)"`) — visible per-node in n8n's execution view. A SYSTEMIC filterability failure presents as **every bare event skipping** (via the existing `lookup_failed` → create-to-skip override), never as silent wrong data — the fail-closed design this phase proved holds regardless of which of these two failure shapes actually occurs live.

**Bounded fallback if the assumption is wrong:** replace the two fetch nodes (`HubSpot Fetch By Id`, `HubSpot Company Fetch By Id`) with credential-bound raw HTTP GETs to `/crm/v3/objects/{type}/{id}?properties=...` — the TRUE v3 single-object-by-id endpoint, which DOES support a `properties` querystring and DOES return flat values (unlike the n8n node's own single-record retrieval OPERATION, which is unusable for the documented v1/legacy-v2 reasons — a different failure mode from this one). **What this fallback changes:** only the two fetch nodes' `type`/`parameters` (from `n8n-nodes-base.hubspot` `search` to `n8n-nodes-base.httpRequest` GET). **What it does NOT change:** `n8n/code/adaptFetchById.js` already handles the single-object response shape (`res.properties` branch, proven by this plan's own unit tests) — both gates, both wrapper Code nodes, and every downstream consumer are unaffected.

- The Lusha Company GET/POST mismatch (`build_cloud_workflows.py` emits a POST to a static URL with the default identity_keys body; the live-verified contract is `GET /v2/company?domain=`, and `ENRICH_BUILD_CO_REQUESTS` already prebuilds an unused `lusha_company_url` for exactly that GET — flagged in 16.1-01, not fixed here).

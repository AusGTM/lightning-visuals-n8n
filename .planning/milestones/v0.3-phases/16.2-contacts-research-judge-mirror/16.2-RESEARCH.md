## Summary

The companies web-research→judge→verdict chain is built by **six code artifacts** in `scripts/build_cloud_workflows.py` — four `_enrich_*_js(cloud)` factory *functions* and two module-level *string constants* (`ENRICH_VALIDATE_RESEARCH`, `ENRICH_APPLY_JUDGE_VERDICT`) — each of which `inline()`s one or more hand-written JS modules from `n8n/code/` and wraps them in a per-item n8n Code-node body. Every one binds **company** fields (`lv_org_type`, `lv_produces_content`, hardware/gambling vendor flags), a **company** research/judge prompt, and the company escalation model. Mirroring to contacts is **net-new design**, not free reuse: the field set, prompts, escalation triggers, and verdict application are all company-shaped and must be re-authored for the two web-verifiable contact fields (`jobtitle`, `seniority`).

The **byte-identical-companies constraint has one hard mechanical consequence** that shapes the whole design: `inline()` (via `strip_module`, `build_cloud_workflows.py:44-70`) concatenates the **entire** text of each JS module (minus `require`/`module.exports`) into the company Code node's `jsCode`. Therefore **any edit to `judge.js`/`webResearch.js`/`scoreEnrichment.js` changes the companies' emitted jsCode and breaks byte-identity.** The only way to reuse the *field-agnostic* helpers (which are already generic) while keeping companies byte-identical is to leave those modules untouched and put **contact-specific field-bound logic in new sibling JS modules** that the *contact* nodes co-inline, and to parameterize the **Python factory functions** (which own the node scaffolding, kill-switch loop, HTTP wiring, and never-throw plumbing) with a `target` argument that **defaults to companies** so the companies call sites emit character-for-character what they emit today. Reuse lives at the Python-factory level; the field-bound JS is target-specific modules that reuse `judge.js`/`webResearch.js`/`scoreEnrichment.js` generic exports by co-inlining.

The **value question** resolves YES-but-narrow. All three providers already return `jobtitle`+`seniority` (`normalizeProviders.js:157-158,204-205,264-267`), so research is not primary acquisition — it is exactly the three things it is for companies: **gap-fill** (all providers miss → `providers:none` or no match), **stale-refresh** (`jobtitle` is `stale_refreshable`, `mergeContacts.js:28`), and **conflict-adjudication** (providers disagree on title/seniority). Gated OFF by default behind the inherited `ALLOW_WEB_RESEARCH`/`ALLOW_SONNET_ESCALATION` caps, the cost/PII exposure is opt-in and bounded, and the PII surface is minimized to *public role facts + evidence URL + provenance* (no phone/email/mobile).

**Primary recommendation:** Parameterize the **six Python factories** by a `target` config object (default = companies, byte-identical), add **two thin contact JS modules** (`contactResearch.js` validate-twin, `contactJudge.js` escalation+verdict) that reuse the field-agnostic exports of `webResearch.js`/`judge.js`/`scoreEnrichment.js` by co-inlining, extend `mergeContacts.js` with the additive `evidence`/`confidenceByField` opts `mergeCompanies.js` already has, and fold the adjudicated contact result into a **second `mergeContacts` call** inside `ENRICH_MERGE` — the exact structural analog of the second `mergeCompanies` fold in `ENRICH_MERGE_CO` (`build_cloud_workflows.py:1901-1931`). Scope contacts to **jobtitle + seniority only** in v1; omit the Phase-15.5 A/R/G/T grounding object (marginal value for a 2-field set).

## Task 1 — Factory anatomy + parameterization plan

### 1.1 The byte-identical mechanism (read this first)

`inline(*modules)` → `strip_module(name)` (`build_cloud_workflows.py:44-70`) reads each `n8n/code/*.js` file, drops `require(...)` lines and everything from the first `module.exports` onward, and concatenates the **full remaining text**. That text is embedded verbatim as the Code node's `jsCode`.

**Consequence:** editing `judge.js` / `webResearch.js` / `scoreEnrichment.js` in place — even a purely additive `opts.fields` parameter — changes the **companies** Judge Gate / Validate Research Output / Normalize+Score jsCode string. That is a byte-identity break. **[VERIFIED: build_cloud_workflows.py:44-70 + every `inline(...)` call site]**

**Node-id shift is NOT a byte-identity concern.** `nid()` is a monotonic counter (`build_cloud_workflows.py:357-362`); inserting contact nodes before the companies branch in build order will renumber every downstream synthetic `id`. This is cosmetic: n8n connections key on node **name**, and `deploy_n8n_workflows.compute_workflow_diff` + `bind_credentials` key on **name** (`tests/test_deploy_n8n_workflows.py:40-70`). No test byte-compares the checked-in `wf_enrichment_cloud.json`; the "frozen file" guards are **structural** (BFS reachability `tests/test_cloud_companies_branch.py:41-62`, no-`$env` `tests/test_architecture_guard.py:287-297`, flag/secret parity `tests/test_builder_flag_parity.py`). The checked-in `wf_enrichment_*.json` files WILL change (new nodes + shifted ids) and must be regenerated & committed — that is expected, not a violation. **[VERIFIED]**

**"Byte-identical companies" therefore means:** each companies Code node's `jsCode` **string** is unchanged. The clean guarantee: make every parameterized factory **default to the companies config**, so `_enrich_research_gate_js(cloud=True)` (no target arg) produces the current string exactly.

### 1.3 Recommended parameterization (keeps companies byte-identical)

**(A) Python factories → add a `target` config, default = companies.** Give each of the six a `target=COMPANIES_TARGET` parameter (a small dict/dataclass): `{ inline_modules, gap_predicate_js, system_prompt_js, task_name, subject_fields, required_fields, judge_fields, verdict_module }`. The companies call sites pass nothing → default → **identical output string**. The contacts call sites pass `CONTACTS_TARGET`. The wrapper *scaffolding* (kill-switch loop, `research_needed`/`needs_judge` short-circuits, HTTP body assembly, `judge_confidence_by_field` carry) is written once and shared. **This is "one set of building blocks."**

**(B) Field-bound JS → new sibling modules, not edits.** Because of §1.1, put contact field-bound logic in **`n8n/code/contactResearch.js`** and **`n8n/code/contactJudge.js`**. Each `require("./webResearch")` / `require("./judge")` / `require("./scoreEnrichment")` for the *field-agnostic* helpers (satisfies the node dev-oracle/test path) and is **co-inlined** into contact nodes only: `inline("webResearch.js","contactResearch.js")` for contact validate, `inline("escalation.generated.js","scoreEnrichment.js","judge.js","contactJudge.js")` for the contact judge gate. Companies keep `inline(..."webResearch.js")` / `inline(...,"judge.js")` unchanged → byte-identical.

**Why not parameterize the JS modules in place?** It is the cleaner-looking "no duplication" option but it is **incompatible with byte-identity** (§1.1): the whole module text is inlined into companies. `computeEscalation` also carries an explicit **2-argument arity discipline** ("must never grow a third argument", `judge.js:97-102`) — adding a `target`/config arg is exactly the shape that contract warns against. Sibling modules + co-inlining is the honest read of CONTEXT Decision 2's "thin contact wrapper around shared sub-helpers" fallback, and it is the one that provably holds companies byte-identical. **[VERIFIED: judge.js:97-102 arity comment; §1.1 mechanism]**

**Duplication cost of sibling modules:** small. `contactResearch.js` is ~1 function (a contact `validateContactResearch` + a `contactResearchCandidateFromHttpItem` that reuses `extractFinalJson`/`extractPageAge…`). `contactJudge.js` is `computeContactEscalation` + `_CONTACT_JUDGE_FIELDS` + `buildContactJudgeRequestBody` + a contact `applyUnadjudicated`/verdict; it reuses `applyCostCap`/`judgeVerdictFromHttpItem`/`applyJudgeVerdict` verbatim. The Phase-15.5 `scoreResearchCandidates` grounding is company-only and **omitted** for contacts v1 (see Task 3.4).

### 2.2 Contact research prompt (mirror of D3, `_enrich_build_research_request_js`)

Same single-HTTP-call, free-text-JSON, `web_search`-tool pattern as companies (`build_cloud_workflows.py:1669-1689`) — **never a forced `tool_use` schema** (D3 rationale: mixing a client tool with the server web_search tool defers the search to a 2nd round-trip). Contact-appropriate content:

- **System prompt** (contact analog of `researchSystemPrompt` `:1636-1659`): *"You are a B2B contact-verification analyst. Research the person's CURRENT role at their company from public sources — prefer the company's own team/about/leadership page and the person's public professional profile (e.g. LinkedIn). Return the current job title and a seniority band. Prefer `null`/unknown over guessing — an absent result is NOT evidence. For every field you set, cite a supporting URL in `evidence_by_field` keyed by that exact field name (evidence_by_field.jobtitle, evidence_by_field.seniority). Return ONLY one JSON object, no prose, no fences, matching: `{"data":{"jobtitle":<str|null>,"seniority":<str|null>},"evidence_by_field":{"<field>":"<url>"},"matched":<bool>,"confidence":<int 0-100>}`."*
- **User payload:** `task:"contact_role_research"`, `contact:{ name: <first+last>, company: <company name>, domain: <company domain> }`, `required_fields:["jobtitle","seniority"]`, `return_only_json:true`. Subject fields come from `identity_keys`/`existingRecord` (contacts identity carries name+company+domain; companies used `id.companyName`/`id.domain` `:1679-1683`).
- **`max_tokens`**: contacts return far less than the company ICP object — 1024 is ample (company uses 4096 `:1675` sized for a 5-field ICP + entity_resolution). Keep it a `target`-provided literal so the planner can tune.
- **PII (CLAUDE.md §16 / CONTEXT 7):** the prompt requests only the role fact + a citation URL; the candidate carries `data.jobtitle`/`data.seniority` + `evidence_by_field` — no scraped bio/contact PII is ever stored.

### 2.3 Research trigger gate (contact `needsResearch`)

Contact analog of `needsResearch` (`build_cloud_workflows.py:1599-1607`). Fires when a target field is unresolved:
- `jobtitle` blank in `existingRecord`, **or** `jobtitle` present-but-stale (`lv_jobtitle_verified_at` older than the 180-day TTL — the same staleness signal `mergeContacts.js:63-66` cache-key + the contacts gate `POLICY.jobtitle.stale_after_days:180` at `build_cloud_workflows.py:822` already track), **or**
- `seniority` blank.
- **Independent of providers** (Task 4): `providers:none` → no provider candidates → gap → research (if enabled) fills from scratch, mirroring companies.

The contact gate does **not** inline `taxonomy.generated.js` (no `EVIDENCE_GATED_ORG_TYPES`) — `inline_modules` for the contact target is empty (or just the flag consts). The kill-switch/cap loop is the shared scaffolding.

## Task 3 — Verdict + validation for contacts

### 3.1 Validation (`ENRICH_VALIDATE_RESEARCH` analog → contact validate node)

`webResearch.js:validateResearchOutput` (`:11-49`) is entirely company-shaped (org_type/content/produces_content/entity_resolution). The contact validate (`contactResearch.js`) instead:
- coerce `data.jobtitle` = trimmed string or `null`; `data.seniority` = trimmed string or `null` (no taxonomy normalization — contacts have no closed vocabulary; `seniority` bands are free provider strings today, `normalizeProviders.js:158`);
- carry `evidence_by_field`, `matched` (default true unless non-dict, mirroring OC-4), `confidence`;
- **reuse verbatim** `extractFinalJson`, `normalizeUrlForMatch`, `extractPageAgeByField`, and the never-throw try/catch skeleton of `researchCandidateFromHttpItem` (`webResearch.js:124-179`) — co-inline `webResearch.js` + `contactResearch.js`, call `contactResearchCandidateFromHttpItem`. Every failure shape resolves to an unmatched candidate (skip-not-retry, CLAUDE.md §26.2) exactly as companies.
- **Tri-state evidence sufficiency:** company `applyEvidenceSufficiency` (`judge.js:45-63`) demotes an unevidenced `lv_produces_content:true` to `null`. Contact analog: require an `evidence_by_field.jobtitle`/`.seniority` URL before a value may promote (see 3.3). A cheap contact version can demote a value whose evidence URL is missing to `null` (needs_review) — mirrors the same tri-state direction.

### 3.2 Verdict (`ENRICH_APPLY_JUDGE_VERDICT` analog)

`judgeVerdictFromHttpItem` (`judge.js:423-447`) is **field-agnostic** (never-throws, JG-3 min-confidence rewrite) — reuse verbatim by co-inlining `judge.js`. `applyJudgeVerdict` (`:454-484`) is nearly generic: promote/confirm at ≥`JUDGE_MIN_CONFIDENCE` writes `data[chosen_field]=chosen_value`; everything else routes to `applyUnadjudicated`. The only contact-specific piece is `applyUnadjudicated`'s demotion set (jobtitle/seniority drop, not vendor/org). So `contactJudge.js` provides `applyContactUnadjudicated` + a thin `applyContactJudgeVerdict` that calls the shared verdict-from-http + the contact unadjudicated. `judge_confidence_by_field` carry (`build_cloud_workflows.py:1824-1830`) is generic (keyed on `chosen_field`) → shared scaffolding.

### 3.3 Fold into `Merge Winners` (the 2nd merge call)

Companies fold the adjudicated research candidate as a **second `mergeCompanies` call** inside `ENRICH_MERGE_CO` (`build_cloud_workflows.py:1901-1931`), passing `evidence` + `confidenceByField` and shallow-merging the two disjoint patches. Contacts must do the same in **`ENRICH_MERGE`** (`build_cloud_workflows.py:863-884`): after the existing provider `mergeContacts` call (`:880`), if `row.research_candidate?.matched`, build a `researchData` of `{jobtitle, seniority}` (skip null/blank), call `mergeContacts(existingRecord, researchData, undefined, { source:"claude_web", confidence: rc.confidence, evidence: rc.evidence_by_field, confidenceByField: row.judge_confidence_by_field })`, and shallow-merge `canonicalPatch`/`provenance`/`cacheKeys` + concat `decisions` (disjoint keys: provider set is email/phone/mobile/jobtitle/seniority/linkedin — jobtitle/seniority overlap, so the research fold must take precedence for those two OR be gated to only-when-adjudicated; recommend: research fold wins for jobtitle/seniority since it is the judged value).

**Gap discovered:** `mergeContacts` (`mergeContacts.js:112`, opts `{source,confidence}`) does **NOT** support `evidence` or `confidenceByField`; `mergeCompanies` (`mergeCompanies.js:150-169`) does. Contact evidence-URL persistence (CONTEXT 7) and the judge per-field confidence override both need them. **Recommend the additive port** of `evidence`/`confidenceByField` + the `_needsEvidence` evidence-URL gate (`mergeCompanies.js:93-99,113-116,183-202`) into `mergeContacts.js`. This is **byte-safe for the existing contact caller**: every current `mergeContacts(...)` omits those opts, so the emitted provider-merge behavior is unchanged (proven the same way `mergeCompanies`'s `confidenceByField` addition was — "Every current caller omits this key and is therefore byte-identical", `mergeCompanies.js:158-161`). ⚠️ But note: `mergeContacts.js` is co-inlined into the **contacts** `Merge Winners` node only, not companies — so even a non-additive edit here cannot touch companies bytes. Still, keep it additive so `mergeContacts.test.mjs` stays green without churn.

### 3.4 Scope decision: omit the A/R/G/T grounding for contacts v1

`scoreResearchCandidates` (`judge.js:269-333`) builds the Phase-15.5 research-vs-prior grounding object fed to the judge. It loops `_JUDGE_DATA_FIELDS` and carries the self-confirmation guard. For a 2-field contact set its marginal value is low and it is the single most field-bound, hardest-to-reuse function (it would force either a `judge.js` edit — byte break — or a full duplicate). **Recommend omitting it in contacts v1:** the contact judge escalates on conflict/stale/miss and adjudicates from the retrieved evidence + `escalation_reasons` alone. This is the "minimal viable scope" answer to the key question. (If the pattern proves out, a contact grounding is a later additive step.)

## KEY QUESTION — Does contact web-research earn its LLM cost + PII exposure?

**Evidence-based recommendation: YES, but narrow (jobtitle + seniority only), and OFF by default.**

- **All three providers already return jobtitle + seniority** (`normalizeProviders.js:157-158,204-205,264-267`), so research is **not** primary acquisition. Its value is the identical triad that justifies it for companies:
  1. **Gap-fill** — when all providers miss (`gap_flag` true) or `providers:none` is requested, research is the only path to a title/seniority. `ENRICH_NORMALIZE_SCORE` sets `gap_flag` when zero candidates (`build_cloud_workflows.py:856`).
  2. **Stale-refresh** — `jobtitle` is `stale_refreshable` (`mergeContacts.js:28`) with a 180-day TTL already tracked (`lv_jobtitle_verified_at`, `mergeContacts.js:63-66`; gate POLICY `:822`). Titles change; providers lag.
  3. **Conflict-adjudication** — providers disagree on title/seniority (ungraded 0.6 accuracy, `normalizeProviders.js:157`); the judge resolves it from public evidence, exactly as it does company org_type conflicts.
- **Cost/PII is bounded and opt-in:** gated behind `ALLOW_WEB_RESEARCH`/`ALLOW_SONNET_ESCALATION` (default OFF) + per-run caps (Task 4). PII surface minimized to *public role fact + evidence URL + provenance* — no phone/email/mobile ever researched or stored (CONTEXT 1/7, CLAUDE.md §16).
- **Minimal viable scope if "yes but narrow":** jobtitle + seniority; omit the A/R/G/T grounding object (Task 3.4); defer persona/linkedin. This proves the symmetry the user asked for at the lowest net-new surface.

**Risk if wrong:** if reviewers judge the value insufficient, the fallback is jobtitle-only (drop seniority) — but seniority reuses the same node chain at ~zero marginal cost, so dropping it saves little. The larger lever is leaving research OFF by default (already the case).

## Open Questions / Risks

1. **Byte-identical-companies guarantee (highest risk).** Enforced only by the factory `target` defaulting to companies + sibling JS modules (never editing `judge.js`/`webResearch.js`/`scoreEnrichment.js`). *Recommend a Wave-0 snapshot test* pinning the companies factory output strings so any accidental shared-module edit fails loudly. The whole-file `wf_*.json` changes (new nodes + shifted `nid`s) — that is expected; do not treat a file diff as a byte-identity break.
2. **jobtitle/seniority key overlap in the 2nd merge fold.** Provider `mergeContacts` already writes jobtitle/seniority; the research fold writes the same two. Decide precedence: research (judged) value should win for those two when adjudicated. Not a disjoint-key situation like companies (`:1920-1929`) — the fold logic must handle the overlap explicitly, unlike `ENRICH_MERGE_CO`.
3. **New anthropic-bound node names** must be added to `SECRET_TO_CREDENTIAL_BOUND_NODES` (`test_builder_flag_parity.py:120`) and `deploy_n8n_workflows.py`'s credential map, or `test_cloud_references_all_six_secrets_via_credential_bound_nodes` and deploy binding break.
4. **`computeEscalation` 2-arg arity.** Keep `computeContactEscalation` at 2 args (`researchCandidate, existingRecord`) to honor the discipline `judge.js:97-102` warns about — pass field config via a module-level `_CONTACT_JUDGE_FIELDS` const, not a 3rd arg.
5. **Value question** (Task 5 / KEY QUESTION) — flagged for cross-AI review: is jobtitle+seniority research worth the LLM+PII exposure given provider coverage? Recommendation is YES-narrow-OFF-by-default; reviewers should pressure-test the target-field set and whether seniority earns its place.

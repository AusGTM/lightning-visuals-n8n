## Decisions Made

- **`EnrichTarget.entry_strip_markers`** (new dataclass field, default `False`) is how the target-parameterized factory adds contacts-only marker-stripping without editing `COMPANIES_TARGET`'s emitted output — proven byte-identical by the Plan-01 frozen guard rather than by code review alone.
- **`applyContactJudgeVerdict` is security-hardened beyond the companies analog**: the generic `judge.js` `applyJudgeVerdict` writes any model-supplied `chosen_field` verbatim, which is safe for companies (a closed, code-controlled field set) but not for contacts, because `ENRICH_PARSE_EVENT_CLOUD` spreads raw caller event props into the row — an allowlist restricted to `{jobtitle, seniority}` plus a decision/confidence gate is the only path that can ever write a field.
- **`foldContactResearch` is a write-safety gate, not adjudication** (SC-3's honest-mirror redefinition, per the reviews): companies does not adjudicate provider-vs-research either, only existing-record conflicts (via the judge). The fold prevents an unadjudicated research value from clobbering a good provider/existing value; it does not decide which candidate is "more correct."
- **Stale-timestamp fix scoped to contacts only** (gpt #6): `mergeCompanies.js` carries the identical latent bug (cache-key stamped unconditionally rather than only on promote) but is explicitly not touched here — Track-B follow-up, protecting the companies byte-identity guard.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] contactJudge.js's multi-line `require()` left a stale `require(...)` call inlined, causing a duplicate `const ESCALATION_CONFIDENCE_BAND` declaration**
- **Found during:** Task 2 (running the item-flow row-recovery regression test against the freshly built `Contact Judge Gate`/`Build Contact Judge Request`/`Apply Contact Judge Verdict` nodes)
- **Issue:** `build_cloud_workflows.py`'s `strip_module()` only recognizes a require destructure as either fully on ONE line (`const {...} = require(...)`) or the specific 4-line form `judge.js` itself uses (`const {` alone on its opening line, then names, then a line containing `require(`). My original contactJudge.js used a 2-line form (`const {...} =` on line 1, `require(...)` on line 2) that matched neither pattern, so BOTH lines survived stripping and were inlined verbatim into every Code node that co-inlines `escalation.generated.js` + `contactJudge.js` — re-declaring the same top-level `const` names `escalation.generated.js` already declares earlier in the same concatenated body. `new Function(...)` (both n8n's actual Code-node compiler and the row-flow test harness) threw a `SyntaxError` at compile time.
- **Fix:** Collapsed the require to a single line, matching the established convention `webResearch.js` and `judge.js` (for their OWN single-name requires) already use.
- **Files modified:** n8n/code/contactJudge.js
- **Verification:** `new Function(...)` compiles every affected node cleanly; the row-flow test passes; full offline suite green.
- **Committed in:** `3f3aa16` (Task 2 commit — the fix was folded into the same commit as the wiring that first exercised the compiled node body, since Task 1's own node tests never compile the co-inlined output the way the builder does)

## Issues Encountered

- **Test-harness/real-topology mismatch (not a product bug):** `tests/n8n/researchChainRowFlow.test.mjs` (and its contact mirror) runs every chain node UNCONDITIONALLY in a fixed linear order — it does not evaluate the `IF Contact Needs Judge` branch the way n8n itself would. With `ALLOW_SONNET_ESCALATION` baked `false` in the Cloud build (its always-off default), any seed row that fires an escalation reason gets `judge_capped:true` (budget 0) and demoted by `applyContactUnadjudicated` — but the harness still force-feeds it through `Build Contact Judge Request → Contact Judge Call → Apply Contact Judge Verdict`, a combination that can never occur in a real execution (the IF-false lane would have bypassed those nodes entirely). Resolved by choosing a seed row with a genuine gap (existing jobtitle/seniority blank) rather than a conflict, so escalation never fires and the cap/demotion path is never exercised — the same constraint the pre-existing companies `researchChainRowFlow.test.mjs` already lives under (its own seed row's `lv_org_type` is blank for the identical reason). Documented inline in the new test file.

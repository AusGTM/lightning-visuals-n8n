### Blocker: Credit HTTP nodes will be deployed without credentials

**Evidence:** The built workflow JSON intentionally has no `credentials` blocks. Deployment adds them through the static `NODE_CREDENTIAL_MAP`, as documented at `scripts/deploy_n8n_workflows.py:17-23` and implemented at `scripts/deploy_n8n_workflows.py:40-65`.

The current map only includes:

- Existing Lusha enrichment nodes at `scripts/deploy_n8n_workflows.py:54-55`
- Existing Apollo enrichment nodes at `scripts/deploy_n8n_workflows.py:56-57`
- Existing ZoomInfo mint nodes at `scripts/deploy_n8n_workflows.py:63-64`

Plan 02 adds new Lusha, Apollo, ZoomInfo usage, and likely ZoomInfo usage-mint node names, but `scripts/deploy_n8n_workflows.py` is absent from its `files_modified`.

Declaring `authentication: genericCredentialType` in a node does not bind a credential ID. `bind_credentials()` only binds names present in `NODE_CREDENTIAL_MAP`; unmapped nodes are left untouched at `scripts/deploy_n8n_workflows.py:135-154`.

**Suggested fix:** Add these files to Plan 02:

- `scripts/deploy_n8n_workflows.py`
- `tests/test_deploy_n8n_workflows.py`

Register every new usage/mint HTTP node in `NODE_CREDENTIAL_MAP`, and add a test that loads the built workflow, identifies every credential-requiring node, calls `bind_credentials()`, and asserts all receive the expected bound credential.

### Blocker: Terminal convergence does not establish a dependency on credit checks

**Evidence:** Plan 02 says the five real terminal nodes and two IF false lanes should connect to `Build Response`. It separately says credit HTTP nodes should run post-enrichment and that `Build Response` should read them by node name.

Connecting terminals directly to `Build Response` allows that node to execute without waiting for the credit nodes. A Code-node expression such as `$('Lusha Credit Check').all()` reads prior execution data if it exists; it does not create an execution dependency.

The current workflow makes order explicit through connections, for example:

- ZoomInfo mint/cache must complete before enrichment at `scripts/build_cloud_workflows.py:2469-2477`.
- Company research and judging must complete before merge at `scripts/build_cloud_workflows.py:2873-2890`.

Plan 02 does not provide an equivalent ordered connection from terminal completion through credit checks to response construction.

**Impact:** `Build Response` can return empty or stale credit results, or execute before credit checks. Credit reporting would not reliably be post-enrichment.

**Suggested fix:** Define the exact execution spine:

```text
all enrichment outcomes
  -> explicit wait/aggregation node
  -> IF Lusha Credit Requested
     true -> Lusha Credit HTTP
     false -> bypass
  -> IF Apollo Credit Requested
     true -> Apollo Credit HTTP
     false -> bypass
  -> IF ZoomInfo Credit Requested
     true -> ZoomInfo usage subgraph
     false -> bypass
  -> Build Response
  -> Respond to Webhook
```

The aggregation node must emit one request-level item before credit checks. `Build Response` must only be reachable after the final credit true/bypass convergence.

### High: The plans do not resolve multi-event and multi-terminal execution semantics

**Evidence:** The parser explicitly accepts arrays and emits one item per event at `scripts/build_cloud_workflows.py:2537-2557`. A single webhook execution can consequently produce:

- Contact creates
- Contact enriches
- Contact skips
- Company creates
- Company enriches
- Company no-op outcomes

Plan 02 connects all of those terminal branches to one Code node and one `Respond to Webhook` node but does not define how the items are collected into exactly one response execution.

Directly connecting multiple branches to the same node is not equivalent to a request-level barrier. A static BFS test proves reachability, not that the node executes once after all branches finish.

**Impact:** Credit endpoints may be called once per terminal branch or once per event rather than once per webhook. `Respond to Webhook` may execute multiple times, with the first result winning or later executions failing.

**Suggested fix:** Define a request-level aggregation contract and response shape. Add either:

- An n8n Merge/wait structure with explicitly configured input behavior, followed by a run-once aggregation Code node; or
- A proven equivalent synchronization mechanism.

Add an n8n execution-level test using a mixed event array. Static JSON graph assertions alone are insufficient for this behavior.

### High: Plan 01’s “Normalize executes exactly once” claim is not proven for mixed contact actions

**Evidence:** The parser can emit multiple rows at `scripts/build_cloud_workflows.py:2537-2557`. `Route Action` has separate create and enrich outputs, and both currently feed the same provider entry at `scripts/build_cloud_workflows.py:2842-2845`.

Plan 01 retains this structure by connecting both outputs to `IF Lusha Enabled`. If one request contains both create and enrich contacts, the gate has two incoming executions. The plan’s bypass test only follows graph edges and cannot prove that `Normalize + Score` executes once.

This is especially risky because `Normalize + Score` rereads all non-skip rows from `Enrichment Gate` at `scripts/build_cloud_workflows.py:1058-1063`. If the downstream chain executes once for each incoming action branch, each invocation can process the full row set and cause duplicate decisions or writes.

**Suggested fix:** Avoid converging create and enrich outputs without an explicit merge. The simplest design is probably a single pre-provider “action is not skip” IF:

```text
Enrichment Gate
  -> IF Provider Processing Needed
     true -> provider gates -> Normalize
     false -> Skip NoOp
```

The original `action` remains attached to each row, so create/enrich routing can happen after normalization. Alternatively, add a correctly configured Merge node and an execution-level mixed-action test.

### High: Unknown object types can still trigger provider calls

**Evidence:** `normalizeObjectType()` returns `"unknown"` for unsupported values at `scripts/build_cloud_workflows.py:2531-2535`. However, `Route By Object Type` sends its false lane to the contacts branch, explicitly covering “contacts/unknown,” at `scripts/build_cloud_workflows.py:2833-2838`.

With `providers: "all"` and an invalid or malformed object type, the request can therefore enter the contact provider chain.

**Impact:** The new provider selector is caller-controlled, but malformed events can still consume credits on the wrong object branch.

**Suggested fix:** Route three outcomes explicitly: companies, contacts, and unsupported. Unsupported events should terminate in a no-op/error response before any provider-selection gate.

### Medium: The CLI utility’s critical failure behavior is effectively untested

**Evidence:** The plan verifies only AST syntax and then runs the existing suite. It deliberately avoids collecting `scripts/check_provider_credits.py`, but no new test imports and exercises it.

The repository already has a strong hermetic pattern for live-operation scripts: `tests/test_deploy_n8n_workflows.py:17-27` monkeypatches HTTP calls to detect network leakage, and tests no-creds behavior at `tests/test_deploy_n8n_workflows.py:119-130`.

**Impact:** Regressions in timeout handling, malformed JSON handling, ZoomInfo token failure, or secret-safe output could pass the suite.

**Suggested fix:** Add `tests/test_check_provider_credits.py` with mocked requests covering:

- No credentials produces zero requests and exits 0.
- Partial credentials call only configured providers.
- Lusha success extraction.
- Apollo 403 returns `null`.
- ZoomInfo mint failure returns `null` without issuing usage GET.
- ZoomInfo usage extraction and fallback.
- Timeout and malformed JSON return `null`.
- Captured output never contains supplied fake secrets.

The script can remain live-only while its functions are unit-tested offline.

### Medium: `active: false` is not carried through deployment

**Evidence:** The builder can emit `"active": False`, but deploy payloads explicitly retain only `name`, `nodes`, `connections`, and `settings` at `scripts/deploy_n8n_workflows.py:157-168`. The `active` property is discarded.

The deploy script also does not call `/activate`, which is correctly documented at `scripts/deploy_n8n_workflows.py:25-26`. That protects newly created workflows, but it does not deactivate an already-active scheduled workflow on update.

**Impact:** The JSON marker is useful documentation and a test hook, but it does not by itself guarantee an updated scheduled workflow is inactive.

**Suggested fix:** State the guarantee precisely:

- Newly created workflows remain inactive because deployment never activates them.
- Existing active workflows remain active unless explicitly deactivated.

Add a deploy test proving no activation endpoint is called. If the requirement truly means “ensure inactive even on update,” add an explicit, safe deactivation operation for the scheduled workflow or make that an operator checkpoint.

### Low: Registry parity is not the same as a single extensible registration point

**Evidence:** The normalization registry remains a separate literal at `n8n/code/normalizeProviders.js:304`. Plan 01 proposes enforcing parity with Python `PROVIDER_REGISTRY`, which prevents half-registration but still requires edits in two places.

This is acknowledged in the research and is reasonable for a Python-builder/JavaScript-runtime split, but the success criterion should not overstate “one place.”

**Suggested fix:** Describe it as:

> One build-time registry plus one provider-specific normalization mapper, with parity enforced mechanically.

That matches the actual design.

## Open Questions

2. **Should `remaining_credits` be `[]` for absent/`none` providers?** The research labels this as an assumption; the plans treat it as decided.

6. **Must deployment deactivate an already-active scheduled workflow, or is inactive-on-create sufficient?** The current deploy implementation guarantees only that it does not activate workflows.

**Suggested fix:** (a) State the per-batch response semantics explicitly and confirm the caller contract accepts a per-batch partial response (SJ-3 is safe — its dispatch is terminal, `:3133-3134`, it consumes nothing). (b) Add an explicit guaranteed-response path for the 0-row/0-event case (e.g., route the parse node's empty output to Build Response too), or document that Respond-first-arrival is accepted. ### MED-2 — `check_provider_credits.py` importing `PROVIDER_REGISTRY` triggers codegen writes

**Mechanism:** `build_cloud_workflows.py:32-33` runs at import time: `(CODE/"taxonomy.generated.js").write_text(...)` and `escalation.generated.js`. ### MED-3 — The `providers` payload contract for HubSpot-style array bodies is unspecified, and the current parser would misparse an envelope

**Mechanism:** `ENRICH_PARSE_EVENT_CLOUD` does `const body = $json.body ?? $json; const events = Array.isArray(body) ? body : [body];` (`:2537-2538`). A HubSpot batch is a bare array — a caller can't attach top-level `providers` to it. The plan says "top-level `providers`, falling back to per-event `providers`", which implies an envelope `{providers: [...], events: [...]}` — but the current code would treat that object as **one event** (`[body]`), producing one garbage row. The plan never specifies the envelope or the parser change.

**Suggested fix:** Specify the contract in Plan 01 Task 1(3): `const events = Array.isArray(body) ? body : (Array.isArray(body.events) ? body.events : [body]); const providers = body.providers ?? event.providers;` — plus a `providerSelection.test.mjs`-adjacent parse fixture for the envelope shape.

## Executive Summary

The enrichment Cloud template (`build_enrichment_cloud()`, `build_cloud_workflows.py:2565`) currently runs its three providers as a **linear chain** — contacts `Route Action → Lusha Enrich → Apollo Match → ZoomInfo(subgraph) → Normalize + Score` (`:2842-2852`), companies `Build Company Requests → Lusha Company → Apollo Org → ZoomInfo Company → Normalize + Score Company` (`:2865-2872`). The downstream `Normalize + Score` node already decouples provider responses from the row: it pulls each provider **by node name** and pairs by index (`$('Lusha Enrich').all()`, `build_cloud_workflows.py:1058-1078`; companies at `:1523-1549`), and `toCandidates()` already returns `[]` for a falsy/absent provider response (`normalizeProviders.js:306-310`). So the runtime *already tolerates a missing provider gracefully* — the only gap is preventing the HTTP node from firing.

**Core structural finding:** the linear chain cannot support an *arbitrary* provider subset (SC-1). In a linear chain, if a provider receives 0 items it does not execute AND passes nothing to the next provider, so you can only drop a *suffix*, never (say) "Apollo only." The minimal correct change is to **fan the providers out in parallel from the gate node**, each behind its own per-provider gate; `Normalize + Score` already collects them independently by node name, so parallel fan-out is a connection-topology change, not a rewrite. Fanning out also fixes a latent fragility: in the current linear chain each HTTP node's response *replaces* `$json`, so `Apollo Match`'s body reference `$json.identity_keys.email` (`:2652`) sees Lusha's response, not the identity — the ZoomInfo split-gate already works around this by recovering the row by paired index (`:2298-2316`). Parallel branches read the original row straight from the gate.

**Recommended skip mechanism:** an **IF node before each provider HTTP node** (Approach a), structured exactly like the existing, offline-tested `ZoomInfo Token Gate → IF Needs Mint → [Mint HTTP] / [bypass]` topology (`:2289-2296`). Because `providers` is **per-run uniform** (parsed once, same for all rows), the IF passes either all rows or none to its provider — preserving the index alignment `Normalize + Score` depends on. This is trivially offline-testable as a built-JSON graph assertion (BFS, mirroring `tests/test_cloud_companies_branch.py`).

**Credit endpoints (live-curled this session, keys in repo `.env`):** Lusha `GET /v3/account/usage` → **200**, `credits.remaining` (real: 4118). ZoomInfo GTM `GET /gtm/data/v1/users/usage` → **200 but ONLY with `Accept: application/vnd.api+json`** (plain `application/json` → 406), remaining lives in a JSON:API `usage[]` array keyed by `limitType` (the real balance is `uniqueIdLimit` → `usageRemaining` 9345/12000). Apollo `POST /api/v1/usage_stats/api_usage_stats` → **403** with THIS key (not a master key) — must degrade to `null`. This is exactly the graceful-degradation case SC-4/SC-5 require, and it's live-confirmed, not hypothetical.

**Primary recommendation:** Parallel-fan the providers behind per-provider IF gates driven by an enabled-set computed in a new pure `n8n/code/providerSelection.js` (`resolveEnabledProviders` + `extractCredits`); make a Python `PROVIDER_REGISTRY` in `build_cloud_workflows.py` the single source of truth (adapter name → enrich-node spec, normalize key, credit descriptor), baked into the runtime credit node the same way `WRITE_SAFETY_DEFAULTS` is baked (`:749-763`); add one convergence "Build Response" node carrying `remaining_credits`; and set `"active": false` explicitly on the scheduled workflow dict with a pytest guard.

- Apollo endpoint is **POST-only** (`GET` → 404). `.continue-here.md` had POST right. THIS key **403s** (non-master). `[VERIFIED: live curl 403]`

The response is JSON:API, and remaining credits are NOT a flat `usageRemaining` field: they're in a `usage[]` array of three `limitType`s (`requestLimit` 0/0, `recordLimit` 0/0, **`uniqueIdLimit`** 2655/12000/9345). The `uniqueIdLimit` entry is the real redeemable-records balance. `[VERIFIED: live curl 200]`

**ZoomInfo token mint (reused from repo idiom, `zoominfoToken.js` + `build_cloud_workflows.py:1099-1116`):**
`POST https://api.zoominfo.com/gtm/oauth/v1/token`, `Authorization: Basic base64(client_id:client_secret)`, body `grant_type=client_credentials` (NO `scope`). Live: **200**, `token_type: Bearer`, `expires_in: 86400` (24h). Granted scope string already includes `api:account-summary:read` and `api:data:company`/`api:data:contact` — the usage call authorizes. `[VERIFIED: live curl 200]`

**Normalized `{provider, credits}` extraction (pure — belongs in `n8n/code/providerSelection.js` `extractCredits(provider, raw)`):**
```js
// Lusha: 200 body -> { credits: { total, used, remaining } }
lusha:    (raw) => raw?.credits?.remaining ?? null
// Apollo: 403 here -> raw is an {error,...}; no remaining field exists -> null (graceful).
//         (With a master key the body carries per-endpoint limits, not a single balance.)
apollo:   (raw) => (raw && typeof raw.remaining === "number") ? raw.remaining : null
// ZoomInfo GTM JSON:API: data[0].attributes.usage[] keyed by limitType.
zoominfo: (raw) => {
  const usage = raw?.data?.[0]?.attributes?.usage || [];
  const u = usage.find((x) => x.limitType === "uniqueIdLimit");
  return (u && typeof u.usageRemaining === "number") ? u.usageRemaining : null;
}
```
Every extractor returns `null` on any shape mismatch — the SC-5/SC-6 "never fail the run" contract. Apollo's live 403 is the built-in test case for the unknown/null path.

**`scripts/check_provider_credits.py` shape (SC-6):** mirror `provision_n8n_credentials.py` — `_has_*()` skip-to-exit-0 when a key is absent, `DRY_RUN`/two-key idiom, NEVER print a secret value (numbers are fine), and it is a live-only utility that must NOT be collected by the offline pytest suite (see Task 5). It mints the ZoomInfo bearer inline (same 4-line Basic-auth POST above) and applies the three extractors. On 403/4xx/timeout it reports `credits: null` per provider — it never raises.

## Task 2 — n8n mechanism for per-provider skip

**How `providers` enters and threads today:** the webhook body is parsed once in `Parse HubSpot Event` (`ENRICH_PARSE_EVENT_CLOUD`, `build_cloud_workflows.py:2530-2558`), which spreads the raw event onto every emitted row (`...event`, `:2555`). `providers` is *not yet parsed* — this phase adds `const providers = normalizeProviders(event.providers)` there and threads a per-row `provider_enabled` map / enabled-set onto each row so both branches (contacts via `Route By Object Type` false lane, companies via true lane) carry it.

**n8n 0-item skip semantics (the mechanism):** an n8n node that receives **0 input items does not execute** and produces no output. This is the lever for "the HTTP node must NOT execute" (SC-2/Locked #3). But it interacts badly with a **linear** provider chain (below).

**Why the current linear chain can't do arbitrary subsets:** contacts run `Lusha → Apollo → ZoomInfo` in series (`:2849-2851`); companies likewise (`:2868-2870`). If Lusha is gated to 0 items it doesn't run — and passes nothing to Apollo, so Apollo (and ZoomInfo) also don't run. A linear chain can therefore only drop a **suffix** of providers, not an arbitrary set like "Apollo only" (fails SC-1's "an array ⇒ exactly those"). Additionally each HTTP node's response replaces `$json`, so Apollo's `$json.identity_keys` reference (`:2652`) is already fragile — only the ZoomInfo split-gate survives it by recovering the row by paired index (`:2298-2316`).

**Recommendation — Approach (a): one IF node before each provider HTTP node, providers fanned out in PARALLEL.**

Restructure both waterfalls so the gate node fans out to N parallel provider lanes instead of a chain:
```
Route Action (contacts) / Build Company Requests (companies)
  ├─ IF lusha_enabled?    → Lusha Enrich / Lusha Company      ─┐
  ├─ IF apollo_enabled?   → Apollo Match / Apollo Org         ─┼─→ Normalize + Score(+ Company)
  └─ IF zoominfo_enabled? → ZoomInfo subgraph                 ─┘   (already pulls each by node name)
```
- The IF condition reads the per-row `provider_enabled.<name>` boolean (uniform across the run). True lane → the paid HTTP node; false lane → dead-ends (no rejoin needed — `Normalize + Score` independently pulls every provider by node name and index-pairs, `:1058-1078` / `:1523-1549`).
- Because `providers` is **per-run uniform**, an enabled provider's IF passes *all* rows in order → index alignment in `Normalize + Score` is preserved. `none`/blank/absent → every IF is false → zero provider HTTP calls, and the rest of the pipeline (identity, gate, scoring, research, writeback) still runs because `Normalize + Score` filters `Enrichment Gate`/`Company Gate` rows independently of the providers.
- **Precedent match:** this is the identical topology to the existing, offline-tested `ZoomInfo Token Gate → IF Needs Mint → [ZoomInfo Mint HTTP] / [bypass]` (`:2289-2296`, connections asserted in `tests/test_cloud_companies_branch.py:44-45`). It's the pattern CONTEXT points to.

*Approaches rejected:* (b) empty-input pass-through Filter — same 0-item skip, but a bare Filter still leaves the linear-chain suffix problem unless you also fan out, so it collapses into (a) with a Filter instead of an IF; an IF matches the ZoomInfo precedent and asserts more cleanly. (c) gate-emits-enabled-set with a routing Switch — a Switch has fixed outputs, so adding a provider means editing the Switch (violates SC-3 "one place"); one IF per lane keeps each provider self-contained in the registry.

**Offline-testable assertion (no live calls):** load `n8n/wf_enrichment_cloud.json`, BFS the connections, assert each provider HTTP node's only inbound edge is the *true* output of its `IF <provider> Enabled` node, and that the gate node fans out to all provider IFs in parallel (no provider→provider edge). Plus a pure unit test on `resolveEnabledProviders` (all/none/array/absent → set). This mirrors `tests/test_cloud_companies_branch.py` exactly.

**`responseMode: "lastNode"` implication (SC-5):** the webhook (`:2576`) returns whatever the **last-executed** node outputs. There are **multiple terminal branches** — contacts create/update/skip (`:2854-2861`, `Skip (NoOp)` `:2704-2710`) and companies create/update/fall-through (`:2892-2899`). With `lastNode` the response is nondeterministic across paths, and `remaining_credits` would only appear on whichever branch happened to end last. **Recommendation:** add a single **convergence node** where all six terminal branches join — a `Build Response` Code node (or switch the webhook to `responseMode: "responseNode"` + a `Respond to Webhook` node) — run the credit checks there (post-enrichment) and attach `remaining_credits`. One shared post-enrichment credit step (CONTEXT discretion) querying the **caller's requested set** (so a requested-but-unmatched provider still reports its balance) is simplest and matches "reported POST-enrichment."

## Task 3 — Adapter registry shape

**What exists today (two half-registries, aligned by name):**
- **Runtime normalize:** `const MAPPERS = { lusha, apollo, zoominfo }` in `normalizeProviders.js:304`, dispatched by `toCandidates(name, raw, ot)` (`:306-310`). This is already the one place normalize adapters live.
- **Build-time node emission:** hardcoded, provider-by-provider `_http_node(...)` calls in `build_enrichment_cloud()` — contacts Lusha `:2642`, Apollo `:2648`, ZoomInfo subgraph `:2661`; companies Lusha `:2757`, Apollo `:2760`, ZoomInfo `:2766`. No single list drives these.

**Recommendation — a Python `PROVIDER_REGISTRY` in `build_cloud_workflows.py` as the single build-time source of truth, baked into the runtime the `WRITE_SAFETY_DEFAULTS` way.** Because the Python builder *emits* the JS Code-node bodies, it can `json.dumps` a registry-derived config straight into the runtime nodes (exactly how `_write_safety_const` bakes constants, `:739-763`) — so there is genuinely one source and zero drift.

```python
# build_cloud_workflows.py — one entry per provider; adding a provider = one dict entry (+ its JS mapper)
PROVIDER_REGISTRY = {
  "lusha":    {"contact_node": "Lusha Enrich",   "company_node": "Lusha Company",
               "normalize_key": "lusha",   # must match normalizeProviders.js MAPPERS
               "credit": {"method": "GET", "url": "https://api.lusha.com/v3/account/usage",
                          "auth": "header", "header": "api_key", "path": "credits.remaining"}},
  "apollo":   {"contact_node": "Apollo Match",   "company_node": "Apollo Org",
               "normalize_key": "apollo",
               "credit": {"method": "POST", "url": "https://api.apollo.io/api/v1/usage_stats/api_usage_stats",
                          "auth": "header", "header": "X-Api-Key", "path": None}},  # 403 w/o master key -> null
  "zoominfo": {"contact_node": "ZoomInfo Enrich","company_node": "ZoomInfo Company",
               "normalize_key": "zoominfo",
               "credit": {"method": "GET", "url": "https://api.zoominfo.com/gtm/data/v1/users/usage",
                          "auth": "bearer", "accept": "application/vnd.api+json",
                          "path": 'data[0].attributes.usage[limitType=uniqueIdLimit].usageRemaining'}},
}
```
- **`"all"` resolution (SC-1):** `resolveEnabledProviders` takes the canonical name set from this registry (baked into the runtime as a `const PROVIDER_NAMES = [...]`), so `"all"` == every registry key with no separate list to keep in sync.
- **Credit node + `check_provider_credits.py`:** both consume the same `credit` descriptors — Python imports `PROVIDER_REGISTRY` directly; the runtime credit node gets them baked in as a const. The pure extraction logic still lives in `providerSelection.js extractCredits` (the `path` strings above are documentation; the three extractors are small enough to keep as explicit functions rather than a path-interpreter — ponytail: don't build a JSONPath engine for 3 providers).
- **The registry keys MUST equal `normalizeProviders.js` MAPPERS keys** — add a parity test (Task 5) asserting `set(PROVIDER_REGISTRY) == set(MAPPERS)` so a new provider can't be half-registered (mirrors the existing `test_builder_flag_parity.py` discipline).

*Minimal, not over-built:* two touch-points to add a provider — one `PROVIDER_REGISTRY` entry (drives node emission, `"all"`, credit check) + one `MAPPERS` mapper (its response shape). That's the irreducible minimum for a POC; a fully shared cross-language schema would be over-engineering. `ponytail: registry is a dict + a mapper, not a plugin framework.`

## Task 4 — Schedules inactive by default

**Current state:** **no** emitted workflow JSON sets `active` at all — `grep '"active"'` over `n8n/*.json` returns zero matches, and `build_scheduled_maintenance_cloud()` returns `{id, name, nodes, connections, settings}` with no `active` key (`:3341-3347`); same for `build_enrichment_cloud()` (`:2981-2987`). Safety today is **incidental**: n8n creates imported workflows **inactive by default**, and `deploy_n8n_workflows.py` deliberately does NOT call activate (`scripts/deploy_n8n_workflows.py:25-26` — "Activation … is a separate operator-runbook step … n8n creates new workflows inactive by default").

**Smallest change to make it explicit + tested (SC-7):**
1. In `build_scheduled_maintenance_cloud()`'s return dict, add `"active": False` (`:3341`). This is the explicit intent marker.
2. Add a pytest asserting `json.loads(n8n/wf_scheduled_maintenance_cloud.json)["active"] is False` (the tested invariant).
3. **Leave `build_enrichment_cloud()` as-is** (no `active` key). The enrichment webhook is caller-triggered and safe to activate; adding `active: true` there would itself be a live-activation act (Track B) and n8n ignores `active` on create anyway. Document that the operator activates ONLY the webhook workflow in Track B and leaves the scheduled one inactive until they choose to enable it.

**Caveat to state in the plan (don't overclaim):** the n8n Public API `POST /workflows` treats `active` as read-only on create — you activate via `POST /workflows/{id}/activate`. So `"active": false` in the JSON is an intent/documentation marker + the offline-test hook; the *functional* guarantee still rests on n8n's inactive-by-default + deploy-doesn't-activate (both already true and unchanged). That's precisely "explicit + tested rather than incidental," which is what SC-7 asks — no behavior change, just a guard against a future edit silently shipping an active schedule.

## Recommended approach (planner-ready)

1. **`n8n/code/providerSelection.js` (NEW, pure):** `resolveEnabledProviders(input, allNames)` (`"all"`/`"none"`/`""`/absent/array → Set) + `extractCredits(provider, raw)` (the three null-safe extractors from Task 1). Node-tested.
2. **`ENRICH_PARSE_EVENT_CLOUD`:** parse `event.providers` via `resolveEnabledProviders`, attach `provider_enabled` map to every emitted row; thread through both branches.
3. **`build_enrichment_cloud()`:** add `PROVIDER_REGISTRY`; fan providers out in **parallel** from `Route Action` (contacts) and `Build Company Requests` (companies), each behind an `IF <provider> Enabled` node (ZoomInfo keeps its split-subgraph *behind* its IF). Wire all provider lanes into the existing `Normalize + Score(+ Company)` (already pulls by node name — no change to its body beyond nothing).
4. **Convergence + credits:** add a `Build Response` Code node (or `Respond to Webhook` + `responseMode: "responseNode"`) where all terminal branches join; bake the registry `credit` descriptors in (WRITE_SAFETY_DEFAULTS idiom), run the checks for the requested set post-enrichment, attach `remaining_credits: [{provider, credits}]`; every failure → `credits: null`.
5. **`scripts/check_provider_credits.py` (NEW, live-only):** `provision_n8n_credentials.py` idiom — no-creds/two-key skip, ZoomInfo inline mint, three extractors, never prints secrets, never in offline suite.
6. **Schedules:** `"active": False` on `build_scheduled_maintenance_cloud()` return; pytest guard.
7. **Tests:** the five in Task 5; rebuild JSON; full offline suite green.

## Open questions / risks

1. **ZoomInfo `uniqueIdLimit` vs plan-specific credit semantics.** The live `usage[]` had `requestLimit`/`recordLimit` at 0/0 and the real balance under `uniqueIdLimit` (2655/12000, 9345 remaining). If a different ZoomInfo plan reports its balance under a different `limitType`, the extractor's hard-coded `uniqueIdLimit` pick would return `null`. Low risk (degrades gracefully, never fails), but the extractor should prefer the entry with a non-zero `totalLimit` as a fallback before returning null. `[VERIFIED: live curl — one account only]`
2. **Apollo credits are unknowable with this key.** THIS key is not a master key (403), so `remaining_credits` for Apollo will always be `null` until a master key is provisioned — AND even a master key's usage_stats returns per-endpoint rate limits, not a single credit balance, so "remaining credits" for Apollo may never be a clean scalar. Recommend the plan treat Apollo's `credits` as best-effort/nullable and not gate anything on it. `[VERIFIED: live curl 403]`
3. **`$json` replacement in parallel lanes.** Fanning out fixes the identity-loss for Lusha/Apollo, but confirm each parallel provider HTTP node reads the row straight from the gate (not a prior provider). The ZoomInfo subgraph already recovers the row by paired index; after fan-out it should read from its own upstream gate. Verify during planning that `Normalize + Score`'s index pairing (`rows[i]` vs `lusha[i]`) still holds when a lane is skipped (it does, because skip is per-run uniform — but a per-row future would break it). `[ASSUMED]` — pairing verified by reading the node body, not by live run.
4. **Webhook response for `none`/absent providers.** With zero providers enabled, `remaining_credits` should be an empty array `[]` (nothing requested) rather than three `null`s — confirm the desired shape with the caller contract. Low risk. `[ASSUMED]`
5. **n8n API ignores `active` on import.** The `"active": false` marker is intent + test hook, not a runtime gate; the real guarantee is n8n-inactive-by-default + deploy-doesn't-activate. If a future deploy step ever adds an activate call, the schedule could go live — the pytest guard only protects the JSON, not the deploy script. Consider a matching assertion in `test_deploy_n8n_workflows.py` that deploy never posts to `/activate` for the scheduled workflow. `[CITED: scripts/deploy_n8n_workflows.py:25-26]`

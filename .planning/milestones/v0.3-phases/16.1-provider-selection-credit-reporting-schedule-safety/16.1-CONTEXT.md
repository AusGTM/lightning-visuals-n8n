## Locked Decisions

1. **Per-request `providers` is the primary burn gate — NO global build-time kill-switch.**
   Decision (AskUserQuestion): "Per-request + schedules-off only." Do **not** build `ALLOW_PROVIDER_CALLS` / `MAX_RECORDS_PER_RUN` build-time constants. Cost-safety comes from (a) the caller-supplied `providers` node and (b) scheduled workflows shipping inactive. This is deliberately lighter than the original `.continue-here.md` recommendation — the `providers` node subsumes it.

2. **Absent / blank / `"none"` `providers` ⇒ enrich nothing (zero provider HTTP calls).**
   Decision (AskUserQuestion): "none — enrich nothing." A payload with no `providers` field (e.g. a real HubSpot-native event, which cannot add custom body fields) makes ZERO provider calls. The live HubSpot→n8n path must therefore inject `providers` explicitly (gateway/caller) to enrich — safe default, explicit opt-in. `"all"` ⇒ every registered adapter; an array ⇒ exactly those adapters.

3. **A disabled provider's HTTP node must NOT execute.** Gating happens BEFORE the paid call (skip the node / route around it), never by calling then discarding. This is the whole point — saving credits, not just filtering output.

4. **Extensibility = an adapter registry.** Providers are registered in ONE place so a new provider is added by a registry entry (+ its HTTP/normalize nodes) rather than by editing the parse / gate / normalize / merge nodes individually. Honour CLAUDE.md §16 provider-adapter contract (normalized `{provider, matched, confidence, data, evidence, cost, model_trace}` output).

5. **Credit endpoints validated live, not just from docs.** Requirement 1: web-search REAL provider docs AND run real curl against Lusha / Apollo / ZoomInfo GTM usage endpoints to confirm method/URL/auth/response-field AND which of THIS account's keys authorize the call. Prior doc-only research (`.continue-here.md`): Lusha `GET /v3/account/usage` (header `api_key`, `credits.remaining`); Apollo `POST /api/v1/usage_stats/api_usage_stats` (`X-Api-Key` MUST be a master key, else 403); ZoomInfo GTM `GET /gtm/data/v1/users/usage` (OAuth2 `api:data:*` scope, `usageRemaining`). Live curl confirms/corrects these.

6. **`remaining_credits` reported POST-enrichment in the webhook response**, nested per provider: `[{ "provider": "zoominfo", "credits": 4156 }, ...]`. A credit-check failure (bad key, non-master, 4xx/5xx, timeout) degrades gracefully — reported as unknown/null, NEVER fails the enrichment run.

7. **Scheduled workflows ship inactive.** The scheduled-maintenance workflow + SJ-1/SJ-2/SJ-3 emit `active: false`; deploy leaves them inactive (already the case — n8n creates workflows inactive); an operator enables each with one n8n UI toggle or one activate call. Make the default explicit + documented, not incidental.

8. **Build the fan-out SYMMETRICALLY; contacts research+judge is deferred to Phase 16.2.** (Decision 2026-07-24 via AskUserQuestion: "16.1 symmetric, judge in 16.2.") The user's north star: contact and company enrichment paths should MIRROR each other so components/nodes are reused (parameterized by target). In 16.1: build the provider fan-out + convergence + adapter registry so contacts and companies are structurally parallel, and make the per-provider IF-gate + convergence use SHARED node-factory helpers (not two hand-rolled copies) — those factories are the reuse seam. On the CONTACTS branch, leave a clean, documented insertion seam AFTER `Normalize + Score` / BEFORE `Merge Winners` (the exact spot where the companies branch has `Normalize + Score Company → Research Trigger Gate → … → Merge Company`) so Phase 16.2 slots the mirrored research→judge chain in without re-plumbing the fan-out. **Do NOT build the contacts research/judge chain in 16.1** — that is 16.2 (needs a contact research prompt, contact-specific escalation reasons, and contact verdict application; the judge/research JS is company-ICP-specific today).

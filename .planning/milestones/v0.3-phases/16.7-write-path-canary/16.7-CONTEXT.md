## The enablement mechanism (already built — do not rebuild)

`7f0dce4` widened the 16.5 deploy-time overlay so the canary needs **no rebuild and no source edit**:

```
ENABLE_BAKED_FLAGS=ALLOW_HUBSPOT_RECORD_WRITES,TEST_RECORD_IDS=201
```

Dry-run verified: rewrites `ALLOW_HUBSPOT_RECORD_WRITES -> "true"` 2× and `TEST_RECORD_IDS -> "201"` 2×, in `LV Enrichment` only. Its guards, all tested: writes cannot be armed without a non-empty allowlist in the same request; `ALLOW_HUBSPOT_CREATE` is refused unless record-writes is enabled too; allowlist values are charset-restricted to id/domain characters; cost caps and model names remain structurally non-overlayable; the fail-closed re-scan still refuses any workflow that would deploy carrying a literal other than the one requested.

`.env` is not readable by the agent — the deploy runs through a loader that reads `.env` in-process. Deploy and webhook-fire commands are also gated by the session's permission classifier and may need the operator to run them.

## Locked Decisions

1. **Contact `201` only.** `TEST_RECORD_IDS=201`, nothing else in the allowlist. Blast radius is exactly one record.
2. **`ALLOW_HUBSPOT_CREATE` stays `"false"`.** No record is created in this phase. Company `create`/`update` are exercised in a later phase, against a throwaway **test company**, with rollback — not here.
3. **Judged node-by-node from the execution API's `runData`.** Never from the webhook's HTTP status or body: `responseMode: responseNode` returns a well-formed 200 regardless of what executed, and canary run 1 returned a plausible `{"action":"skip"}` 200 while the fetch was silently 400ing.
4. **The protected-field proof is the point, not the write.** A run that writes successfully but does not demonstrate a protected field surviving has not proven the core claim.
5. **Rollback is exercised, not assumed.** Whatever is written to 201 is reverted once the proof is captured, and the revert is verified by re-read. `scripts/rollback_canary_proof.py` exists for this — check whether it fits before writing anything new.
6. **Restore is unconditional.** The disabled build is redeployed at the end regardless of how the run went, and confirmed by API read-back — both write-safety constants back to `"false"`, allowlist back to empty, workflow still `active`.

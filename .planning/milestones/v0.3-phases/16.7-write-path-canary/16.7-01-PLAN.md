<objective>
Make the HubSpot write nodes capable of carrying the merge's computed patch, so that Plan 02's armed
live window can actually prove something.

Purpose: the deployed `HubSpot Update` and `HubSpot Company Update` nodes are native HubSpot nodes with
an EMPTY `updateFields` map, documented in source as placeholders. They reference `$json.properties`
nowhere. A canary fired against them would issue a property-less update, leave contact 201 unwritten,
and let criterion 3 pass vacuously. That is BUG 11, found by reading the built artifact instead of by
spending an armed window on it.

Output: both update nodes on a credential-bound `httpRequest` PATCH that sends the computed patch and
fails hard on rejection; structural guards; and an offline oracle that writes down the exact live
request Plan 02 will confirm.
</objective>

<scope_note>
HONEST SCOPE STATEMENT.

The 16.7 CONTEXT scope fence forbids amending merge/promotion policy, ICP scoring, provider fan-out,
cost caps, and the research/judge JS. This plan touches NONE of those. It changes the TRANSPORT of two
write nodes, which is the same category of change Phase 16.6 made for the six company search nodes and
for the same reason: the native node cannot do the job.

It is nevertheless a change the 16.7 CONTEXT did not anticipate, because the CONTEXT assumed the write
path was merely disarmed rather than incapable. The finding that changes it is stated above and is
checkable in one command against the committed workflow JSON. If a reviewer disagrees that this belongs
in 16.7, the alternative is not "run the canary anyway" — it is "the canary cannot meet criteria 3 and
4 and must be re-planned". Running it against a placeholder node would burn the armed window and
produce a non-clobber claim backed by an empty write.

`company:create` / `company:update` live-defect status (ROADMAP 16.6 criterion 5): this plan changes
`company:update`'s transport, so the native-node question for that operation becomes moot rather than
answered — the native path is simply no longer used. `company:create` and the contacts `HubSpot Create`
are left native and UNVERIFIED, and stay unexercised because `ALLOW_HUBSPOT_CREATE` remains `"false"`
for the whole phase. Say that; do not imply coverage.
</scope_note>

<scope_note>
SEQUENCING DECISION, stated explicitly because the 16.7 CONTEXT requires it.

The BUG 10 companies verification (ROADMAP 16.6 criteria 1 and 7) runs in the SAME armed window as the
write canary, and is fired FIRST. Reasons:

  - The companies event needs NO write permission of its own. Company 9604614548 is not in the
    allowlist, so `_writeSafetyAllows()` denies it and the run must reach `write_blocked`. Firing it
    while writes ARE armed is therefore not a widening of blast radius — it is the only way to test the
    allowlist empirically instead of arguing it from source.
  - It costs nothing extra. `IF Research Needed`'s false branch connects directly to `Merge Company`
    (verified by connection-graph trace), so the companies chain reaches the node BUG 10 blocked with
    research disarmed and zero providers requested.
  - Deploying at all deploys the 16.6 fix, which has never been live. There is no version of this
    window in which the fixed companies transport is not running.

Firing it first means containment is established BEFORE any write is attempted. If the companies run
fails, that is a BUG 10 finding recorded as such, and the contacts write proceeds independently — the
two lanes share only the webhook.

CRITERION 4's WORDING IS STALE AND IS RESTATED HERE. ROADMAP 16.7 criterion 4 asks for a written field
carrying `_source`, `_confidence`, `_verified_at`, `_verified_by_model`, `_validation_status`. Phase 15
retired flat per-field metadata properties in favour of ONE provenance JSON blob per object
(`lv_contact_enrichment_provenance`), keeping only the cache-key datetimes top-level; and the merge's

`_verified_by_model` key at all (no model participates in a deterministic provider merge). Criterion 4

cache-key datetime, all quoted from a post-run record read. Say this in the SUMMARY; do not silently

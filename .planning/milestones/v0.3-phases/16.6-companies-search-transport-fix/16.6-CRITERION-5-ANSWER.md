# 16.6 Criterion 5 — the direct answer

**Answered:** 2026-07-29 (closing Gap 2 of `16.6-VERIFICATION.md`)

16.6-CONTEXT.md §"Open question the plan must answer explicitly" asked:

> `company:create` and `company:update` have **also never run live**. Do they share the
> defect? State the answer.

## The answer

**No. `company:create` and `company:update` do not share BUG 10's defect.**

BUG 10 is not a defect in n8n's HubSpot node generally — it is specific to an operation
value that does not exist. `_hs_search_node()` emitted `operation: "search"` for
`resource: company`, and the node's company branch is a flat if-chain with no case for it
and no default/throw, so `responseData` stayed undefined and serialized to `null` with
`status: success`. An operation that DOES have a dispatch branch cannot fail that way.

Verified against upstream source rather than restated from the BUG 10 RCA — fetched
`n8n-io/n8n:packages/nodes-base/nodes/Hubspot/V2/CompanyDescription.ts` on 2026-07-29. The
complete `companyOperations` option set is:

```
create  delete  get  getAll  getRecentlyCreatedUpdated  searchByDomain  update
```

`create` and `update` are both present. `search` is absent — only `searchByDomain`, a
different domain-path-only v2 operation that is not a drop-in. That single list is the
whole of BUG 10: our value was not in it, and the node did not validate.

## Why this still matters operationally, not just documentarily

It would be wrong to read this as "the company write path no longer touches the native
node." As of this commit the three cloud workflows carry these native
`n8n-nodes-base.hubspot` nodes:

| Workflow | Node | resource:operation |
|---|---|---|
| `wf_enrichment_cloud.json` | HubSpot Search | contact:search |
| `wf_enrichment_cloud.json` | HubSpot Fetch By Id | contact:search |
| `wf_contact_ingest_cloud.json` | HubSpot Search by Email | contact:search |
| `wf_scheduled_maintenance_cloud.json` | SJ-1 Set Requested | **company:update** |
| `wf_scheduled_maintenance_cloud.json` | SJ-2 Set Requested | **company:update** |
| `wf_scheduled_maintenance_cloud.json` | Dedupe Search (candidate contacts) | contact:search |

So `company:update` is still dispatched through the native node in two places. They are
safe — `update` is a real operation — but they are safe on the strength of the list above,
not because the native transport was retired. (`company:create` in the enrichment workflow
was separately moved to a credential-bound `httpRequest` POST by 16.9's BUG 13 fix, so it
is unaffected by construction.)

## Asking the general question found a second instance — BUG 18

The table above had one more row when this answer was first drafted:
`Dedupe Set Needs Review`, `contact:update`. **There is no `update` operation for
`resource: contact`** — upstream `ContactDescription.ts` offers
`upsert/delete/get/getAll/getRecentlyCreatedUpdated/search`. That node had BUG 10's exact
defect on the contacts side, in the same workflow as the six nodes BUG 10 fixed, and
survived because BUG 10's fix and its regression guard were both scoped to *company search*
rather than to the class.

Fixed in the same commit as this answer; see
`.planning/debug/bug-18-dedupe-contact-update-nonexistent-operation.md`. It was never live —
`LV Scheduled Maintenance` has never been activated.

That is the real lesson of criterion 5: the useful answer was not "no, create/update are
fine", it was the operation table that makes the question decidable for every node at once.

## Now enforced, not just stated

`tests/test_hubspot_native_operation_validity.py` asserts that every native
`n8n-nodes-base.hubspot` node in every cloud workflow names an operation that exists for
its resource, with the supported sets transcribed from the upstream descriptions above. It
fails on `company:search` specifically — BUG 10's exact input — so the answer to this
question is now a predicate rather than a paragraph someone has to remember to re-read.

## What this answer does NOT claim

It says nothing about whether the company write path works. `company:update` was later
found broken for two unrelated reasons (BUG 13's discarded patch, BUG 14's missing portal
properties, both fixed in 16.9), and `company:create` has still never run live. Not sharing
BUG 10's defect is a narrow claim about one operation-dispatch bug, not a clean bill of
health.

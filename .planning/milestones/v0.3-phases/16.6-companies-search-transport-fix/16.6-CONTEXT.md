## Ground Truth (established live, 2026-07-28 — do not re-derive, but verify before depending)

n8n's HubSpot node with `resource: company, operation: search` emits **one item whose `json` is `null`**.

Evidence, all captured from the real system:
- `HubSpot Company Fetch By Id` produced `[{json: null}]` on execution 10.
- The **byte-identical request** — same `hs_object_id EQ` filter, same 14-property list read straight out of the built node — issued directly against `POST /crm/v3/objects/companies/search` returns **HTTP 200, `total:1`**, with the real record (`domain: mrc.racing.com`, `annualrevenue: 206078000`, …).
- The node **does not throw**. With `onError` temporarily cleared and the run re-fired, the execution still reported `status: success`, no failing node, no message. The null propagates silently.
- Its input was correct: `Build Company Identity` emitted `object_id: '9604614548'`.
- The contacts twin `HubSpot Fetch By Id` — structurally identical config, only `resource: contact` — works and returns `{archived, createdAt, id, properties, updatedAt, url}`.

Downstream cascade: `Adapt Company Fetch By Id` reports `fetch_diagnostic: "error: unrecognized response shape"` and sets `lookup_failed: true` → `Company Gate` overrides its own `create` decision to `skip` (the Phase 16-01 fail-closed guard, working correctly) → `Normalize + Score Company` reads `$('Company Gate').all().filter(action !== "skip")` → **0 rows** → everything downstream, including the entire research/judge lane, never executes.

## Leading fix (confirm or refute)

Replace the company search nodes with **credential-bound `n8n-nodes-base.httpRequest` POSTs** to `https://api.hubapi.com/crm/v3/objects/companies/search`. This was already scoped as the bounded fallback in `16.4-RESEARCH.md` for a different reason, and `n8n/code/adaptFetchById.js` already parses the CRM v3 search-envelope response (unit-tested for both the search-envelope and single-object forms), so the adapters may need no change at all.

Constraints any fix must satisfy:
- **Credential-bound.** `predefinedCredentialType` / `genericCredentialType` with the provisioned `LV HubSpot` credential — never a token in a Code node, never `$env`/`$vars`. `tests/test_architecture_guard.py::test_no_env_or_vars_in_cloud_workflows` enforces this.
- **Registered in `NODE_CREDENTIAL_MAP`** (`scripts/deploy_n8n_workflows.py`), so `bind_credentials()` fails closed rather than deploying it unbound — the exact bug class fixed earlier today.
- **`_node_requires_credential()`** already treats an `httpRequest` node as requiring a credential only when its `authentication` parameter is credential-bearing; the new nodes must satisfy that guard, not evade it.
- **Contacts untouched.** Prove by diff that every `contact:search` node's type and parameters are byte-identical to HEAD. Contacts is the one live-proven path.
- Remember today's lesson: `properties` must be a **list**, not a CSV string, and HubSpot search rejects a string with a 400 VALIDATION_ERROR. `tests/test_hubspot_node_auth.py` guards this for `n8n-nodes-base.hubspot` nodes — if the transport changes, check whether that guard still covers the new node type or needs widening.

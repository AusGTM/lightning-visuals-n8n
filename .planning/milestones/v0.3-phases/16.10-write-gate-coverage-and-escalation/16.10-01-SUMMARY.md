# Phase 16.10 — write-gate coverage (BUG 15) and the first live Sonnet escalation

## BUG 15 — six write nodes with no allowlist at all

`_writeSafetyAllows()` and the `ALLOW_HUBSPOT_*` constants existed **only** in
`wf_enrichment_cloud.json`. The other two cloud workflows carried six write nodes between them
with no gate:

| workflow | write node |
|---|---|
| scheduled maintenance | `SJ-1 Set Requested` (sets `lv_enrichment_requested=true`) |
| scheduled maintenance | `SJ-2 Set Requested` (same) |
| scheduled maintenance | `Dedupe Set Needs Review` (sets `lv_enrichment_needs_review=true`) |
| scheduled maintenance | `Review Apply Update` — **and it carries `updateFields: {}`**, a third instance of the BUG 11 empty-field-map defect, so it is gated now but still writes nothing |
| contact ingest | `HubSpot Update` |
| contact ingest | `HubSpot Create` |

Both workflows are INACTIVE, so there was never live exposure — but activating either would have
written to HubSpot with nothing bounding the blast radius, which is the exact guarantee the write-path
canary existed to establish.

**Fix**: `splice_write_gates()` inserts a gate Code node between each write node and everything
feeding it, re-pointing every inbound connection. Implemented as a splice rather than by editing each
builder so a write node added later cannot quietly skip one.

**Guard**: `tests/test_write_gate_coverage.py` walks **upstream** from every write node in every cloud
workflow and fails if any path reaches a write without crossing `_writeSafetyAllows`. The walk accepts
both designs deliberately — enrichment gates *inside* `Decide Action` (which sets
`action: "write_blocked"` so the routing IF cannot match), the other two gate directly in front. It
also asserts the constants are declared wherever a gate reads them, and that all four ship disabled in
every committed workflow.

Two node tests asserted direct wiring into a write and were retargeted to hop through the gate rather
than deleted — the property each protects is unchanged.

Suite 542 pytest / 278 node, zero regressions. Rebuild deterministic. Deployed to all three workflows;
the two remaining stay INACTIVE.

## The first live Sonnet escalation — execution 18

Escalation had never fired because the judge consumes the **research candidate**: no research → no
judge → no Sonnet call. And a judge needs a *conflict*, which a blank field cannot produce. So the
conflict was constructed, on a throwaway company created and deleted for the purpose:

```
name       LV CANARY JUDGE TEST — delete me
domain     racing.com
lv_org_type  "hardware_vendor"        ← deliberately wrong, to force org_type_conflict
```

Armed `ALLOW_WEB_RESEARCH` + `ALLOW_SONNET_ESCALATION` only. **Writes stayed off**
(`ALLOW_HUBSPOT_RECORD_WRITES "false"`, empty allowlist), verified by pre-fire read-back — so this run
cost LLM spend and nothing else.

34 nodes ran. Quoted from `runData`:

| check | evidence |
|---|---|
| research gate | `research_needed: true`, no skip reason |
| `Claude Web Research` | real `claude-sonnet-5` response, `msg_011CdVPbJ7C5Y75AwaYaMJLx`; node error field `null`, output item carries no error key |
| row survival, **first** hop | `Validate Research Output` still carries `existingRecord`, `scored`, `identity_keys`, `object_id` — all four |
| **`Judge Gate`** | **`needs_judge: true`, reasons `["org_type_conflict", "confidence_band"]`** |
| **`Judge Call`** | real `claude-sonnet-5` response, `msg_011CdVPc72DiTKsByWGWQNZv`; node error `null` |
| row survival, **second** hop | `Apply Judge Verdict` still carries `existingRecord` and `scored` |
| `Merge Company` | merge **NON-NULL**, `canonicalPatch: {"lv_content_type": ["live_broadcast","streaming","highlights"]}` |
| the contested field | **`lv_org_type` is NOT in the patch** |
| containment | `Decide Company Action` → `write_blocked`; no write node in `runData` |

The judge's own verdict, verbatim:

> "The only evidence supplied (Wikipedia) directly identifies Racing.com as a broadcast/streaming
> media entity, not a hardware vendor. The prior_on_file value has no supporting citation and per
> policy cannot be treated as corroborating evidence, so the research candidate's broadcaster
> classification is adopted."

with `judge_flags: {unadjudicated: true, needs_review: true, insufficient_content_evidence: true,
reasons: ["org_type_conflict","confidence_band"]}`.

**The behaviour is the finding.** The judge reasoned from the evidence, reached a defensible
conclusion — and the pipeline still declined to promote `lv_org_type`, routing it to review instead,
because the evidence did not clear the bar for a contested high-risk field. It promoted only
`lv_content_type`, which had a citation. That is CLAUDE.md §21's high-risk write gate working on real
data, not a fixture.

This also verifies the companies-side `bd682a2` at both hops with the research lane genuinely
executing — a stronger result than execution 12, where the lane was skipped.

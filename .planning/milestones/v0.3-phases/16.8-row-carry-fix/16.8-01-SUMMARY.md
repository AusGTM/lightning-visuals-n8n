# Phase 16.8 — BUG 12 row-carry fix, and the write-path proof it unblocked

## The defect

`Merge Winners → Set Data Quality + Gap Flag → Decide Action`. That middle node was an
`n8n-nodes-base.set` typeVersion `3.4`, which emits **only its assigned fields** — so its live
output keys were exactly `['data_quality', 'gap_flag']` and `merge`, `existingRecord`, `object_id`
and `scored` were destroyed in transit. `Decide Action` then resolved
`row.existingRecord.hs_object_id` to `null` and `_buildContactPatch(undefined)` to `{}`, so
`_writeSafetyAllows()` denied whatever the allowlist said, no `action` key was emitted, `IF Enrich`
received zero items, and `HubSpot Update` never ran.

The contacts write path could not write to **any** record under **any** flag combination. Execution
8 (2026-07-28) shows the identical `Decide Action` output, so this predates the session — invisible
because writes were disabled and the webhook still returned a plausible 200.

## The fix, and the wrong turn on the way to it

**First attempt — the platform option — did not work.** `options: {includeOtherFields: true}` was
added, built, and deployed. Execution **14** read the option back as live on the deployed node and
the node **still emitted only `{data_quality, gap_flag}`**. That is not where or what this
typeVersion reads.

Rather than guess n8n's Set parameter schema a second time against production — the failure mode
that has now produced twelve live-only bugs in this project — the node became a **Code node that
spreads the row explicitly**:

```js
return $input.all().map((it) => ({
  json: { ...it.json, data_quality: "scored_waterfall", gap_flag: it.json.gap_flag === true },
}));
```

The node **name is unchanged**, so connections and every name-keyed map hold. The row-carry property
is now a property of code this repo controls and can test offline, not of a vendor parameter schema
it cannot.

Generated diff is confined to that node plus regenerated `id` values on sibling nodes (verified by an
id-scrubbed semantic diff: no other node body changed, `connections` byte-identical).

## Guard

`tests/test_row_carry.py` — RED before the fix (2 failures), green after:

1. The specific node pinned by name: must be a Code node, must spread `...it.json`, must still sit
   between `Merge Winners` and `Decide Action`, and must **not** regress to a Set node.
2. A sweep across all three cloud workflows: every `n8n-nodes-base.set` node **with a downstream
   consumer** must either carry the row or appear in `ROW_REPLACING_BY_DESIGN` with a stated reason.
3. A staleness check on that waiver list, so a future node reusing a waived name cannot inherit the
   exemption silently.

Swept and recorded as deliberately row-replacing: `Unsupported Object Type` and `Skip (NoOp)`
(terminal markers consumed whole by `Build Response`), `Set Config` (head-of-chain seed, no upstream
row), `Set Review` / `SJ-2 Skip (NoOp)` / `Review Stale (NoOp)` (terminal, no consumer).

Suite **533 pytest / 278 node**, zero regressions. Rebuild deterministic.

## Rollback — performed and verified

`PATCH {"properties": {"seniority": "", "lv_contact_enrichment_provenance": ""}}` → HTTP 200. Re-read
confirms every other property byte-identical to the Task 1 snapshot.

**One honest caveat:** the two reverted fields now read `""` rather than `null`. HubSpot represents a
*cleared* property as an empty string and a *never-set* property as null, and that distinction cannot
be undone through the API. Both are blank to every consumer — `_isBlank()` in `mergeContacts.js`
treats `""`, `null` and `undefined` identically — so the record is functionally restored, but the
claim is "restored to blank", not "byte-identical". `lastmodifieddate` is HubSpot-managed and
likewise cannot be reverted.

`scripts/rollback_canary_proof.py` was checked and is unfit for this: it creates and archives a
throwaway property *definition*, not record values.

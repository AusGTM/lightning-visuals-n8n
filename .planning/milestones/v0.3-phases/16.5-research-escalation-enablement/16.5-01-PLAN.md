<objective>
Make research and Sonnet escalation deployable as a deliberate, auditable operator act, without
the committed workflow JSON ever carrying those flags on — then prove offline, over the ENABLED
node bodies, that the research-then-judge lane actually fires and the row survives both HTTP hops,
so Plan 02/03's live runs confirm a prediction instead of discovering one.

Purpose: `ALLOW_WEB_RESEARCH` and `ALLOW_SONNET_ESCALATION` are baked as literal `false` JS
constants into every Cloud Code node by `_flag_const(..., cloud=True)`. That is deliberate — Phase
16's Criterion 5 forbids any env/vars expression surviving in a built Cloud workflow, so there is
no runtime toggle by design. Enablement must therefore be a build- or deploy-time decision, and the
naive fix (flipping `CONFIG_FLAG_DEFAULTS`) would make every future build ship LLM-spending paths
on by default.

Output: a deploy-time overlay in the same module and the same shape as `bind_credentials()`, its
fail-closed guard, the artifact invariants asserted on the ENABLED build rather than only the
committed one, and the offline oracle for the live runs.
</objective>

<design_decision>
CONTEXT's leading candidate — the deploy-time overlay — is CONFIRMED against the code, and the code
makes it strictly better than CONTEXT anticipated.

`scripts/deploy_n8n_workflows.py:192` already holds `bind_credentials(workflow, ...) -> dict`: a
pure, deep-copying, fail-closed-with-`ValueError` transformation over a workflow dict, applied in
flight between reading the committed JSON and POSTing it. The overlay is the same function shape,
in the same module, applied at the same point, tested the same way. There is no new architecture.

The confirming detail CONTEXT could not know without reading the emitted artifact: the target is a
plain string literal inside `parameters.jsCode`. `_flag_const(name, cloud=True)` emits exactly
`const ALLOW_WEB_RESEARCH = false;` — bare boolean — while `_write_safety_const` emits
`const ALLOW_HUBSPOT_RECORD_WRITES = "false";` — quoted string. The two forms are textually
disjoint, so an exact-literal rewrite of the first physically cannot reach the second. "Enabling
research does not widen writes" is a property of the emitted text, not a promise.

The tradeoff, stated plainly:

  WHAT IT COSTS. The deployed artifact is no longer byte-identical to the committed one. There is a
  workflow shape that exists only in flight, so the ONLY way to know what is actually running is to
  read it back from n8n. Plan 02 therefore makes read-back a mandatory step and refuses to trust a
  deploy's own 200. That cost is real, and it is the one this design deliberately accepts.

  WHAT IT BUYS. `scripts/build_cloud_workflows.py` is untouched, so `n8n/wf_*.json` does not move at
  all — no rebuild, no frozen-fixture risk, no chance of an enabled artifact reaching git, and the
  deterministic-rebuild invariant is preserved by construction rather than by discipline. Criterion 1
  is satisfied because there is nothing enabled to commit.

  WHY NOT THE ALTERNATIVES. Flipping `CONFIG_FLAG_DEFAULTS` arms every future build. Reading ambient
  env inside `_flag_const` makes the committed JSON depend on whoever last ran the builder — and this
  repo's `.env` ALREADY sets `ALLOW_WEB_RESEARCH` and `ALLOW_SONNET_ESCALATION` for the Python lane,
  so that variant would have armed production the first time anyone rebuilt. The overlay's operator
  flag is deliberately a different name for exactly that reason, and a test pins the inertness.

  RESEARCH AND ESCALATION ARE INDEPENDENTLY TOGGLABLE (CONTEXT left this to discretion). Their cost
  profiles differ — research is a web-search-enabled call per record, escalation a Sonnet arbitration
  only on conflict — and the operator names each constant explicitly, so `ENABLE_BAKED_FLAGS` reads
  as a manifest of exactly what is being armed.
</design_decision>

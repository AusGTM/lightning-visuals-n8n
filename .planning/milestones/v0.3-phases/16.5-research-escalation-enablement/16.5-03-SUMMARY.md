## BUG 10 — `company:search` returns null json

The failure is in the node, not the API and not our inputs:

- `Build Company Identity` produced the correct `object_id` `'9604614548'`.
- The identical search issued directly against HubSpot — same `hs_object_id EQ` filter, same
  14-property list read out of the built node — returns **HTTP 200, `total:1`**, with the real
  record (`domain: mrc.racing.com`, `annualrevenue: 206078000`, …).
- With `onError` temporarily cleared, the node **still did not throw**: `status: success`, no error
  node, no message. It simply emits an item with `json: null`.
- The contacts twin (`HubSpot Fetch By Id`, structurally identical config, `resource: contact`)
  works correctly and returns `{archived, createdAt, id, properties, updatedAt, url}`.

So the difference is `resource: company` in n8n's own HubSpot node implementation. Note that
`HubSpot Company Search` (the pre-existing companies search) shares this shape and has **also never
run live** — every canary to date fired contact events only, so it is likely affected identically.

**Candidate fix**, already scoped by 16.4's research and requiring no new adapter work: replace the
two companies search nodes with credential-bound `httpRequest` POSTs to
`/crm/v3/objects/companies/search`. `n8n/code/adaptFetchById.js` already parses that response shape
(its unit tests cover the single-object and search-envelope forms), so the change is confined to the
node type/parameters. This needs its own planned phase — it was NOT hand-patched here.

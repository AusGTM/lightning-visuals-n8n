# Phase 16.9 — create-path fix (BUG 13) and the first live company write

## BUG 13 — the create nodes were broken two ways at once

Found by auditing the built artifact **before** spending a live window — the same discipline that
caught BUG 11 at plan time. Both create nodes were:

1. **Discarding the patch.** `additionalFields: {}` — the same empty-map placeholder as BUG 11 — so
   the merge's computed patch on `$json.properties` was referenced nowhere. A create would have
   produced a record carrying only its identifier.
2. **Reading fields that do not exist on their own input.** `Decide Action` / `Decide Company Action`
   emit exactly `{action, object_type, hs_object_id, gap_flag, needs_review, properties}` — verified
   from live execution 12's `runData`. Yet `HubSpot Company Create` read
   `$json.name || $json.identity_keys.companyName || $json.identity_keys.domain` (all undefined, and
   dereferencing the absent `identity_keys` would have **thrown**), and `HubSpot Create` read
   `$json.properties.email`, which is never present because `email` is `manual_protected` and can
   never promote into the patch.

**Fix** (`c6462e9`): `_hs_http_create_node()`, mirroring `_hs_http_patch_node()`. Both nodes now POST
`{"properties": $json.properties}` to the CRM v3 collection endpoint, credential-bound via
`predefinedCredentialType`/`hubspotAppToken`, node names preserved so `NODE_CREDENTIAL_MAP` binding
still applies, and `onError` deliberately absent so a rejected create fails its execution.

The 2026-07-28 note about `name` being a required activation-time parameter applied to the **native**
node only; the REST endpoint takes it inside `properties` like any other field.

**Five tests had pinned the creates as native-and-unverified.** Those pins were correct when written
and became stale by design, so each was **retargeted rather than deleted**: the BUG 10 suite now
asserts the create is not a search; the auth suite asserts no native `company:create` survives
anywhere and that the create sends the patch; the transport suite asserts both nodes POST the patch
and that the two unresolvable expressions are gone for good.

## BUG 14 — found live, and the loud-failure design earned its keep

Execution **16**, against a throwaway company created and deleted for the purpose:

```
PATCH https://api.hubapi.com/crm/v3/objects/companies/278602619330
body  {"properties":{"lv_enrichment_status":"complete"}}
->    Property "lv_enrichment_status" does not exist   (PROPERTY_DOESNT_EXIST, portal 22617666)
```

The execution status was **`error`**, not a plausible 200 — because 16.7-01 deliberately left
`onError` off the write nodes. Had it swallowed the error, this would have looked like a successful
write.

Enumerated against the live portal schema, exactly **two** company properties the pipeline depends on
were absent — `lv_enrichment_status` (written on every companies run by `ENRICH_DECIDE_CO_CLOUD`,
and an SJ-3 poller filter) and `lv_enrichment_requested` (also an SJ-3 filter). Every other property
the write path touches already existed.

**Resolution**: both were **already declared** in `config/hubspot_properties.yaml` — the Phase 15
migration had defined them and they had simply never landed in the portal. So this was not authoring
new schema but *running the existing idempotent migration*, which created exactly the two missing on
**both** companies and contacts:

```
created property companies/lv_enrichment_requested (201)
created property companies/lv_enrichment_status (201)
created property contacts/lv_enrichment_requested (201)
created property contacts/lv_enrichment_status (201)
undo manifest: undo-manifest-73c5342c-a455-4d69-a0a7-41df85ef1a8f.json
```

This is a schema change to the production portal and was taken to the operator as an explicit
decision rather than performed unilaterally.

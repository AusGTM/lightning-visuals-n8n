<objective>
Settle, by observation, the one fact this phase's risky half rests on: what HubSpot actually
does when asked to convert an existing, data-bearing property's type from text to
enumeration. Research could find no authoritative answer — only uncorroborated community
signal that it is blocked once a property holds values — and the migration's shape, its
rollback command, and whether a cheap rollback exists at all all branch on that answer.

Purpose: `lv_org_type` is a one-way door. Designing the migration script from an assumption
and discovering the truth by running it against live CRM data is how a phase destroys
records. A throwaway property costs nothing and answers the question completely, which is
the same discipline this project already used for the ZoomInfo GTM and Lusha v3 contracts.

Output: a self-contained probe ladder that one operator invocation runs end to end and that
prints greppable verdicts; a read-only live inventory of every distinct `lv_org_type` value
on company records; and a recorded decision on the migration shape that Plan 04 builds
against.
</objective>

    Write `scripts/probe_org_type_migration.py`: a single-invocation ladder that empirically
    answers every open question about in-place property type conversion, using ONE disposable

    (`lv__phase21_org_type_probe` — deliberately double-underscored, never colliding with a
    real field), against ONE designated test company read from the environment.

    Ladder steps, each printing its own step banner, HTTP status, and a one-line reading of
    what the status means:
    1. Create the disposable property as text (type string, fieldType text).
    2. Write an IN-VOCABULARY org-type value onto the test company's disposable property.
    3. Attempt the in-place conversion: PATCH the property to type enumeration, fieldType
       select, options built from the taxonomy vocabulary.
    4. Read the test company back and classify the surviving value: preserved verbatim,
       blanked, or the record now errors.
    5. If step 3 succeeded, attempt to write an OUT-OF-VOCABULARY value to the now-enum
       property and record whether HubSpot rejects it — this is the direct evidence for the
       roadmap's "pipeline writes validate against the enum options, no silent 400s" claim.
    6. Attempt the REVERSE conversion back to text and record whether it is permitted — this
       determines whether a cheap in-place rollback exists at all, which is the single most
       important input to Plan 04's runbook.
    7. If step 3 was blocked, blank the test company's value and retry the conversion, to
       isolate whether the blocker is "holds values" or something else (referenced by an
       asset, formField, and so on).
    8. Archive the disposable property, then immediately attempt to create a property with
       the SAME internal name and a different type, recording whether the name is reusable
       at once.
    9. Cleanup: archive whatever remains and print the residual state so nothing is left
       behind in the portal.

    Finish with a `=== VERDICT ===` block of greppable single lines, one per open question,
    each with a small closed value set: whether the in-place type PATCH is allowed, what

    conversion, whether the reverse PATCH is allowed, whether emptying the property lifts a
    block, whether the name is immediately reusable, and a final recommended migration shape
    (in place, archive-and-recreate under the same name, or a shadow property under a new
    name). Plan 04 copies these lines into its runbook, so they must be stable, one per line,
    and unambiguous.

    Safety, all enforced in code and all refusing BEFORE any HTTP call:
    - Refuse if the resolved target property name is anything other than the probe constant.
      Take no target-name argument at all; there is no legitimate reason for this script to
      be pointable at another property, and an argument is an invitation.
    - Refuse unless the portal id matches the expected portal, reusing the existing constant.
    - Refuse unless BOTH the dry-run key is off AND the property-write key is on, matching
      the existing two-key gate exactly — do not invent a third gate name.
    - Refuse unless the test company id is present in the environment's existing test-record
      allowlist; step 2 writes a record value, so the record-write allowlist governs it.
    - Skip to exit 0 with a banner when credentials are absent.
    - Exit non-zero if any ladder step fails in a way that leaves residue in the portal, and
      print exactly what is left and how to remove it. A probe that half-ran must not look
      clean.

    Dry-run (the default) prints the full ladder it WOULD execute — every URL, method and
    body — and makes zero calls, so the operator can read the whole plan before arming.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Probe script → HubSpot property schema (armed) | The probe creates, converts, archives and recreates real portal schema objects; a targeting mistake here mutates production CRM structure. |
| Probe script → HubSpot company record (armed) | Step 2 writes a record value; the test-record allowlist is the boundary between a throwaway write and touching a real account. |
| Inventory artifact → git history | The committed JSON permanently discloses whatever it contains about company records. |
| Agent session → armed HubSpot writes | Project policy: agents may read and dry-run; arming is operator-only. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-21-12 | Tampering | Probe accidentally targeting the real org-type property | critical | mitigate | The target name is a module constant with no CLI override and an explicit pre-call refusal; the offline gate test asserts the refusal; the checkpoint requires the operator to read the dry-run ladder and confirm the only property named is the probe constant. |
| T-21-13 | Tampering | Probe writing a record value to a non-test company | high | mitigate | Step 2 refuses unless the company id is in the existing test-record allowlist; the checkpoint requires the operator to confirm the designated company before arming. |
| T-21-14 | Repudiation | A half-run probe leaving schema residue while reporting clean | high | mitigate | Non-zero exit plus an explicit residual-state line whenever anything is left in the portal, and an independent post-probe schema snapshot check at the checkpoint. |
| T-21-15 | Information Disclosure | Committed inventory artifact leaking company identity | medium | mitigate | Record ids only, capped at ten samples per stray value; no names, domains or websites; acceptance requires reading the artifact before committing. |

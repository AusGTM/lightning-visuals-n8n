## Concerns

- **[MEDIUM] The `preflight_before_send` trap is mitigated by a docstring only.** Verified the trap is real: `preflight_before_send` (lines 1720-1751) checks the same local `WRITE_ENABLING_FLAGS` tuple being widened, so called on the review lane mid-batch it would read the window's own arm as `writes_still_live`, close the grant and disarm. But `grep` shows **no production caller today** — only `write_grant.py` itself and tests reference it. So the trap is latent: the plan's entire mitigation is a docstring paragraph in `authorize_review_batch`. A future skill or plan that wires `preflight_before_send` into a review loop hits it silently. A structural mitigation would be cheap: `preflight_before_send` already knows its lane; it could skip write-enabling flags irrelevant to that lane's window state, or refuse outright when called with `lane="review"` while that lane's window-open state is detectable. At minimum the prohibition should also live in `preflight_before_send`'s *own* docstring (the function a future caller will actually read), not only in `authorize_review_batch`'s.
- **[MEDIUM] Plan 01's `disarm` rework doesn't mention `_declaring_nodes`/`node_names`.** Current `disarm` (n8n_arming.py:423-472) computes `node_names = _declaring_nodes(original)` with the default `DISPATCH_FLAGS` (line 444) and passes it to `apply_mutation` as the allowed-node list — and `apply_mutation` refuses out-of-allowlist diffs (per its T-28-06 contract, cited in the research). If targets are derived from "every overlayable flag the workflow declares" but `node_names` still comes from dispatch-flag declaration only, then any node that declares the review flag but no dispatch flag would have its rewritten line fall outside the allowlist and the disarm would refuse. Deployed workflows declare all 5 consts on the same nodes (verified in research), so this is latent rather than live — but the plan's own "derive from what the workflow declares" principle should be applied consistently to `_declaring_nodes(original, derived_flags)` in the same change, or the docstring should state why dispatch-flag declaration is a safe proxy.
- **[MEDIUM] D-60-07's "cannot strand a flagged record" guarantee is client-side only, and the plans don't say so.** The backend gates a reject identically to an approve: `reviewDecision.js`'s `writeAllowed === false` check (verified at the allowlist-guard branch, lines ~218-228) fires **before** the reject branch, returning `not_allowlisted` for both. So a reject with `grant=None` and no armed review window reaches the POST but the backend still refuses the write — the record *is* stranded, just with an honest `not_allowlisted` outcome. This matches today's behavior (the env-var bypass was equally client-side), so it's not a regression — but CONTEXT.md's D-60-07 rationale ("a closed authority must never be able to strand a flagged record") overstates what the carve-out delivers, and neither Plan 01's Test 4 nor the threat model acknowledges that the carve-out only guarantees the request is *sent*. A one-line note in the test docstring would close the gap.
- **[LOW] Plan 03's `classify_review_item` defaults `object_type` to `"contacts"`** "matching `classify_item`'s own default" — but review decisions in this system are overwhelmingly on *companies* (the review queue is company ICP records; `reviewDecision.js` has both branches but the flagging pipeline is company-centric). The default will be wrong on the common path whenever the response omits the key. Check whether the review endpoint's five-key response actually carries `object_type`; if it does, the default is dead code and harmless; if it doesn't, the default should probably be `"companies"` for this classifier.
- **[LOW] `disarm`'s new fallback ("when the workflow could not be read as a dict, fall back to `DISPATCH_FLAGS`")** means an unreadable review workflow disarms only its dispatch flags and leaves a potentially live `ALLOW_HUBSPOT_REVIEW_WRITES` behind — silently, since the verify step then passes over the 4 fallback flags. The plan should state what the disarm result reports in that case (ideally a `DISARM_FAILED` or an explicit "could not read, review flag unverified" detail) rather than a clean `DISARMED`.
- **[LOW] Plan 04 Task 1's acceptance criterion** (`git status --porcelain n8n/` must list exactly two files) is the right guard against generator drift, but the builder rewrites *every* workflow — if the committed JSON has drifted from the generator for any unrelated reason (common in long-lived repos), this task halts mid-wave for a problem it didn't cause. The plan does say "STOP and report," which is correct, but the executor should be pre-authorized to run the builder *first, before any edit*, to detect pre-existing drift cleanly.

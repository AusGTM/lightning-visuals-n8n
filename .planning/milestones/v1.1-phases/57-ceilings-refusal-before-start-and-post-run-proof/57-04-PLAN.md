<objective>
G-4: two of three provider balances read `unknown` in the same preview — Apollo **`http_403`**
(expected and permanent) and ZoomInfo `provider_error` (new as of the 2026-08-25 walk). That is
thin cover for an unattended run that spends against them, and D-57-02 puts the FIX in scope, not
only the disclosure: with the ceiling unable to fully guard provider spend while a balance is
unreadable, narrowing the blind spot is the cheapest available increase in how much of the spend
is genuinely guarded.

**A factual correction, carried from cross-AI review (REVIEW-57-M1) — read this before trusting
any Apollo label in the phase artifacts.** The first pass of this plan described Apollo's existing
disclosure as `unrecognized_response_shape` in three places. It is not.
`operator-claude-plugin/tests/conftest.py:542` sets `error="http_403", status=403`, and `:544`
sets credential health `reason="http_403"`; the string `unrecognized_response_shape` does not
occur in `conftest.py` at all. Two independent reviewers flagged it and a grep confirmed it.
**`57-RESEARCH.md` carries the same wrong term and is stale on this point** — where the research
and this plan disagree about Apollo's label, this plan is right; do not "correct" the plan back to
the research. The distinction is not cosmetic: `http_403` means the request was REFUSED (a
credential/permission fact), `unrecognized_response_shape` means it SUCCEEDED and the body could
not be parsed (a contract fact). They imply different fixes, which is the entire premise of Task 1.

The two halves of G-4 have opposite shapes, and this plan does not pretend otherwise.

**Apollo is disclosure only, and permanently so.** The account's Apollo API key is structurally
not a master key, and Apollo's `usage_stats` endpoint 403s for any non-master key by design —
verified in this repo's own live-curl-confirmed comments at `n8n/code/providerSelection.js:76-106`
and `scripts/provider_registry.py:26-33`, and observed as the `http_403` label above. Fixing it
needs a different Apollo credential, an account-level change outside this repo. Nothing in this
plan attempts a code fix for it.

**ZoomInfo needs an observation, not a patch.** The cause recorded in this project's own memory
— a missing `Accept: application/vnd.api+json` header — is ALREADY FIXED in current code
(`scripts/build_cloud_workflows.py:4614-4630` sends the header). Meanwhile the label observed
is `provider_error`, which by `ENRICH_STATUS_BUILD_RESPONSE`'s own logic
(`build_cloud_workflows.py:6354-6362`) means the HTTP request itself errored — a DIFFERENT label
from `unrecognized_response_shape`, which is what an unparseable body produces. An expired mint,
a stale cached token and a genuine transient 5xx all produce the label observed, and code
inspection cannot tell them apart. So this plan probes and reports; it does not guess a fix for a
cause that may already be gone.

Purpose: G-4, and the honesty requirement D-57-02 creates — because the ceiling cannot fully
guard provider spend while a balance is unreadable, the report must not imply that it did.

## What closes G-4, defined rather than left conditional (REVIEW-57-M5)

The first pass associated this plan with G-4 without stating what closure means, so a probe
returning `inconclusive` could have been read as closing it. It cannot. This table is binding, and
57-01's requirement-coverage map points at it.

| Probe verdict | Apollo | ZoomInfo | G-4 status |
|---|---|---|---|
| `readable` | permanent blind spot, disclosed with the `http_403` structural reason | fixed by observation — the balance reads | **CLOSED.** One of two providers now readable; the other is disclosed with a cause no code can remove. |
| `provider_error` | as above | still unreadable; the verdict names the token mint and cache subgraph as the next thing to check | **PARTIAL.** Honest `unknown` disclosure ships (D-57-02) and the blind spot is unchanged. G-4 is NOT closed by disclosure alone; the milestone owner decides whether to accept it as closed at the phase gate. |
| `unrecognized_response_shape` | as above | a contract change, not a credential problem — a different and newly-identified cause | **PARTIAL,** same as above, but the follow-up is a response-parsing fix rather than a token one. |

In every row, the disclosure half — the report naming which balances were readable and therefore
which part of the spend was bounded — is delivered by 57-05 regardless. That half is not
conditional; only the ZoomInfo FIX is.

## The probe's real network path — wider than "a read-only GET" (REVIEW-57-M7)

The first pass called this read-only and stopped there. The full path, so nobody is surprised by
what a "gate on" run touches:

1. The probe POSTs to the deployed backend's status endpoint, the same way
   `operator-claude-plugin/scripts/backend_status.py:40-54` already does. **It is a POST, not a
   GET** — the read-only property is about EFFECT, not HTTP verb.
2. That request runs the deployed status workflow, which probes the configured providers.
3. Apollo's usage call is itself configured as a POST (`scripts/provider_registry.py:26-33`).
4. ZoomInfo may MINT and CACHE an auth token (`scripts/build_cloud_workflows.py:4168-4184`) — a
   state change on the instance, not on any CRM record.
5. No HubSpot object is read or written; no enrichment is dispatched; no armed window opens.

**On credit spend:** provider USAGE/credit-balance endpoints are not enrichment calls and are not
expected to consume enrichment credits, but this plan does not assert that from belief. The probe
records the Lusha `credits.remaining` figure BEFORE and AFTER its own run (Lusha is the one
provider whose balance currently reads) into the verdict file, so the claim is evidenced by
observation on the one lane where observation is possible. If the two figures differ, the verdict
says so and the claim is withdrawn rather than restated. Apollo and ZoomInfo cannot be checked
this way for the same reason G-4 exists.

**`RUN_LIVE_PARITY` (REVIEW-57-M):** it is the ROOT test suite's ambient-credential guard
(`tests/test_conftest_credential_guard.py:6,34,39`) and governs whether live-credentialled TESTS
may run. It is NOT a second gate on this script. The probe's only gate is
`ALLOW_ZOOMINFO_BALANCE_PROBE`; the probe is a script an operator runs deliberately, not a test
the suite collects, and it must never be wired into a pytest run. State this in the module
docstring so nobody adds a redundant second gate later.

1. **Request #1 — the probe.** Its ZoomInfo entry IS the verdict. Its Lusha `credits.remaining`

2. **Request #2 — an identical status read issued immediately after.** Its Lusha figure is
   recorded as `lusha_after`.

`lusha_after - lusha_before` therefore measures the credit cost of REQUEST #1 — the probe read —
which is the claim the phase actually needs to make. **Request #2's own cost is not measured, and
the verdict file says so in its own field rather than leaving it implied**: measuring it would
take a third read, whose cost would take a fourth, and so on. The regress is cut deliberately at
two and disclosed, not hidden. If request #1 spent nothing, the honest reading of a zero delta is
"the probe read costs nothing"; it is not a claim that the whole probe run touched zero credits,
because the last read is unmeasured by construction.

Distinguish the labels explicitly in the verdict, because they mean different things and imply
different fixes: `provider_error` means the HTTP request itself errored (an expired mint, a
stale cached token, a transient 5xx upstream); `unrecognized_response_shape` means the request
succeeded and the body could not be parsed (a contract change). Record which, and record the
HTTP status when the response carries one.

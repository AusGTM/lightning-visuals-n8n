<objective>
Ship the stable launcher shim (D-63-01) and the wrapper's staleness self-check (D-63-02), reusing
`durable_paths.py`'s existing version ordering (D-63-04) rather than writing a second one.

Purpose: the sweep's schedule currently pins a versioned plugin directory, so every plugin update
either orphans the schedule or silently freezes it on old code. Twelve versioned directories exist
on the operator machine and the newest cached one (`0.33.0`) is already behind the shipped
`0.35.0`. The shim fixes this going forward; the self-check is the only mechanism that can signal
staleness from inside a run that is already happening.

Output: `operator-claude-plugin/scripts/sweep_shim.py` (resolution + installer + CLI), the
`/bin/sh` shim it installs into the durable home, a staleness block inside `lv-sweep-run.sh`, and a
`SWEEP-CRON-TEMPLATE.md` that pins the shim.

**Tracer note (TRACER_MODE):** this phase is two independent halves that must not be made to
depend on each other, so each half leads with its own end-to-end tracer rather than one tracer
spanning both. Task 1 below is 63-A's tracer: schedule-shaped invocation → version resolution →
`exec` → the real wrapper, proven end to end before Tasks 2 and 3 expand outward from it. 63-B's
tracer is 63-03 Task 1.

**Reach, stated honestly.** The self-check ships inside the 0.36+ wrapper. The twelve directories
already on the machine hold OLD wrappers, so a schedule pinned to `0.33.0` or earlier structurally
cannot execute this code and will not start notifying. On the shim path the check never fires at
all, because the shim always resolves the newest root. What the self-check actually covers is: a
legacy-shaped pin made from this version onward, and a run whose durable home was wiped. The path
that reaches the machine's CURRENT state is the admin's one-time re-point in Task 3.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| scheduler → shim | cron/launchd invokes the shim unattended with no human present to see a prompt or a refusal; whatever the shim execs runs as the operator |
| cache-root directory listing → `exec` target | the shim chooses an executable path at run time from a directory listing under the plugin cache root, which is a user-writable location |
| wrapper → log file | the wrapper appends operator-supplied path strings to a log the admin later reads |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-63-01 | Tampering | `sweep_shim.newest_install_root` → shim `exec` | high | mitigate | Candidates are direct children of the baked cache root that match `durable_paths._VERSION_DIR_RE` AND carry `skills/backend-sweep/lv-sweep-run.sh`; any entry whose `Path.resolve()` leaves the resolved cache root is skipped, so a symlink cannot redirect the `exec` outside the plugin tree. The cache root is baked at install time by code that knows `PLUGIN_ROOT.parent` — never read from the environment at run time. |
| T-63-02 | Elevation of Privilege | installed shim file | high | mitigate | `install_shim` writes mode `0o700` under the durable home, so a non-owner cannot rewrite the file the scheduler executes. Idempotent rewrite (Task 1) means a tampered shim is restored by the next `--install`. |
| T-63-03 | Spoofing | resolver output consumed by the shim | medium | mitigate | The shim treats empty output or a non-zero resolver status as a hard failure (banner + non-zero exit) rather than falling back to `$1`; there is no path by which an unresolved answer becomes an executed one. |

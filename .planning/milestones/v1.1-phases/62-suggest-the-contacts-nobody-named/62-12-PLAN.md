<decisions>
Seven decisions taken at planning time. Implement them; do not re-litigate them.

**Decision 1 — what "related to" means, exactly.**
Compare two BARE DOMAIN STRINGS, both normalised through `enrichment._clean_domain`, and call
them related when they are EQUAL or when the email's domain is a **label-boundary subdomain**
of the company's:

```
related  <=>  ed == cd   or   ed.endswith("." + cd)
```

- `_clean_domain` already lowercases, strips a scheme, strips a leading `www.`, keeps the host
  only, drops path and query, and returns `None` for a profile host. **That is the entire
  apex/`www` story for this question** — `www.romaturfclub.com.au` and `romaturfclub.com.au`
  normalise to the same string with no extra helper.
- The subdomain arm is what lets a club's own mail host count: `staff@mail.romaturfclub.com.au`
  is that club's own domain, not a stranger's.
- The direction matters and is deliberate. `ed.endswith("." + cd)` accepts a host UNDER the
  company's domain, which the company's own DNS controls. It refuses
  `romaturfclub.com.au.attacker.tld`, which does not end with `.romaturfclub.com.au`. Pin that
  case; it is the send-direction sibling of the suffix trap 62-10 pinned in the fetch guard.
- The reverse direction (company recorded at a subdomain, email at the apex) is NOT related.
  Fail-closed; a company recorded as `mail.example.com` is a rarity and holding it is cheap.

**Do NOT reuse `url_fallback._canonical_authority` (62-10), and here is why.** It is a URL
*authority* comparator built for a security guard on what the agent will FETCH: it parses a
netloc, carries the port as part of the comparison, and refuses a dotless remainder. This
question has no URLs and no ports — it compares an email's domain to a CRM property and decides
what to SEND. `_clean_domain` is the guard the rest of this repo's domain vocabulary already
agrees on (`companyLink.js::cleanCompanyDomain` is its JS mirror), so using it keeps one
normalisation across the client, the ingest lane and this check. Importing a fetch-guard's port
semantics into a send decision would be borrowing the wrong invariant.

**No public-suffix / registrable-domain logic.** It would need a PSL dependency to know that
`.com.au` is a suffix. Rejected — see Decision 3 for what that costs.

**Decision 2 — the freemail list: the brief's premise is wrong, and here is the correct reuse.**
`62-UAT.md`'s `missing` list and the planning brief both say
`operator-claude-plugin/scripts/company_domain.py` "already classifies freemail and AU ISP
domains as resolving nothing". **It does not.** `company_domain.py` contains no host collection
of its own — it imports `enrichment._clean_domain`, which knows `NOT_A_COMPANY_DOMAIN` (profile
hosts) and nothing about freemail. Verified by reading both files and by grepping the whole
repo: the only freemail set is `FREEMAIL_DOMAINS` in `n8n/code/companyLink.js`, in JavaScript,
in the backend.

The faithful reading of "reuse that classification, do not write a second list" is therefore
the arrangement this repo has already established for exactly this problem: **the JS set stays
authoritative, and the Python side gets a mirror pinned equal by a parity test.**
`enrichment.NOT_A_COMPANY_DOMAIN` is that precedent, and its docstring says why — *"a host one
accepts and the other rejects is a silent divergence"* — with
`test_people_and_url_normalisation.py::test_the_two_engines_agree_on_what_is_not_a_company_domain`
parsing the JS block and asserting set equality. Add `enrichment.FREEMAIL_DOMAINS` the same way,
with the same kind of test. Two copies that cannot diverge is one list; a second unpinned list
is what the instruction forbids.

**Parsing gotcha, and it will bite silently.** The existing parity test does
`block.replace("\n", " ").split(",")` and drops pieces starting with `//`. The
`FREEMAIL_DOMAINS` block contains a `// AU consumer ISPs` comment on its own line; after the
newlines are flattened, that comment swallows the rest of its joined line and `bigpond.com`
onward would be silently dropped from the JS side. **Strip each line's `//` tail BEFORE joining
lines**, and prove the parse by asserting the JS side has the expected member count and
contains `bigpond.com` explicitly.

**Decision 3 — `kdaniel@lismoreturfclub.com` is HELD, and that is recorded as a known cost.**
The one genuinely-correct person the round-1 sitting enriched came back as
`kdaniel@lismoreturfclub.com` (`.com`) while HubSpot records the club at
`lismoreturfclub.com.au`. Under Decision 1 that is a MISMATCH and the row is held, in the same
bucket as `thehartford.com`.

Keep the strict rule and pin this case as a fixture. Relating `x.com` to `x.com.au` needs
registrable-domain logic (a PSL dependency) or a heuristic that would relate two domains one of
which the club may never have registered — and the operator already accepted a zero-sendable
outcome with the numbers in view. Record it in the classifier's own docstring and in the
CHANGELOG as the measured cost, with the widening path named (one helper, one fixture set) for
when the operator asks for it. Do not widen it now, and do not let this case argue the rule
down.

**Decision 4 — the check lives at the sendability seam, and only on the suggestion lane.**
`62-UAT.md` says it: *"the check belongs where sendability is decided, not in the provider
adapters."* That seam is `suggest_contacts.partition_for_dispatch`.

`extraction.hold_emailless` is NOT touched. It is shared by `contact-upload` and
`enrich-before-ingest`, where the operator supplied the email themselves — holding a
hand-typed gmail address there would be wrong, and the ruling was made about a SUGGESTED row
whose email came from a provider resolving a weak identity-group-2 key. Scoping the rule to the
suggestion round is what keeps the other lanes correct.

`partition_for_dispatch`'s current docstring promises it *"adds no logic, filtering,
re-ordering or annotation of its own"*. This plan deliberately breaks that promise under an
operator ruling; rewrite the docstring to say what it now does and why, and cite the ruling
date. A stale docstring next to a changed rule is worse than no docstring.

**Signature: `partition_for_dispatch(rows, company_domains)` — `company_domains` is REQUIRED,
positional, with no default.** An optional argument defaulting to `None` becomes a silent
bypass of an operator ruling the first time a caller forgets it. A row whose company is absent
from the map is held with its own reason code, never sent.

**Decision 5 — four reason codes, prose that says the reason, and no widening of the hold
vocabulary.**
Every held entry `partition_for_dispatch` returns carries `reason_code` alongside the existing
`index` / `row` / `reason` keys — including the emailless ones, so the shape is uniform:

| `reason_code` | When | Prose reason must |
|---|---|---|
| `no_email` | `hold_emailless` held it | be `hold_emailless`'s own text, verbatim and unchanged |
| `email_domain_freemail` | the email's domain is in `FREEMAIL_DOMAINS` | name the domain and say it is a personal mailbox; must NOT contain the words "does not match" |
| `email_domain_mismatch` | related test fails | read `email domain thehartford.com does not match romaturfclub.com.au` — the gap's own wording, both domains named |
| `company_domain_unknown` | the company has no usable recorded domain to compare against | name the recorded value and say nothing could be compared |

Freemail is tested BEFORE the relatedness comparison, so a gmail address is never reported as a
mismatch — that separation is the operator's "held pile legible at a glance" requirement, in
code rather than in the report's rendering.

**`confidence.ALL_HOLD_CODES` is NOT widened.** It is a closed vocabulary `held_queue.save()`
validates persisted entries against, and these codes describe why a SUGGESTION round declined
to send, not a held-queue class. The reason codes live in `partition_for_dispatch`'s own return
shape; the held-row path downstream (`confidence.assess()` -> `held_queue.build_entry()`) is
unchanged.

**Index discipline:** every held entry's `index` is the row's position in the ORIGINAL `rows`
list, for both passes. Run `hold_emailless(rows)` first, remember which indices it held, then
walk `enumerate(rows)` and apply the relatedness test to the rest — never index into the
`sendable` sublist, which would renumber the second pass's holds.

**Decision 6 — one pre-existing test is replaced, named here.**
`test_suggest_contacts.py::test_partition_for_dispatch_is_a_thin_call_to_hold_emailless` asserts
the exact property this plan removes. Replace it with a test asserting the new relationship: for
rows whose emails are all on their own companies' domains, the partition agrees with
`hold_emailless`; for the stranger fixture it deliberately does not. Additionally ADD a test
pinning that `extraction.hold_emailless` ALONE still returns the stranger as sendable — that is
what proves the other lanes are unaffected and that the new rule, not a change to the shared
helper, is what holds the row.

**Decision 7 — release 0.38.3, and what it may claim.**
Bump `.claude-plugin/plugin.json` and add the CHANGELOG section in the SAME commit (an unbumped
version means the Update button stays greyed out). The section names `G-62-7` and the measured
cost from Decision 3. Name `G-62-6` in the same section **only if** `62-11-SUMMARY.md` records
that plan 62-11 shipped a code change; if 62-11 stopped at a diagnosis, do not claim it.
</decisions>

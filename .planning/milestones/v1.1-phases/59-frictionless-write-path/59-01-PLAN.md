<objective>
D-59-07 half (b), and this phase's TRACER: prove the whole path from an n8n response body,
through per-chunk classification, to a durable on-disk list an operator can read — end to end,
with the interruption case proven, before any other plan expands on it.

what actually landed in HubSpot. Its load-bearing constraint is that the list must survive a
PARTIAL run and a REVOKED run, which makes it a durable artifact flushed as records land — not
a summary printed on the happy path. Getting that wrong is invisible until exactly the run the
operator most needs it for.

flush in `chunking.dispatch_plan`'s existing loop, and tests that drive the interruption and

FUNCTIONS:

- `classify_item(item)` — pure, no I/O. Takes ONE per-row response item and returns a dict with
  keys `object_type`, `action`, `hs_object_id`, `outcome`, `reason`. Raises
  `WrittenRecordsError` on a non-dict item, naming the flattening idiom documented at
  `chunking.py:93-96` — this is the same fail-loud-on-shape-mismatch discipline
  `preingest.merge_enriched` adopted in commit `9e603d6`, and the reason a new ad hoc indexer
  must never silently skip. The write/no-write rule, stated once here so no caller re-derives
  it: an action of `update`, `enrich` or `create` means the backend passed the row through its
  write gate; anything else (`write_blocked`, `proposed`, `needs_match_review`, `skip`,
  `review`, `held`, or an unrecognised value) means no write. `outcome` is `written` when a
  write action carries a non-empty `hs_object_id`, `created_id_unknown` when the action is
  `create` and `hs_object_id` is absent or null, and `not_written` otherwise. `reason` is the
  item's own `reason` key verbatim, or None. `object_type` defaults to `contacts` when the item
  does not carry one — contacts-lane bodies from `Build Ingest Response` have no `object_type`
  key at all, and the companies branch's own `Build Response` already applies exactly this
  default (`row.object_type || "contacts"`), so matching it keeps one convention rather than
  inventing a second.
- `append_chunk(run_id, chunk_index, body, path=None)` — flattens `body` with the documented
  idiom (a list stays a list, a bare dict becomes a one-item list), classifies each item, reads
  the current document, appends, and rewrites the WHOLE file through
  `durable_paths._atomic_write_0600`. Whole-file rewrite per chunk is deliberate and adequate:
  a run is tens of chunks, and an append-in-place scheme would need its own crash-consistency
  story that `_atomic_write_0600` already provides. If the document on disk carries a different
  `run_id`, start a fresh document rather than mixing two runs.
- `append_chunk` MUST NOT raise on an I/O failure. Catch `OSError` and return a falsey result
  instead. This is load-bearing: `append_chunk` is called from inside the dispatch loop, and a
  bookkeeping failure that halted a live HubSpot run would convert a missing log line into a
  mid-run stop — the exact opposite of D-59-06's run-to-completion contract. A
  `WrittenRecordsError` (a shape or forbidden-name problem) DOES propagate; that is a defect,
  not an environment condition.
- `load(path=None)` — returns the document's `entries` as a list, or `[]` when there is nothing
  usable. Missing, unreadable, malformed, half-written and schema-mismatched all degrade to the
  SAME empty result, never a partially-trusted one — `run_manifest.load()`'s reasoning verbatim.

<objective>
D-59-06: ship a `SessionStart` plugin hook that tells the operator, once per session and
non-blockingly, that once enrichment and writing start the run continues until done — a revoke
refuses the NEXT send, and a dispatch already running finishes its remaining chunks.

Purpose: 53-04 left open whether revocation at the next send is enough. D-59-06 answers yes,
and CLOSES the question — the alternative (a grant-aware, chunk-granular dispatch loop) changes
the shared loop every lane in this plugin uses, which `write_grant.py` already names as why it
was not done. Telling the operator the true behaviour once, up front, where it informs the
decision to begin, is the honest and cheap version. This plan is that note and nothing more.

Output: the plugin's first `hooks/` directory, a hook script, and a contract test that proves
the note's content without needing a Claude Code host.
</objective>

**`operator-claude-plugin/hooks/hooks.json`**

Follow the verified installed precedent quoted in `59-RESEARCH.md` § Code Examples exactly: a
top-level `hooks` object containing a `SessionStart` array; one entry with `matcher` set to the
alternation covering startup and resume; that entry's `hooks` array holding one object with
`type` of `command` and a `command` that invokes bash against
`${CLAUDE_PLUGIN_ROOT}/hooks/session-start.sh`. Use `${CLAUDE_PLUGIN_ROOT}` and never a
hardcoded or version-pinned path — Claude Code resolves that variable at hook-invocation time,
which is exactly what makes this immune to the versioned-install-path problem this project's
own memory records for the sweep crontab.

**`operator-claude-plugin/hooks/session-start.sh`**

A shell script, executable (`chmod +x`), with a `#!/usr/bin/env bash` shebang and `set -eu`.

It does ONE thing: print the note. It must have NO dependencies at all — no python, no config
read, no credential read, no network call, no filesystem write, no reading of grant state. A
session-start hook that can fail is a session-start hook that fails on a fresh install before
the operator has configured anything, and the note is worth exactly nothing if it only appears
for already-working installs. It must exit 0 unconditionally.

Its output leads with a one-line instruction to Claude to relay the following to the operator
once, near the start of the session, without asking anything — then the note itself. The note
carries exactly three facts and no more:

- Once enrichment and writing start, the run continues until it is done.
- Revoking a write grant refuses the NEXT send.
- A dispatch that is already running finishes its remaining chunks; a revoke arriving mid-run
  does not stop it.

Then a single closing line stating this is information, not a decision, and that nothing is
waiting on the operator.

Constraints on the wording, which are NOT discretionary even though the phrasing is:
- No question mark anywhere in the output. It is a statement, never a prompt.
- No imperative directed at the operator ("confirm", "approve", "reply", "type"). Nothing must
  read as though the session is blocked.
- No claim that revocation stops a running dispatch — that would contradict
  `test_a_revocation_midway_does_not_stop_a_running_dispatch`, the exact contract D-59-06
  chose to disclose rather than change.
- No mention of arming phrases, secrets, tokens or file paths under the operator's home. The
  hook's output is context; it must not become a place credentials or private paths surface.
- Put a comment block at the top of the script naming D-59-06, the date 2026-08-28, and the
  fact that this note EXISTS INSTEAD OF a grant-aware dispatch loop — so a future reader who
  wonders why revocation is not chunk-granular finds the answer at the artifact that replaced
  it.

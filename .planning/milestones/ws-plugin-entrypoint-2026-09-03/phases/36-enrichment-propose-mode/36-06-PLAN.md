<objective>
Make `Parse HubSpot Event`'s batch-size refusal **mode-aware** before Phase 36's paused deploy, so a
`mode:"propose"` request is bounded by its own cost rather than by full-waterfall cost.

Purpose: the operator's ruling (37-CONTEXT.md §13) — the unconditional `events.length > 2` refusal was
derived from probe B4's measured 37.44 s/record **full waterfall**. A propose/match call runs **zero
provider calls**; its per-row cost is two HubSpot search POSTs. Applying the waterfall's ceiling to it
is an unnecessarily strict boundary that would force Phase 37's client into 2-row chunks for work that
comfortably fits 20. One deploy, not two: this lands before 36-05's checkpoint fires.

Output: `ENRICH_MAX_PROPOSE_RECORDS` (provisional 20, derivation in the comment), a mode-aware ceiling
selection in the guard, and the boundary tests proving the write path did not move.

**Scope fence.** This plan changes exactly one thing: WHICH ceiling the existing guard compares against.
It does not touch the refusal shape, the refusal message template, the empty-array branch, the routing
edge, the write ceiling's value, or anything downstream of `Parse HubSpot Event`.
</objective>

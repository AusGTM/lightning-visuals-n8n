<objective>
The credit slice of `hubspot/backend-status`: the one legal path by which a client that holds no
provider credential can learn how many credits are left, and can tell "we could not read this" apart
from "this is zero".

Purpose: PREVIEW-02's warning is only trustworthy if an unreadable balance is visibly unreadable.
This account already carries a permanent real instance of that case — the Apollo key is non-master
and returns 403 on every usage read — so the tri-state is not hypothetical.

Output: a new built workflow `wf_backend_status_cloud.json`, its builder function, its credential
registration, and offline proof that a null balance survives the response assembly as null.
</objective>

    Graph, deliberately a straight line rather than a fan-out:
    `Status Webhook Trigger` (POST, path `hubspot/backend-status`, response-node mode, header auth) →
    `Status Credit Request` (Code, emits exactly one item naming all three providers, unconditionally
    per D-10 and research A4) → `Lusha Usage` → `Apollo Usage` → the ZoomInfo usage subgraph from
    `_zoom_split_usage_subgraph` → `Build Credit Status` (Code) → `Respond to Webhook`.

    Chain them sequentially rather than fanning out. A fan-out gives the response node three
    independent arrivals and it answers on the first one, returning a partial picture — the
    first-arrival semantics documented on the enrichment lane's `Build Response`, tolerable there and
    not tolerable for a status read. Sequential chaining means exactly one item reaches the responder
    and all three probes have already run. Every probe node uses the continue-on-error mode and none of
    the usage URLs reads anything off its incoming item, so a failing probe passes an error item along
    instead of stopping the chain — which is exactly what the tri-state depends on.

    Reuse the node names `Lusha Usage`, `Apollo Usage`, and the ZoomInfo usage subgraph's names exactly
    as the enrichment workflow uses them. `NODE_CREDENTIAL_MAP` is keyed by node name and already
    carries all three, so reuse costs zero new registration. Build them with the same helpers
    (`_credit_http_node`, fed from the matching `provider_registry` entry's method and url, header
    auth), never with hand-written parameters.

    `Build Credit Status` reads each usage node BY NAME through the same guarded `nodeAll` helper
    `ENRICH_BUILD_RESPONSE` uses, passes each raw body through `extractCredits` from the inlined
    `providerSelection.js`, and emits a single item whose per-provider shape mirrors
    `scripts/check_provider_credits.py`'s result: whether the provider is configured, its extracted
    credit number or an explicit unreadable marker, a short error label, and the HTTP status. Carry a
    timestamp so the caller can state when the reading was taken.

    Two hard constraints on that node. First, an absent, empty, or error-carrying node result resolves
    to the unreadable marker; a numeric fallback anywhere in that node is the exact defect D-10 exists
    to prevent, because a defaulted number is indistinguishable from a real balance. Second, never
    place a provider's raw response body into the emitted item — only the extracted number, a boolean,
    a short label, and a status code. A raw usage body can carry account metadata that has no business
    crossing to a client (T-25-03).

    Rebuild every workflow with the builder and confirm the diff under `n8n/` is confined to the one
    new file — no existing workflow may change as a side effect of this task.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin client → `hubspot/backend-status` | An untrusted caller crosses here; the shared webhook secret is the only gate |
| n8n → provider usage APIs | Provider credentials live only on this side and never cross back |
| provider response body → status response body | Account metadata must not cross this boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-04 | Spoofing | `Status Webhook Trigger` | high | mitigate | Credential-bound header auth on the trigger node itself, same mechanism and same credential as the enrichment webhook; not left open because the endpoint is read-only |
| T-25-03 | Information Disclosure | `Build Credit Status` | high | mitigate | The emitted item carries only an extracted number, a configured boolean, a short error label, a status code and a timestamp — never a raw provider body; a test asserts no unextracted key survives |
| T-25-05 | Tampering | credit tri-state | critical | mitigate | No numeric fallback anywhere in the assembly; a genuine zero and every unreadable case are asserted distinguishable in `backendStatusResponse.test.mjs` |
| T-25-13 | Denial of Service | unconditional three-provider probe on every status call | low | accept | Research A4; the probes are usage endpoints, not data endpoints, and burn no credits. If a future rate limit appears it surfaces as an unreadable balance, which is already a first-class state |
| T-25-14 | Elevation of Privilege | deploy/activation of the new workflow | high | mitigate | This plan commits a disarmed artifact only; no task deploys or activates, and arming stays coupled to the `TEST_RECORD_*` allowlist at deploy time |
| T-25-SC | Tampering | package installs | low | accept | This plan installs nothing |
</threat_model>

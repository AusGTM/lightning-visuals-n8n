  <behavior>
    - `label_headers()` maps `Email Address` to the canonical email prop and reports an unknown
      header as dropped; matching is case-insensitive and whitespace-collapsed, so `  first   NAME `
      resolves the same as `first name`.
    - `build_preview()` on a 3-row CSV returns every row and a row count of 3.
    - `build_preview()` on a 40-row CSV returns 10 leading rows, 3 trailing rows, a row count of 40,
      and a per-column fill rate for each source column.
    - Fill rate counts non-empty cells over total rows and is reported per source column, including
      dropped ones — a column the backend will drop is exactly the one an operator wants to notice.
    - The preview reports the canonical props that no source column maps to, so a missing email
      column is visible before the send rather than after.
    - With the mapping file absent or unreadable, `build_preview()` still returns headers, rows and
      counts, and flags the labels as unavailable rather than guessing.
    - `build_preview()` performs no network call and mutates no file — the fixture file's bytes are
      identical before and after.
  </behavior>
  <action>
    Write `operator-claude-plugin/scripts/preview.py` exposing `label_headers(headers, mapping_path)`
    and `build_preview(path, mapping_path=None)`, plus a `__main__` block printing the preview
    structure as JSON so the skill can render it.

    Resolve the mapping file in this order: an explicit `column_mapping_path` in the operator's
    config, then the repository's `config/column_mapping.yaml` relative to the plugin root, then

    with it — never write it, never transform a row with it (D-07). Reimplement the normalization
    rule in a line or two (strip, collapse internal whitespace, lowercase, then dictionary lookup);

    and keeping rendering out of Python is what makes both surfaces one convention.

    Return the outgoing byte count or row count alongside, so the approval step describes the actual
    payload rather than an approximation of it.

    Write `tests/test_preview_rendering.py` covering every behaviour above against the 23-03

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator-supplied file → preview | Arbitrary headers and cell values are read and rendered back into the conversation |
| repository config → plugin | `config/column_mapping.yaml` is read, never written |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-23-11 | Tampering | `preview.build_preview()` | high | mitigate | The preview reads and reports only; a test asserts the source file's bytes are unchanged, so no client-side transformation can hide behind a rendering change |
| T-23-12 | Repudiation | mislabelled columns | medium | mitigate | Header normalization mirrors the backend's documented rule exactly rather than improving on it, so the preview cannot promise a mapping the backend will not perform |
| T-23-13 | Information Disclosure | preview rendered into the conversation | low | accept | Contact data the operator supplied is echoed back to that same operator; no secret is rendered, and the config secret never enters the preview structure |
| T-23-SC | Tampering | package installs | low | accept | No new dependency; `preview.py` uses PyYAML, already declared and audited in 23-03 |
</threat_model>

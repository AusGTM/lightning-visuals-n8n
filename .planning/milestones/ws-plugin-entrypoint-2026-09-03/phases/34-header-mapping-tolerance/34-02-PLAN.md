<objective>
Widen the deterministic alias table so the unambiguous near-misses read with zero operator
action, in all three places the table lives, together — then get the widened table into the
RUNNING backend, not merely the stored one.

This is Half A. It is a data-table edit whose whole risk is asymmetry: `config/column_mapping.yaml`
(what the plugin's preview reads), its byte-identical shipped copy, and `n8n/code/columnMap.js`
(what the backend actually executes) agree today by hand, not by construction. The guard that
makes this safe — `tests/n8n/columnMapAliasParity.test.mjs` — is already built, green and
committed at `634fe31`. This plan's job is to keep it green through the widening and then run
the redeploy ceremony that makes the change real.

Purpose: INGEST-02 — a CSV or XLSX reads without the operator pre-cleaning its headers.
Output: three widened alias tables, two rebuilt workflow artifacts, and a disarmed tenant whose
running `Map Columns` node knows the new aliases.
</objective>

**New alias keys — added identically to `config/column_mapping.yaml`,
`operator-claude-plugin/config/column_mapping.yaml` and `n8n/code/columnMap.js`'s `ALIASES`:**

| Key (already normalized) | Canonical prop | Why deterministic |
|---|---|---|
| `e-mail address` | `email` | A punctuation variant of the existing `email address` key. Lookup, not judgment |
| `org.` | `company` | Measured: scores 0.222 against every canonical prop, so the fuzzy suggester would never surface it — deterministic is the ONLY place it can live |
| `linkedin profile` | `linkedin_url` | A wording variant of the existing `linkedin url` key |

**Deliberately NOT added** (planner discretion, per 34-RESEARCH.md assumption A3): `company name`,
`work email`, `mobile phone`, `e-mail address:`. None has been observed to miss against a real
operator file, and each one measures cleanly above the Half B cutoff — `company name` 0.737,
`work email` 0.667, `mobile phone` 0.588, `e-mail address:` 0.500 — so all four already get a
suggestion with a confirmation turn. Adding a speculative key to a hand-maintained table that
lives in three files costs three files of drift risk to save one keystroke on a file nobody has
sent. `ph.` is also deliberately absent: CONTEXT.md §3 makes it the cautionary case (it could
plausibly be a photo column, and measured, `photo` scores 0.6 against `phone`), so it must stay a
confirmed suggestion, never a silent lookup.

**Rebuilt artifacts:** `n8n/wf_contact_ingest_cloud.json`, `n8n/wf_contact_ingest_local.json` —
the only two of the eight that embed `mapRow`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo alias table → running `Map Columns` node | A hand-maintained table crosses into executing backend code via an inline-and-deploy step |
| local deploy driver → live n8n tenant | A PUT and two POSTs per workflow mutate production |
| built artifact → operator's belief about live state | An artifact's `active` key is not live activation state |

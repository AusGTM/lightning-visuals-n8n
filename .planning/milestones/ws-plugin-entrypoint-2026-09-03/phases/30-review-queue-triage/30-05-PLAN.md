<objective>
Turn the queue payload into something a non-technical operator can actually adjudicate (REVIEW-01).
This is the load-bearing half of the phase: the writeback plumbing is worthless if the conflict is
unreadable.

Two rules shape it. The client reads `config/field_policy.yaml` display-only, to say "this value is
protected — a review decision cannot overwrite it" before the operator invests in a decision (D-06);
it never refuses locally, because a second policy authority drifts from the backend's (D-07). And it
renders only what is stored — the resolved source, its confidence, the machine's held-back reason,
the evidence link — labelled as the resolved source rather than a provider-by-provider disagreement,
because that disagreement is computed transiently during scoring and never persisted (D-08f, D-11).

Output: a plugin module that fetches the queue through the n8n read endpoint, labels protected
fields, links each record back to HubSpot, and renders the whole thing in plain language.
</objective>

    `fetch_queue(config, object_type, transport=requests)` POSTs to the configured n8n base URL's
    `hubspot/review/queue` path with the same header-auth convention the plugin already uses, and
    returns the parsed rows plus the queue total. It refuses through
    `config_gate.require_capability(cfg, "review")` before any network call, and never shows a secret.

    **The `transport` parameter defaults to the bare `requests` MODULE and the call goes through
    `transport.post(...)` — never `transport=requests.post`, and never a direct `requests.post(...)`
    (D-17, Phase 28 D-28/D-33).** This is a structural guard, not a style choice:
    `tests/test_retry_reuses_dispatch.py` scans every plugin script including ones not yet written,
    and a `requests.post` default here would make this function an unexpected send-shaped function
    and turn the suite red. **When that happens the tempting fix is to append this module to
    `_EXPECTED_SEND_SHAPED`. Do not.** That list is what stands between a client path and the arming
    gate `dispatch()`'s no-default `armed` parameter enforces; widening it to quiet a test is a
    weakening. If the guard fires, the module is wrong, not the guard.

    `policy_class(object_type, field, policy_path)` loads `config/field_policy.yaml` once and returns
    the field's ownership class, or None when the field is not in the policy. This is a lookup for
    explanation only: nothing in this module may branch on the returned class to block, filter, or
    alter a decision — the backend is the authority (D-06, D-07). Say that in the module docstring so
    the constraint survives the next edit.

    `record_link(object_type, record_id, portal_id)` builds the HubSpot record URL, returning None
    when no portal id is configured so the caller can render the raw id and name what is missing
    instead of emitting a broken link.

    Add two optional keys to `operator-claude-plugin/config/operator.local.example.json`:
    `hubspot_portal_id` (for the record link) and `field_policy_path` (nullable, defaulting to the
    repo's config file), mirroring the existing nullable `column_mapping_path` key. Document both in
    the plugin README's configuration section.

    earlier draft said the stub transport had to be extended because every call returned a fixed

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| n8n response → rendered chat output | CRM text, including operator- and model-written free text, is rendered to the operator |
| operator config file → outbound request | Holds the webhook secret the client must never display |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-20 | Information Disclosure | config handling | high | mitigate | The secret is only ever placed in a request header, never rendered, logged, or echoed in a refusal message (Task 1, inherited from Phase 23's refusal path) |
| T-30-20a | Elevation of Privilege | capability routing | medium | mitigate | `review` is its own `CAPABILITY_KEYS` row, so a review refusal never borrows `contact-upload`'s authority and a config withheld from review cannot be widened by convention (Task 1, D-18) |
| T-30-21 | Tampering | policy lookup | medium | mitigate | The lookup is display-only by construction; the module docstring and tests forbid branching on it, so no second policy authority can drift from the backend (Task 1) |
| T-30-22 | Spoofing | rendered evidence links | low | mitigate | Evidence URLs come from CRM data and are rendered as text/links only; the client never fetches them |
| T-30-23 | Repudiation | single-source rendering | medium | mitigate | The rendering discloses that it shows the resolved source, so an operator cannot mistake it for provider consensus (Task 2, D-08f) |
</threat_model>

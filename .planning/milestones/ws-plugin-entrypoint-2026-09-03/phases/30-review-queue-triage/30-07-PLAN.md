<objective>
Close the phase with the one thing no automated test can establish: that an armed review decision
actually lands in HubSpot as intended, on exactly one allowlisted record, and that the window is shut
afterwards.

allowlist, exactly the shape Phase 23's armed contact canary used.

documentation for the two new endpoints.

<task type="checkpoint:human-verify" gate="blocking-human">
  <name>Task 2: Human-executed armed review canary on one allowlisted record</name>
  <what-built>
    A synchronous review-decision endpoint (`hubspot/review/decision`) and a queue read
    (`hubspot/review/queue`) on a new, committed-inactive Cloud workflow; a rejection path that writes
    exactly one property and leaves the record queued; an approve path that applies the record's own
    stored candidate through the existing `reviewApply` compare-and-set and stamps a human-attributed
    provenance entry; a plugin surface that shows the backend's exact intended write and, armed, sends
    it and verifies by read-back. Every automated check so far runs against committed artifacts with
    no network access.
  </what-built>
  <how-to-verify>
    Agent tooling in this repo is blocked from arming writes. A human performs all of the following.

    1. Choose ONE HubSpot test company that is currently flagged for review and holds a stored review
       candidate. Note its record id. This id is the entire blast radius.
    2. Capture the before state: run `scripts/canary_record_snapshot.py` in snapshot mode with a label
       for this canary and the chosen record as the target, and keep the snapshot path.
    3. Deploy the review workflow armed for review writes only, with `ENABLE_BAKED_FLAGS` naming
       `ALLOW_HUBSPOT_REVIEW_WRITES` and a `TEST_RECORD_IDS` entry holding only that record id, and
       with the deploy's own write-enabling environment set as the deploy script requires. Confirm the
       deploy reported a non-zero rewrite count for the flag.
    4. Activate the review-decision workflow in n8n Cloud.
    5. From a Claude session with the plugin installed: open the review queue, confirm the chosen
       record appears with its conflict rendered in plain language and any protected field labelled.
    6. Without arming review writeback in the conversation, and with `ALLOW_REVIEW_SUBMIT` still unset,
       take a decision to the point of the exact-write display. Confirm the plugin shows the property
       write and states that nothing was sent — the preview is deliberately not gated on the variable
       (D-16), so this step works before step 6b.
    6b. Confirm the plugin-side gate refuses on its own: arm review writeback in the conversation with
       `ALLOW_REVIEW_SUBMIT` still unset, and attempt the rejection. The plugin must refuse, naming the
       variable, with nothing sent. THEN set `ALLOW_REVIEW_SUBMIT=true` on the session's environment.
       This is the only step that proves the env gate independently of the conversation arm.
    7. With review writeback armed for the conversation and `ALLOW_REVIEW_SUBMIT` set, REJECT the record
       with a short reason. Confirm the plugin reports verified. In HubSpot, confirm the review reason
       now holds your text, and that the record is STILL in the queue — its needs-review flag and
       stored candidate are unchanged.
    8. Approve the same record with a short reason. Confirm the plugin reports verified, the candidate's
       values are now on the record, the review flags are cleared, and the provenance blob contains an
       entry for each applied field naming a human source, the human-approved status, the timestamp and
       your reason — with the previously-recorded machine source still readable in that entry, and with
       provenance entries for untouched fields intact.
    9. Redeploy the workflow DISARMED (no `ENABLE_BAKED_FLAGS`), deactivate it, and unset
       `ALLOW_REVIEW_SUBMIT` on the session. Then read the deployed workflow back from the n8n API and
       confirm the review-write constant is in its disabled form on the live instance. A deploy that
       reports success is not evidence; the read-back is. Both gates close, not just the backend one.
    10. Capture the after state with `scripts/canary_record_snapshot.py` in compare mode against the
        snapshot from step 2, and record in the SUMMARY: the record id, both outcomes, the observed
        property changes, and the confirmed disarmed state.

    If any step writes to a record other than the chosen one, stop and report it — that is a gate
    failure, not a variance.
  </how-to-verify>
  <resume-signal>Type "approved" with the record id and the confirmed disarmed read-back, or describe what happened instead</resume-signal>
</task>

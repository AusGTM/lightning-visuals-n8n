1. **New classification logic** — credential failure and exhausted quota. These are not execution-

   do not fail an n8n execution, so they must be read from the credit-probe data instead. The data
   already exists; the judgment does not.
2. **Reuse of Phase 27's reads unmodified** — failed scheduled run and review backlog over threshold,
   plus the stuck-armed backend D-10 adds as the backstop for Phase 28 D-03's arm/disarm crash window.
3. **Behaviour across conditions** — silence when healthy, grouping when several fire at once, and
   attribution on every notice.

The condition that carries the most subtlety is the first one, and for a reason worth restating:
"unknown" and "exhausted" both feel like "can't rely on this provider" but mean opposite things and
require opposite attribution. Apollo's key in this deployment is not a master key and returns 403 by
design — telling the operator Apollo is out of credits when it has never once returned a readable
balance is a confidently wrong answer on the surface whose entire job is telling someone whether
they can act.

| provider probe data → operator-facing cause | The place a confident wrong classification does the most damage |
| n8n run status → "the backend is healthy" | A boundary that looks trustworthy and is not (D-08b) |
| notice text → operator action | Attribution decides whether the operator acts or escalates |

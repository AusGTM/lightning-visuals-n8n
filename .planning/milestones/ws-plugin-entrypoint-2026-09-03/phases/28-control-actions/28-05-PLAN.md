<objective>
The operator-facing surface: one entry point every control action passes through, and the skill that
drives it in conversation. Consequence stated first, change shown, explicit confirmation, then the
mutation, then a verdict from an independent re-read and the sentence saying how to undo it.

Purpose: the machinery in plans 01–04 is correct but silent. CONTROL-05's requirement is not that
the plugin happens to be careful — it is that the operator is told what will happen before it
happens, in language a non-technical person can act on, and that anything outside the allowlist is
refused rather than attempted. That is a surface, and it needs one choke point or it will be
bypassed by the next capability someone adds.

Output: `control_actions.py`, `skills/backend-control/SKILL.md`, and the documentation amendments
D-05c and D-25 require before this phase can seal — four scoped edits across two files.

  <action>
    Write `operator-claude-plugin/scripts/control_actions.py` as the single entry point the skill
    calls. Split it into `plan_action` and `execute_action` so the confirmation gate is structural
    rather than a convention: planning is what reads current state and composes the consequence, and
    executing is the only thing that can mutate. A caller that skips planning has no proposal to
    execute.

    `plan_action` classifies the request into the allowlisted kinds — workflow on/off, live-write
    arming for a named batch, schedule cadence, and per-job schedule enablement as 28-04 settled it
    — and returns a refusal for anything else. The refusal names what was asked for, says the plugin
    does not change workflow structure, nodes or credentials, and says an admin does that from the
    repository. The refusal path must be reachable before any mutating call exists in the flow, so a
    request to edit a node cannot get as far as a deactivate.

    Compose the consequence per action kind. For arming, the sentence has to say what live writes
    actually permit in this deployment — enrichment overwriting HubSpot company and contact fields —
    and it must also say the grant is bounded to the specific records in this batch, because 28-03
    derives the record allowlist from the batch and that bound is the strongest safety property the
    operator has. For cadence, the sentence names the current cadence and the proposed one, both
    from `describe_cadence`. For workflow on/off, it names what stops or starts running.

    `execute_action` takes the proposal and an explicit confirmation value. Make the affirmative
    explicit in the signature — no default, no truthy-by-omission — so a caller that forgets to pass
    it refuses rather than proceeds. Run the underlying mutation, and return the result's verdict
    verbatim. Do not translate `failed` into softer language and do not add a success path that any
    status code can reach; 28-01 already established that the verdict comes from an independent
    re-read, and this layer's job is to carry it, not to reinterpret it.

    `start_lane` implements CONTROL-01's surviving half. It calls the plugin's existing dispatch
    entry point unchanged and returns what it returns, plus a sentence naming where the outcome will
    arrive. It makes no n8n API call at all: starting a lane through the API would bypass the
    preview, cost guard and arming gate that Phases 23 and 25 built, and those guards live on the
    dispatch path (D-06).

    **Front whichever lane dispatchers exist at execution time — discovered, not assumed.** Today
    there is exactly one: `dispatch.dispatch`, contact lane only. The enrichment lane's dispatcher
    is Phase 25's 25-03/25-04, both blocked behind the 25-01 human checkpoint, which is not yet
    written. So `start_lane` resolves its dispatcher per lane at call time and, when a lane has
    none, returns a refusal that names the reason plainly — "the enrichment lane's dispatcher is
    Phase 25 work and has not landed yet; contact upload works now" — rather than raising an
    ImportError or, worse, silently routing an enrichment batch down the contact lane's multipart
    CSV path. Write the resolution so that a later Phase 25 landing needs no edit here: if the
    dispatcher is importable, the lane is offered.

    Gate the whole surface on the control capability. `plan_action` and `execute_action` both call
    `config_gate.require_capability(cfg, "control")` before constructing any transport, using the
    row 28-01 added to `CAPABILITY_KEYS`. This is why control is its own capability rather than
    reusing `"status"`: a config that can read the backend is not thereby a config that may mutate
    it, and the refusal message should name the mutating capability by name so an operator whose
    status checks work understands why control does not.

    `start_scheduled_scan` is a refusal, and writing it as a refusal rather than omitting it is the
    point — an operator who asks gets an honest answer naming the two things they can do instead,
    turning the whole workflow on or off, and re-timing the job. The module must contain no path
    that changes a schedule in order to make something fire: D-05c rejected that explicitly because
    a crash mid-sequence leaves the backend on the wrong schedule and silently changes how often it
    burns provider credits.

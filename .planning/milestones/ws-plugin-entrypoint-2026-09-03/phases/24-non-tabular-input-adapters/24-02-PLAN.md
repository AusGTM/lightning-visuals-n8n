<objective>
The two mechanics the screenshot adapter needs that no other adapter does: collapsing rows that
appear twice in a scrolled sequence, and refusing to guess where the image was unreadable.

Purpose: criterion 4 asks for a scrolled sequence to read as one source without duplicating overlap
rows, and criterion 5 asks for an ambiguous value to be surfaced rather than completed. Both are
built on the identity rule 24-01 already derived — one dedupe concept across the whole system, per
D-08, rather than a second fuzzy matcher that drifts from the backend's.

Output: dedupe and ambiguity behaviour in `extraction.py`, and the tests that make STRUCT-04's
checkable half a runnable assertion rather than a promise about a model.
</objective>

    - `24-RESEARCH.md` Pitfall 5 — why a similarity score is the wrong tool here, and the note that a
      dedupe MATCH should case-fold even though the identity PRESENCE check does not.
    - `operator-claude-plugin/scripts/extraction.py` as written in 24-01 — `identity_groups()`,

  <behavior>
    - Two records whose rows carry the same `email` differing only in case and surrounding whitespace
      collapse to one accepted row, and the collapse is reported.
    - Two records with no `email` on either side but the same `firstname`, `lastname` and `company`
      collapse to one accepted row.
    - Two records with different emails do not collapse.
    - Where two records collapse, the surviving row carries the union of the fields the two sides
      supplied where they do not conflict, and its provenance names both source inputs — the operator
      auditing a merged row can see it came from two captures.
    - Where two records collapse but disagree on the value of a non-identity field, the disagreement
      is added to the ambiguity list and the field is absent from the surviving row.
    - Two records that agree on every identity field one of them carries, but where the other side
      has that field absent or an ambiguity entry names it as truncated, are NOT collapsed: both are
      kept and an ambiguity is added asking whether they are one person.
    - Dedupe over a single-record batch returns that record unchanged and reports no collapse.
  </behavior>
  <action>
    Add dedupe to `extraction.py`, running over accepted records after the identity pre-flight — a
    record that failed the identity rule has no identity key to dedupe on, so ordering is forced, not
    stylistic.

    Build each record's identity key from `identity_groups()` so the key and the pre-flight cannot
    drift apart: for the first satisfied group, the tuple of that group's field values, each trimmed
    and case-folded. Case-folding is correct here and wrong in `has_identity()` — two vision reads of
    the same name should match, but presence is a different question from equality, and 24-RESEARCH.md
    names conflating them as the pitfall. Compare keys for exact equality. Do not compute a similarity
    score, an edit distance, or a fuzzy threshold: anything short of an exact identity-key match is an
    ambiguity by D-09, and a threshold is precisely the knob that would let two different people
    silently become one.

    When two records share a key, merge them: take each field from whichever side supplied it, keep
    both provenance records so the merged row names every image it was read from, and where the two
    sides supply different non-empty values for the same field, drop the field and add an ambiguity
    rather than picking a winner. Report each collapse so the preview can state that the batch
    contained overlap and how much.

    For the near-duplicate case D-09 describes — one side has an identity field the other lacks, or
    an ambiguity entry names that field as truncated or unreadable — keep both records and add an
    ambiguity asking whether the two partial captures are one person. Keeping both is the safe
    default: the operator can merge two rows they recognise, but cannot recover a row that was
    silently absorbed.

    Return the collapses and the newly-raised ambiguities on `ExtractionResult` so the preview built
    in 24-01 renders them without a second data path.

    Write `tests/test_overlap_dedupe.py` covering every behaviour above. Build the two-screenshot
    overlap case explicitly — a record from one image and a record from a second image that reads the
    same person — so the test file documents the scenario criterion 4 names.
  </action>

      list on `ExtractionResult`, each entry naming the record it concerns, the field, what was seen,
      and why it is uncertain.
    - An ambiguity entry naming a field that is nonetheless present with a value on that record's row
      causes that record to be rejected with a reason — a value cannot be both flagged as unresolved
      and asserted, and permitting it would be exactly the guess STRUCT-04 forbids.
    - An accepted record whose ambiguity names a field simply does not carry that field.
    - A record whose only identity field is the one an ambiguity names therefore fails the identity
      pre-flight and appears in rejected, not accepted.
    - `validate()` on an artifact with no ambiguities returns an empty ambiguity list, not a missing
      key — the preview renders the block unconditionally and an absent key would read as a crash.
    - Running the validator twice on the same artifact returns the same accepted rows, rejects and
      ambiguities — nothing about the batch depends on order of processing or a random tiebreak.
  </behavior>
  <action>
    Aggregate every ambiguity source into the single list D-06 requires, normalising the three
    producers to one entry shape so the preview renders one block. Sort deterministically by record
    index then field so two runs over the same artifact produce byte-identical output — a preview that
    reorders itself between runs is one the operator cannot diff.

    Add the D-07 enforcement: a record carrying both an ambiguity for a field and a value for that
    same field is a contradiction — the extraction step said it was unsure and then filled it anyway.
    Reject that record with a reason naming the field. This is the strongest structural statement
    available for STRUCT-04, and it is deliberately narrow: Python cannot verify that an extracted
    value is true, only that a value the extractor itself flagged as uncertain is not silently

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| image-derived records → accepted rows | A vision read is the least reliable input this phase accepts; a truncated or misread glyph crosses here |
| ambiguity list → row values | Must be one-way: an ambiguity reports, it never writes a value into a row |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-24-05 | Tampering | dedupe merge | high | mitigate | Exact identity-key equality only; no similarity threshold exists to tune, so two different people cannot be merged by a scoring accident. Conflicting non-identity values drop to an ambiguity rather than one side winning |
| T-24-06 | Repudiation | merged row provenance | medium | mitigate | A merged row keeps both source provenance records, so an operator auditing a questionable row can name every image it was read from |
| T-24-07 | Tampering | ambiguity that also carries a value | high | mitigate | A record flagged uncertain for a field yet carrying a value for it is rejected — the structural half of STRUCT-04, and the only invention Python can actually detect |
| T-24-08 | Spoofing | crafted image causing a forged row | medium | accept | Presence, not truthfulness, is what the pre-flight checks; documented ceiling carried forward from T-24-03. Containment is the canonical-prop allowlist from 24-01, which bounds what any extraction can emit |
| T-24-SC | Tampering | package installs | low | accept | This plan installs nothing; no dependency is added beyond 23-03's declared set |
</threat_model>

<objective>
Close the loop the governing rule demands: once ingested rows have HubSpot object ids, hand
them to the queue the backend already sweeps, so nothing the pre-ingest pass could not finish
ends the cycle unenriched.

Purpose (37-CONTEXT.md §13b): §12's rejection of stub records stands — a row with no email
still does not get a manufactured HubSpot footprint. But that rejection's cost is now bounded:
pre-ingest exclusion becomes temporary rather than terminal, because everything that DID land
gets swept afterwards by the existing scheduled poller.

Output: `report.queue_handoff_ids`, plus a recorded operator decision on the transport that
actually sets the flag.
</objective>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 2: choose the transport that sets lv_enrichment_requested</name>

  <decision>
How the created record ids from Task 1 actually get `lv_enrichment_requested = true` set on them,
so the existing fifteen-minute scheduled poller sweeps them.
  </decision>

  <context>
37-CONTEXT.md §13(b) names the outcome — the poller sweeps whatever pre-ingest could not finish —
but the client has no path to that property today. Verified against source while planning:

- `hubspot/review/decision` writes only the COMPANY field-policy keys, via `reviewApply`, and only
  on records already flagged for review with a candidate. It cannot set an arbitrary property on
  a freshly created contact.
- `hubspot/contact-upload` writes only the seven canonical props; `extraction.write_dispatch_csv`
  refuses any eighth key, which is a guarantee this phase deliberately strengthened.
- `hubspot/enrichment/event` enriches. It spends provider credits and needs an arming grant.

So the outcome is agreed and the mechanism is not. The three options differ in what they cost at
run time and in where the change lands. This is a blocking decision because it changes both the
skill's turn sequence (option A adds a third arming phrase) and whether any backend work rides
Phase 36's already-scheduled deploy (option B).
  </context>

  <options>
    <option id="option-a">
      <name>Hand the created ids to the existing enrich-records lane</name>
      <pros>Zero backend change. Uses a lane that already exists, is already tested, and is
      already how this flow hands off confirmed-match ids. Enrichment happens immediately rather
      than within fifteen minutes.</pros>
      <cons>Spends provider credits at that moment, on a batch the operator has already paid to
      enrich once pre-ingest. Requires a THIRD arming phrase in the same conversation, which
      directly weakens §6's two-phrase design — the whole argument for two phrases is that each
      one guards a distinct irreversible thing at the moment it happens, and a third grant
      immediately after the second trains the operator to say yes reflexively.</cons>
    </option>
    <option id="option-b">
      <name>Set lv_enrichment_requested = true in the ingest lane's create payload (backend)</name>
      <pros>Costs nothing at run time and needs no additional arming — the poller picks the
      records up on its own schedule. Matches §13(b)'s stated mechanism exactly. It is a small,
      single-constant edit in `scripts/build_cloud_workflows.py` that can ride the Phase 36
      mode-aware-ceiling amendment's already-scheduled deploy, so it costs no extra deploy
      cycle.</pros>
      <cons>It is backend work in a phase scoped as client-only, so it must be handed to the
      Phase 36 amendment rather than executed here. Every created contact gets queued, including
      ones the pre-ingest pass fully enriched — the poller's own staleness gate would then decide
      whether to act, which is one more thing to verify live.</cons>
    </option>
    <option id="option-c">
      <name>Report the ids and let the operator flag them in HubSpot</name>
      <pros>No code and no backend change at all. The ids are already available from Task 1.</pros>
      <cons>"Run this in HubSpot yourself" is the requirement failure v0.6 exists to remove — the
      operator is non-technical, works in Claude Desktop, and never opens n8n. It also does not
      satisfy §13's governing addition, which is that no contact ends a cycle unenriched.</cons>
    </option>
  </options>

# Roadmap — Milestone v1.1: Unattended Session Runs

**Created:** 2026-08-25. **Status:** PLANNED, NOT STARTED.
**Requirements:** `.planning/milestones/v1.1-REQUIREMENTS.md`
**UAT evidence:** `.planning/quick/260825-contact-company-association/UAT.md` (G-1..G-4)

Phase numbering continues the global sequence and starts at **53**: Phase 52 remains v1.0's
own outstanding phase and is not part of this milestone.

## Decisions taken before planning (operator, 2026-08-25)

- **D-1.1-01 — the grant is operator-openable in Claude.** The `ALLOW_N8N_ARM` environment
  variable is replaced as the authority for interactive runs: an admin enables the capability
  once, in the settings file, and the operator opens a session grant in conversation. This is
  what removes the terminal dependency that made G-2 a blocker. The env gate is not deleted
  blindly — it stays the authority for headless/cron paths (`scheduled_arm.py`), which have no
  operator to confirm anything.
- **D-1.1-02 — grant first, then a single async pass.** The grant is opened *before* the run,
  so a record is enriched once and written in the same pass (killing G-3's double spend), and
  the run submits and polls rather than blocking on n8n Cloud's ~100 s response window.
- **D-1.1-03 — the first slice is the full pair pipeline.** Ingest → enrich → create →
  associate, unattended, **creates included**. This is the largest blast radius available, so
  the safety phases are not optional tail-end work: Phase 57's ceilings and post-run proof
  ship inside the milestone, not after it.

## Phases

### Phase 53 — Operator-openable write grant

**Goal:** an operator in Claude Desktop can authorize writes without anyone touching a
terminal, and the authorization is bounded, expiring, and revocable.

- Replace the interactive path's `ALLOW_N8N_ARM` dependency with an admin-set capability in
  the settings file plus an operator-opened session grant. Headless paths keep the env gate.
- The grant object: object types, record set, creates yes/no, ceilings, expiry. Never
  persisted, never inferred, never carried across sessions (GRANT-06 is unchanged).
- Expiry on batch completion, ceiling breach, revocation, session end, unhandled error — each
  disarming the backend and reporting the verdict; `disarm_failed` keeps its own loud state.
- Revocation mid-run, effective at the next send (re-scoped by the operator 2026-08-25;
  `dispatch_plan` has no grant-aware loop, so a running dispatch finishes its chunks).

**Plans:** 4 plans (planned 2026-08-25)

- [x] `53-01-PLAN.md` — the grant core: settings-key authority, grant shape, one send armed
      end to end, and the one deliberate re-point of the arm/probe parity pin
- [ ] `53-02-PLAN.md` — envelope arithmetic, the five close reasons, revocation, and both
      proposed guardrails (refuse-over-armed-backend; bound the disarm unknown)
- [ ] `53-03-PLAN.md` — the operator surface: the settings key in the example config, the
      initialize report, the plan-then-yes exchange, revoke, and the grant-to-dispatch bridge
- [ ] `53-04-PLAN.md` — the four lane skills, the README, the release cut, and a blocking
      operator walk of the whole path from Claude Desktop

**Closes:** G-1, G-2, GRANT-01, GRANT-03, GRANT-04, GRANT-05, GRANT-06.
**Risk:** this phase moves the safety line. Every test that pins "arming refuses without the
env var" has to be re-pointed deliberately, one at a time, with the reason recorded — a
sweeping update to those tests is how the property gets lost.

### Phase 54 — Single-pass armed dispatch

**Goal:** a record is enriched once. No derive-then-rearm-then-derive-again.

- When a grant is open, the dispatch runs inside the armed window from the start; there is no
  unarmed first pass to throw away.
- The `write_blocked`-then-arm path stays reachable for the ungranted case and is reported as
  what it is: a rehearsal that will cost a second pass if it proceeds to a write.
- Measure the actual saving live on one record before claiming it (the projection is 2 provider
  passes → 1, ~$0.07 → ~$0.035 Anthropic, 2 executions → 1).

**Closes:** G-3. **Feeds:** GRANT-02's arithmetic, which is only honest once the cost model is.

### Phase 55 — Async run: submit, poll, resume

**Goal:** a batch is no longer bounded by the synchronous response window.

- Submit returns a run id immediately; the client polls run state rather than holding a request
  open. Decide and record where run state lives (n8n static data, a HubSpot object, or an
  external store) — each has a different failure mode when n8n restarts mid-run.
- Progress readable while running: records done, held, failed, spend so far against ceiling.
- A run interrupted by a restart resumes or fails loudly; it never silently half-completes.

**Closes:** RUN-01, RUN-03, RUN-04.
**Risk:** the highest-uncertainty phase. n8n Cloud's execution model, not our code, decides
what is possible here — spike it before planning tasks.

### Phase 56 — The unattended pair pipeline

**Goal:** one grant carries a batch through ingest → enrich → create → associate, with held
rows collected rather than guessed.

- The full pair lane under a single grant, creates included, association enforced (the
  2026-08-25 contract: a contact that cannot resolve a company is held, never landed).
- Held and failed rows land in a queue that survives the session; failed records stay
  re-sendable as one well-formed request.
- The search-index lag between a company create and the contact ingest that must find it is
  handled by the run itself, not by an operator watching and waiting.

**Closes:** RUN-02, AFTER-02, and the milestone's client-facing promise.

### Phase 57 — Ceilings, refusal-before-start, and post-run proof

**Goal:** an unattended run cannot spend what it does not have, and can prove afterwards that
it wrote only what it was granted.

- Per-run ceilings on provider credits, Anthropic dollars and n8n executions, enforced before
  the first record, with the arithmetic shown at proposal time.
- A run that would exhaust the monthly execution allowance refuses before starting and offers a
  smaller batch. The allowance is sampled, not read — n8n exposes no usage endpoint.
- Post-run proof: an independent re-read showing that every record written was in the grant's
  allowlist and nothing outside it changed. G-4's unreadable balances are resolved or the run
  refuses to treat "unknown" as headroom.
- End-of-run report: per-record outcome, association outcome, held rows named individually,
  spend actuals vs ceiling, disarm verdict, and a clear line between "written" and "would have
  been written".

**Closes:** RUN-05, AFTER-01, AFTER-03, G-4.

## Sequencing

53 → 54 → 55 → 56 → 57 is the dependency order, but **57 is not deferrable to the end in
practice**: Phase 56 is the first phase that can create records unattended, so 57's ceilings
and post-run proof must land before 56 is run against anything but a capped pilot batch. Plan
56 and 57 together, or gate 56's first live run on 57's ceiling work.

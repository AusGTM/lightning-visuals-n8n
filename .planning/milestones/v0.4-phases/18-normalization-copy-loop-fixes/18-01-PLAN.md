<objective>
Stop a numeric provider industry code from masquerading as a normalized industry value, and
therefore from winning the cross-provider waterfall on the ZoomInfo source-trust constant alone
(NORM-01, ROADMAP Phase 18 success criteria 1 and 2).

Purpose: execution 19 promoted ZoomInfo's `"71"` over Apollo's `"media production"` as the
company `industry`. The mechanism is fully determined by code: for `industry` both providers push
a flat ungraded accuracy of 0.6, neither carries a differentiating recency date, a numeric code
can never text-agree with a competitor, so A/R/G tie and `T` (zoominfo 0.85 vs apollo 0.75)
decides — every time, regardless of value quality. The root-cause fix is upstream of the scorer:
never emit a bare code as an `industry` candidate value in the first place.

Output: one `_industryText` helper in `n8n/code/normalizeProviders.js` used by both the ZoomInfo
and Lusha company mappers, a new offline test proving both success criteria against the real
recorded live fixture, two updated collateral assertions, and regenerated workflow artifacts.
</objective>

## Planner decisions (edge probes — no SPEC exists for this phase)

These resolve the `$COVERAGE` unresolved edges for NORM-01. They are decisions, not open
questions; the tasks below implement them and the acceptance criteria check them.

- **D-NORM-empty** — When `naicsCodes` is absent/empty, or its first entry is a bare code string
  with no `.name`, the helper falls back to the provider's industry TEXT field
  (`primaryIndustry` for ZoomInfo, `mainIndustry` for Lusha; first element if it is an array).
  When that fallback is also absent, the helper returns `null` and **no industry candidate is
  emitted at all** for that provider. Rationale: a bare code is not a valid industry text value,
  and converting one into text would require a NAICS lookup table — explicitly rejected by
  RESEARCH "Don't Hand-Roll". Emitting nothing is honest and satisfies criterion 2 by
  construction (a field with no candidate cannot win any comparison).
- **D-NORM-encoding** — Equality/agreement semantics are NOT changed by this plan. Agreement stays
  `scoreEnrichment.js`'s existing `_eq` (`String(a) === String(b)`) over `_norm` output
  (`String(v).trim().toLowerCase()`). No Unicode normalization form, no locale-aware casing, no
  grapheme handling is introduced. The "is this a bare code" assertion in the new test uses an
  ASCII-digit-only anchored pattern; a non-ASCII industry NAME correctly passes it.
- **D-NORM-precedence** — When BOTH a NAICS `.name` and a text fallback are present, the NAICS
  `.name` wins (RESEARCH + PATTERNS both specify this order). For the Racing NSW live fixture that
  yields `"Arts, Entertainment, and Recreation"` rather than `"Hospitality"`. Alternative
  considered and rejected: preferring `primaryIndustry[0]`, which is more specific but provider-
  proprietary and not cross-provider comparable.
- **D-NORM-lusha** — The identical-shape hazard in `lushaCandidates()` IS fixed in the same pass
  via the same helper (RESEARCH Open Question 2, recommendation accepted). Labelled defensive:
  no live fixture proves Lusha ever returns object-shaped naicsCodes. Consequence to accept
  knowingly: with the flat `lusha_company.json` fixture (bare code, no `mainIndustry`) Lusha now
  emits **no** industry candidate, so the cross-provider NAICS-code agreement signal that the
  existing test at `tests/n8n/enrichment.test.mjs` line 265 pins disappears. That signal is
  replaced by a genuine TEXT agreement between Apollo and ZoomInfo on the same fixtures — see
  Task 2.

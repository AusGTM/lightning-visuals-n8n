## Planner decisions

- **D-GAP1-scope** — Fix the n8n request contract for `lv_sponsorship_reliant` ONLY; do NOT bring
  the n8n `required_fields` list to full parity with `src/web_research.py`'s nine-field
  `REQUIRED_FIELDS`. The three extra Python fields are a deliberate scope difference, not drift, and
  requesting them would silently widen what a live model is asked to classify — outside this gap's
  fence and unbudgeted in the prompt's token accounting.
- **D-GAP1-noparitytest** — Do NOT add a builder-vs-Python parity test over the two lists. A
  superset assertion (`n8n ⊇ python`) fails today by design; a subset assertion (`n8n ⊆ python`)
  passes both before and after and therefore would not have caught the drift that actually occurred.
  A test that cannot fail on the observed failure mode is not a guard. The executed request-contract
  test in Task 1 pins the n8n side directly, which is the assertion with teeth.
- **D-GAP1-pyoracle** — `src/web_research.py`'s `RESEARCH_SYSTEM` schema string gets the same one
  field, because that file's own header comment (:27-30) states it is kept in parity with the
  production n8n prompt and its `REQUIRED_FIELDS` already names the field. Leaving the schema string
  behind would recreate, in the oracle, the exact inconsistency being fixed in production.
- **D-GAP2-provider** — Of the three producer options weighed, choose the provider mapper reading a
  provider's OWN department field (option c). It is verified live-present in recorded fixtures for
  two of three providers (table above), costs zero LLM tokens, invents no taxonomy, touches no
  frozen module, does not widen the Phase-16.2 `applyContactJudgeVerdict` allowlist, and produces a
  value with real source attribution through the same waterfall `seniority` already flows through.
  Option (a), a hand-written title-to-persona heuristic, was rejected: it would fabricate a
  classification from a string the provider never classified, and no such mapping exists anywhere in
  the Python lane to mirror (`grep persona src/*.py` finds only a property name in `src/ingest.py:23`).
  Option (b), extending the contacts research/judge prompt, was rejected: it costs live tokens, only
  fires on rows the research gate selects, and collides with the 16.2 allowlist decision.
- **D-GAP2-othervalue** — Lusha's live `departments: ["Other"]` is treated as a NON-signal and emits
  no candidate. This is not an invented taxonomy rule; it is the same null-rather-than-fabricate
  precedent `_industryText` established one plan ago in this exact file for a bare NAICS code. A
  persona group of `Other` is not a classification — it renders in a HubSpot view as though a
  decision were made when none was, which is strictly worse for the RevOps reviewer than the
  property staying blank. The check is a single case-insensitive comparison.
- **D-GAP2-rawvalue** — The promoted value is the provider's raw department string (Apollo's
  `media_and_communication`), because `scoreEnrichment.js:104` sets `winners[field] = top.value`.
  No prettifier, no normalizer, no case transform: `lv_persona_group` is free text
  (`config/hubspot_properties.yaml:343`) and this is byte-for-byte how `seniority` already behaves
  with three mutually inconsistent provider formats. Reformatting is a separate, deliberate decision
  for a future phase, not a drive-by in a gap-closure plan.
- **D-GAP2-nozoominfo** — No ZoomInfo persona push. No department field appears in either recorded
  ZoomInfo shape; reading a speculative key would assert a provider contract never observed. A
  missing source is already handled by the waterfall.
- **D-GAP1-order** — Within Task 1, land the prompt edit, rebuild, run the bounded frozen check, and
  re-baseline BEFORE making the CSV edit; then rebuild again and confirm the CSV edit moves ZERO
  frozen pairs. Bundling both edits into one rebuild would make an unexpected frozen diff
  unattributable, which is precisely the condition the bounded procedure exists to catch.

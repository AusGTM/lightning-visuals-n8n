## Planner decisions (edge probes — no SPEC exists for this phase)

- **D-COPY-scope** — This plan lands the copy-loop WIRING ONLY. It does NOT extend the companies or
  contacts research prompt schemas so a live model would ever produce either value. RESEARCH Open
  Question 1, recommendation accepted: ROADMAP criteria 3 and 4 require a test proving the property
  populates from a real candidate, not a live producer. Explicit planner assumption to record:
  **neither field currently has ANY producer** — no provider mapper in `normalizeProviders.js`
  emits the persona field, and the companies research prompt's required-fields list does not ask
  for the sponsorship field. Task 3 records this as a named carry-forward so it is not lost a
  second time.
- **D-COPY-adjacency** — Both additions are into disjoint key spaces. The companies waterfall
  candidate loop copies domain / industry / revenue band / employee band / country only, so the
  sponsorship field can only ever come from the research fold — the "two mergeCompanies calls
  handle DISJOINT field sets" invariant documented in the wrapper's own comment still holds after
  the change, and no shallow-merge key collision is introduced. On the contacts side the new key
  is `lv_persona_group`, which collides with neither the five array-copied keys nor
  `lv_linkedin_url` nor the contacts research fold (jobtitle/seniority only).
- **D-COPY-empty** — A null, undefined, empty-string, or empty-array candidate value is skipped by
  the guard that already exists in each loop; the key is simply absent from the candidate object
  and the merge call never sees it. On the companies side, if skipping leaves `researchData` empty
  the existing non-empty check means the second `mergeCompanies` call is not made at all. When
  `row.scored` is null (contacts) or the research candidate is absent/unmatched (companies), the
  existing skip branches are unchanged. No new blank-check variant is introduced — reuse the
  guard form already present in each loop verbatim.
- **D-COPY-ordering** — Both additions go at the END of their construct: the sponsorship entry is
  APPENDED to the existing five-element array (never inserted mid-array), and the persona if-block
  is placed AFTER the existing linkedin block. This keeps every existing field's key-insertion
  order — and therefore the order of entries in each merge result's `decisions` array — byte-stable,
  which is what makes the frozen-fixture diff in Task 2 provably confined to the one added entry.
- **D-COPY-redevidence** — COPY-01 gets DURABLE red evidence for free by reading the existing
  write-once `tests/fixtures/merge_company_prefix_jscode.json`, whose `Merge Company` body predates
  this fix. No new pre-fix fixture is captured. COPY-02's node is not frozen and has no pre-fix
  snapshot, so its red is a recorded verbatim run before the edit, per the standard red-before-green
  discipline.

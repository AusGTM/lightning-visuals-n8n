<objective>
Make the run's ledger say what actually happened to each row. Today
`written_records.classify_item` collapses every non-write action into one word,
`not_written`, and the concrete consequence is AFTER-03's exact case: a `write_blocked` row —
one the backend would have written, and which an operator can recover by opening a grant and
re-sending — is indistinguishable from a failure. The other consequence is the mirror image:
`skip` and `proposed` are successes, and they currently make a clean run read as though half of
it did not land.

Purpose: AFTER-03, and the join key AFTER-01 cannot be built without.

Output: one widened outcome vocabulary, used by both client-side readers, with `row_id` and
`association` captured on every entry and reaching the ingest lane's response.

## The two explicit resolutions this plan owes the phase

**1. `enrich` — the tenth action.** The backend emits ten distinct `action` values, not the
nine D-57-03's table accounts for. `enrich` is a genuine write (it is in
`written_records.WRITE_ACTIONS`) and has no row in the operator's table. It is placed on
`written`, exactly as `update` is, because that is what it is. It is not dropped and it does not
fall through to a default.

**A seventh outcome word is added, and this plan is declaring it rather than smuggling it.**
`update` or `enrich` whose response carried no `hs_object_id` has nowhere honest to go: it is
not `written` (constraint: "written" must never be inferred), and `created_id_unknown` is
literally named for creates and D-57-03 says it stays as-is. That row gets
`written_id_unknown`. This EXTENDS the operator's six-outcome table by one word for a case the
backend can in principle emit; the operator action for it is "open this row's record and
confirm", which is distinct from every other word's action, so it earns its place by the same
test the other six are held to.

**2. The two-vocabulary divergence is reconciled here, not deferred.** PATTERNS grepped the
whole repo and confirmed exactly TWO client-side surfaces map an `action` to an operator-facing
word: `written_records.classify_item`/`WRITE_ACTIONS`, and
`report_enrichment._ACTION_TO_OUTCOME`. The second maps only 6 of 10 values — `update`,
`review`, `research_failed` and `recompute_refused` all render as `"unknown"` today, uncovered
by any test — and uses different words for overlapping concepts (`"blocked"` where D-57-03 says
`gated`). Leaving them divergent is not an option; CLAUDE.md section 13.0.1 records what a
second copy of one rule costs, and closed exactly that class of gap by refusing to duplicate.
`report_enrichment` imports `written_records`' outcome constants and delegates to
`classify_item`. It does not keep a second table.

The per-module `_FORBIDDEN_NAME_MARKERS` anti-DRY convention is NOT weakened by that import: it
covers the forbidden-name tuple specifically (each module carries its own copy so a change to
one cannot silently weaken another), and says nothing about an outcome vocabulary that must, by
definition, be identical everywhere.
</objective>

<objective>
RUN-05 does not stop at refusing. It says the run "refuses before starting, with the
arithmetic, and offers a smaller batch," and D-57-04 makes that offer concrete: a batch that
would exhaust the allowance is split into affordable runs and the remainder is queued, so the
whole batch completes over time without the operator re-deciding each round.

D-57-05 is what keeps that honest, and it is a hard constraint rather than a preference:
**auto-split queues WORK, never AUTHORITY.** GRANT-06 is that a grant is never persisted and
never rehydrated, and 61-06 restated it — a resumed run gets a FRESH grant. Auto-split is the
most autonomous thing in this milestone and it schedules future spend at the moment of one yes;
the only thing that stops it becoming a standing licence is that each subsequent run is still
separately authorised.

Purpose: RUN-05's offer, D-57-04's remainder, D-57-01's durable home for the rows a mid-run
breach did not send.

Output: one new durable store, one split calculator, and the breach path wired into both.

## Decisions taken here (Claude's Discretion, per CONTEXT.md)

**The remainder lives BESIDE `held_queue.py`, not in it — and the two questions CONTEXT told
the planner to keep separate are both answered the same way, for one reason.**

CONTEXT asks separately where breach-held ROWS go (D-57-01) and where the remainder BATCH goes
(D-57-04). Both go to the same new `remainder_queue.py`, because a ceiling-breach row and a
ceiling-breach remainder are the same fact at two granularities, and splitting them across two
stores would be the second copy of one rule this codebase keeps paying for.

They are not `held_queue.py` entries. That module's `hold_code` is a validated, CLOSED
vocabulary (`confidence.ALL_HOLD_CODES`) built for per-row confidence holds, and its
`fingerprint()` requires a `preingest.Outcome`-shaped object with `.match_tier` and
`.candidate_count`. A row that was never dispatched because the budget ran out was never
assessed by `confidence.assess()` and has neither. Forcing it through would mean either adding
a hold code `assess()` never emits — breaking that module's own stated invariant — or
synthesising a fake outcome for `fingerprint()` to hash. Both are worse than a small sibling
file following the same idiom.

What IS reused, verbatim: `durable_paths._atomic_write_0600`, the per-run
`<name>-<run_id>.json` filename plus glob-and-union reader (D-59-09), the fail-loud-on-shape
discipline, and a FRESH per-module copy of `_FORBIDDEN_NAME_MARKERS` — never an import, per the
convention `written_records.py`, `held_queue.py` and `run_state.py` each already follow and each
document.

**The operator's one review pass is preserved by the report, not by the store.** D-57-01 asks
for one review pass over a run's held rows. Plan 57-05's end-of-run report presents held_queue
rows and remainder-queue rows together in one section, so the operator still reviews once. Two
stores, one surface.

## Corrections and deferrals from cross-AI review

**A queued remainder is not a scheduled one, and the operator-facing text must not say
otherwise.** D-57-04's phrase "the whole batch completes over time" was carried into the first
pass as though queueing implied completion. Under D-57-05 it does not: the queue holds work, and
nothing in this system will pick that work up without a human opening a fresh grant for it. The
refusal text, this plan's `<done>` blocks and 57-05's report all say **queued for a future run
you will separately authorise** — never "will complete automatically".

**Crash-mid-run recovery is explicitly OUTSIDE the remainder guarantee (deferred, with
rationale).** The remainder is written when the ceiling predicate fires — a deliberate stop. A
process crash between two chunks writes nothing, so the unsent chunks are not in the remainder
queue. Reviewers proposed check-pointing the remaining chunks after every successful chunk; that
is a durable write per chunk on the hot dispatch path, for a failure mode the existing per-chunk
`written_records.append_chunk` evidence already makes RECONSTRUCTABLE (what was sent is on disk;
what was planned is the operator's own batch). The honest position, stated here rather than
implied: after a crash, the remainder queue is silent about that run, and 57-05's report names
that as a gap. Revisit if a crash-mid-run is ever actually observed.

**What is fixed rather than deferred:** `failed_batch`'s lost shapes (Task 3), the missing
`REASON_ALLOWANCE_SPLIT` producer and its state transition (Task 3), and the id/domain
distinction (Task 3).

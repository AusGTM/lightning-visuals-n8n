<objective>
G-4: two of three provider balances read `unknown` in the same preview — Apollo
`unrecognized_response_shape` (expected) and ZoomInfo `provider_error` (new as of the 2026-08-25
walk). That is thin cover for an unattended run that spends against them, and D-57-02 puts the
FIX in scope, not only the disclosure: with the ceiling unable to fully guard provider spend
while a balance is unreadable, narrowing the blind spot is the cheapest available increase in how
much of the spend is genuinely guarded.

The two halves of G-4 have opposite shapes, and this plan does not pretend otherwise.

**Apollo is disclosure only, and permanently so.** The account's Apollo API key is structurally
not a master key, and Apollo's `usage_stats` endpoint 403s for any non-master key by design —
verified in this repo's own live-curl-confirmed comments at `n8n/code/providerSelection.js:76-106`
and `scripts/provider_registry.py:26-33`. Fixing it needs a different Apollo credential, an
account-level change outside this repo. Nothing in this plan attempts a code fix for it.

**ZoomInfo needs an observation, not a patch.** The cause recorded in this project's own memory
— a missing `Accept: application/vnd.api+json` header — is ALREADY FIXED in current code
(`scripts/build_cloud_workflows.py:4614-4630` sends the header). Meanwhile the label observed
is `provider_error`, which by `ENRICH_STATUS_BUILD_RESPONSE`'s own logic
(`build_cloud_workflows.py:6354-6362`) means the HTTP request itself errored — a DIFFERENT label
from `unrecognized_response_shape`, which is what an unparseable body produces. An expired mint,
a stale cached token and a genuine transient 5xx all produce the label observed, and code
inspection cannot tell them apart. So this plan probes and reports; it does not guess a fix for a
cause that may already be gone.

Purpose: G-4, and the honesty requirement D-57-02 creates — because the ceiling cannot fully
guard provider spend while a balance is unreadable, the report must not imply that it did.

Output: a disarmed live probe, a fixture that tells the two ZoomInfo failure labels apart, and a
recorded verdict.
</objective>

  <action>
Create `scripts/prove_zoominfo_balance.py`, following `prove_async_recovery.py`'s shape exactly,
per G-4 and D-57-02.

Gate: an `ALLOW_ZOOMINFO_BALANCE_PROBE` environment variable read EXACTLY as the string `"true"`,
never truthy-coerced. Instance guard: mirror `deploy_n8n_workflows.py::_instance_ok()` so the
probe cannot run against an unrecognised instance.

This probe needs LESS safety scaffolding than its two siblings, and the reason should be stated
in the module docstring rather than left as an unexplained omission: the balance check is the
existing `Status Credit Request` to `ZoomInfo Usage` chain, which is read-only, already runs
with `onError: continueRegularOutput`, writes nothing and spends no provider credit. So there is
no `mode: "propose"` gate and no empty-providers trick to apply — there is no write to make
structurally impossible, because the call being probed is a GET.

What it does: POST the existing status request to the deployed backend's status endpoint the
same way `cost_guard.fetch_balances` already does, read the ZoomInfo entry out of the response,
and write a verdict file `.planning/phases/57-ceilings-refusal-before-start-and-post-run-proof/57-ZOOMINFO-BALANCE-VERDICT.json`
carrying: the observed label, the raw credits value if any, whether an HTTP status was present,
the ISO timestamp, the instance host, and a `verdict` of `readable`, `provider_error`,
`unrecognized_response_shape` or `inconclusive`.

Distinguish the labels explicitly in the verdict, because they mean different things and imply
different fixes: `provider_error` means the HTTP request itself errored (an expired mint, a
stale cached token, a transient 5xx upstream); `unrecognized_response_shape` means the request
succeeded and the body could not be parsed (a contract change). Record which, and record the
HTTP status when the response carries one.

Do NOT write a fix in this task. If the probe comes back `readable`, G-4's ZoomInfo half is
resolved by observation and the correct output is a recorded verdict, not a patch. If it comes
back `provider_error` again, the verdict names the next thing to check (the token mint and cache
subgraph) and D-57-02's disclosure is the shipped answer for this milestone.

Never fabricate a balance. An `inconclusive` run reports `inconclusive`.

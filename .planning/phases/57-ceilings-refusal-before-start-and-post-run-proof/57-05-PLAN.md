<objective>
AFTER-01: one end-of-run report — per-record outcome, association outcome, held rows named
individually with reasons, spend actuals against the ceiling, and the disarm verdict. This is
what the operator reads INSTEAD of watching the run, which is the whole point of an unattended
batch, and it is the last thing standing between Phase 61's deployed-but-disarmed backend and
the first live credit-spending run that D-61-08 gates on this phase.

Everything this report needs already exists in FIVE durable stores that have never been joined —
`written_records`, `run_state`, `run_manifest`, `held_queue` and, after plan 57-03,
`remainder_queue`. Two of them had no shared key until plan 57-02 put `row_id` on a
written-records entry and on the ingest lane's response — and `row_id` matters precisely because
the rows AFTER-01 most needs to name individually are the held and gated ones, which have no
`hs_object_id` to fall back on. Five independently written stores also means five stores that can
disagree after a crash, which is why this plan carries a contradiction matrix rather than a merge
order.

Purpose: AFTER-01; AFTER-03's operator-facing half (a gated record must never read as a completed
one on the surface an operator actually opens); and G-4's disclosure half (D-57-02's honesty
requirement — the report must not imply the ceiling guarded spend it could not see).

Output: one report builder and both lanes calling it.

## Decisions taken here (Claude's Discretion, per CONTEXT.md)

**Format and surface: a markdown block in the register `write_grant.envelope()` already
returns** — a dict of figures plus a `block` key holding the rendered markdown. That register is
already established for the pre-run side of the same conversation, so the operator reads the
after in the same shape as the before, and a caller that wants a number does not have to parse
prose. Rendered by both lane runbooks at end of run.

**A new small module rather than an extension of `report_enrichment.py`.** The existing module
reports on ONE n8n execution read from the executions API; this one joins five durable on-disk
artifacts for one run. Different inputs, different lifetime, different failure modes. It reuses
`build_sync_report`'s join-and-render shape rather than a second convention, and — after plan
57-02 — the one outcome vocabulary both surfaces now share.

**Per-run scoping is load-bearing.** `written_records.load()` with no path globs and unions
EVERY run's file; this report filters to its own `run_id` (each entry is stamped with its
document's `run_id` by that loader) and never presents another run's rows as this one's.
Likewise `run_manifest.load_scoped(run_manifest.run_manifest_path(run_id), expected_run_id=run_id)`,
never the shared default path.

**`held_queue` is global and carries no run attribution** — `run_state.py`'s own docstring says
so and declines to count it for that reason. This report presents held-queue entries as a
clearly-labelled DURABLE BACKLOG section beside this run's own held rows (which come from
`run_manifest`'s run-scoped `held`/`confidence_held` verdicts and from the remainder queue's
per-run file), rather than silently attributing the backlog to this run.

## Corrections from cross-AI review

**Five stores, not four.** `written_records`, `run_state`, `run_manifest`, `held_queue` and —
after 57-03 — `remainder_queue`. Every reference to "four durable stores" in the first pass of
this plan is wrong and is corrected throughout. The count matters because each is written
independently and any two can disagree after a crash, which is why Task 2 carries a contradiction
matrix rather than a merge order.

**`load()` cannot say WHY evidence is missing.** `written_records.load()` returns `[]` for an
absent file and skips a malformed one (`written_records.py:291-323`); `run_manifest.load_scoped`
collapses several malformed states (`run_manifest.py:242-274`). The plan promised a precise gap
reason it could not produce. Task 1 adds `classify_read` to both, mirroring the two that already
have one, rather than weakening the promise.

**`row_id` is not a complete join key, and this report says so.** 57-02 lands `row_id` on
`written_records` entries and on `Build Ingest Response`, which closes the join for the enrichment
lane and for any lane carrying `row_id` into the backend. It does NOT close the pair pipeline's
final ingest leg, where `extraction.strip_row_id` removes the key before the CSV is written
(`enrich-before-ingest/SKILL.md:639`). Those rows come back `row_id: null` and are joined by
`hs_object_id` where one exists and marked UNJOINABLE otherwise, with the leg named in `gaps`.
The report must not present a partial join as a complete one.

**Keying by `row_id` alone loses events.** One row can have an enrichment event, an ingest event
and an association event under one run. Rows are modelled as event histories keyed by
`(row_id, lane)`, with each entry keeping its own `action` and `outcome`, so a later event never
overwrites an earlier one.

**One `outcome` cannot describe a multi-leg run.** `build_run_report` accepts `outcomes` — a
sequence — because the pair pipeline runs match, enrich, re-request and ingest passes under one
grant and one `run_id`. A single-outcome caller passes a one-element sequence.

**`written` may not mean what it says.** Whatever 57-02's Task 1 checkpoint selected, this report
renders that decision faithfully: if option-a was chosen, the report states once, in its evidence
line, that `written` means the backend decided to write and the response carried an id, and that
terminal write confirmation is not available in this milestone.

Two small, additive pieces of evidence plumbing that the report cannot be honest without.

**`classify_read` on `written_records` and on `run_manifest`** (REVIEW-57-M9). Mirror
`held_queue.classify_read` (`held_queue.py:260-279`) — same four words, same never-raise
contract, same "a second probe, because `load()`'s return value cannot carry this by design"
docstring reasoning. **`held_queue` is the template for the FOURTH word specifically:
`held_queue.py:106-110` defines `ANOTHER_RUN` next to the other three, while
`run_state.py:151-154` defines only three and has no `ANOTHER_RUN` at all** — so copying
`run_state`'s constant block would silently produce a three-word classifier and the
`ANOTHER_RUN` behaviour test would have nothing to name. Reuse each module's existing
`ABSENT`/`PARSEABLE`/`ANOMALOUS`/`ANOTHER_RUN` constants where it has them and define all four
alongside where it does not. Do NOT change either `load()`'s behaviour: the
degrade-whole discipline stays, and a caller still calls `load()` for entries and
`classify_read()` for the sentence to say about them.

**`record_audit` / `load_audit` in `run_report.py`** (REVIEW-57-M11). Four facts a run's report
needs are ephemeral today: the ceiling verdict from grant time, which provider balances were
readable, the disarm result, and any ceiling-stop metadata. A crashed run loses all four, so its
report is not reconstructable — on the phase whose entire purpose is proving afterwards what a run
did. Persist them at the moment each is OBSERVED, into
`run_audit-<run_id>.json` beside the other per-run artifacts, through
`durable_paths._atomic_write_0600`, with a FRESH per-module copy of the forbidden-name markers
(never an import — the same deliberate anti-DRY convention every sibling documents).

**What must not go in it, stated at the top of the file in the register `remainder_queue.py`
uses.** These are OBSERVATIONS: a verdict word, a readability state, a disarm result word, a
chunk index and a count. The GRANT is not among them and never will be. GRANT-06 forbids a grant
being persisted or rehydrated, D-57-05 is rated one-way, and this file sits close enough to
authority that the boundary has to be written down rather than assumed. A disarm VERDICT
("disarmed" / "disarm_failed") is an observation about state; an arming token is authority. The
forbidden-name scan is what enforces the difference, and the authority test is what proves the
scan runs.

**The audit record is itself a durable input, so it gets its own classifier** (REVIEW-57-M4).
`run_audit-<run_id>.json` can be absent, malformed or another run's exactly as the five stores
can, and a report that treated an unreadable audit record as "no ceiling verdict was observed"
would be making the same silent-degrade mistake `classify_read` exists to prevent. Add
`run_report.classify_audit_read(run_id, path=None)` beside `load_audit`, with the same four words,
the same never-raise contract and the same `gaps` handling as the two classifiers above. The
report therefore joins **five stores plus its own per-run audit record — six durable inputs**, and
says so wherever it counts them.

`record_audit` merges into whatever the file already held rather than replacing it, because the
ceiling verdict is observed at grant time and the disarm result at the end of the run — two
calls, one record. The merge is load-bearing, not a convenience: a second call that replaced the
first would erase the ceiling verdict at the exact moment the disarm result arrives, which is why
it gets its own acceptance criterion rather than resting on the behaviour list. It degrades on a write failure exactly as `written_records.append_chunk` and
`remainder_queue.save` do (D-59-10): falsey return, never an exception out of a live path.

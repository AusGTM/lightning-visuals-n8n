<objective>
AFTER-01: one end-of-run report — per-record outcome, association outcome, held rows named
individually with reasons, spend actuals against the ceiling, and the disarm verdict. This is
what the operator reads INSTEAD of watching the run, which is the whole point of an unattended
batch, and it is the last thing standing between Phase 61's deployed-but-disarmed backend and
the first live credit-spending run that D-61-08 gates on this phase.

Everything this report needs already exists in four durable stores that have never been joined.
Two of the four had no shared key until plan 57-02 put `row_id` on a written-records entry and on
the ingest lane's response — and `row_id` matters precisely because the rows AFTER-01 most needs
to name individually are the held and gated ones, which have no `hs_object_id` to fall back on.

Purpose: AFTER-01; AFTER-03's operator-facing half (a gated record must never read as a completed
one on the surface an operator actually opens); and G-4's disclosure half (D-57-02's honesty
requirement — the report must not imply the ceiling guarded spend it could not see).

Output: one report builder and both lanes calling it.

## Decisions taken here (Claude's Discretion, per CONTEXT.md)

**Format and surface: a markdown block in the register `write_grant.envelope()` already
returns** — a dict of figures plus a `block` key holding the rendered markdown. That register is
already established for the pre-run side of the same conversation, so the operator reads the
after in the same shape as the before, and a caller that wants a number does not have to parse
prose. Rendered by both lane runbooks at end of run.

**A new small module rather than an extension of `report_enrichment.py`.** The existing module
reports on ONE n8n execution read from the executions API; this one joins four durable on-disk
artifacts for one run. Different inputs, different lifetime, different failure modes. It reuses
`build_sync_report`'s join-and-render shape rather than a second convention, and — after plan
57-02 — the one outcome vocabulary both surfaces now share.

**Per-run scoping is load-bearing.** `written_records.load()` with no path globs and unions
EVERY run's file; this report filters to its own `run_id` (each entry is stamped with its
document's `run_id` by that loader) and never presents another run's rows as this one's.
Likewise `run_manifest.load_scoped(run_manifest.run_manifest_path(run_id), expected_run_id=run_id)`,
never the shared default path.

**`held_queue` is global and carries no run attribution** — `run_state.py`'s own docstring says
so and declines to count it for that reason. This report presents held-queue entries as a
clearly-labelled DURABLE BACKLOG section beside this run's own held rows (which come from
`run_manifest`'s run-scoped `held`/`confidence_held` verdicts and from the remainder queue's
per-run file), rather than silently attributing the backlog to this run.
</objective>

## Trust Boundaries

| Boundary | Description |
|---|---|
| durable on-disk artifacts to operator-facing report | four stores of varying trust, joined and rendered as one account of what a run did |
| report text to operator decision | what the operator does next is decided entirely by this text; a wrong word here is a wrong action |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|---|---|---|---|---|---|
| T-57-21 | Repudiation | a gated row reported as completed, so an operator believes a write landed that did not | critical | mitigate | Distinct rendered text for `gated` versus `written`, pinned by a test asserting the two strings differ, and the gated text names the recovery |

## Decisions taken here (Claude's Discretion, per CONTEXT.md)

**Where the ceiling check lives: the CLIENT, at both ends, and nowhere else.** No backend
change, no workflow JSON regeneration, no deploy. Evidence: RESEARCH's Architectural
Responsibility Map — the backend has no concept of "this batch's ceiling" and no cross-chunk
state, while `chunking.dispatch_plan` is the only place in the system that sees every chunk of
one run in sequence.

**How a breach is detected: a running tally inside `dispatch_plan`'s existing loop, checked
BEFORE each chunk is sent.** REVISED after cross-AI review (REVIEW-57-H2): the first pass placed
the tally after `append_chunk`, which sits after `dispatch_enrichment` — so the chunk that
breached the ceiling had already been sent by the time the stop fired. The plan's own `<done>`
disclosed that overshoot, and disclosure of a design that contradicts "a run cannot spend what
it does not have" is not resolution. The tally now runs at the TOP of the loop body: it computes
what this chunk WOULD cost, adds it to what has already been spent, and breaks before
`enrichment.build_envelope` when the total would exceed the ceiling. Overshoot from this
mechanism is zero chunks.

Rejected: post-chunk reconciliation between separate `dispatch_plan` calls, which would require
restructuring both lane SKILL.md runbooks for a benefit the tally already gets. Also considered
and rejected: a re-sample of `executions_in_window` per chunk — at `max_records_per_chunk` of 2
that is ~170 extra cross-workflow GETs on a 340-record batch, against a sample that is laggy and
instance-wide.

**What the guarantee actually is, stated honestly.** This is a conservative POINT-IN-TIME local
control, not a reservation. `executions_in_window` observes instance-wide executions
(`n8n_read.py:258-266`); a scheduler, another session, or another grant can consume the sampled
headroom concurrently while this run is mid-flight. Zero local overshoot does not mean zero
instance-wide overrun. A shared reservation would need a mechanism n8n Cloud does not offer
(P-12: no usage endpoint), so this bound is the honest one and the runbook and report say so
rather than implying a hard cap.

**When the mid-run breach is actually reachable — state this plainly, it is not a defect.**
Within a single `dispatch_plan` call under an un-overridden grant the tally cannot diverge
from the pre-flight projection, because both are computed from the same fixed plan. The breach
is reachable when the budget is consumed across MORE than that one projection: (a) the operator
overrode the pre-flight refusal, (b) several `dispatch_plan` calls run under one grant — the
pair pipeline's match, enrich and ingest passes, and `preingest.rerequest_unanswered`'s
re-request, (c) the allowance was `unknown` at grant open and became sampleable later, (d) a
remainder run resumes against an allowance a previous run has since eaten into. The ceiling
handed to each call is therefore the grant's remaining allowance MINUS what this grant has
already spent, not this call's own projection.

**The projection over-states, deliberately, and that is disclosed.** `EXECUTIONS_BASIS`
(`chunk_count + record_count`) was measured by P-10 to over-state a real 2-record chunk by
roughly 3x (projected 3, the executions list showed 1), and nothing found suggests it ever
under-projects. Used as a refusal trigger, over-stating can only refuse too early — never let
an over-budget batch through. That direction is chosen on purpose and is named in the
operator-facing arithmetic, not left implicit.

**Evidence tags carried, never upgraded** (CLAUDE.md §13.0.3): the Starter plan's 2,500
executions/month is `[documented]`; the over-statement factor is `[measured]` from execution
`11950`; the executions API list is NOT the billing quota, so every figure here is what the
API *listed*.

## The finding that nearly sank this plan: the refusal may be unreachable on this account

REVIEW-57-H1, confirmed in source this session. `n8n_read.executions_in_window` sets
`covers_full_window = saw_older_than_cutoff` (`n8n_read.py:378`), and `saw_older_than_cutoff`
only becomes True when a walked page contains an execution STRICTLY OLDER than the window. That
is "we paged back far enough", **not** "the sample is complete". Two consequences, at opposite
ends of the traffic range, both of which fall to `CEILING_UNKNOWN` and therefore never refuse:

- **Quiet instance.** The walk ends because there is no next cursor (`n8n_read.py:358-360`) — the
  listing is exhausted, every execution the API will return has been read — yet
  `saw_older_than_cutoff` is False and `truncated_by_page_cap` is also False (the `for/else`
  clause only runs when the loop was NOT broken). The sample is in fact complete and is reported
  as unsampled. **This account sits at this end.**
- **Busy instance.** `MAX_EXECUTION_PAGES` (4) x `EXECUTIONS_WINDOW_PAGE_LIMIT` (250) caps the
  walk at 1,000 executions across ALL workflows (`n8n_read.py:69,73`). A month with more than
  1,000 instance-wide executions truncates before reaching the month boundary.

**Two fixes, both cheap, both in Task 2.** (a) Treat an EXHAUSTED listing as a complete sample —
a new `listing_exhausted` key on `executions_in_window`'s return, True when the walk ended on a
missing cursor with no failed page. (b) Size the page budget to the allowance: a new
keyword-only `max_pages` on `executions_in_window`, which `allowance_headroom` sets to
`ceil(allowance / EXECUTIONS_WINDOW_PAGE_LIMIT) + 2` so a month that fits inside the configured
allowance cannot truncate. At the documented Starter 2,500/month that is 12 pages, up to 12 GETs
per grant instead of 4.

**The residual, which no code fix removes.** An exhausted listing is complete only with respect
to what the API RETAINS. n8n prunes execution history; a pruned execution was still billed. So
`spent_sampled` is a LOWER bound on month-to-date spend and `remaining_sampled` is an UPPER bound
on headroom — the permissive direction, the one that can let an over-budget batch through. That
must be stated in the operator-facing arithmetic and in the end-of-run report, tagged
`[documented]` (n8n's retention behaviour) rather than `[observed live]`. It is also the reason
Task 1 is a checkpoint: if the refusal still cannot fire on this account after both fixes, what
RUN-05 means is an operator ruling, not a planner's judgement call.

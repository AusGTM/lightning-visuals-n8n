<objective>
Put a budget floor on the runtime cadence path — the one path that changes how often the
backend spends money without ever passing a build.

Purpose: the 2026-08-10 USAGE.md fact-check found that the plugin's `cadence` control
action reaches a live PUT with neither of Phase 44's tripwires executing. `parse_cadence`
accepts "every 30 seconds" as a legal, confirmable request; the only guard is a
plain-language read-back and the operator's yes — a comprehension check, not a budget
check. The 2026-08-09 runaway was this exact budget domain. 45-01's alarm detects
everywhere; this plan prevents at the front door (FLOOR-01, D-09/D-10).

Output: a whole-schedule monthly-cost computation and refusal in `n8n_cadence`, a
single-shot conversational override, the control surface wired to state the arithmetic
before offering it, and the two docs that currently say no such guard exists.
</objective>

`n8n_read.HOURS_PER_MONTH` rather than written as a fresh literal: seconds is hours times

weeks is `DAYS_PER_MONTH` divided by 7, months is 1.0. Comment that this is the same
30-day month `scripts/build_cloud_workflows.py`'s `_schedule_trigger` and
`tests/test_execution_budget.py` already document, reached here through 45-01's shared
constants so the three cannot drift. Note in the same comment the one deliberate
refinement over the build-time table: a `weeks` entry carrying `triggerOnWeekdays` fires
once per listed weekday, so the runtime floor multiplies the weekly base by the number of
listed weekdays — the build-time guard has no need of this because no committed trigger
uses weekdays, and undercounting a weekday schedule by five times at runtime would be the
kind of silent gap this floor exists to close. `cronExpression` has no entry and must

**`interval_month_cost(interval)`.** Sum over every entry in an interval array:
`TICKS_PER_MONTH[field]` divided by the entry's companion interval value (from
`SUPPORTED_FIELDS`), defaulting the value to 1 and treating anything below 1 as 1;
multiplied by the number of `triggerOnWeekdays` entries when the field is `weeks` and that
key is present and non-empty. An entry whose field is not in `TICKS_PER_MONTH` — including
`cronExpression` and anything unrecognised — makes the whole cost UNKNOWN: return None
rather than silently skipping it, so a caller cannot mistake an uncomputable schedule for a
cheap one.

**`schedule_month_cost(workflow_items, workflow_id, node_name, interval)`.** Sum
`interval_month_cost` across EVERY schedule trigger node in EVERY workflow in
`workflow_items` (the `items` list `n8n_read.list_workflows` returns; this tenant's

**`check_budget_floor(workflow_id, node_name, interval, config, workflow_items,
override=False)`.** Read `n8n_monthly_execution_allowance` and
`n8n_schedule_floor_max_share` from `config` with float attempts. Then, in this order:

1. Either key missing, blank, unparseable or not strictly positive: raise `CadenceRefused`
   naming the missing key and saying plainly that without it the cost of this change
   cannot be judged, so the change is refused rather than guessed at. Never name the
   value of a key that IS set. This refusal is NOT overridable.
2. `workflow_items` is None, or the computed total is None: raise `CadenceRefused` saying
   the other scheduled jobs could not be read (or one of them uses a schedule this plugin
   cannot cost), so the total cost of the change is unknown — and an unknown cost is
   refused, not permitted. NOT overridable: D-10's override presupposes arithmetic on the
   table, and overriding an unknown number restates nothing.
3. Total at or below `allowance * share`: return the arithmetic dict and do not raise.
4. Total above the ceiling and `override` false: raise the over-budget `CadenceRefused`.
5. Total above the ceiling and `override` true: return the arithmetic dict with an
   `overridden` flag true. Task 2 owns what the caller says at that point.

Return shape on every non-raising path: a dict carrying `requested_month_cost`,
`schedule_month_cost`, `allowance`, `share`, `ceiling`, `within` and `overridden`.

The over-budget refusal's wording is the D-09 register — numbers FIRST, then the way
forward, in the same plain voice as this module's existing refusals. It must state, in
this order: what the requested job would cost per month, what the whole schedule would
then cost per month, the ceiling, and the allowance the ceiling is a share of. Then the
way forward. It must contain no schedule-expression syntax anywhere, and no `_EXAMPLES`
entry that is itself over the ceiling — pass explicit examples to `CadenceRefused` that
are actually affordable (the module's default first three examples include "every 15
minutes" and "hourly", which would be a refusal that recommends the thing it just
refused).

Do not add a new exception subclass. `CadenceRefused` already carries reason plus a way

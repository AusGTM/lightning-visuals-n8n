<objective>
Persist the Lusha record identifier on matched HubSpot records and send it back on the next run, so
already-revealed data re-enriches without new spend.

Two design constraints shape this plan. First, REQ-lusha-v3-normalize requires the candidate stream
stay field-identical, so the identifier must NOT be emitted as a scored candidate — a new candidate
field would enter `scoreCandidates`, hit the merge policy with no policy entry (defaulting to
fill-blank-only at a confidence threshold the provider base accuracy cannot clear) and pollute the
needs-review queue. The identifier therefore travels as a plain row field alongside the existing
provenance carry-through, and is spread into the property patch at the same place `cacheKeys`
already is. Second, the read-back path only works if the HubSpot search asks for the property, so
four property lists across the two lanes and both build targets need the new names.

Whether the zero-cost claim actually holds was settled by Plan 01's probe (assumption A7). If that
verdict came back REFUTED, this plan's success criteria need renegotiating before it runs — the
Plan 01 checkpoint is where that was caught.

Purpose: make re-enrichment cheap and make provider matches stable across runs.
Output: two additive HubSpot properties, an id extractor, a write-through path, a request-side
reuse branch, and tests for each.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Lusha response -> HubSpot property patch | A provider-supplied identifier crosses into a written CRM field. |
| HubSpot record -> Lusha request | A stored CRM value crosses back out to a paid third-party API as a lookup key. |
| repo config -> live HubSpot schema | A config edit becomes a live portal schema mutation once the two-key gate is armed. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-03 | Information Disclosure | the property patch assembled in the decide nodes | medium | mitigate | Only the opaque record identifier is written, into a property declared for exactly that purpose. No revealed email, phone or other provider PII rides along, because the id travels as its own narrow row field rather than as a slice of the raw response. An absent id contributes no key at all, so the patch never grows an empty write. |
| T-20-09 | Tampering (a stale or wrong stored id silently redirecting enrichment to the wrong person) | the stored-id request branch | medium | mitigate | The stored id supplements the existing identity keys rather than replacing the builder's identity logic, so a wrong id degrades to a no-match rather than to a confident mismatch; blank and null ids are treated as absent, asserted by test; and the id is only ever written from a matched response, never fabricated. |
| T-20-02 | Elevation of resource consumption | the stored-id branch | medium | mitigate | Reuse of a stored id is the cost-reduction mechanism, not a new spend path, and the reveal derivation is deliberately left unchanged by this plan so the branch cannot widen what is paid for. The actual credit outcome was measured in Plan 01 rather than assumed. |
| T-20-10 | Tampering (an unintended live schema mutation) | `scripts/sync_hubspot_properties.py` armed run | high | mitigate | Two-key gate (both `DRY_RUN=false` and the property-write allow flag in one invocation), dry-run-by-default, a diff reviewed before arming that must show exactly two creates and nothing else, an undo manifest recording only confirmed creates, and an operator checkpoint rather than executor-armed writes. |
| T-20-01 | Information Disclosure | the armed sync command | high | mitigate | Credentials are loaded in-process by `load_dotenv()`; no command in this plan reads or prints `.env`, and the sync script prints diffs and counts, never token values. |
| T-20-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task in this plan. `python-dotenv` and `requests` are already present and already used by the Phase 19 runbook and the existing sync script; the JS changes remain dependency-free because n8n Code nodes cannot resolve modules. No new supply-chain surface, so no legitimacy audit applies. |
</threat_model>

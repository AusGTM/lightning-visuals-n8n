`walkWorkflow(wf, {triggerItems, httpStubs, respondMode})` drives the graph from `wf.connections`:

- Maintain `runData` in exactly the `{nodeName: [itemsOfRun0, itemsOfRun1, ...]}` shape

- Honour `wf.settings.executionOrder`: when the key is absent or `"v0"` walk breadth-first by
  depth; when `"v1"` walk each branch to completion in canvas top-to-bottom order. Record which
  ordering was used on the returned `trace`.
- Node type handlers, keyed on `node.type`:
  `n8n-nodes-base.code` — evaluate `parameters.jsCode` with `new Function`, supplying `$`,
  `$input`, `$json`, `$runIndex`, `$node`, `$now`, `$today`, `$getWorkflowStaticData`, `$env`.

  `makeDollar` implements, and must expose `.all(branch, run)`, `.first()`, `.last()` and

  forbid it.
  `n8n-nodes-base.if` — evaluate `parameters.conditions` per item and route true items to
  output 0, false items to output 1.
  `n8n-nodes-base.merge` — buffer per input index; fire once when every configured input has
  delivered at least one run. If a configured input never delivers, the Merge NEVER fires and
  the walker records `{node, reason: "merge_input_never_fired", missingInputs: [...]}` on
  `trace.stalled`. This models research Pitfall 1 and is the behaviour the walker's unit tests
  assert against.
  `n8n-nodes-base.httpRequest` and `n8n-nodes-base.hubspot` — look the node name up in
  `httpStubs`; a stub is either an array of response items or a function

  expressions where present.
  `n8n-nodes-base.respondToWebhook` — record the FIRST firing only on `trace.respond`

  the double-`Respond` class D-70-18 requires the walker to expose.
  `n8n-nodes-base.webhook`, `n8n-nodes-base.scheduleTrigger`, `n8n-nodes-base.executeWorkflowTrigger`

  Any other type — pass through unchanged and append the type to `trace.unhandledTypes` so an
  unmodelled node is visible rather than silent.
- Honour the per-node `alwaysOutputData` setting: when a node's own run produced zero items and
  `node.alwaysOutputData === true`, emit exactly one empty item `{json: {}}`. This is what makes

  documented mitigation).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| test harness -> committed workflow JSON | The walker executes committed `jsCode` via `new Function` in the test process; the JSON is repo-controlled, not attacker-controlled, but a walker that silently mis-models a node type would produce false assurance for every later plan. |
| builder -> generated JSON | The detector is the structural input-validation gate for the by-name-read contract; a detector with a blind spot is a bypass. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-70-07 | Tampering | `tests/n8n/lib/walkWorkflow.mjs` — false assurance from an incomplete node model | high | mitigate | `trace.unhandledTypes` records any node type the walker passed through unmodelled, and an unstubbed HTTP node throws by name rather than returning empty; Task 1 acceptance asserts `unhandledTypes` is empty for the ingest workflow |

| T-70-09 | Denial of Service | `new Function` evaluating committed jsCode in the test process | low | accept | The jsCode is repo-controlled and already executed this way by ~50 existing tests; no new trust boundary is crossed |

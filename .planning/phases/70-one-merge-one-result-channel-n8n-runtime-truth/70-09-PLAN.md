Correct `walkWorkflow.mjs` so the engine's rules hold, and cite each in a comment naming the
execution that observed it.

The delivery change: propagation must enqueue a delivery even when the emitting node produced
nothing, because the live engine treats that as a delivery. The existing always-output-data
substitution stays exactly as it is — it models a node that RAN and produced nothing, which is a
different rule and still correct. At the consuming end, split the two cases: a Merge target
records the delivery and its readiness; any other target with an empty delivery is skipped
entirely, recording no run, which is how the engine leaves a zero-item lane unexecuted.

The readiness change: track per input index whether a delivery has ARRIVED, separately from the
items buffered, because after this change an arrived input can legitimately hold zero items.
Readiness is every declared input having arrived. A second delivery to an already-arrived input is
dropped, and the already-fired guard stays.

One consequence to mark honestly: after the delivery change the walker also models an IF's EMPTY
branch as a delivery to a Merge input, and this repo has never observed whether the engine does.
Comment that model as inferred rather than observed, and note that the routing pass-throughs plan
70-10 adds make every generated graph independent of the answer either way.

The stalled-report change: the post-walk report must list inputs that never received a delivery.
Leaving it keyed on an empty buffer would make it report the wrong inputs and hide exactly the
starvation this phase is chasing.

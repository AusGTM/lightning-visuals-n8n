<objective>
Deploy the committed workflow JSON to n8n Cloud disarmed, bounce it, and prove by a disarmed
execution what the running instance now holds (D-63-08) — without arming anything (D-63-09).

Purpose: the committed JSON has been ahead of the live instance since 2026-09-02, when Phase 62
regenerated six workflows and deliberately did not deploy them. The running instance therefore
lacks `num_associated_contacts` and the `sourceByField` provenance wiring. If 63-04 shipped the
judge routing, that is undeployed too, and an undeployed throughput fix is worth nothing. Deploying
63's change alone was rejected: it would require a deliberately reverted build and would put JSON on
the instance that matches no commit.

Output: `63-DEPLOY-RECORD.md` — the dated evidence of what was PUT, what the bounce restored, and
what a disarmed execution observed.

**This plan runs on both of 63-04's branches.** On SHIP it carries two phases' worth of change and
the record says so. On DROP it carries Phase 62's alone, and the record says that instead. The
reason to deploy does not depend on the lever.
</objective>

Deploy the workflows the committed tree holds, disarmed, and bounce them so the running instance
actually reloads.

**Step 1 — dry run.** Run `.venv/bin/python scripts/deploy_n8n_workflows.py` with no environment
overrides. It is dry-run by default and makes zero writes. Read its create/update lists and confirm
they name the enrichment workflow and the other workflows Phase 62 regenerated. Request no overlay
flags: `_requested_overlay_flags()` must come back empty, so nothing is armed at deploy time and the
JSON that lands is byte-for-byte the JSON the test suites ran against.

**Step 2 — the PUT.** Run the same script with `DRY_RUN=false ALLOW_N8N_DEPLOY=true`. Deploy the
whole regenerated set rather than a single `--only` file: the divergence spans several workflows and
splitting it would leave a partial instance. Record each workflow id the script reports.

**Step 3 — the bounce.** A bare PUT does not reload a running workflow, so after the PUT each
affected active workflow must be deactivated and reactivated. Follow
`prove_scale_up_runtime._bounce_and_verify`'s shape rather than inventing one: POST deactivate,
POST activate, then GET the workflow back and assert its node count. For the enrichment workflow the
expected count is 123 — this phase edits jsCode strings and adds no node, so any other number means
the build carries something unplanned and the deploy stops there for investigation.

**Step 4 — the read-back.** GET each deployed workflow from the API and assert on the STORED
content, understanding that this proves what was uploaded and not what is running (Task 2 supplies
that): the `Build Judge Request` node's `jsCode` names the cheap model constant if and only if
63-04 took the SHIP branch, and the company-search node body names `num_associated_contacts`
(Phase 62's change, which lands either way). If the SHIP/DROP expectation and the read-back
disagree, halt — the deployed content does not match the branch the phase took.

node actually carries and record the number in the deploy record. This is lever 3's open question

observed value costs nothing while the JSON is already open, and gives a later phase a starting
fact instead of a guess. Do not change it.

Arm nothing at any step. No allowlist entry, no test-record id, no baked-flag overlay.

<objective>
Prove 63-A under a real scheduler: install the shim, let a genuine scheduled fire resolve it,
introduce a newer version directory, and observe the next fire follow the update — with no schedule
edit in between.

Purpose: memory `sweep-trigger-llm-free` records that this project's earlier trigger design passed
its own host probe interactively and still failed under a real schedule, because the interactive
run inherited an environment the scheduler never has. An in-session `sh` invocation of the shim
therefore proves nothing about the case that matters. The todo this closes says so in its own
words: "it needs a real-scheduler proof, not an interactive approximation".

Output: `scripts/verify_sweep_shim_scheduler.sh` (a self-contained, re-runnable harness) and
`63-SWEEP-SHIM-SCHEDULER-PROOF.md` (the dated record with the observed log lines).

**Why launchd and not cron — resolved here rather than left to the executor.** CONTEXT.md's
Specific Idea names a cron tick, but that is a Specific Idea, not a locked decision, and D-63-03
is a locked decision that forbids rewriting any crontab. The only way to add a temporary cron line
is `crontab -` , which REPLACES the whole user crontab; a restore that goes wrong destroys the
operator's real sweep entry, which is precisely the failure mode this phase exists to remove. A
temporary launchd agent with a unique label is additive, removable by label, touches no other job,
and is the template's own Option B — the same class of non-interactive scheduler environment
(no session credentials, minimal PATH, no controlling terminal) that the memory is about. The
proof standard is satisfied; the prohibited mutation is avoided.
</objective>

to a specific root. Install the shim into a `durable/` directory inside the work directory by
invoking the real CLI with both `--cache-root` and `--durable-dir` pointed at the temporary world.

Register a launchd agent whose label embeds both a fixed prefix (`com.lightningvisuals.sweep-shim-proof`)
and the harness PID, so no two runs and no pre-existing job can collide. Its `ProgramArguments` are
exactly the five entries the template documents — `/bin/sh`, the installed shim path, the temporary
cache root's `1.1.0` directory as the legacy `$1`, the python interpreter, and the temporary log
path — with `StartInterval` set to 60 and `RunAtLoad` false, so the first fire is a genuine
scheduled one rather than a load-time side effect. Write the plist under a temporary directory, not
under `~/Library/LaunchAgents`, and load it by absolute path.

Observation phase 1: poll the temporary log for up to 150 seconds for a stamped line proving the
wrapper ran, and assert the marker it carries names `1.1.0`. Then create `1.2.0` in the temporary
cache root (same three copied files plus its own marked stub) — the simulated plugin update, made
with no edit to the plist and no edit to the shim. Observation phase 2: poll for a further 150
seconds for a NEW stamped line whose marker names `1.2.0`.

Read the evidence by line CONTENT (the version marker), never by counting lines or assuming the
last line belongs to the latest fire, because two fires may overlap and both append.

Teardown must run on every exit path (trap on `EXIT`): `launchctl bootout`/`unload` the agent by
its label, then INDEPENDENTLY confirm with a `launchctl list` read that no job carrying the label
prefix remains, and remove the temporary directory. If the independent read still shows the label,
exit non-zero with a message naming the label that must be removed by hand — a failed teardown is
reported, never swallowed.

Exit codes: 0 only when BOTH observations succeeded and teardown verified clean. Non-zero, with a
message distinguishing the cases, when: launchd is unavailable, the first fire never appeared, the
second fire never appeared, the second fire still resolved `1.1.0`, or teardown could not be
confirmed. A run that timed out waiting is inconclusive and exits non-zero — it is never reported
as a pass.

The harness must contain no `crontab` invocation of any form, and must never write outside its own
`mktemp -d` work directory except for the launchd registration it removes.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| harness → host scheduler | the harness registers a real job on the operator's machine that will execute code without a human present |
| harness → operator's existing schedule | the harness runs on a machine that already carries the operator's real sweep registration |
| temporary world → real plugin cache root | the harness copies real plugin source into a temporary tree |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-63-06 | Denial of Service | the operator's existing sweep schedule | high | mitigate | The harness never invokes `crontab` in any form and never writes to `~/Library/LaunchAgents`; it registers a uniquely labelled agent from a temporary plist path and removes it by label. A whole-crontab replace — the only way to add a temporary cron line — is prohibited outright, so the operator's real entry is untouchable by this harness. |
| T-63-07 | Elevation of Privilege | orphaned launchd registration | high | mitigate | Teardown runs from a `trap` on `EXIT` so it fires on failure and interrupt alike, and its success is confirmed by an INDEPENDENT `launchctl list` read rather than by the unload command's own status; an unconfirmed teardown exits non-zero naming the label. |
| T-63-08 | Tampering | temporary world under `mktemp -d` | medium | mitigate | The world is created fresh per run under a `mktemp -d` path and removed at teardown; the harness references no path under the real plugin cache root, so a proof run cannot mutate a real install directory (D-63-03). |
| T-63-09 | Spoofing | evidence read from the log | medium | mitigate | Each version directory's stub carries a distinct marker and the harness asserts on marker CONTENT, so a leftover line from a prior fire cannot be mistaken for the post-update fire. A missing marker is inconclusive and exits non-zero. |
| T-63-10 | Information Disclosure | proof record committed to `.planning/` | low | accept | The record holds temporary paths, version directory names and stub output only. The stubbed sweep entrypoint prints `[]`, so no backend response, credential or operator datum is ever produced during the run. |
| T-63-B-SC | Tampering | npm/pip/cargo installs | low | accept | This plan adds no package-manager install task and no new dependency; the harness is `/bin/sh` plus `launchctl` and the plugin's own scripts. No package legitimacy audit is required because no package is installed. |

Open the one declared W1 window and re-score the entire live scored population under the procedure
built in plan 49-01 and documented in plan 49-02 — canary first, remainder second, one window — and
close the parity red window Phase 46 deliberately opened.

Purpose: Phase 46 changed three rubric weights in commit `caae5d6`, so the ROADMAP's "if the weight
changed" branch is live and the full-population re-score is owed, not merely proven. The acceptance
anchor is `scripts/run_scoring_parity.py`'s live population sweep exiting green — it has been red by
design since that commit because it compares each record's old-weight live score against the
new-weight oracle. Do not fix the sweep; make it true.

Output: committed P2 and P3 census snapshots, a W1 arm record with full window accounting, and a
committed parity verdict.

Declared cost: ZERO n8n executions, ZERO Anthropic calls, ZERO provider credits, and one HubSpot
batch call plus settle reads. `ALLOW_SCORE_BACKFILL` gates a direct CRM v3 batch call; it arms a
surface n8n knows nothing about, so no n8n allowlist is armed and none should be.

  <context>
Read the pre-flight record from Task 49-05-01 before deciding: the live population count, its
derivation date, whether it matched the earlier capture, and the P2 tier distribution.

What will happen, in one window: the driver arms with `DRY_RUN=false` and
`ALLOW_SCORE_BACKFILL=true` set together per-shell; it re-derives the population at arm time and
refuses unless the sample matches exactly; it writes ONE canary record chosen by rule, settles, and
reads back its derived score and tier; then, in the same window, it writes the remaining records;
then it settles and disarms.

What is written: only the five component score properties, on every record. Nothing else. The
derived score, the tier, the veto flag and the veto reason are never in a payload — they are
produced by a HubSpot calculated property, by workflow WF1, and by the n8n decide node respectively.

What it costs: ZERO n8n executions, ZERO Anthropic calls, ZERO provider credits. One HubSpot batch
call for the canary, one for the remainder, plus settle reads. No n8n allowlist is armed — W1's
authority is a Python-side env gate on a direct CRM call, and arming the n8n record-write surface
here would widen the blast radius for nothing.

Why the canary exists: HubSpot's default-value stamp is not readable through the API, so whether
overwriting an already-stamped component behaves like writing a never-set one cannot be settled by
inspection. The canary means a stamp-related failure surfaces on one record instead of the whole
population, and it costs no extra arm cycle because it happens inside this same window.

Reversibility: reversible. Components are recomputable from any rubric config; re-running with the
prior `config/icp_scoring.yaml` restores the prior values exactly.

Waiver `D-49-01` (49-CONTEXT.md D-06) delegates the arming to Claude for this phase only. It expires
when the phase seals and does not revive any earlier waiver. It changes who types the command, never
how many times it may be typed: D-05 declares exactly one W1, and any excess is a disclosure
obligation in the run report.

<objective>
Tell the operator, in plain language, what this milestone did to the target list — with the levers
separated so no movement is misattributed, and with the milestone's known limits stated rather than
smoothed over.

Purpose: RESCORE-03 asks for a before-and-after tier distribution so a rubric change's effect is
visible rather than inferred. A two-point entry-to-after series would satisfy the letter and lump the
veto clear, the veto recompute, the coverage enrichment and the weight re-score into one
undifferentiated delta — the exact misattribution a prior phase spent a whole plan building a
three-column report to avoid.

Output: a report builder that renders from committed snapshots, the committed markdown report, a
published private Artifact, and the phase run report carrying window accounting and cost actuals.

Declared cost: zero n8n executions, zero Anthropic calls, zero provider credits, zero HubSpot writes.
Every input is already committed; the report performs no live read of its own.
</objective>

  <action>
Create `scripts/build_rescore_report.py`, consuming only committed JSON — no HubSpot import, no
network call, no credentials.

`load_point(path, label)` reads a snapshot document and normalises it to a dict of `label`,
`derived_at`, `population_count`, `tier_distribution` and `records` keyed by record id. The P1 source
is the Phase 46 simulation capture's live column, whose shape differs from the driver's snapshot
documents; write an adapter for it rather than reshaping the committed file, and record in the
docstring why that capture is P1's source — it is the only dated full-population snapshot predating
every write this milestone made.

`build_report(p1, p2, p3)`:
  - Validate each point before anything else: the distribution values must sum to the stated
    population count, and the count must be greater than zero. Raise a clear error naming the
    offending point otherwise. This mirrors the parity sweep's own false-green guard — an empty or
    inconsistent input must fail loudly, never render clean.
  - Build two movement tables: entry to pre-re-score, and pre-re-score to post-re-score. Include a
    record only when its tier differs between the two points being compared. Sort by record id.
  - Build a separate score-only section listing records whose score changed while their tier held.
    That case is real and expected — some genuinely-vetoed records' scores move under the new weights
    while their tiers do not — and reporting it as a tier movement would be wrong.
  - Compute every delta with integer arithmetic. Scores arrive from HubSpot as strings; coerce through
    `int` and raise on a value that will not coerce, rather than falling back to a float or to zero.
  - Emit tier keys in a fixed canonical order followed by any residual key sorted, so two renders of
    the same data cannot differ in column order.

`render_markdown(report)` produces the tables in the shape `simulate_rubric_weights.py::render_markdown`
already established — a three-column distribution table plus annotated named-record rows — extended
from three in-memory configs to three live time points. Do not call `build_simulation()`; it scores
in-memory configs, which is a different measurement.

Create `tests/test_build_rescore_report.py` driven entirely by small inline fixtures. Cover every
behavior above, including the byte-identical double render, the raise on a non-summing distribution,
the raise on a zero-count point, the integer type of every delta, and the separation of tier movements
from score-only changes.
  </action>

permanent guard that a future weight change cannot land unaccompanied by the re-score obligation.

First capture the numbers, then write the doc around them.

**Capture.** Run the driver's read-only plan mode through the absolute-path dotenv wrapper — `.env`
is Read/Bash permission-blocked, and python-dotenv's bare `load_dotenv()` resolves relative to the
calling file, so the wrapper must pass an absolute path. Run it for both branches and write the
output to `.planning/phases/49-re-score-strategy-reporting/49-PLAN-OUTPUT.json`. This read costs
zero n8n executions, zero Anthropic calls and zero provider credits, and performs no write.

**Write `docs/OPERATOR-RESCORE.md`.** Structure, in this order:

1. **Step 1 is a classifier, not a procedure** (D-08). Lead with the question: did the rubric change
   touch a hard-veto predicate — non-ANZ, no-content, or hardware-vendor? Answer NO routes to the
   weight branch: component backfill only, zero n8n executions, zero Anthropic calls, zero provider
   credits. Answer YES routes to the veto branch: the same backfill plus one recompute POST per
   record, roughly one n8n execution per record against the 2,500/month allowance, still zero
   Anthropic and zero provider credits. State that the veto-branch figure is measured, not
   estimated — Phase 47.5 clocked the recompute lane at one execution per POST across executions
   11858 through 11861 — and state plainly that the veto branch is documented this phase and not
   exercised.

2. **Why the whole population, every time.** No `lv_icp_scoring_version` property exists and none
   will (the standing no-new-properties constraint), so records scored under a superseded rubric
   cannot be segmented in a HubSpot list. Any rubric change therefore re-scores the entire scored
   population wholesale. That is RESCORE-02's reason, and it belongs in the runbook in plain
   language, not as a cross-reference.

3. **Which records.** The scored population is defined by a single live search for companies that
   carry `lv_icp_fit_score` at all — the same definition `scripts/run_scoring_parity.py` and
   `scripts/simulate_rubric_weights.py` deliberately share, so there is no second definition. State
   that it is re-derived live on every run and never carried as a list, and give the count and date
   stamp from the captured plan output. Say once, plainly, that only a small fraction of the 712
   companies in the portal have ever carried a score, so every count in a re-score report describes
   that fraction and not the portal.

4. **Chunk size and window shape.** Quote the captured `chunk_size`, `chunks`, `max_records`,
   `window`, `arm_keys` and `arms_n8n_allowlist` values. Explain what `arms_n8n_allowlist: false`
   means operationally: the weight branch's write authority is a Python-side env gate on a direct
   CRM batch call, so no n8n allowlist is armed and no execution is spent; arming the n8n record
   -write surface for a weight re-score would widen the blast radius for nothing (D-05).

5. **The exact-set gate, and why it is stronger than what it supplements.** A count cap permits any
   sample under the cap; the exact-set gate permits only the live-derived scored population and
   refuses everything else, including a smaller subset. Say this explicitly so a reader who sees the
   raised ceiling does not read it as a relaxation.

6. **Engines first, then re-score** (Claude's discretion item, made explicit). Because the backfill
   computes components from the Python oracle, a HubSpot flow still carrying the old weights will
   silently overwrite correct backfilled components with old-weight ones the next time any input
   changes on that record. So a weight change lands in both engines — `config/icp_scoring.yaml` and
   the HubSpot org-type score flow — in one commit, with a running-content read-back, **before** the
   re-score runs. No work is owed on this today; Phase 46 already landed both. It is a sequencing
   rule the next weight-changer must follow.

7. **The canary step.** One record first, inside the same window, chosen by rule at run time; settle;
   read back the derived score and tier; only then release the remainder. State the reason: HubSpot's
   default-value stamp is not readable through the API, so whether overwriting an already-stamped
   component behaves like writing a never-set one is a live-only question, and the canary means a
   stamp-related failure surfaces on one record rather than the whole population.

8. **Invocation.** Give the literal absolute-path dotenv wrapper commands for plan, snapshot, canary
   and execute, and note that the driver defaults to dry and that the arm vars are set per-shell
   only — never in `.env`, never in a profile, never exported into a shell that outlives the window.

9. **Acceptance.** The live population parity sweep exiting green is the proof a re-score landed.
   State that the sweep is never edited to make it pass.

10. A dated AMENDMENT-block convention section at the foot, matching the veto-refresh runbook's
    house style, so a future correction is appended rather than rewritten.

Voice: plain language for a non-technical operator working in Claude Desktop, matching
`docs/OPERATOR-VETO-REFRESH.md`. Warnings come from measured live executions, never from theory.

### 8. The MEDIUM-confidence Track-B dependency — RECORDED, honesty caveat noted (see Human Verification)

Confirmed the checkpoint is recorded as a first-class section in `16.4-02-SUMMARY.md` and mirrored into `.planning/STATE.md` Blockers/Concerns (2026-07-28 entry), with:

- Explicit pass/fail conditions.
- A bounded fallback (swap the two fetch nodes' type/parameters to raw HTTP GET on `/crm/v3/objects/{type}/{id}` — `adaptFetchById.js` already handles that response shape).

**Honest assessment of diagnosability, since the SUMMARY's claim deserves scrutiny rather than a rubber stamp:** the SUMMARY states "a systemic filterability failure presents as every bare event skipping ... never as silent wrong data" and that `fetch_diagnostic` "distinguishes an errored response ... from a genuine zero-result response." Reading `adaptFetchByIdResult()` directly confirms this distinction exists in the code — but its usefulness for diagnosing a *systemic* failure depends entirely on which shape HubSpot actually returns for an unfilterable property:
- If HubSpot returns **HTTP 400** naming the property as invalid/unfilterable, this is caught by the `item.error`/`item.json.error` branch and the diagnostic clearly reads `"error: <HubSpot's 400 body>"` — genuinely distinguishable from a real deleted/stale record, per-event, in n8n's execution view.
- If HubSpot instead returns **HTTP 200 with `results: []`** for a filter it silently doesn't support (a real possibility for some REST APIs, though HubSpot's search endpoint does generally schema-validate filter properties and tends to 400 on unsupported ones), the diagnostic reads identically to a genuinely deleted/stale record (`"zero-results: hs_object_id not found..."`). In that failure mode, a systemic filterability bug is **NOT** distinguishable from a legitimate absence at the single-event level — only visible in aggregate, as a pattern of every bare event skipping across many runs.

The SUMMARY's fail-closed-safety claim ("never silent wrong data") holds regardless of which shape occurs — that part is accurate and is the actual safety property that matters. But the stronger implicit claim that in-flight per-event diagnostics will always let an operator tell the two failure modes apart is **only guaranteed for the 400-error shape**, not the 200-empty-results shape. The one-shot pre-flight `curl` check is the real safety net here (it resolves the ambiguity before any live traffic flows), and it is present and well-specified — that is the part of criterion 8 the phase actually needed to deliver, and it does. Recorded as a **human verification item** above (an operator must run the curl checkpoint against portal `22617666` before trusting this lane live) — this is an external-service dependency this offline phase correctly did not, and could not, resolve itself.

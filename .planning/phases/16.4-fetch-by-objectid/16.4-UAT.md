### 2. A systemic filterability failure is distinguishable from a legitimate absence
expected: |
  16.4-VERIFICATION.md §8 refused to rubber-stamp the SUMMARY's diagnosability claim,
  narrowing it precisely: the claim holds IF HubSpot 400s on an unsupported filter
  property, and FAILS if it returns 200 with results:[] — in which case a systemic bug
  would read identically to a deleted record and only be visible in aggregate. The probe
  must settle which shape HubSpot actually returns.
result: pass
source: automated
evidence: |
  Both shapes probed on contacts:

    hs_object_id=99999999999            -> HTTP 200  total=0  ids=[]     (legitimate absence)
    lv_definitely_not_a_property=201    -> HTTP 400                      (unsupported property)

  The shapes are distinct. `adaptFetchByIdResult()` (n8n/code/adaptFetchById.js:31-81)
  routes the 400 through its `item.error`/`item.json.error` branch, so `fetch_diagnostic`
  reads "error: <body>" for a filterability failure and "zero-results: hs_object_id not
  found..." for a genuine absence. The verifier's stated precondition is met, so its
  narrowed claim resolves in the favourable direction: per-event diagnosis IS possible,
  not merely aggregate.

  REFINEMENT, recorded rather than glossed: HubSpot's 400 body is generic —
  {"status":"error","message":"There was a problem with the request.","correlationId":...}
  — and does NOT name the offending property. So an operator can tell "the filter was
  rejected" from "the record is absent", but must still identify WHICH property from the
  request, not the response. That is weaker than 16.4-VERIFICATION.md §8's optimistic
  reading ("the diagnostic clearly reads error: <HubSpot's 400 body>" implies the body is
  informative; it is not), and stronger than its pessimistic branch. Both were hypotheses;
  this is the measurement.

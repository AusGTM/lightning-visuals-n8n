<breakdown_shape_facts>
Verified against the current tree. Read these before writing the serializer — they are the
reason a naive implementation will be wrong:

1. `breakdown` has FOUR keys and no total: `version`, `components`, `hard_vetoes`,
   `graduated_deductions`. **There is no `total` key.** The score lives only on the sibling
   `ICPScoreResult.score`. D-02 requires the payload to always retain the total, so the
   serializer must ADD it from the result object (C4).
2. `components` entries are `{signal, value, points}`. `graduated_deductions` entries are
   `{signal, points}` — asymmetric, no `value` key. `hard_vetoes` is REASSIGNED to a flat
   list of reason strings, not appended dicts.
3. There are no per-component evidence or reason strings in the breakdown today. A real
   payload is a few hundred bytes and shedding will never fire naturally — the offline test
   must exercise shedding against a synthetic oversized breakdown, not a real one. Do not go
   hunting for evidence fields that do not exist.
4. `lv_icp_score_breakdown` is `type: string, fieldType: textarea` in
   `config/hubspot_properties.yaml` — the 60k limit is the budget.
5. `scripts/run_scoring_parity.py` currently has ZERO custom CLI flags: `main()` builds a
   parser and calls `parse_args(argv)` with nothing added. `--write-breakdown` is the first.
6. Its module docstring asserts the script "never creates, patches, or deletes a company
   (T-40-06's structural mitigation: no create-record, patch-record, delete-record ... is
   imported anywhere in this file)". **No test enforces this** — it is documentation only.
   Adding a conditional write makes that sentence false on disk unless it is amended.
</breakdown_shape_facts>

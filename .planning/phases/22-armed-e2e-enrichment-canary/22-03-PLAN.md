<objective>
Turn the token half built in Plan 01 into the full cost ledger REQ-canary-cost-ledger asks for:
provider credit balances before and after, Anthropic tokens per call priced into dollars, both
compared against a committed baseline of the 2026-07-30 estimates, producing one calibrated
per-record cost figure.

Purpose: the whole point of spending an audited armed window is to come out of it able to answer
"what does one enriched record actually cost?" — the question that decides whether a fleet-wide
sweep is affordable. Research found no consolidated estimates document exists, so assembling it is
part of the requirement, not a preamble to it: without a committed baseline there is nothing for the
measured actuals to be a delta against.

Output: the completed ledger script with credit capture, settle handling and an estimate-versus-
actual report; the committed 2026-07-30 estimates table with a cited source per row; and the ledger
document the operator fills during the armed window.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Ledger → provider usage APIs | Authenticated read-only calls; the adjacent match and enrich endpoints on the same hosts are billable, so endpoint scope is a cost boundary. |
| Ledger → n8n execution data | Already established in Plan 01; token rows are consumed here, not re-fetched with wider scope. |
| Ledger output → committed ledger document | Cost figures and evidence become permanent committed record. |
| Estimates table → the operator's fleet-arming decision | A wrong or uncited baseline propagates directly into a spend decision. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-22-11 | Repudiation | A confident per-record figure derived from partly-unknown inputs | high | mitigate | Unknowns propagate as unknown rather than zero; any total containing one is marked partial; tests pin both behaviours. |
| T-22-12 | Denial of Wallet | The ledger itself calling a billable provider endpoint while "just checking credits" | high | mitigate | Only the registry's usage URLs are reachable through the reused check functions; an acceptance grep asserts no match or enrich endpoint appears in the module. |
| T-22-13 | Information Disclosure | A provider or n8n credential printed into the ledger document or a snapshot | high | mitigate | The reused credit checker's discipline is preserved: balances and status codes only; snapshots hold numbers, labels and timestamps, and are reviewed before commit. |
| T-22-14 | Tampering | Stale v2 credit arithmetic silently anchoring the v3 baseline | medium | mitigate | Every estimates entry cites its source document and section; an acceptance grep asserts the retired v2 figures appear nowhere; the contract document is named as superseding. |
| T-22-15 | Repudiation | Lusha's balance lag under-reporting spend | medium | mitigate | The after-capture settles before reading and re-reads to stability, recording attempts and the stability flag in the snapshot. |
</threat_model>

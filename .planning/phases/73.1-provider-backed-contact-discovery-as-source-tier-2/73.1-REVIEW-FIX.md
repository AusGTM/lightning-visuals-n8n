## Fixed Issues

### CR-01: The discovery lane's now-unconditional ZoomInfo mint would 401 all but the last gap company in any multi-company round

**Status:** `fixed: requires human verification` — not plain `fixed`. Per the
verification_strategy's logic-bug limitation, Tier 1 (re-read) and Tier 2 (syntax check)
only prove the JSON is well-formed and the offline walker's own model of it behaves as
intended — neither proves n8n's real engine behaves the way this fix assumes. Two
assumptions here are `[documented]` only (CLAUDE.md §13.0.3's own tagging discipline), not
`[observed live]`:
1. `executeOnce: true` on a native `httpRequest` node makes it fire its request exactly
   once per execution and emit exactly one output item, regardless of input item count.
   The offline walker does not model `executeOnce` at all (confirmed by reading
   `tests/n8n/lib/walkWorkflow.mjs`'s HTTP-node branch — it never reads `node.executeOnce`);
   the CR-01 test's stub returning one item per call is what makes the test pass, not a
   simulation of the engine's own `executeOnce` semantics.
2. A `combine`/`combineAll` Merge with input 0 holding 1 item and input 1 holding N items
   performs the full 1×N cartesian broadcast this fix relies on. This repo's own
   platform-facts table (CLAUDE.md §13.0.3) has zero `[observed live]` rows for
   `combineAll` at all — every existing live-verified Merge row in that table is about
   `append`/`combine` input-starvation and firing-twice behavior, never a `combineAll`
   broadcast specifically.

Both are standard, long-documented n8n Merge/HTTP-node behaviors, and the walker's own
`combineAll` cartesian-math implementation (`mergeBuffers`, `tests/n8n/lib/walkWorkflow.mjs`)
is exercised by pre-existing tests elsewhere in this repo (e.g. the `"Source By Field
Broadcast"` 1-to-N pattern `splice_carry_merge_after` already uses at
`scripts/build_cloud_workflows.py:2043`) — so this is a low-risk, well-precedented fix, not
a speculative one. It is still unverified against the real engine. **Discriminating check
for the operator's first disarmed multi-gap-company send** (2+ gap companies in one
round): confirm every gap company's `search_diagnostics.rung1.status` is present (proves
the row still reached Rung1 with a token at all — a broken `??` fix, see WR-01 below,
would instead route every company past `IF ZoomInfo Eligible` silently) AND that no
company's `rung1.status` is `401` while a sibling company's is `200` in the SAME round
(the specific failure shape CR-01 fixes — a mixed 200/401 outcome in one round would mean
the broadcast did not reach every row, or `executeOnce` did not behave as assumed). A
clean round upgrades both assumptions above to `[observed live]`.

### WR-01: `per_company_cap: 0` was still silently treated as "unset" (carried forward, unresolved before this run)

**Status:** `fixed`, with one `[documented]`-only caveat worth naming rather than treating
as fully settled: `$json.per_company_cap ?? {DISCOVERY_DEFAULT_CAP}` inside an n8n IF
node's `{{ }}` expression string is the first use of `??` inside a `{{ }}` expression
anywhere in this repo (every prior `??` in this file is inside real Code-node `jsCode`,
not an n8n tmpl expression) — `[documented]` only, because n8n's expression engine has
supported standard JS operators including nullish coalescing for years, but this repo has
no `[observed live]` row for it. If it were ever rejected by the live engine, the blast
radius would be worse than the bug it fixes: `IF ZoomInfo Eligible` would fail to evaluate
and could route every gap company past the eligibility gate rather than merely
mis-handling `per_company_cap: 0`. The offline walker's own `evalExpr` (`new Function`,
real JS) evaluates it correctly, which is the strongest offline evidence available; live
confirmation is a byproduct of the same disarmed send CR-01's discriminating check above
already asks for (any `search_diagnostics.rung1` entry appearing at all proves the
expression parsed and routed a company through).

**Files modified:** `scripts/build_cloud_workflows.py`, `n8n/wf_suggest_discovery_cloud.json`, `tests/n8n/suggestDiscoveryLane.test.mjs`
**Commit:** `ab09dafa`
**Applied fix:** Replaced `||` with `??` at all three consumer sites the review cited —
`_discovery_provider_eligible_expr()`'s n8n IF-node expression, and the `cap = row.per_company_cap || DISCOVERY_PEOPLE_CAP` lines in both
`ENRICH_DISCOVERY_WATERFALL_COMPLETE_JS` and `ENRICH_DISCOVERY_ADAPT_ZOOM_PEOPLE_JS` —
matching how `ENRICH_PARSE_DISCOVERY_REQUEST` already preserves an explicit
`per_company_cap: 0` with `??`. Verified `??` is well-supported both by n8n's own
expression engine (standard JS, used unqualified elsewhere in this same file for

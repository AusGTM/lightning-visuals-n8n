## Summary

This is an incremental review of only the 7 files that changed since the phase's prior
review (`40afd0cd`, commit `40afd0cd`). Plan 73.1-10 added per-request role-family
filtering (`titlesForFamilies`, D-11a); plan 73.1-11 (Task 3) moved ZoomInfo pagination
off the URL string onto the `qs` option (`buildQuery`) and added `extractErrorDetail` for
richer diagnostics, and (Task 2) made the discovery lane's ZoomInfo token gate
unconditional/cache-free (`_discovery_zoom_search_gate_js`) to close a stale-cached-token

The role-family filtering and error-detail additions are correct, well-tested (Python

for the stale-cache 401 class, as implemented, composes with an existing, already-

true` live verdict) to reintroduce token-invalidation 401s deterministically for any
discovery round with 2 or more gap companies — which is this lane's normal, tested,
intended use case, not an edge case.

## Critical Issues

### CR-01: The discovery lane's now-unconditional ZoomInfo mint will 401 all but the last gap company in any multi-company round

**File:** `scripts/build_cloud_workflows.py:12091-12117` (`_discovery_zoom_search_gate_js`),
wired at `scripts/build_cloud_workflows.py:12345-12381` in `build_suggest_discovery_cloud`;
generated into `n8n/wf_suggest_discovery_cloud.json`'s "ZoomInfo Search Token Gate" /
"ZoomInfo Search Mint" nodes.

**Issue:** This is a composition of four facts already established elsewhere in this
codebase, not a new premise of my own:

1. `_discovery_zoom_search_gate_js` (this diff, 73.1-11 Task 1) sets `zoom_needs_mint:
   true` **unconditionally** for every item it sees — "no execution can ever reuse a
   token another execution minted" is the docstring's own framing. Given a round with N
   gap companies (`IF Company Is Gap` / `IF ZoomInfo Eligible` both eligible), all N items
   arrive at "IF ZoomInfo Search Needs Mint" with the identical `true`, and all N flow
   into "ZoomInfo Search Mint" **together, in one wave**.
2. "ZoomInfo Search Mint" is a native `httpRequest` node built via `_zoom_mint_node` →
   `_http_node` with no `batch_interval_ms` (no `options.batching` in the generated node —
   confirmed by reading the parameters block in `n8n/wf_suggest_discovery_cloud.json`).
   `_http_node`'s own docstring states the consequence plainly: *"A per-row search node
   fed 48 items fires 48 requests in one burst"* — this is an established, already-proven
   behavior of this exact node type in this exact codebase (F-A3,
   `uat-stress-2026-09-15`), not a guess. N gap companies therefore mean N separate
   ZoomInfo OAuth mint calls in this one execution.
3. `splice_carry_merge_after(..., combine_by="combineByPosition")` correctly pairs mint
   response *i* with row *i*, so each company does end up carrying its own,
   individually-minted token — the carry mechanism is not itself the bug.
4. `scripts/probe_provider_discovery.py --token-replay`'s live result, recorded the same
   day this fix landed (`73.1-TOKEN-REPLAY-VERDICT.json`):
   `prior_token_invalidated_by_later_mint: true` — minting token B **immediately
   invalidates** token A server-side, independent of token A's own claimed expiry (token A
   worked at step 1, then 401'd at step 3, mere seconds after token B was minted).

Composing 1–4: under this workflow's confirmed `executionOrder: "v1"` (nodes run to
completion in canvas order before the next branch starts), all N mint calls complete
*before* any row reaches "ZoomInfo Search Rung1". By the time Rung1 runs, only the
**last**-minted token is still valid on ZoomInfo's server — the other N−1 companies'
individually-carried tokens have already been invalidated by mints that happened for
*other* companies in the same batch, and their Rung1/Rung2 searches will both 401.

This is a composed inference, not something observed on a post-fix execution — say so
plainly: no live execution since this fix landed has exercised 2+ gap companies with a
genuinely cold cache (the two live executions after the fix, `12668`/`12669`, both reused
a token cached by the *pre-fix* code's `12666` run, so "ZoomInfo Search Mint" never ran in
either — 73.1-UAT.md line 302-303). One real uncertainty worth naming: the token-replay
probe's two mints were roughly 1 second apart; it is conceivable (unverified either way)
that ZoomInfo's OAuth server coalesces sub-second concurrent grants rather than
invalidating them. That would not change the severity if wrong — a design whose
correctness depends on the vendor happening to dedupe rapid grants is still a design
defect — but it is the one gap in the chain.

**Weak corroboration already sitting in the required reading, not previously connected to
this cause:** execution `12666` (pre-fix, cold cache, 2 gap companies) shows
`ZoomInfo Search Rung2: [2]` returning **zero people for both rows**, including
`tennis.com.au` — a domain the very same day's offline replay shows returns
`totalResults: 1094` unfiltered. Rung 2 carries no title filter, so the title-length 400
(the bug 73.1-09's follow-through diagnosed and fixed) cannot explain a rung-2 zero for
tennis. A dead/invalidated token is consistent with that unexplained zero (`73.1-UAT.md`
line 376 leaves it explicitly open). This is offered as consistent-with, not proof — the
per-row HTTP status was swallowed pre-diagnostics and no fixture was frozen from that
execution.

**Consequence:** the discovery lane's flagship, most-tested scenario throughout this
phase's own test suite (`threeCompanyRequest()` — 2 gap companies + 1 non-gap, used in
essentially every Task 1/2/3 test) is exactly the shape that triggers this. A real
operator batch of 2+ gap companies will very likely see person search fail (spurious
401s recorded in `search_diagnostics`, read as "provider error" or folded into
"found nobody") for all but one company per round, silently, with no test catching it —
every offline test stubs "ZoomInfo Search Mint" with a function that fabricates a
distinct fake token per item and never models real-world cross-item invalidation
(`tests/n8n/suggestDiscoveryLane.test.mjs`'s `zeroPeopleHttpStubs`, whose own comment
already documents "one output item per input item" as the modeled shape — it just never
simulates the invalidation).

**Second-order issue:** the `kind: design` todo this same plan filed
(`.planning/todos/pending/2026-09-18-zoominfo-mint-invalidates-prior-token-enrich-lane-cache-risk.md`)
offers, as option (b), "drop the cache on the enrich lane too, mirroring the discovery
lane's mint-per-execution gate" — adopting that option would import this exact defect
into the enrichment lane, which fans out *many* rows per execution, making the failure
far more frequent than even the discovery lane's typical batch size. That option's text
should be corrected or the todo should link this finding before anyone acts on it. (The
enrichment lane's own cold-cache case already has a latent, milder version of the same
underlying bug — pre-existing, outside this diff's scope, not itself a new finding here.)

**Fix:** Two mechanisms already exist in this codebase and either closes it:
```python
# Option A — one mint per execution regardless of item count (n8n node-level
# property, not inside "parameters"):
nodes.append(code_node("ZoomInfo Search Token Gate", _discovery_zoom_search_gate_js(), zx, zy))
mint_node = _zoom_mint_node("ZoomInfo Search Mint", zx + 400, zy - 120)
mint_node["executeOnce"] = True
nodes.append(mint_node)
```
This mints once for the whole batch; every row must then be re-attached to that single
token in the carry step, e.g. by switching
`splice_carry_merge_after("ZoomInfo Search Mint", ..., combine_by="combineAll")` —
`splice_carry_merge_after`'s own docstring already names `combineAll` as "a genuine 1-to-N
broadcast (a single config item onto every row)", which is exactly this shape.
Alternatively, restore a cache-based gate but scope its cache lifetime to *this single
execution only* (e.g. keyed on `$execution.id`, cleared at the start of each run) rather
than either the old cross-execution 24h cache or the current always-mint gate — closing
the stale-token class 73.1-11 targeted without reopening the intra-execution multi-mint
class. Add a test that stubs "ZoomInfo Search Mint" to return a **distinct** token per
call and asserts every row's carried `zoom_token` in "ZoomInfo Search Rung1" is identical
(or, for the cache route, that the Mint node runs exactly once for an N-gap-company
round) — the current `zeroPeopleHttpStubs` stub does not catch this because it never
inspects the *value* of the per-row token, only shapes items 1:1.

### WR-01 (carried forward from `40afd0cd`, unresolved): `per_company_cap: 0` is still silently treated as "unset"

**File:** `scripts/build_cloud_workflows.py:12074`, `:12088`, `:12255`
**Issue:** Unchanged by plans 73.1-10/73.1-11. `ENRICH_PARSE_DISCOVERY_REQUEST` correctly
preserves an explicit `per_company_cap: 0` with `??`, but every downstream consumer still
reads it with `||`:
```
12074:  const cap = row.per_company_cap || DISCOVERY_PEOPLE_CAP;
12088:  f"(($json.people)||[]).length < ($json.per_company_cap || {DISCOVERY_DEFAULT_CAP})")
12255:  const cap = row.per_company_cap || DISCOVERY_PEOPLE_CAP;
```
`0 || 10` is `10` in JavaScript, so a caller sending `per_company_cap: 0` (intending "do
not search this company") is silently overridden and the company is searched anyway.
Still latent, not exercised by any test.

**Note on the review scope_note's description:** the task's `scope_note` described the
prior review's two WARNINGs as "capRoleTitles naive fold, buildUrl query-string
pagination". That does not match the actual `40afd0cd` review file — its two WARNINGs
were WR-01 (`per_company_cap: 0`, above) and WR-02 (below, the bracketed query string).
There is no prior WARNING about `capRoleTitles`'s greedy-stop algorithm; see IN-03 for
that as a fresh, minor observation. Recording this here so the review history isn't
silently rewritten by a mislabeled carry-forward.

**Fix:** unchanged from the prior review — replace the three `||` sites with `??`, and
`($json.per_company_cap ?? 10)` in `_discovery_provider_eligible_expr`'s generated
expression string. Add a test sending `per_company_cap: 0` for a gap company and
asserting zero search calls.

### WR-03: `titlesForFamilies`'s silent no-op on an unrecognized family label has no operator-facing signal

**File:** `n8n/code/discoverySearch.js:87-102`
**Issue:** By design (documented in the function's own docstring — the plugin is the
validator, this function must not be a second one), a `role_families` entry that doesn't
match any label in the shipped vocabulary contributes zero titles and never throws. That
is a defensible contract for the *n8n* layer, but it means a request that manages to send
a stale/misspelled family label (e.g. after a future rename of `role_vocabulary.yaml`
that the caller's cached copy hasn't picked up) silently falls through to **zero title
filtering intent honored** with no error and no diagnostic — the round proceeds as if
`role_families` had matched nothing, indistinguishable in the response from "operator
genuinely wants an unfiltered rung-1 search" only by checking `role_families` was
non-empty on the request, which the response never echoes back. `73.1-UAT.md` line 527
already records this as an open, undecided question ("whether `titlesForFamilies`'s
deliberate no-op-on-unknown-label behaviour should ever surface a warning to the
operator"), so this is not a new discovery, but it is worth carrying into this review as a
real (if low-severity) gap rather than letting it stay filed only as a design todo.
**Fix:** Have `Adapt ZoomInfo People` (or `search_diagnostics`) echo which of the
requested `role_families` labels actually matched a known family, so a caller can detect
a drifted/misspelled label without a second offline lookup.

**File:** `scripts/build_cloud_workflows.py:12349,12360-12363`
**Issue:** Since `_discovery_zoom_search_gate_js` now sets `zoom_needs_mint: true`
unconditionally, "IF ZoomInfo Search Needs Mint"'s FALSE output (wired directly to
"ZoomInfo Search Rung1", bypassing the mint/cache path entirely) can never fire. This is
inherited scaffolding from the shape shared with `_zoom_split_contacts_subgraph` (which
does have a real FALSE branch) and is harmless, but it is dead graph structure worth a

**Fix:** Either delete the FALSE edge (since it's unreachable) or add a one-line comment
at the wiring site noting it is intentionally unreachable, matching the shared-shape

### IN-02: "ZoomInfo Search Cache Token" writes to workflow static data that is never read on this lane

**File:** `scripts/build_cloud_workflows.py:12351-12352`; leaf catch block at
`scripts/build_cloud_workflows.py:12216` (`delete sd.zoominfo`)
**Issue:** `_discovery_zoom_search_gate_js`'s whole point is to consult no cross-run
cache — but "ZoomInfo Search Cache Token" (reusing `_zoom_split_cache_js`) still writes
`sd.zoominfo = parsed` after every mint, and the Rung1/Rung2 leaves' catch blocks still
`delete sd.zoominfo` on an auth error. Both are dead effects on this specific workflow:
nothing in this lane's own gate ever reads `sd.zoominfo` again. This is harmless (separate
per-workflow static data, no cross-lane leakage) but it is confusing: a future reader
skimming the leaf's `isAuthError` handler will reasonably assume a self-heal mechanism is
active here, when it is not — the comment at line ~12168-12174 already half-acknowledges
this ("a cloud split-code-node cannot mint inline ... so this is 'self-heals across
runs'") but doesn't flag that self-heal is now moot on this lane specifically.
**Fix:** Either drop the now-pointless cache write/clear from this lane's specific node
bodies, or add a one-line comment at the write site noting it is inert here (kept only
for shared-code-path parity with the enrich lane's leaf).

### IN-03: `capRoleTitles`'s greedy title-fold is a reasonable but unoptimized packing choice

**File:** `n8n/code/discoverySearch.js:60-72`
**Issue:** `capRoleTitles` stops at the **first** title that would push the joined string
past the cap and drops everything after it in list order, rather than continuing to try
smaller/later titles that might still fit under the same cap (a first-fit-in-order
strategy, not a best-fit/knapsack one). For the shipped vocabulary this is a non-issue
(D-11c's own test confirms two full families fit comfortably under 500 chars), but as
more `role_families` are selected together in a single request, this greedy strategy can
drop a short, easily-fitting title purely because it appears after a long one that didn't
fit — never revisited. This is a design choice, not a defect, and not worth more than a
one-line note.
**Fix:** None required. If drop-avoidance ever matters in practice, sort candidates
shortest-first before the greedy fold (trading title-selection order for fewer drops).

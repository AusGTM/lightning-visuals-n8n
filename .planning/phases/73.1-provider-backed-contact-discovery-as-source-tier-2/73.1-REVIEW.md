## Warnings

### WR-01: `per_company_cap: 0` is silently treated as "unset" in the discovery lane, defaulting to 10

**File:** `scripts/build_cloud_workflows.py:12074`, `:12088`, `:12205`
**Issue:** `ENRICH_PARSE_DISCOVERY_REQUEST` (the "Parse Discovery Request" node) correctly
preserves an explicit `per_company_cap: 0` using nullish coalescing:
```js
per_company_cap: (c && c.per_company_cap) ?? ENVELOPE_CAP ?? DISCOVERY_PEOPLE_CAP,
```
but every downstream consumer of `row.per_company_cap` uses `||` instead of `??`:
- `_discovery_provider_eligible_expr()` (the "IF ZoomInfo Eligible" gate, line 12088):
  `($json.per_company_cap || 10)`
- `ENRICH_DISCOVERY_WATERFALL_COMPLETE_JS` ("Discovery Waterfall Complete", line 12074):
  `row.per_company_cap || DISCOVERY_PEOPLE_CAP`
- `ENRICH_DISCOVERY_ADAPT_ZOOM_PEOPLE_JS` ("Adapt ZoomInfo People", line 12205):
  `row.per_company_cap || DISCOVERY_PEOPLE_CAP`

In JavaScript, `0 || 10` evaluates to `10`. A caller that legitimately sends
`per_company_cap: 0` for a company (e.g. "already complete, do not search") would have
that intent silently overridden: the eligibility gate reads `0 < 10` as true and the
company is searched anyway, spending a ZoomInfo credit/call the caller explicitly tried
to avoid. This is not exercised by the current plugin (which only marks a company `gap:
true` when it wants a search) or by any test in `tests/n8n/suggestDiscoveryLane.test.mjs`
(no test passes `per_company_cap: 0`), so it is latent rather than observed, but it is a
real inconsistency between the parse step (which gets zero right) and every consumer of
its output (which does not).
**Fix:**
```js
// in all three spots, replace:
row.per_company_cap || DISCOVERY_PEOPLE_CAP
// with:
row.per_company_cap ?? DISCOVERY_PEOPLE_CAP
// and in _discovery_provider_eligible_expr's generated expression string:
($json.per_company_cap ?? 10)
```
Add a test in `tests/n8n/suggestDiscoveryLane.test.mjs` sending `per_company_cap: 0` for
a gap company and asserting zero search calls.

### WR-02: ZoomInfo discovery-search leaf builds a bracketed query string that has no precedent elsewhere in this codebase, alongside the still-open live 401

**File:** `n8n/code/discoverySearch.js:115-122` (`buildUrl`), consumed by
`scripts/build_cloud_workflows.py`'s `_discovery_zoom_search_leaf_js` (~line 12144)
**Issue:** Per the required-reading SUMMARY (`73.1-09-SUMMARY.md`, Issue 4), the
discovery search leaf gets HTTP 401 from ZoomInfo live inside n8n while an out-of-band
Python `requests` call with the same token claims succeeds — root cause explicitly
recorded as unresolved. One structural difference from the live-proven enrich leaf
(`_zoom_split_enrich_contacts_js`, `n8n/code/discoverySearch.js`'s own sibling) that is
worth naming for whoever picks this up: the enrich leaf's URL is a bare path with no
query string, while the discovery leaf's `buildUrl` appends
`?page[size]=${limit}&page[number]=1` with un-encoded `[`/`]` characters directly
interpolated into the URL string, then passed as `url:` to `this.helpers.httpRequest`.
Headers, body shape, and auth are otherwise byte-identical between the two leaves. This
is not proven to be the 401's cause (the SUMMARY's own investigation ruled out token-TTL
expiry specifically and left the true cause open), but it is the one shape difference
between a leaf that has always worked and one that has not, and was not called out in the
SUMMARY's own reasoning trail.
**Fix:** Not a code change to make blind. When next replaying this live, try
`this.helpers.httpRequest({ url: DISCOVERY_ENDPOINTS.zoominfo, qs: { "page[size]": limit,
"page[number]": 1 }, ... })` (letting the HTTP client's own query-string encoder handle
the brackets) as an isolating A/B test against the current string-interpolated URL, and
record which one actually reaches ZoomInfo with a 200.

### IN-01: `DISCOVERY_DEFAULT_CAP` (Python) and `DISCOVERY_PEOPLE_CAP` (JS) are two independent literals with no parity test

**File:** `scripts/build_cloud_workflows.py:12002`, `n8n/code/discoverySearch.js:44`
**Issue:** `DISCOVERY_DEFAULT_CAP = 10  # mirrors discoverySearch.js's DISCOVERY_PEOPLE_CAP
exactly` is a hand-mirrored constant used only inside the Python-generated IF-node
expression string in `_discovery_provider_eligible_expr()` (a native n8n IF node cannot
`require()` the JS module the way every Code node in this lane does via `inline()`). Every
other reference to the cap in generated Code-node bodies correctly inlines
`discoverySearch.js` and reads its real `DISCOVERY_PEOPLE_CAP` export, so this one IF-node
expression is the sole place the value is retyped by hand. No test pins the two constants
equal (checked: no hit for either name together in
`tests/n8n/suggestDiscoveryLane.test.mjs`), unlike `MAX_FALLBACK_SEARCHES`, which the same
file imports directly from `search_fallback.py` for the identical "generate-the-constant-
in" reason. A future change to one value without the other would silently desync the
eligibility gate's default from the cap every other node in the lane enforces.
**Fix:** Add an assertion in `tests/n8n/suggestDiscoveryLane.test.mjs` (or a Python-side
test importing both the generated workflow JSON and `discoverySearch.js` via a `node -e`
eval, mirroring `probe_provider_discovery.py`'s own `_node_eval` pattern) that the literal
`10` embedded in the "IF ZoomInfo Eligible" node's expression equals
`discoverySearch.js`'s exported `DISCOVERY_PEOPLE_CAP`.

### IN-02: `dedupe_discovered`'s grouping is transitive, not strictly pairwise, despite its own docstring's framing

**File:** `operator-claude-plugin/scripts/suggest_contacts.py:710-720`
**Issue:** The docstring for `dedupe_discovered` (D-03) describes the rule as pairwise
("the SAME person into ONE record"), and `_same_discovered_person` is written as a
pairwise predicate. However the grouping loop places a new record into the first existing
group where it matches **any** current member of that group, not just the group's first
(seed) member:
```python
if any(_same_discovered_person(row, records[j].get("row") or {}) for j in group):
```
This means three records A, B, C where A~B match (e.g. same `linkedin_url`) and B~C match
(e.g. same casefolded name+company) but A and C do **not** directly match each other will
still all be folded into one group and reported as one person. In practice this is
low-risk — a shared `linkedin_url` or an exact casefolded `firstname+lastname+company`
match is itself strong evidence of the same real person, so a "bridge" merge is unlikely
to conflate two different people — but it is a real divergence from the docstring's
pairwise framing and is worth a one-line acknowledgment or a test pinning the intended
behavior for a 3-record chain, since a corroboration entry silently absorbed into the
wrong winner would suppress a real, distinct person from the sendable set with no error.
**Fix:** Either update the docstring to say "transitive closure of pairwise matches"
(if intentional), or change the `any(...)` to compare only against `records[group[0]]`
(the group's seed) if strict pairwise-only grouping was intended. Add a 3-record
chain test either way.

### IN-03: `n8n/code/discoverySearch.js` header comment claims dependency-freedom while the file itself uses `module.exports`

**File:** `n8n/code/discoverySearch.js:38-40`
**Issue:** Minor documentation nit. The comment states "NO npm, dependency-free (no
CommonJS/ESM module-loading statement in the body below)", but the file's own final
statement is `module.exports = {...}` — a CommonJS statement. This is not a bug (build
time `strip_module()` in `scripts/build_cloud_workflows.py` truncates everything from
`module.exports` onward before inlining into a Code node, and the export is required for
`node --test`/`probe_provider_discovery.py`'s own `require()` of the file), but the
comment's phrasing reads as though the raw file itself has no such statement, which is
not literally true — only the *inlined* body doesn't.
**Fix:** Reword to "…no CommonJS/ESM statement survives inlining (module.exports and
everything after it is stripped by `strip_module()`)" for precision.

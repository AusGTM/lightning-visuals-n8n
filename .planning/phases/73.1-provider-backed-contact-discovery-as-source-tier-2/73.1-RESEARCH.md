- D-01: Ranks 1 and 2 are sendable; 3 and 4 are held. `STRONG_TIERS` becomes `(1, 2)` with

## Summary

This phase is a mechanical re-tiering plus four small, well-precedented extensions, glued
together by one genuinely new thing: a 6th n8n cloud workflow that calls provider *search*
endpoints this repo has never called before. The re-tiering (D-01/D-05a) is a pure constant
and config diff across four named files, all read this session, with a ready-made comment
block already documenting exactly how tiers are validated. The identity-ladder widening
(D-16a/b) and the LinkedIn-rung idiom to copy (D-16a) are both already-shipped patterns in
this codebase (`n8n/code/matchProposal.js::laneOf`, the `IF Linkedin Searchable` subgraph) —
extending them to `mobilephone` is additive, not novel. The role-vocabulary addition
(D-11c) is a pure YAML diff plus one structural test that already exists and will simply
gain two more clean cases.

The genuinely new risk is the provider discovery lane itself (D-06/D-11). **None of the
three providers' currently-wired endpoints in `scripts/build_cloud_workflows.py` are
search-by-role-title endpoints** — Apollo's `/v1/people/match`, ZoomInfo's
`/gtm/data/v1/contacts/enrich`, and Lusha's `/v3/contacts/search-and-enrich` all require an
already-known identity (email, or firstname+lastname+company) to return one match; they
cannot answer "who works at this company with this job title." A true discovery endpoint
(Apollo `/v1/mixed_people/search`, a hypothetical ZoomInfo `/gtm/data/v1/contacts/search`
mirroring the *confirmed-live* `/companies/search`, or Lusha's separate "Prospecting" API)
has never been probed in this repo. CONTEXT.md's own D-12 already anticipates this with a
plan-time live probe deferred to the operator's ruling — this research treats every
discovery-endpoint claim as `[ASSUMED]` and defers the live probe to a dedicated plan task,
consistent with the "back-load blocking-human live probes" standing rule and the fact that
a probe spends real provider credits and needs operator judgment on the result.

CONTEXT.md also folds in three UAT items from the 2026-09-18 pickleball sitting that are
easy to lose track of because they read as "fixes," not "discovery": D-14 (portal pin —
skill-text rule + grep test only, per D-14a's own instruction not to invent a runtime
gate, plus one live-verified backend read, see Pattern 4/A4), D-15 (session grant —
`write_grant.open_grant`/`covers` changes that touch EVERY skill opening a grant:
suggest-contacts, enrich-before-ingest, contact-upload, enrich-records, review-triage,
backend-control), and D-16's ingest-lane identity ladder (a `wf_contact_ingest_cloud`
change, distinct from D-01's suggest-contacts tier renumbering even though both use the
word "identity"/"tier"). None of these three touch the discovery lane's uncertain provider
endpoints, so none needs to wait on D-12 either.

**Primary recommendation:** Plan the phase as seven independent, sequenceable slices —
(1) tier re-tiering + parity test (D-01/D-05/D-05a), (2) role vocabulary (D-11c),
(3) suggest-contacts identity/dedupe widening (D-02/D-03/D-04/D-16b/D-16c/D-16d — the
suggest-contacts-side half of the emailless-create fold), (4) cost-guard/`cost_rates.json`
extension (D-13/D-13a), (5) the new discovery workflow (D-06 through D-11b), (6) portal pin
+ session grant (D-14/D-15 — cross-skill, skill-text + `write_grant.py`), (7) the ingest
lane's identity ladder (D-16a/D-16a-i — a `wf_contact_ingest_cloud` builder change, reusing
the LinkedIn-rung idiom per Pattern 3) — with the discovery workflow's provider HTTP node
bodies left as a `checkpoint:human-verify`-gated placeholder until the D-12 live probe (a
separate, small, disarmed script run before the workflow is regenerated) reports back which
endpoints exist and what they cost. Do not let slice 5's uncertainty block slices 1-4, 6-7,
which have zero live-endpoint risk and can be planned, built and tested offline today
(slices 6-7 also benefit from the two live probes already run in this research — see
Pattern 4, A4, and the resolved Open Question 2).

### Pattern 1: The tier-gate is TWO independent passes, not one
**What:** `search_fallback.hold_weak_sources` (records-level, tier gate) runs AFTER
`suggest_contacts.partition_for_dispatch` (email-domain relatedness gate). Both must hold;
neither weakens the other.
**When to use:** Any provider-found person must pass the SAME two gates a ladder/search-found
person passes — D-05 explicitly says the widening must not create a bypass.
**Example (current fail-open, to be closed by D-05)** [VERIFIED: operator-claude-plugin/scripts/search_fallback.py:400-421]:
```python
# operator-claude-plugin/scripts/search_fallback.py:400-421 (hold_weak_sources)
for index, record in enumerate(records):
    provenance = record.get("provenance") or {}
    if provenance.get("input") != SEARCH_INPUT:
        continue  # <-- fails OPEN: a provider-stamped record with a DIFFERENT
                  #     provenance.input value passes through untouched today
```
Also [VERIFIED: operator-claude-plugin/scripts/search_fallback.py:60-62]:
`STRONG_TIERS = (1, 2)`, `KNOWN_TIERS = (1, 2, 3)`, `LISTED_TIERS = (2, 3)`.
The planner's two options per D-05 (spelled out in full in Pattern 2 below): (a) widen this `!=` check to recognise the discovery
lane's own `provenance.input` value, or (b) have `synthesise_rows` stamp provider hits with
the SAME `suggest_contacts_web_search` input value plus `source_tier: 2` (the mechanism
`synthesise_rows` already supports — see Pattern 2 below). Option (b) is the smaller diff:
zero code change to `hold_weak_sources`, only a config/constant change to
`SEARCH_SOURCE_TIERS`/`STRONG_TIERS`/`KNOWN_TIERS`.

### Pattern 2: `synthesise_rows`'s `source_tier` parameter already supports a provider tier
**What:** `synthesise_rows(company, people, fetched_url, per_company_cap, source_tier=None)`
[VERIFIED: operator-claude-plugin/scripts/suggest_contacts.py:495-587] already accepts an
integer `source_tier` and stamps `{"input": "suggest_contacts_web_search", "locator": ...,
"source_tier": N}` when non-`None`; `N` must be in `SEARCH_SOURCE_TIERS`, currently
`(1, 2, 3)` [VERIFIED: operator-claude-plugin/scripts/suggest_contacts.py:492
`SEARCH_SOURCE_TIERS = (1, 2, 3)`].

**The actual fork D-05 leaves open, stated precisely:**
- **Option (a) — a new gate, discovery keeps its own `provenance.input`.** The discovery
  adapter stamps something other than `suggest_contacts_web_search` (e.g.
  `"suggest_contacts_provider_search"`), and `hold_weak_sources`'s
  `if provenance.get("input") != SEARCH_INPUT: continue` guard
  [VERIFIED: operator-claude-plugin/scripts/search_fallback.py:400-421] widens to recognise
  BOTH input values. `SEARCH_SOURCE_TIERS` becomes `(1, 3, 4)` (2 never reaches this
  function via this path) plus whatever set the discovery-side stamping function uses.
- **Option (b) — reuse, discovery calls `synthesise_rows(..., source_tier=2)` directly.**
  `SEARCH_SOURCE_TIERS` becomes `(1, 2, 3, 4)`; zero code change to `hold_weak_sources`.
  This is the smaller diff and answers "How the tier gate recognises provider records
  (D-05)" (Claude's discretion) in the cheapest way — **but it has a real cost**: reusing
  the identical `"suggest_contacts_web_search"` literal for BOTH a search-fallback hit and
  a provider-discovery hit erases the very distinction D-03's dedupe/corroboration and the
  step-9 report need ("named by a provider" vs "named by an industry-body web page" read
  differently to the operator, and D-03's corroboration entry needs to say WHICH). The fix
  is one more free-form key inside the SAME provenance dict —
  `extraction.validate` only checks that `input` and `locator` are present
  [per `synthesise_rows`'s own docstring, `operator-claude-plugin/scripts/suggest_contacts.py:519-522`],
  so a sibling key such as `provenance.provider: "apollo_search"` (or reusing `locator` to
  carry the provider+endpoint name — see below) travels safely to `write_dispatch_csv`
  without being written to HubSpot as a property. Recommend option (b) with this added key.

**Why this matters for the plan:** `fetched_url` (positional arg 3) has no natural value for a
provider-found person — there is no "page fetched." The planner must decide what locator a
discovery hit carries (a provider result has no URL at all, unlike a ladder/search-fallback
hit). Candidate: a synthetic locator string like `"apollo people search"` /
`"zoominfo contact search"` naming the provider and endpoint, since `synthesise_rows`'s
`locator` field is free text (not validated as a URL) — this ALSO doubles as the
provider-vs-web-search distinguisher from the paragraph above if a separate `provenance`
key is judged unnecessary.

### Pattern 3: The LinkedIn-rung idiom to copy for `mobilephone` (D-16a)
**What:** The enrichment lane already has a `IF Linkedin Searchable` → `HubSpot Linkedin
Search` → `Adapt Linkedin Search` subgraph, with a carry-Merge splice
(`scripts/build_cloud_workflows.py:7046-7094`, `:7853-7863`, `:8199-8200`) that:
1. Gates on whether the row has a usable LinkedIn URL (`IF Linkedin Searchable`).
2. Fires a `HubSpot Linkedin Search` HTTP node filtering `hs_linkedin_url EQ <url>`.
3. Adapts the result (`Adapt Linkedin Search`, `ENRICH_ADAPT_LINKEDIN_SEARCH`).
4. Splices a carry-Merge after the search node so downstream nodes never do a by-name
   `$('HubSpot Linkedin Search')` read (§13.0.2/13.0.3 rule).

**When to use:** D-16a explicitly says to reuse this idiom for the contact-ingest lane's
`mobilephone` rung, regenerated by the builder — the ingest lane (`build_cloud()`,
`n8n/wf_contact_ingest_cloud.json`) does NOT currently have this LinkedIn subgraph at all
(it lives in the enrichment lane, `build_enrichment_cloud()`); it must be freshly added to
the ingest lane's own match chain (`HubSpot Search by Email` → new rungs → `Adapt Search
Results`), one search per identity property, in priority order:
`email > linkedin_url > mobilephone > other`.
**Difference from the LinkedIn precedent:** D-16a-i requires the `mobilephone` rung to
route to `review` (not silently update) when the search returns MORE THAN ONE hit — the
LinkedIn precedent (per `matchProposal.js::summarizeMatch`'s `lane === "linkedin"` branch,
`n8n/code/matchProposal.js:200-217`) already has this exact three-outcome shape (`0 hits` ->
fall through, `1 hit` -> auto=true, `>1 hits` -> `auto: false, tier: "medium"`) — so the
`mobilephone` lane can literally copy `summarizeMatch`'s linkedin branch's multi-hit handling
rather than invent a new one.

### Pattern 4: The plugin-side transport/recovery mechanics D-07/D-08 depend on

**How the plugin talks to n8n today — two shapes, not one.** `dispatch.py`'s only exported
call (`dispatch()`, [VERIFIED: operator-claude-plugin/scripts/dispatch.py:1-42]) is a
**multipart** POST carrying a CSV file, purpose-built for `hubspot/contact-upload`'s row-set
upload — **not reusable as-is** for a JSON discovery request. The reusable shape is the
OTHER existing pattern, used by the two read-only lanes:

```python
# operator-claude-plugin/scripts/backend_status.py:27-53 [VERIFIED]
STATUS_PATH = "webhook/hubspot/backend-status"
def status_target(config: dict) -> str:
    return f"{str(config.get('n8n_url') or '').rstrip('/')}/{STATUS_PATH}"
def fetch_backend_status(config: dict, transport=requests.post) -> dict:
    ...
    response = transport(status_target(config), headers=headers, json={}, timeout=DEFAULT_TIMEOUT)
```
```python
# operator-claude-plugin/scripts/review_queue.py:74-105 [VERIFIED]
def queue_target(config: dict) -> str:
    return f"{str(config.get('n8n_url') or '').rstrip('/')}/{QUEUE_PATH}"
    ...
    response = transport.post(queue_target(config), headers=headers, json=body, ...)
```
Both modules follow the SAME four-part shape: a `<NAME>_PATH = "webhook/hubspot/<path>"`
constant, a `<name>_target(config)` URL builder, a `fetch_<name>(config, transport=...)`
function doing a plain `json=` POST (never multipart), and headers from the shared-secret
convention (never printed/logged — see `config_gate.py`'s header helper, mirrored from
`src/hubspot_client.hs_headers()`'s discipline). **Recommendation: a new
`suggest_discovery.py` client module, copying this exact four-part shape**, with
`DISCOVERY_PATH = "webhook/hubspot/suggest/discover"` and a POST body
`{"run_id": ..., "companies": [...]}` (D-08) — not a variant of `dispatch()`.

**The durable/runData recovery path (D-07's fallback) already exists and generalises.**
`watch.recover_async_dispatch(config, run_id, expected_chunk_count, *, workflow_id=None,
workflow_name=None, echo_node=None, response_node=None, ...)`
[VERIFIED: operator-claude-plugin/scripts/watch.py:540-571] already accepts
`workflow_name`/`echo_node`/`response_node` as OVERRIDES of the enrichment lane's own
defaults — meaning the SAME function, unmodified, can recover the discovery lane's results
by passing the new workflow's name and its own response node (e.g. `"LV Suggest Discovery
(Cloud template)"` / `"Build Response"`), with zero code change to `watch.py` itself. It
never falls back to time-proximity correlation — a miss is `recovered: False`, matching
D-07's "recover the same people from settled runData keyed on the client-minted `run_id`"
requirement exactly.

**`run_id` minting.** `run_state.new_run_id()` [VERIFIED: operator-claude-plugin/scripts/run_state.py:224]
is the existing, sole mint point (`uuid.uuid4().hex`-style, per `dispatch.py`'s own doc
comment describing the same default) — the discovery POST's `run_id` should come from
here, not a fresh ad hoc `uuid` call, so it can register with the SAME run-state bookkeeping
`start_run`/`mark_dispatched` other lanes use if the plan wants this round tracked
alongside an existing batch's run_id (per `enrich-before-ingest`'s two-lane precedent noted
in `dispatch.py`'s own docstring).

**Caution for D-14c specifically (portal-proof), surfaced by tracing this same credential
question:** the LOCAL `.env` `HUBSPOT_PRIVATE_APP_TOKEN` used by `src/hubspot_client.py` and
the N8N-SIDE HubSpot credential bound inside `wf_backend_status_cloud` are two DIFFERENT
app registrations against the same portal (per this session's own memory
`hubspot-projects-app-auth-model`: the deployed side is a projects-app static app, not a
private app). A probe run with the local token (as this research did, see Sources below)
proves the LOCAL token's portal and scope — it does NOT prove the n8n credential's portal.
D-14c's own design already accounts for this correctly: it routes the live portal check
through `wf_backend_status_cloud`'s OWN read (the n8n credential), never through a
local-`.env` probe — the plan must not substitute the cheaper local check for that live
backend read.

### Anti-Patterns to Avoid
- **Do not let a provider-found candidate become sendable via the ladder's OWN dedupe key
  without going through the tier gate.** D-03's dedupe (lowest-rank-wins) must run BEFORE
  `hold_weak_sources`, not instead of it — a merged row that inherits rank-1 provenance from
  the company page is legitimately sendable; a merged row that keeps only rank-2 provenance
  is not automatically sendable just because it was also found by a provider (D-01: rank 2 IS
  sendable now, so this specific case is fine, but a rank-3/4 corroboration must never be
  allowed to "upgrade" a row's effective rank).
- **Do not hand-write `n8n/wf_suggest_discovery_cloud.json`.** It must come from a new
  `build_suggest_discovery_cloud()` function in `scripts/build_cloud_workflows.py`,
  registered in `main()` exactly like the five existing builders (`scripts/build_cloud_workflows.py:12209-12270`).
- **Do not add a 15-input Merge.** Phase 70's own gap-closure history (CLAUDE.md §13.0.3)
  shows a confounded 15-input Merge that never fired live; split any wide fan-in into
  staged Merges of ≤10 inputs each, per the existing convention.
- **Do not spend real provider search credits inside this research or planning step.** D-12's
  probe is explicitly a live, credit-spending action requiring an operator ruling on the
  result — it belongs in a dedicated, small, disarmed plan task, not folded into research.

## Common Pitfalls

### Pitfall 1: Assuming the existing provider "enrich" endpoints can do discovery
**What goes wrong:** A planner reuses `Apollo Match` (`/v1/people/match`), `ZoomInfo Enrich`
(`/gtm/data/v1/contacts/enrich`), or `Lusha Enrich` (`/v3/contacts/search-and-enrich`) as-is
for the discovery lane, assuming "search-and-enrich" already means what CONTEXT.md's
roadmap calls "search."
**Why it happens:** The naming is confusing — Lusha's endpoint is literally called
`search-and-enrich`, but per `docs/LUSHA-V3-CONTRACT.md` §3, EVERY probed request body
requires an identity (`firstName+lastName+companyName`, `email`, or `linkedinUrl`) — it
resolves ONE known identity to enrichment data, it does not return a LIST of unknown people
matching a company+role filter. Same for Apollo's `/v1/people/match` (single match) and
ZoomInfo's `/contacts/enrich` (`matchPersonInput` requires email or firstName+lastName+
companyName).
**How to avoid:** Treat discovery as a genuinely separate HTTP call needing a genuinely
separate endpoint (Apollo `/v1/mixed_people/search`, an unconfirmed ZoomInfo
`/gtm/data/v1/contacts/search` mirroring the confirmed-live `/companies/search`, or Lusha's
separate Prospecting product) — verify each with the D-12 live probe before wiring
production code.
**Warning signs:** A request body built from `firstname`/`lastname`/`email` fields for a
"search" call — that shape only ever matches ONE already-known person; a company+role-only
body with no name is the actual discovery shape.

### Pitfall 2: Treating `SEARCH_SOURCE_TIERS` and `STRONG_TIERS`/`KNOWN_TIERS`/`LISTED_TIERS`
as one constant
**What goes wrong:** Only `search_fallback.py`'s three constants get updated, and
`suggest_contacts.py:492`'s separate `SEARCH_SOURCE_TIERS = (1, 2, 3)` is missed — it
currently does NOT include tier 4, and per D-05a all four constants must be pinned together
by one parity test. A provider stamping `source_tier=4` (if that representation is chosen
for "absence of a match" — see D-01's open discretion item) would then be REJECTED by
`synthesise_rows`'s own `ValueError` guard (`suggest_contacts.py:552-559`), which is
probably correct behavior but must be a DELIBERATE decision, not a missed update.
**How to avoid:** Update all four constants in the same commit, add the D-05a parity test
first (RED before the constants are re-numbered would be the wrong order here — the test
needs to be written to assert the NEW numbers, so write it expecting the target state and
watch it fail against today's `(1,2)`/`(1,2,3)`/`(2,3)`/`(1,2,3)`, then make the config+
constant change to turn it green).

### Pitfall 3: `hold_emailless`'s "sendable" and `partition_for_dispatch`'s "sendable" answer
different questions
**What goes wrong:** D-16b relaxes `extraction.hold_emailless` (used by contact-upload/
enrich-before-ingest, and — per `suggest_contacts.partition_for_dispatch`'s own docstring —
called internally as the FIRST pass inside `partition_for_dispatch` too,
`operator-claude-plugin/scripts/extraction.py:833-870`). A planner might assume relaxing
`hold_emailless` alone makes a LinkedIn/phone-only suggest-contacts row sendable — but
`partition_for_dispatch` ALSO runs `email_domain_relation` as its second pass, which
currently only knows how to evaluate an `email` field. D-16c says this second pass must
NOT hold an emailless row for `company_domain_unknown` — the planner must add an explicit
branch: "no email present" skips the domain-relation check entirely rather than routing
through a code path that reads a `None` email and holds it.
**How to avoid:** Trace `partition_for_dispatch`'s existing loop
(`operator-claude-plugin/scripts/suggest_contacts.py:881-940`) line by line; the fix is
almost certainly a guard added to the existing `for i, row in enumerate(rows):` loop:
`if not row.get("email"): sendable.append(row); continue` for a row that ALREADY survived
`hold_emailless`'s relaxed check (i.e., it has linkedin_url/mobilephone/phone but no email).

### Pitfall 4: The discovery lane's Merge count and starved-lane sentinels
**What goes wrong:** A gap-set-only lane with a ZoomInfo → Apollo → Lusha waterfall per
company, fanned across N companies in one POST, is exactly the shape (per-batch fan-out,
multiple HTTP hops, carry-Merges reattaching results) that produced Phase 70's entire class
of starvation bugs (CLAUDE.md §13.0.3: "a Merge with an input that never receives any
delivery never fires, and its downstream terminates silently with `success`"). A naive
implementation with no starved-lane sentinel on, e.g., the "provider returned zero
candidates" branch will silently drop that company's echo row from the response (violating
D-09, which requires ALL eligible companies echoed, gap or not).
**How to avoid:** Every branch that can legitimately produce zero items (a provider
disabled, a provider returning no matches, rung-1 filtering to zero before rung-2 fires)
needs its own sentinel-gate Code node emitting a marker item, per the established Phase 70
pattern (`Recompute Not Requested Sentinel Gate`, `Refusal Row Absent Sentinel Gate`, etc. —
search `scripts/build_cloud_workflows.py` for `Sentinel Gate` for ~10 existing examples to
copy the shape from).

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Unauthenticated webhook accepting a company/domain list, enabling third-party enumeration of the operator's HubSpot company book | Information Disclosure | Native Header Auth on the new webhook trigger, bound to the SAME shared credential as every other workflow (`build_backend_status_cloud`'s precedent, `scripts/build_cloud_workflows.py:9047-9048`) |

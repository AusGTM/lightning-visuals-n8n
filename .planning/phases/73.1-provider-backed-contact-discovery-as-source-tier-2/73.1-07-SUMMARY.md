# Phase 73.1 Plan 07: The Sixth Cloud Workflow — Provider Discovery Lane Summary

**A new read-only `LV Suggest Discovery (Cloud template)` n8n workflow searches gap companies through a ZoomInfo → Apollo → Lusha waterfall with a two-rung role-title filter, echoing every eligible company back with its `num_associated_contacts` and whatever people were found — zero HubSpot reads, zero writes, zero reveal calls.**

## Decisions Made

See `key-decisions` in the frontmatter for the full list. The two most consequential:

1. **Sentinel index-sharing over dedicated indices.** An early design gave the `Discovery Response Merge` a third, dedicated index for the "zero companies in this round" sentinel. That design tripped the walker's `merge_fired_with_unfilled_input` check on every ordinary mixed round (some companies gap, some not) — Task 3's own Test 7 forbids any such entry. Reverted to the established `_MERGE_MULTI_PRODUCER_TOLERANT` pattern (sentinel shares its real producer's index, mutually exclusive by construction), matching the enrichment lane's own precedent exactly.
2. **Combined eligibility expression per provider.** Rather than a separate `IF <Provider> Enabled` / `IF <Provider> Cap Not Met` pair (the enrichment lane's own two-gate shape), each provider hop here is gated by one `_if_bool_expr_node` testing `gap && domain && people.length < cap` together. D-11's stop-at-cap rule is enforced identically; this is fewer nodes for the same guarantee.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Missing carry-merge after "ZoomInfo Search Mint" silently dropped the row**
- **Found during:** Task 2, first full test run against the 3-company fixture
- **Issue:** The native "ZoomInfo Search Mint" HTTP node's raw token response (`{access_token, expires_in}`) was wired directly into "ZoomInfo Search Cache Token", which assumes it is fed the COMBINED `{mint response, carried row}` object per `_zoom_split_cache_js`'s own docstring. Without a carry-merge, the carried row (`company_id`, `people`, `run_id`, ...) was discarded entirely — a stray `{zoom_token, people: []}` item reached "Discovery Waterfall Complete" instead of the two real gap companies, and `Discovery Response Merge` fired with partial data (1 company instead of 3).
- **Fix:** Added `splice_carry_merge_after(nodes, conns, "ZoomInfo Search Mint", "IF ZoomInfo Search Needs Mint", merge_name="ZoomInfo Search Mint Carry Merge")`, mirroring `build_enrichment_cloud()`'s own identical splice for its "ZoomInfo Mint" node exactly (found by re-reading that precedent after the failure surfaced).
- **Files modified:** `scripts/build_cloud_workflows.py`
- **Verification:** `tests/n8n/suggestDiscoveryLane.test.mjs` Task1/Test2, Task2/Test6-8 all pass; debug script confirmed `Discovery Response Merge` receives the full 3-company/2-company fold correctly.
- **Committed in:** `325d1848`

**2. [Rule 1 - Bug] Test stubs using bare-array form silently dropped items on multi-item batches**
- **Found during:** Task 2, same test run
- **Issue:** `httpStubs` entries written as plain arrays (e.g. `"ZoomInfo Search Mint": [{...}]`) return that exact array regardless of how many items the node actually received — when 2 gap companies fed the node in one round, only 1 output item resulted, silently losing the second company from the walker's perspective. This is a property of `runNode`'s stub contract, not a builder bug, but the test file (mine, authored in this plan) needed the function form.
- **Fix:** Converted `zeroPeopleHttpStubs()`'s entries to `(items) => items.map(() => ({...}))` — one output item per input item, matching real n8n per-item HTTP semantics.
- **Files modified:** `tests/n8n/suggestDiscoveryLane.test.mjs`
- **Verification:** Task1/Test1-8 all pass with the 3-company mixed fixture.
- **Committed in:** `325d1848`

**3. [Rule 3 - Blocking] `discoverySearch.js`'s header comment contained the exact forbidden endpoint-path substrings the plan's own acceptance grep checks for**
- **Found during:** Task 2, running the plan's `Task2: no identity-enrich endpoint is wired into this lane` test
- **Issue:** The module is `inline()`'d verbatim into several generated Code nodes (`strip_module` only strips `require`/`module.exports` lines, not comments), and its explanatory header prose literally named the competitor endpoints (`/v1/people/match`, `/gtm/data/v1/contacts/enrich`, `/v3/contacts/search-and-enrich`) it exists to explain the module is NOT using — those exact strings then appeared in the generated `n8n/wf_suggest_discovery_cloud.json`, failing the acceptance criterion's grep.
- **Fix:** Reworded the header comment to describe those endpoints without spelling out their literal URL path fragments, while keeping the explanatory intent.
- **Files modified:** `n8n/code/discoverySearch.js`
- **Verification:** `/usr/bin/grep -c 'people/match\|contacts/enrich\|search-and-enrich' n8n/wf_suggest_discovery_cloud.json` returns 0.
- **Committed in:** `325d1848`

**4. [Rule 3 - Blocking] Registry tests outside the plan's own listed `<verify>` scope failed after regeneration**
- **Found during:** Running the FULL root `.venv/bin/python -m pytest` suite (not one of the plan's own listed `<verify>` commands, which scope narrowly to `tests/test_provider_registry_parity.py` and the n8n/operator-plugin suites)

- **Fix:** Added `wf_suggest_discovery_cloud.json` to both registries, with a comment explaining why (mirroring the existing `wf_backend_status_cloud.json` entries in each).
- **Files modified:** `tests/test_architecture_guard.py`, `tests/test_write_gate_coverage.py`

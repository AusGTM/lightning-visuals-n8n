number alone still fails identity and an email row with an unrelated domain is still

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `held_queue.identity_keys()`'s closed-vocabulary fail-fast
raised on the two new identity groups**
- **Found during:** Task 3's full-plugin-suite verification run (the plan's own
  `<verify>` block requires it green).
- **Issue:** `held_queue.py`'s `identity_keys()` derives its key-building branches
  from `extraction.identity_groups()` at call time but matches each group against a
  closed, hand-written set of shapes — any group it does not recognise raises
  `ValueError` by explicit design ("the YAML changed underneath a hand-written
  builder and the drift must fail the run"). Task 1's widening to five groups tripped
  this on `test_held_queue_facets.py`'s collection (a module-level constant calls
  `held_queue.stable_key()`), and `test_held_queue_identity_parity.py`'s own
  `_FIELD_VALUES`/`_GROUP_PREFIX` tables — the same fail-loud-by-design pattern —
  raised `KeyError` for the same reason.
- **Fix:** Added two `identity_keys()` branches (`[firstname, lastname,
  mobilephone]`, `[firstname, lastname, phone]`), each mirroring the existing
  `linkedin_url` branch's shape (name via `suggest_contacts.name_key()`, number
  stripped, both required); widened the parity test's field-value and prefix tables.
- **Files modified:** `operator-claude-plugin/scripts/held_queue.py`,
  `operator-claude-plugin/tests/test_held_queue_identity_parity.py`
- **Verification:** `test_held_queue_facets.py` (26 passed), `test_held_queue.py` (47
  passed), `test_held_queue_identity_parity.py` (3 passed).
- **Committed in:** `84f1a81a` (Task 3 GREEN commit)

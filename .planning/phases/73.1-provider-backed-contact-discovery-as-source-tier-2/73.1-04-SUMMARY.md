## Known Findings (non-blocking)

**Acceptance-criteria shell quirk, Task 2 (BSD grep, not a code defect).** Task 2's
acceptance criteria included `/usr/bin/grep -lc "22617666" operator-claude-plugin/skills/*/SKILL.md | wc -l`
reporting `11`. On this machine's `/usr/bin/grep` (BSD grep, GNU-compatible, FreeBSD
2.6.0, macOS Darwin 25.5.0), `-l` and `-c` combined do NOT collapse to `-l`'s behavior as
GNU grep does — each matching file emits BOTH a `-c`-style `file:1` line and an
`-l`-style bare filename line, so the piped count is `22`, not `11`. This is a
grep-implementation difference, not a defect in the inserted content: plain
`/usr/bin/grep -c "22617666" <file>` (used by the plan's actual `<verify>` block, not
its acceptance-criteria prose) correctly reports `1` for every one of the eleven files,
and the pytest suite's own line-by-line assertions (`test_every_skill_carries_the_crm_access_block`,
`test_no_skill_carries_a_second_copy_of_the_rule`) independently confirm exactly one
occurrence per file. Not filed to `WINDOWS.md` — no stub, skipped test, or unrun
`<verify>` resulted; the substantive check passed by every instrument that is

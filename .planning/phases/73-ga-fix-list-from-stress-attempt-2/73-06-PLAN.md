<objective>
One duplicate-email conflict aborted the whole ingest batch in attempt 2 (execution `12454`): the
create node threw, its output was discarded, no association ran, no ingest response was built, and
roughly seventeen contacts landed in HubSpot with no company. Containing that is D-73-01.

But the containment cannot ship alone. `Create Carry Merge` pairs the create responses with the
carried rows BY POSITION, which holds today only because the node's output count equals its input
count by construction. The moment any item leaves on an error output, the success array shrinks
and every create after the first failure pairs with the wrong carried row — a wrongly-associated
contact, which is worse than the orphan this plan is fixing. So pairing is fixed FIRST, on its own,
provable with nothing more than a stub that returns fewer responses than it was given.

The walker cannot see an HTTP node's second output at all today, so the offline proof D-73-19
requires does not exist yet either. That extension is its own task, not a free side effect.

Purpose: a bad row must cost its own row and nothing else. Output: an ingest lane where a rejected
create is a visible refusal row and every surviving create still lands on its own company.
</objective>

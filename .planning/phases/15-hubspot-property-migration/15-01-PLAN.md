<objective>
Phase 15 is the first phase that mutates the live HubSpot portal (22617666). Its primary
deliverable is SAFETY AND REVERSIBILITY, not features: make it impossible to leave the
portal half-migrated or to lose data. It creates the enrichment properties the pipeline
needs, retires the ICP-output write paths (Approach C), applies the `lv_` naming convention
to code-generated names, and ships the tooling + runbook that can undo the whole migration.

Six ROADMAP criteria (C1..C6):
- C1: Missing properties created; sync dry-runs by default and emits an undo manifest.
- C2: Research caching by domain / 180-day TTL becomes possible (unblocks spec RT-5) — the
  4 datetime cache keys exist.
- C3: `lv_org_type` text→enumeration is NOT performed (one-way door; explicitly out of scope).
- C4: `lv_icp_fit_score` / `lv_icp_tier` write paths retired (HubSpot owns the derived outputs).
- C5: PN-1..PN-5 naming applied to code-generated names.
- C6: The 4 missing contact properties created (`lv_linkedin_url`, `lv_persona_group`,
  `lv_jobtitle_verified_at`, `lv_mobilephone_verified_at`).

PROVENANCE STORAGE MODEL (coordinator decision, supersedes RESEARCH §6.3's 45/63 flat-suffix
design): per-field enrichment metadata is stored as ONE JSON text property per object
(`lv_enrichment_provenance` / `lv_contact_enrichment_provenance`), NOT as ~60 flat
`lv_<field>_source/_confidence/...` properties. EXCEPTION: four `_verified_at` datetimes stay
top-level and queryable because HubSpot cannot filter inside JSON and RT-5/SJ-2 must query
"verified_at older than 180 days" for exactly the fields research fires on. Rationale
(recorded per coordinator): provenance is audit-read (you read it inspecting one record),
not segmentation (you never filter a list by "org_type confidence"). Inputs stay real
queryable properties; provenance rides in one JSON field; filterability lost on provenance
internals is acceptable and intended. This SUBSUMES the PN-4 flat-metadata rename and folds
staging (RESEARCH §6.2's `lv_waterfall_*`/`lv_claude_web_*`) into the blob — there is no
Approach-C consumer that queries staging, so it is audit data and belongs in provenance.

Purpose: unblock RT-5 cost control and give the operator a proven, reversible, non-lossy
migration.
Output: 4 operator scripts + 1 manifest config + stamper/rename code changes + a rebuilt,
byte-deterministic workflow set + full offline test coverage + an operator runbook.
</objective>

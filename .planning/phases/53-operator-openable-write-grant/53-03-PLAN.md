<objective>
Give the grant an operator-reachable surface: the key an admin sets and can see they have set, the
plan-then-yes exchange that opens a grant, the revoke that closes one, and an honest answer when an
operator asks the plugin to turn writes on.

Purpose: G-1 and G-2 are both surface defects. G-2 is that the authority lives somewhere an operator
cannot reach — plans 01 and 02 moved it. G-1 is that reaching one write took three separate arming
surfaces, each defensible alone and never walked end to end from the operator's chair. This plan is
where the remaining two surfaces collapse into one exchange, and where an admin can confirm from
inside Claude that they have enabled the thing the operator is about to ask for.

Output: the settings key in the example config with its note, `init_check` reporting it, the
`plan_grant` / `open_grant` confirmation pair, `revoke_grant`, and one line of `control_actions`
wording.

Scope note: the skill documents that tell an operator to use any of this are plan 53-04, along with
the release that ships it.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Admin's settings file → operator authority | One JSON boolean is the whole authority for interactive writes; how it is displayed is how an admin knows what they enabled |
| Operator request → grant proposal | The proposal is what consent attaches to; a proposal that under-states its scope buys consent for something wider |
| Grant → dispatch arm | `authorize_send` is the only bridge; a bridge that widened the allowlist would silently break record scoping |
| Plugin capability wording → operator expectation | An out-of-allowlist message that omits the grant path sends an operator back to a terminal, which is the defect being fixed |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-53-13 | Elevation of Privilege | example config shipping enabled | high | mitigate | The example carries the JSON boolean false; a test asserts the shipped example does not enable write grants |
| T-53-14 | Spoofing | a settings key mistaken for a capability | medium | mitigate | Reported in its own settings section; a test asserts it is absent from `CAPABILITY_KEYS` and from the keys section |
| T-53-15 | Elevation of Privilege | a grant opened without an explicit yes | critical | mitigate | Confirmation has no default so omission is a TypeError; only the exact string yes proceeds; open takes a proposal so planning cannot be skipped; both pinned against `execute_action`'s contract by source inspection |
| T-53-16 | Tampering | the bridge widening the allowlist to the grant's whole set | high | mitigate | `authorize_send` passes the send's own records to the arm; a test asserts the armed allowlist equals the send's records, not the grant's |
| T-53-17 | Denial of Service | an existing operator's file reading as broken | medium | mitigate | Overall status stays derived from capability readiness only; a test pins that a file without the new key reports its pre-phase status |
| T-53-SC | Tampering | npm/pip/cargo installs | low | accept | No package is installed by this plan |

<flagged_assumptions>
- **The grant open deliberately does not join `control_actions.ACTION_KINDS`.** That is a planner's
  discretion call under 53-CONTEXT's "which module owns it". The reasoning is that `ACTION_KINDS`
  gates `execute_action`, documented as the only mutating path, and the grant open mutates nothing;
  putting a read-only action on a mutation allowlist blurs a distinction this phase is otherwise
  careful about. The cost is a second confirmation gate in the codebase, mitigated by pinning the
  two comparisons as identical. If the operator would rather have one gate in one place, this is the
  decision to revisit and it is a small change.
- **`init_check`'s settings table has one row.** It is a table rather than a single field because a
  second admin-set setting is plainly coming (Phase 57's ceilings), and a one-row table costs
  nothing now while a second field bolted on later costs a refactor of the report shape.
</flagged_assumptions>

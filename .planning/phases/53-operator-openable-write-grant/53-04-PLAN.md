operator what the key and the grant are, cut the release so an installed operator is offered the
update, and have the operator walk the path from their own chair.

find the grant, or find it and be told by a skill to say an arming phrase anyway. This plan is where
the surfaces agree with each other and where a human confirms they do.

CHANGELOG cut and version bump, and a recorded operator walk.

  <name>Task 3: The operator walks it — the same walk that found G-2</name>
  <what-built>
Phase 53 makes the HubSpot write path reachable from an operator's own surface for the first time.

1. **Authority moved.** The interactive arm no longer needs `ALLOW_N8N_ARM` in the session's shell
   environment. It needs one key, `allow_write_grants`, set to the JSON boolean true by an admin in
   `operator.local.json` — the file that already lives outside the versioned install directory and
   survives plugin updates. `ALLOW_N8N_ARM` is unchanged and remains the sole authority for the
   scheduled and cron paths, which have no operator to confirm anything.
2. **A grant.** The operator names a batch on one lane; the plugin shows the record count, the
   worst-case provider credits per provider, the worst-case Anthropic dollars, the projected n8n
   executions and the configured monthly allowance; the operator says yes once. Every send in that
   batch then arms and disarms its own window, bounded to that send's records, without asking again.
3. **Two guardrails you asked to be surfaced rather than assumed.** Opening a grant first reads the
   live write-safety state and refuses to open if it finds writes already armed, naming what it
   found and offering a disarm. And two consecutive disarm failures — or a pre-flight read finding
   writes still live before the next send — end the grant and block further sends. One isolated
   disarm failure still fails only that send, as you chose.
4. **Nothing about record scoping, guaranteed disarm, the ungated disarm, or the arm's independent
   re-read changed.** Each has a test naming the property it defends.

Zero live HubSpot writes have been performed by this phase so far. The plugin version is bumped and
the CHANGELOG is cut, but the push and the marketplace clone refresh have deliberately not been run.
  </what-built>
  <how-to-verify>
Do this from Claude Desktop, as the operator, not from a terminal — the point of the walk is that
the terminal is not needed. The one exception is step 1, which is the admin's job by design.

1. **As admin:** open `~/.claude/plugins/data/operator-claude-plugin-lightning-visuals-operator/operator.local.json`
   and set `allow_write_grants` to `true`. Confirm the file already had your other values in it and
   that you did not have to recreate anything.
2. **Ask the plugin whether it is set up.** Confirm the answer now includes a line saying write
   grants are enabled. Then, if you can, try it once with the key set to `"true"` as a STRING rather
   than a boolean, and confirm it reports NOT enabled — the near-miss behaviour is deliberate and
   worth seeing once.
3. **Ask to open a write grant** over one or two records you are willing to have written. Read what
   comes back and answer these:
   - Does it name the lane, the records, and whether creates are included?
   - Are the cost figures ones you find plausible, and is the rate table's age shown?
   - Does it say clearly that the figure discloses rather than prevents, and that the remaining
     monthly allowance is not yet being checked?
   - Is there exactly one yes to give?
4. **Send the batch.** Confirm you were NOT asked for an arming phrase, and that the report still
   tells you what was armed, what was sent and whether the disarm verified.
5. **Revoke the grant** mid-batch if the batch is long enough, or immediately if it is not. Confirm
   the next send refuses and says the grant was revoked.
6. **Try to open a second grant covering a record NOT in the first**, then attempt a send for a
   record outside it. Confirm it is refused by name before anything is armed.
7. **Read the refusal you get with the key unset.** Ask an admin to unset it, ask to open a grant,
   and confirm the refusal names the key, the file and who sets it — and that it does not tell you to
   set a shell environment variable, which is the thing you cannot do.

Then decide the open question this phase leaves with you: **does a grant covering one lane match how
you actually work?** The `enrich-before-ingest` flow now needs two grants in order — one before the
waterfall, one after the enriched preview lands — because authorizing the HubSpot write before the
preview exists would let you approve writing something you have not yet seen. That is a real
constraint carried over from an earlier deliberate decision. If two grants for that flow is one too
many for you, say so: the alternative is a single grant whose ingest half is withheld until the
preview lands, which is buildable but is a different design and would be its own phase.

Finally: if you approve, run the two release steps that were deliberately left to you — push to
master, then refresh the marketplace clone with the two commands printed at the end of the previous
task. Until the clone is refreshed, an installed plugin will not see the update however correct the
version bump is.
  </how-to-verify>

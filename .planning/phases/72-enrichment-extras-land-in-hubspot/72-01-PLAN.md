<objective>
Prove the thinnest end-to-end path this phase exists to open: ONE enrichment extra
(`mobilephone`) travels CSV header → `columnMap.js` → the ingest lane's candidate →
`mergeContacts()` → the `HubSpot Create` body, and — in the same slice — is PROTECTED
rather than clobbered when the matched HubSpot contact already holds a different value.

Purpose: F71-5 recorded Busteed `352422766048` landing with email + phone + title while his
held row carried a paid-for `mobilephone +61 419 212 580`. `mobilephone` is the cheapest
possible tracer for that defect: it needs no naming reconciliation (unlike LinkedIn), it has
a producer in all three providers, and it is the first field the D-72-17 gate reads back.

**Unstated prerequisite discovered at plan time — read this before touching the wrapper.**
The ingest lane calls `mergeContacts({}, candidate, ...)` with a literal empty object
(`scripts/build_cloud_workflows.py:425`, comment "no existing HubSpot props fetched here =>
{}"), because `ADAPT_SEARCH_RESULTS` deletes the search response's `results` after extracting
id lists. Every candidate field therefore promotes unconditionally on an UPDATE row today.
Widening the candidate from 7 keys to 16 (plan 02) without fixing this would convert every
update into a 16-field clobber — the exact opposite of the phase charter — and would make
D-72-17's "one UPDATE row proving a non-blank `fill_blank_only` field was NOT overwritten"
assertion unpassable. Wiring `existingRecord` through is therefore part of the tracer, not a
later refinement. It is jointly required by SAFE-01, D-72-06 and D-72-17; it is not a new
decision.

**Two operator-visible consequences to surface, not to decide silently.** Once `existingProps`
is real, the ingest lane starts honouring policy classes it has never consulted.

- `firstname`, `lastname` and `company` have no `config/field_policy.yaml` entry and take the
  engines' `fill_blank_only`/80 default, so they stop overwriting a non-blank HubSpot value on
  an UPDATE row. A CSV correcting a misspelled first name will no longer apply.
- `jobtitle` is `stale_refreshable`, and that branch is blank→promote, else→`needs_review`
  today (the TTL is plan 04's work). So a differing `jobtitle` on an UPDATE row now routes to
  review rather than applying. F71-5's "provider jobtitle replaced the CSV jobtitle" was the
  PLUGIN's `merge_enriched` rule, not this lane; the lane only applied it because it merged
  against `{}`.

Both are the policy behaving as written (D-72-02 makes `field_policy.yaml` the single source),
but the operator ruled explicitly on the `jobtitle` case in F71-5 and may want a different
answer. Record both in the SUMMARY as explicit "operator, confirm this is intended" items and
add them to plan 08's read-back list. Do NOT change a policy default to work around either.

Output: the alias flip, the `existingRecord` wiring, the `mobilephone` candidate, a new
walker test proving both directions over the committed JSON, and a recorded inventory of
which regenerated workflow bodies changed (the seed for D-72-21's deploy set).
</objective>

<assumption_delta_decision>
**Signal:** `pluralization` — "multiple email / phone / mobilephone values are acceptable",
"additional" (`hs_additional_emails` / `hs_additional_domains`).

**Noun now primary:** a contact's phone/email is a *set* of observed values, not a single value.

**Decision: `add-alongside`** — the primary slot (`phone`, `mobilephone`, `email`) stays
primary and is what every existing consumer reads; a single capped `_2` slot holds the
runner-up by `config/source_registry.yaml` trust rank (D-72-12); a third value lives in the
provenance JSON only (D-72-11 forbids `_3`, ever).

**Rationale:** HubSpot's own schema is single-valued per property, and every downstream
consumer (sequences, lists, the operator's views) reads the primary slot. Promoting "the set"
to primary would mean inventing a repo-side multi-value representation with no HubSpot
counterpart — a second source of truth for a fact HubSpot stores singly.

**Accepted debt:** the tail beyond two values is queryable only by reading the provenance
blob. **What would force a promote:** a live case where a third value is operationally needed
(already recorded as a Deferred Idea in `72-CONTEXT.md`); at that point the `_3`/multi-value
question reopens rather than being answered by adding one more slot.
</assumption_delta_decision>

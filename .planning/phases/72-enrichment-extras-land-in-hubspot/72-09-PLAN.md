<objective>
Close gap G1 (D-72-04 / D-72-17, review WR-01, live finding F72-1): a `linkedin_url` value on
an ingest CREATE row is silently withheld from HubSpot because `MERGE_CONTACTS` derives
`confidenceByField` and `sourceByField` from `row.source_by_field`'s own key vocabulary
(post-alias: `linkedin_url`) while building the merge candidate under the renamed keys
(`lv_linkedin_url`, `hs_linkedin_url`). The lookup in `mergeContacts()` never finds an entry,
falls back to the flat `csv`/80 confidence, and `fill_blank_only @ 85` withholds the value even
into a blank field.

Fixed at the ONE place the rename happens — the candidate-alias map inside `MERGE_CONTACTS` —
read by BOTH the confidence/source derivation and the candidate builder, so the two halves can
never again disagree about what this field is called. Not fixed in callers: `preingest.py`'s
alias table (D-72-19) is correct and stays untouched, and `columnMap.js`'s canonical vocabulary
(`linkedin_url`) is load-bearing for `required_identity.any_of` and stays untouched.

Purpose: LinkedIn is one of the five field categories the phase goal names; the canonical
property currently does not reach a created contact.
Output: a corrected `MERGE_CONTACTS`, a fixture that reproduces the real production key
vocabulary, and the two regenerated ingest workflows.
</objective>

<objective>
Give the second phone, the second mobile and the second email somewhere real to land, and
stamp every one of them in the provenance blob rather than in a fan of new properties.

Purpose: the waterfall regularly returns two different mobiles or two different work emails for
the same person. Today the trust-rank winner takes the slot and the runner-up is discarded
silently — paid for, then thrown away. D-72-11 caps the answer deliberately at ONE overflow
slot per kind: a fixed schema the operator can see in a HubSpot view, with the tail in the
provenance JSON, rather than an unbounded set of properties nobody maintains.

**Two portal facts must be checked live before the code that depends on them is written.**
`72-CONTEXT.md` records `hs_additional_emails` as writable, verified 2026-09-12. This repo's
own 2026-08-26 property export does not contain that property at all, and HubSpot's community
reports it as read-only via the standard v3 API on other portals. The same doubt applies to
`hs_additional_domains` on companies (plan 06's concern, probed here in one pass). These are
read-only API calls and are permitted; only ARMING a write is blocked. Task 1 runs them, writes
the verdict to a committed artifact, and each dependent behaviour has a stated fallback so the
plan cannot stall on an unavailable credential.

Output: a probe verdict artifact; three property declarations added to
`config/hubspot_properties.yaml` for the existing sync tool to create at the gate; winner/loser
slot routing driven by the trust ranks the engines already sort by; and provenance entries for
every landed slot under the correct per-object key.
</objective>

<objective>
Close the plugin-side half of the drop: the provider's LinkedIn value stops being filtered out
by a name mismatch, a CREATE row takes the researched value over the operator's stale
spreadsheet cell, and a held row keeps the extras a later create will need.

Purpose: three separate mechanisms currently lose paid-for data before dispatch.
(1) The waterfall's promotable name is `lv_linkedin_url`; the CSV canonical name is
`linkedin_url`. They are different strings, so widening `canonical_props()` cannot make them
meet — D-72-19 reconciles them inside `merge_enriched` (Option B, the smaller diff; Option A's
second canonical column cascades into the identity rules and the lane wrapper).
(2) `merge_enriched`'s fill-not-overwrite rule keeps a CSV cell over a provider value for every
field except `jobtitle`. On a CREATE — where there is no HubSpot record to protect and the
spreadsheet cell is often the operator's guess — that is the wrong default (D-72-05).
(3) `held_queue.ROW_FIELD_ALLOWLIST` admits `mobilephone` and `lv_linkedin_url` but excludes
`seniority`, `lv_persona_group` and the five location keys. Its own comment gives the reason:
"none is named in F2-1, none is needed by a create." D-72-01 and D-72-15 now falsify the second
clause — a create through the held/resume route is exactly what D-72-17 reads back. The
rationale flipped; it is not being overridden.

Output: a one-entry alias table, an additive `create_row_ids` kwarg with both call sites
passing it, a widened held-row projection, and behavioural tests proving the strip is inert.
</objective>

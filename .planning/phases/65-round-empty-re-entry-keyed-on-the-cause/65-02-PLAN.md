<objective>
Close RICH-04: audit `merge_enriched`'s keep/replace rule for a CREATE row and stop the seam
silently dropping the fields the waterfall actually returned.

Purpose: on an all-blank CREATE row the round discovered `Head of Marketing and Content` and

allowlist — `merge_enriched` filters the waterfall's `properties` map through

the waterfall's promotable output is the 12 contact keys of `field_policy.yaml`. Nine of those
twelve are dropped before the fill-versus-conflict rule is ever consulted.

Output: a policy-derived widening of the merge allowlist, the boundary strip that keeps the
widened keys out of the dispatch CSV, both callers traced and asserted, and a named pending todo
for the second root cause this phase deliberately does not build.

## Findings the plan is built on (verified this planning session — read before starting)

1. **`operator-claude-plugin/config/field_policy.yaml` does not exist.** The orchestrator's
   ruling names that path; the only copy in the repo is **`config/field_policy.yaml`** at the
   repo root (`git ls-files -- config/field_policy.yaml` returns it; the plugin's `config/`
   directory holds `column_mapping.yaml`, `company_column_mapping.yaml`, `cost_rates.json`,
   `operator.local*.json`, `role_vocabulary.yaml`, `source_allowlist.yaml` and nothing else).
   65-RESEARCH.md quotes the plugin path; it is wrong about the location and right about the
   contents.
2. **The installed plugin does not contain the repo root.** `.claude-plugin/marketplace.json`
   ships `source: "./operator-claude-plugin"`. In an operator's installed tree the repo-root
   policy file is absent, so a repo-root-only lookup resolves to nothing and the RICH-04 fix
   would be **inert in production**. This is why Task 1 ships a plugin-local copy pinned to the
   repo source by test — the same shape the plugin already uses for `column_mapping.yaml`, and
   the reason `preview.resolve_mapping_path` exists at all ("the plugin's own shipped copy, then
   the repo's (dev checkouts)").
3. **No shared public policy loader exists.** `scripts/review_queue.py` has `_load_policy` /
   `policy_class`, but it is private, module-cached, hard-wired to `REPO_ROOT`, and bound by its
   own D-06/D-07 rule that the read is DISPLAY-ONLY. Reaching into it would import `requests`
   and `config_gate` into the merge path and would reach into another module's private name —
   which `preingest._present`'s own docstring says this module deliberately does not do. A new
   public loader in `preingest.py` is the correct home; `review_queue` is left untouched, so its
   own repo-root-only lookup and its display-only degradation are unchanged.
4. **The widened keys WOULD break the dispatch CSV.** `enrich-before-ingest/SKILL.md` step 7
   passes `merge_report.rows` through `extraction.hold_emailless` and `extraction.strip_row_id`
   into `extraction.write_dispatch_csv`, whose STRUCT-01 guard raises
   `non_canonical_key_in_row` for any key outside `canonical_props()`. A widened key therefore
   needs the same treatment `row_id` already gets: it rides the row through every stage and is
   removed by a NAMED strip at the one CSV boundary. A blanket "drop anything unknown" is
   refused — it would blunt STRUCT-01, which the 2026-08-29 operator ruling already declined to
   weaken for `row_id`.
5. **The `suggest-contacts` caller does not reach a CSV of its own.** Its block ends at
   `extraction.validate`, which reports a non-canonical key in `dropped_keys` and still accepts
   the record; its final dispatch goes through `enrich-before-ingest`'s step-7 block, so the one
   strip site covers both callers.
6. **`tests/test_preingest_merge.py::test_every_merged_row_key_is_in_canonical_props_or_row_id`
   asserts the invariant this plan changes** (line ~233: `allowed = set(extraction.canonical_props())
   | {"row_id"}`). It passes today only because its response carries no widened key; it must be
   broadened and re-pointed at the new allowlist rather than left as a stale claim.
7. The widened keys are kept for the report, the held-row path and Phase 69's future decline
   entries — **they do not reach HubSpot through the dispatch CSV**, whose header is the ingest
   lane's own column map. The SUMMARY must say so plainly.

## P1 — Revenue unit inversion

**Suspected:** ZoomInfo GTM returns `revenue` in THOUSANDS; Apollo/Lusha in dollars. The
2026-07-30 finding (`memory/provider-firmographic-units.md`) was that raw pass-through banded
every ZI company 1000x low.

**Current code (`n8n/code/normalizeProviders.js:404-415`, inlined into "Normalize + Score
Company"):**

```js
// UNITS: GTM `revenue` is in THOUSANDS, not dollars — confirmed live against three
// records (Racing NSW 268163 + revenueRange "$250 mil. - $500 mil."; ZoomInfo 1254000
// + "$1 bil. - $5 bil."; FanDuel 14050000 + "Over $5 bil."), and Apollo independently
// reports Racing NSW annual_revenue 268000000 dollars. Feeding the raw number to
// normalizeRevenueBand (which expects dollars) banded every company 1000x low —
// FanDuel's $14b read as "5-50M". Prefer the unambiguous `revenueRange` string;
// fall back to revenue*1000.
const ziRev = raw.revenueRange != null && raw.revenueRange !== ""
  ? raw.revenueRange
  : (typeof raw.revenue === "number" ? raw.revenue * 1000 : null);
_push(out, "lv_revenue_band", src, ziRev, normalizeRevenueBand(ziRev), 0.6, recency);
```

The thousands conversion **already exists**. A fix, not a live defect — the memory note predates
it (2026-07-30 vs a later commit; not dated further here, but the code is unambiguous).

**Repro** — ran the actual "Normalize + Score Company" `jsCode` (extracted from the generated
JSON, not the source file) with `node run_p1.mjs`:

```bash
node /private/tmp/claude-501/.../scratchpad/run_p1.mjs
```

```

zi-co.example -> lv_revenue_band candidates: [{"source":"zoominfo","value":"50-500M"}]
```

**Verdict: DISPROVEN — already fixed**, at `n8n/code/normalizeProviders.js:412-414`
(`zoominfoCandidates`). No action needed for Phase 40.

## P2 — Veto promotes at confidence 0

**Suspected:** `Merge Company`'s policy declares `lv_anti_icp_flag` / `lv_anti_icp_reason` as
`{ class: "veto_output", min_confidence: 0 }`, so any confidence — even the lowest a provider/judge
can emit — passes the gate's `confidence < minConfidence` check trivially and falls straight into
the `veto_output` branch, which unconditionally returns `decision: "promote"`.

**Code (`n8n/code/mergeCompanies.js:60-61`, `DEFAULT_COMPANY_POLICY`):**

```js
lv_anti_icp_flag:        { class: "veto_output",       min_confidence: 0 },
lv_anti_icp_reason:      { class: "veto_output",       min_confidence: 0 },
```

**`_gate()` (mergeCompanies.js:113-135):** `if (confidence < minConfidence)` → with
`minConfidence: 0` this is only true for a negative confidence, which never occurs — so the
threshold is a no-op for this field, and any confidence reaches
`if (fieldClass === "... || "veto_output") return { decision: "promote", ... }` unconditionally.

**Repro** — called `mergeCompanies()` (the exact function inlined into the deployed "Merge
Company" node — extracted, wrapper tail stripped, library slice re-executed directly) with

Confirmed exactly as suspected: a confidence-5 (or confidence-0) candidate for
`lv_anti_icp_flag`/`lv_anti_icp_reason` promotes straight to `canonicalPatch` with
`validation_status: "provider_only"` — no `needs_review`, no escalation marker, even the reason
string is copy-pasted from the generic system-owned branch ("passed confidence threshold" — false;
0 is not a real threshold). Control: the same confidence against `lv_is_hardware_vendor`
(min_confidence 85) correctly gets `needs_review`, so the gate mechanism itself works — the bug is
narrowly the `min_confidence: 0` policy value for these two fields.

**But — is this candidate ever actually built?** `ENRICH_MERGE_CO` (the "Merge Company" node's
n8n wrapper, `scripts/build_cloud_workflows.py:2397-2512`) constructs exactly two candidate
objects and passes them to `mergeCompanies()`:

1. The waterfall candidate: `["domain", "industry", "lv_revenue_band", "lv_employee_band",
   "lv_country_region_normalized"]`
2. The Claude-web-research candidate (`researchData`): `["lv_org_type", "lv_produces_content",
   "lv_content_type", "lv_is_hardware_vendor", "lv_is_gambling_operator",
   "lv_sponsorship_reliant", "lv_country_region_normalized"]`

**`lv_anti_icp_flag` and `lv_anti_icp_reason` are not in either list.** No caller anywhere in
this workflow ever supplies those keys to `mergeCompanies()` — the policy entry is declared but
dead. This is not my inference alone: the repo already has a test asserting exactly this
(`tests/test_cloud_companies_branch.py::test_company_canonical_patch_never_contains_a_derived_icp_output_field`,
docstring: *"mergeCompanies.js's DEFAULT_COMPANY_POLICY still declares lv_anti_icp_flag/
lv_anti_icp_reason as veto_output classes — dead policy entries, since no candidate ever supplies
those keys — this test targets the reachable surface, not the unreachable policy declaration."*).
Ran it to confirm it's current, not stale:

```bash
.venv/bin/python -m pytest tests/test_cloud_companies_branch.py -q
# 12 passed in 0.11s
```

This is intentional design (**Approach C**, HANDOVER §5 decision 1 / §10.1): the pipeline does
not compute `lv_anti_icp_flag` at all today — HubSpot's four native workflows do (already
catalogued live in HANDOVER §10.2 F4–F7, with their own separate defects: non-ANZ match-list
misses `AU`, the flag is a one-way latch, no `geography_score` on the veto branch, etc.).

**What DOES have a live escalation guard:** the actual hard-veto **INPUT** fields
(`lv_is_hardware_vendor` / `lv_is_gambling_operator`) are guarded twice — once by their own
`min_confidence: 85` policy entry (control test above), and once upstream of `mergeCompanies()`
entirely, in `n8n/code/judge.js`'s `computeEscalation()` / `applyUnadjudicated()` (the §21.2-style
gate): any research candidate carrying `lv_is_hardware_vendor === true` or
`lv_is_gambling_operator === true` unconditionally forces `needs_judge: true`
(`judge.js:122-127`), and if the judge doesn't run or doesn't confirm, `applyUnadjudicated()`
demotes the value to `null` — **never lets an unadjudicated hard-veto input reach `true`**
(`judge.js:146-155`, comment: *"Unadjudicated hard-veto INPUT must never promote (Pitfall 6) ->
demote to null, never false."*). That guard is real and exercised on the live path.

**Verdict: PARTIAL.** The `min_confidence: 0` policy bug is real and reproduces exactly as
described when `mergeCompanies()` is called directly (`n8n/code/mergeCompanies.js:60-61`) — but it
is **currently unreachable**: no wired node ever builds a `lv_anti_icp_flag`/`lv_anti_icp_reason`
candidate, confirmed by both static analysis of `ENRICH_MERGE_CO` and the repo's own passing test.
It matters for Phase 40 **only if/when** a future change (e.g. reinstating pipeline-owned vetoes)
adds either field to a candidate list — at that point this exact `min_confidence: 0` entry would
need fixing first, or it silently reintroduces an unguarded veto write. Recommend either deleting
the two dead policy entries (so a future accidental candidate falls through to the safe default
`fill_blank_only` class instead of `veto_output`) or setting a real threshold now, before the
field is ever wired live.

## P3 — Research-lane row loss (`merge:null`)

**Suspected (memory: `companies-research-lane-rowloss.md`):** HTTP hops in the research lane
strip `existingRecord`/`scored` off the row, so `Merge Company` sees `merge:null` whenever the
research path runs.

**Topology** (read directly off `n8n/wf_enrichment_cloud.json`'s `connections` block):

```
Normalize + Score Company -> Research Trigger Gate -> IF Research Needed
  [false] ---------------------------------------------------------------> Merge Company
  [true] -> Build Research Request -> Claude Web Research (HTTP) -> Validate Research Output
         -> Judge Gate -> IF Needs Judge
              [false] -----------------------------------------------------> Merge Company
              [true] -> Build Judge Request -> Judge Call (HTTP) -> Apply Judge Verdict -> Merge Company
```

`Merge Company` has three incoming wires. Two of the three paths cross an `httpRequest` node
(`Claude Web Research`, `Judge Call`) — and n8n's `httpRequest` node **replaces** `$json` with the
raw HTTP response, which is exactly the mechanism the memory note predicted would drop
`scored`/`existingRecord`.

**But the code already documents and fixes exactly this failure mode**, at both hops:

`n8n/code/webResearch.js` (inlined into "Validate Research Output"):
```js
// --- n8n wrapper (companies): Validate Research Output ---
// ROW-RECOVERY (bug fix): the upstream "Claude Web Research" HTTP node REPLACES $json with
// the API response, so it.json here is the HTTP response — NOT the enrichment row. The
// research candidate is correctly extracted from that response, but the row itself
// (existingRecord, scored, identity_keys, gap_flag) must be recovered by paired index from
// the last pre-HTTP node ("Build Research Request"), exactly as "Normalize + Score" recovers
// provider rows via $('Company Gate'). Without this, existingRecord/scored are lost for the
// rest of the research→judge→merge lane and Merge Company returns merge:null.
const preHttp = (function () {
  try { return $("Build Research Request").all(); } catch (e) { return []; }
})();
return $input.all().map((it, i) => {
  const research_candidate = researchCandidateFromHttpItem(it.json);
  const row = (preHttp[i] && preHttp[i].json) || it.json;
  return { json: { ...row, research_candidate } };
});
```

`n8n/code/contactJudge.js`/judge apply-verdict factory (inlined into "Apply Judge Verdict"), same
pattern against `Judge Call`:
```js
// ROW-RECOVERY (bug fix): the upstream "Judge Call" HTTP node REPLACES $json with the API
// response, so it.json is the verdict response — NOT the row. ... existingRecord/scored
// never reach Merge Company (merge:null). ...
const preHttp = (function () {
  try { return $("Build Judge Request").all(); } catch (e) { return []; }
})();
```

**Repro** — ran the deployed `jsCode` of `Validate Research Output`, `Apply Judge Verdict`, and
`Merge Company` end to end for both lanes with `node run_p3.mjs`:

```bash
node /private/tmp/claude-501/.../scratchpad/run_p3.mjs
```

```
=== P3a: research SKIPPED lane (IF Research Needed -> false -> Merge Company directly) ===
merge === null ? false
merge.canonicalPatch: {"lv_revenue_band":"50-500M"}

=== P3b: research RAN + judge RAN lane (2 HTTP replacement hops) ===
after Validate Research Output: scored present? true | existingRecord present? true | research_candidate.matched: true
after Apply Judge Verdict: scored present? true | existingRecord present? true
FINAL merge === null ? false
FINAL merge.canonicalPatch: {"lv_revenue_band":"50-500M","lv_org_type":"governing_body_league","lv_produces_content":true}
```

Both lanes — research skipped, and research+judge both run through two consecutive HTTP
`$json`-replacement hops — preserve `scored`/`existingRecord` and produce a non-null `merge` with
the expected `canonicalPatch`.

**Verdict: DISPROVEN — already fixed**, via the paired-index row-recovery pattern at
`n8n/code/webResearch.js` (Validate Research Output) and the judge apply-verdict factory
(Apply Judge Verdict) referenced from `scripts/build_cloud_workflows.py:2361-2386`. The fix
comments even name the exact failure mode from the memory note, confirming this was a known bug
that has since been closed, not a re-discovery. No action needed for Phase 40.

## P4 — Veto flag written as boolean vs `"true"` string

**Suspected:** HubSpot's `EQ` search/filter operator compares as a string, so any writer that
emits `lv_anti_icp_flag` as a native JS `true`/`false` (rather than the string `"true"`/`"false"`)
would silently break every downstream filter/view/workflow-trigger that reads it.

**Step 1 — find every writer in the generated JSON.** Grepped every `n8n/*.json` for
`lv_anti_icp_flag`:

```
n8n/wf_enrichment_cloud.json         2 hits
n8n/wf_enrichment_local_live.json    2 hits
n8n/wf_review_decision_cloud.json    3 hits
n8n/wf_scheduled_maintenance_cloud.json  1 hit
```

Inspected every hit. All of them resolve to one of two things, **never a write**:

1. `DEFAULT_COMPANY_POLICY`'s `lv_anti_icp_flag: { class: "veto_output", min_confidence: 0 }`
   declaration line — `mergeCompanies.js` is inlined into "Merge Company", "Decide Company
   Action", "Build Review Decision", and "Apply Review" (they all need the field-policy table for
   other reasons), so the dead policy line appears in all four even though none of them ever
   assigns a value to the key.
2. A read-only HubSpot Search `properties` list (`"Review Fetch By Id"`, `"Review Verify Fetch"` —
   both POST-as-GET search calls) that includes `lv_anti_icp_flag` among the properties to fetch
   back, not to write.

**There is no writer of `lv_anti_icp_flag` anywhere in this repo's currently-generated n8n JSON.**
This is the same Approach-C conclusion P2 reached independently: the pipeline does not compute or
write this field today.

**Step 2 — what would the writer emit, if it existed?** The only function in this codebase
capable of producing a `lv_anti_icp_flag` value is `mergeCompanies()` (P2's repro output,
verbatim):

```
canonicalPatch: {"lv_anti_icp_flag":true,"lv_anti_icp_reason":"hardware vendor"}
```

`JSON.stringify` renders that as bare `true` — a native JS boolean, not a quoted string. Traced
the value from there forward to the actual HubSpot PATCH: `Decide Company Action` builds the
final `properties` object with a **shallow spread**, no type coercion:

```js
// scripts/build_cloud_workflows.py — ENRICH_DECIDE_CO_CLOUD (companies)
properties = { ...merge.canonicalPatch, ...(merge.cacheKeys || {}), ...(row.lusha_ids || {}) };
```

The one post-processing loop that DOES exist (BUG 27) only handles arrays
(`lv_content_type` → semicolon-joined string for multi-checkbox), never booleans:

```js
// BUG 27 (live 400 on execution 328): HubSpot v3 PATCH rejects JSON arrays —
// multi-checkbox values (lv_content_type) must be semicolon-joined strings.
for (const k of Object.keys(properties)) {
  if (Array.isArray(properties[k])) properties[k] = properties[k].join(";");
}
```

`HubSpot Company Update` (the actual PATCH `httpRequest` node) just
`JSON.stringify({ properties: $json.properties })`s whatever it's handed — no further coercion.
So if `lv_anti_icp_flag` were ever wired into a candidate (P2's "what happens if this becomes
live" case), it would ship to HubSpot as a bare JSON boolean.

Corroborating: `properties.lv_enrichment_needs_review = true;` (`ENRICH_DECIDE_CO_CLOUD`, a field
that IS live and written on every run today) is assigned the exact same way — a native JS
boolean, same gap. And this repo has already fixed this exact class of bug once, deliberately, for
a different field: `.planning/workstreams/plugin-entrypoint/phases/36-enrichment-propose-mode/
36-07-SUMMARY.md` — `lv_enrichment_requested` was changed from a boolean to the literal string
`"true"` specifically because *"the poller's HubSpot search filter is `operator: EQ, value:
"true"`; a boolean serializes to something that filter does not match, and the handoff would
silently never fire."* That is precisely the mechanism the HANDOVER's Phase 39 proposal depends on
for `lv_anti_icp_flag` (Success Criterion 4: *"that record drops out of working views regardless
of score"* — a view filter, same EQ-string mechanism).

**HANDOVER comparison (§10.1, not re-validated here per the objective's instruction):** the
four *live* HubSpot-native workflows write `lv_anti_icp_flag` via HubSpot's own "Set property
value" workflow action, not this repo's JSON — outside repo-static-analysis and outside this
validation's offline-exercisable scope. HANDOVER §10.2 F4–F7 already validated their behaviour
live; this document adds nothing there and doesn't re-check it.

**Verdict: PARTIAL.** No live pipeline-side writer of `lv_anti_icp_flag` exists today, so there is
no current boolean-vs-string defect in production traffic (**DISPROVEN as a live bug**). But the
one function that would produce the value emits a bare JS boolean with zero stringification
anywhere in its path to the HubSpot PATCH body (**CONFIRMED as a latent bug**, same class this repo
already fixed once for `lv_enrichment_requested` in 36-07). If Phase 40 (or the Phase 39 proposal)
ever reinstates pipeline-owned veto writes, `mergeCompanies()`'s `value` needs an explicit
`String(value)` (or a boolean→`"true"`/`"false"` coercion step in `ENRICH_DECIDE_CO_CLOUD`) before
it reaches `canonicalPatch`, or the exact 36-07 failure mode repeats.

## Summary for Phase 40 planning

- **P1, P3: no action required.** Both were already fixed by the time this validation ran; the
  fixes are documented in-code with comments that name the exact failure mode the suspicion
  described (strong signal these are deliberate, tested fixes, not accidental).
- **P2, P4: no live action required today**, but both point at the **same dead code path** —
  `lv_anti_icp_flag`/`lv_anti_icp_reason` in `DEFAULT_COMPANY_POLICY`
  (`n8n/code/mergeCompanies.js:60-61`) — that would need two things fixed together before it's
  ever safely reactivated: a real `min_confidence` threshold (P2) and explicit string coercion for
  the boolean (P4). Worth flagging as a checklist item on whichever remediation path Phase 40
  picks for HANDOVER §10.3 option 1 (fix the HubSpot-native workflow chain) or if pipeline-owned
  vetoes are ever revived instead.

<assumption_delta_decision>
**Noun:** veto ownership / parity harness ("a parity harness lands alongside each fix"; "the
Geography flow's veto branch is deleted ... another writer").

**Decision:** no-change.

**Rationale:** the harness is a new verification artifact, not a new domain entity, and moving
`lv_anti_icp_flag` / `lv_anti_icp_reason` from a HubSpot workflow action to the n8n pipeline changes
*which tier writes* two single-valued properties on the same company identity — it does not
pluralize the identity model, add a second veto record, or introduce a per-source veto. One company,
one flag, one reason string (multi-reason cases join into that one string, per the oracle). No
schema or cardinality change follows from this phase.
</assumption_delta_decision>

<objective>
Move `lv_anti_icp_flag` and `lv_anti_icp_reason` onto the n8n pipeline as their sole writer (D-01,
honouring HANDOVER §5 decision 2 literally), and close the two latent bugs (P2/P4) that would
otherwise go live the moment that write exists (D-04).

This plan lands in Wave 1, before 40-05 deletes the Geography flow's veto branch, deliberately: the
pipeline must already be writing the flag before HubSpot's only current writer is removed, or the
portal is left with no writer at all.

The derivation goes in `ENRICH_DECIDE_CO_CLOUD`, not in `ENRICH_MERGE_CO`'s candidate list. That
looks like the obvious spot because `mergeCompanies.js` already declares a `veto_output` policy
class for exactly these two fields, but 40-RESEARCH.md Pitfall 4 documents why it is the wrong
shape: the policy class expects a provider-supplied candidate, while the veto is derived from three
already-merged fields on the same row, which are only known after `mergeCompanies()` has run.

Purpose: one veto writer, deriving from the same branch the parity oracle uses, so drift between
HubSpot and `compute_icp_score` is structurally impossible for the veto.
Output: a hardened policy table, a ported derivation block, regenerated workflow JSON, an extended
test, and the operator refresh procedure D-02 requires be written down.
</objective>

# Phase 17 Plan 01: Transport swap + pin removal + harness reachability (offline)

## Objective

Move `HubSpot Search` and `HubSpot Fetch By Id` in `wf_enrichment_cloud.json`'s contacts lane
off the native `n8n-nodes-base.hubspot` `contact:search` node onto the credential-bound
httpRequest CRM v3 envelope transport (the BUG 10 / BUG 22 answer), drop both from the
byte-identical pin with a documented rationale, and close the harness gap so the offline
suite can tell a 0-hit search from a stopped chain.

This plan makes NO live call and deploys nothing. Plan 02 is the live canary; nothing here
is proven until that runs.

## Context (what exists, what changes, why safe)

**What exists.** `build_enrichment_cloud()` emits both nodes as native
`n8n-nodes-base.hubspot` `resource: contact, operation: search`. That operation genuinely
exists (unlike BUG 10's `company:search`) and genuinely returns the record on a hit — which
is why every enrichment contacts execution ever run (8–15, 19, all against contact 201 or
another existing record) passed. On ZERO hits the native node emits ZERO items and n8n stops
the chain there; established live by execution 22 on the ingest lane (BUG 22). Consequences,
per `.planning/debug/bug-23-enrichment-contact-nomatch-chain-stop.md`:

- an event for an email with no HubSpot record dies at `HubSpot Search` — `Enrichment Gate`
  never runs, `action: "create"` is structurally unreachable;
- a bare event for a deleted/nonexistent object id dies at `HubSpot Fetch By Id`, making
  `adaptFetchById.js`'s 0-result / `lookup_failed` branch dead code for the exact case it
  exists for.

**What changes.** `_hs_http_search_node()` (today companies-only by a deliberate hard-fail)
gains a resource→URL table so it can also emit the contacts endpoint; both nodes are rebuilt
through it. Node NAMES are unchanged, so `NODE_CREDENTIAL_MAP` binds them exactly as before
(`hubspotAppToken` / `LV HubSpot`) — no deploy-script change is needed, and the fail-closed
unmapped-credential guard stays untouched.

**Why safe.** Nothing downstream needs new code. `ENRICH_ADAPT_SEARCH` already parses the
`{total, results}` envelope branch first, and already maps `item.error || item.json.error` to
`lookup_failed: true` (the BUG 22 item-error mapping — an httpRequest node with
`onError: continueRegularOutput` delivers a failure as an item, not a node error).
`adaptFetchById.js` parses the same three shapes and maps 0-results on a known
`hs_object_id` to `lookup_failed: true` → gate override `create` → `skip`. The real fix is
item alignment: both adapters pair rows to responses by index (`search[i]`, `fetched[i]`),
which only holds when the transport emits exactly one item per input row — which the envelope
transport does and the native node does not.

**Blast radius, checked.** After the swap `wf_enrichment_cloud.json` contains ZERO native
HubSpot nodes. Three native nodes remain elsewhere (`SJ-1 Set Requested`,
`SJ-2 Set Requested` = `company:update`; `Dedupe Search (candidate contacts)` =
`contact:search`), so the vacuity guards in `tests/test_hubspot_native_operation_validity.py`
still have something to look at. `Dedupe Search (candidate contacts)` carries the SAME 0-item
hazard and is deliberately OUT of this phase's fence (REACH-01 is scoped to the enrichment
lane) — record it as a concern, do not fix it here.

## Rollback

Both commits are pure repo changes; nothing is deployed. `git revert <task-2-sha> <task-1-sha>`
restores the native nodes, the pin, and the old guards in one step. If only the transport is
suspect, `git checkout <pre-swap-sha> -- scripts/build_cloud_workflows.py` and rebuild — but
then the pin removal and the new guard file must be reverted too, since they describe the
httpRequest shape (they are deliberately in the same commit for exactly that reason).

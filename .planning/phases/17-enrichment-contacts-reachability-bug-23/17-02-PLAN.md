# Phase 17 Plan 02: Dual live canary — match-path regression + create-path reachability

## Objective

Prove on the live n8n Cloud instance that (A) the contacts match path — the single most
live-proven path in the system — still matches and enriches after the transport swap, with
before/after evidence rather than an inference from a green offline suite; and (B) a genuine
no-match event now reaches `Decide Action` with `action: "create"`, write-gated. Then restore
the deployment to its disarmed state and read it back.

## Context (what exists, what changes, why safe)

Plan 01 changed the repo only. The LIVE instance still runs the pre-swap build until Task 2
deploys — which is what makes a real before/after possible, and why Task 1 must run FIRST and
must not be skipped or reordered.

Two shapes of evidence exist for the "before" half:

1. a fresh, deterministic, zero-cost baseline captured in Task 1 against the still-deployed
   pre-swap build (`providers: []`, so the diff isolates the transport and no provider
   nondeterminism or credit spend pollutes it);
2. the historical full-chain executions (8–15, 19 — contact 201, all three providers), already
   on record, which are the "enriches" half of ROADMAP criterion 3. Task 2 fires ONE post-swap
   full-chain run (`providers: ["lusha"]`, ~1 credit) against those.

Case B needs no arming: the point is that the create path is REACHED, and `Decide Action`'s
`_writeSafetyAllows()` converts it to `write_blocked` while `ALLOW_HUBSPOT_RECORD_WRITES` is
`"false"` and both allowlists are empty. The optional armed window (Task 4) exists only if the
operator wants to watch an actual create land on a throwaway record; it is **skip by default**.

## Live command conventions

Read once; applies to every command below.

- The live env is NOT exported into the agent's shell and `.env` cannot be read by the agent.
  Every live command runs in a subshell that sources it: prefix with `set -a; . ./.env; set +a;`
  and reference variables by NAME only. Never echo, print, cat or write a secret value anywhere
  — not to stdout, not to the scratchpad, not to the evidence file or SUMMARY.
- If the session's permission classifier blocks a command, hand the operator the exact command
  (prefixed with `!`) and ask for the output pasted back. Do not paraphrase, weaken or
  substitute it.
- Workflow under test: `LV Enrichment (Cloud template)`. Resolve its id by NAME from
  `GET $N8N_URL/api/v1/workflows` — 16.7 recorded `950HPb7a1GgSAIyZ`; confirm it, do not assume
  it. The other two workflows stay untouched.
- n8n Public API calls carry `X-N8N-API-KEY: $N8N_API_KEY`. Executions:
  `GET $N8N_URL/api/v1/executions?workflowId=<id>&limit=5`, then
  `GET $N8N_URL/api/v1/executions/<execId>?includeData=true`; per-node records live at
  `data.resultData.runData["<node name>"]`.
- The webhook is `POST $N8N_URL/webhook/hubspot/enrichment/event` with header
  `X-Enrichment-Secret: $N8N_ENRICHMENT_WEBHOOK_SECRET` and a JSON body.
- HubSpot reads use `Authorization: Bearer $HUBSPOT_PRIVATE_APP_TOKEN` against
  `https://api.hubapi.com`.
- Write every captured API response to the session scratchpad as a file, then analyse the file.
  Execution payloads are large; re-fetching to re-read one field is slow and invites quoting a
  different execution than the one under discussion.
- Disarmed deploy: `DRY_RUN=false ALLOW_N8N_DEPLOY=true .venv/bin/python
  scripts/deploy_n8n_workflows.py` with `ENABLE_BAKED_FLAGS` **absent entirely**.
- Search eventual consistency (knowledge-base `scheduled-lane-canary-timing`): HubSpot's
  `/search` index lags writes by ~6s to ~3min. It bites here in one direction only — a
  "no record was created" check can be a FALSE negative inside that window, so poll twice at
  least 3 minutes apart before concluding. Contact 201 is long-indexed; the fabricated canary
  address is never seeded. This lane is webhook-triggered, so the tick-predates-seed race does
  not apply.

**Payload bodies** (fixed; use verbatim, substituting only contact 201's real email):

```jsonc

  "email": "<contact 201's real email, read from HubSpot>"}]}

// A2 — bare event: no email => IF Bare Event true => HubSpot Fetch By Id
{"providers": [], "events": [{"objectId": 201, "objectType": "contact",
  "subscriptionType": "contact.propertyChange", "propertyName": "lv_enrichment_requested"}]}

// B — no-match: email present and nonexistent => HubSpot Search returns total 0
{"providers": [], "events": [{"objectId": 999999999999, "objectType": "contact",
  "subscriptionType": "contact.propertyChange", "propertyName": "lv_enrichment_requested",
  "email": "lv-bug23-canary-delete-me@lv-canary-delete-me.example"}]}
```

  no effect on the live instance.

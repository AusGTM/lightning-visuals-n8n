## Gaps Summary

**Gap 1 (criterion 1, the substantive one):** ROADMAP Phase 16.6 Criterion 1 requires "All six `company:search` nodes retrieve real records live, verified by read-back of an actual execution — not by a green offline suite." Only `HubSpot Company Fetch By Id` meets this bar. The other 5 nodes have the correct transport deployed (confirmed by API read-back of node shape, which is a real and valuable check) but have never round-tripped a real HubSpot response in an actual execution:

- `HubSpot Company Search` — same workflow, same fix, but the bare-event live run that closed BUG 10 took the *other* branch of `IF Company Bare Event`. No execution anywhere in the phase record exercises this node.
- `SJ-1 Search`, `SJ-2 Search`, `SJ-3 Search`, `Review Search` — all four live in `wf_scheduled_maintenance_cloud.json`, which has been inactive through Phase 16.10 (the most recent phase). STATE.md's own words: "both inactive workflows remain live-untested beyond their new gates."

This is not a code defect — the fix (identical transport, identical credential, same URL, differing only in filter/property list, all pinned by `tests/test_bug10_company_search_transport.py`) is very likely correct for all six given one has round-tripped successfully and the mechanism (bypassing the native node's broken operation dispatch) is generic. But the ROADMAP criterion was deliberately written to demand live execution evidence over generalization — precisely because this same debugging session found ten separate live-only defects that an offline-green suite and "the same pattern worked before" reasoning did not catch (documented in HANDOFF.json's ten-bug list). Applying that same lesson here, the honest verdict is that criterion 1 is not fully met, and the ROADMAP's "Complete — criteria 1 & 7 VERIFIED LIVE" line and the debug file's "criteria 1 and 7 are MET" both overstate the evidence for criterion 1 specifically. Criterion 7 is accurately claimed.

**Gap 2 (criterion 5, minor):** The phase never wrote a direct sentence answering 16.6-CONTEXT.md's explicit question, "do `company:create`/`company:update` share the defect? State the answer." The record is honest (never implies they are fixed or covered — the opposite bar CONTEXT set) and the underlying evidence (the RCA's read of `CompanyDescription.ts`) supports "no, they do not share this specific defect, because `create`/`update` are valid operations with real dispatch branches, unlike `search`" — but that conclusion was never written down as the direct answer. This is a documentation completeness gap, not a functional one, and does not block downstream work (16.9 later fixed and live-verified `company:update` for an unrelated pair of bugs, BUG 13/14, independent of BUG 10).

# Phase 47.5 Plan 05: Hardware-Veto Trigger (Workstream C) Summary

The hardware-vendor hard veto now fires on `lv_org_type == "hardware_vendor"` as well as on
`lv_is_hardware_vendor === true`, landed in both engines that carry the predicate in one
commit, with a table-driven parity test proving they are equal rather than inspected. No
HubSpot record was written and nothing was armed.

## What was done

### Task 1 — the decision, recorded (commit `ca87000`)

The operator decided `or-retroactive` on 2026-08-12; the decision is recorded in full at the
foot of `.planning/todos/pending/2026-08-12-hardware-veto-keys-off-an-unpopulated-boolean.md`
(commit `661691c`) and phase-locally in `47.5-C-DECISION.md`, as the plan's resume-signal
requires. The checkpoint was pre-answered by the orchestrator; no halt.

The veto widened because the boolean is suppressed **by design**, not by accident: the
research contract answers null for both vendor flags without a cited source, a `true` forces
judge escalation, the D5 fail-safe demotes an unconfirmed value back to null, and merge then
wants 85 confidence. Live census: `lv_is_hardware_vendor` populated on **1 of 66** companies;
`lv_org_type == "hardware_vendor"` on **2**. That is the same unreachable-rule class as
workstream A.

`lv_is_gambling_operator` is **answered with no work**: same shape, zero divergent records, and
it is a graduated deduction whose `graduated_deductions` entry Phase 46 D-03 already removed —
the deduction is zero either way. Recorded so it is not re-derived; no code changed for it.

### Task 2 — the predicate, in both engines, in one commit (commit `f817ec5`)

**The engine set was determined from source, not assumed.** A repo-wide grep for the reason
string `"Hardware/AV/LED vendor"` hits `config/icp_scoring.yaml` (the source of the string),
`src/icp_scoring.py`, `scripts/build_cloud_workflows.py` (→ built
`n8n/wf_enrichment_cloud.json`) and tests. **Two engines carry the predicate**, which is a
different inventory from `46-ENGINE-INVENTORY.md`'s org-type **weight-table** count (oracle +
HubSpot flow `4626124224`) — the HubSpot flows map an already-written flag to a tier and never
derive the veto (D-01). `scripts/remediate_veto_companies.py` also reads
`lv_is_hardware_vendor`, but to classify an *org type* from a research result; it is not a
scoring engine and was correctly left alone.

## Deviations from Plan

**1. [Adapted] TDD commit sequence collapsed into one commit.** Task 2 carries `tdd="true"`,
whose default flow is a separate red `test(...)` commit followed by a green `feat(...)`. The
plan's own action text and its `must_haves` both require the two engines, the built workflow
**and** the tests in the SAME commit, and threat `T-47.5-20` names a one-sided landing as the
critical risk. The plan's explicit instruction wins over the default. RED/GREEN was run
locally and observed on all three test surfaces; the result is one commit.

**2. [Noted] The parity table needed an anti-vacuity column.** As first written, the
oracle-vs-node table passed *before* the engine change — both engines agreed on the old rule,
so equality alone proved nothing. An expected-outcome column was added so a rubric that lost
the veto in both engines fails rather than passing as agreement. Worth recording because a
pure equality harness is silently vacuous whenever both sides are wrong the same way.

**3. [Deferred to operator] Task 3 (deploy + bounce) is outstanding.** `ALLOW_N8N_DEPLOY` is
operator-only and is NOT covered by D-47.5-01's arming waiver, which covers arming only. The
commands are handed over below.

## Decision: `or-retroactive`

**The hardware veto fires if EITHER trigger is true:**

```js
if (isHardwareVendor === true || orgType === "hardware_vendor")
    vetoReasons.push("Hardware/AV/LED vendor, not sports-media buyer");
```

**Retroactive: yes.** Simtech LED (`18047161864`) moves Tier B → D on its next recompute.

## Why OR rather than replacing the boolean

The change is purely **additive**, so no record can lose a veto it currently holds — there is
no regression path. It also keeps `lv_is_hardware_vendor` alive as a manual override for a
record whose org type says otherwise.

Replacing the boolean outright would have produced identical outcomes today (both current
hardware vendors carry the org type) but would silently stop vetoing any future record that
has the boolean set and no org type.

## Why the trigger had to widen at all

The boolean is suppressed **by design**, not by accident: the research contract instructs the
model to answer null for both vendor flags unless a cited source supports them; a `true`
forces judge escalation; if the judge does not run or does not confirm, the D5 fail-safe
demotes the value back to null; and merge then requires 85 confidence on top. Live census
2026-08-12: `lv_is_hardware_vendor` is populated on **1 of 66** companies. `lv_org_type` faces
none of that and is what the pipeline reliably lands — it holds `hardware_vendor` for **2**.

| Company | `lv_org_type` | `lv_is_hardware_vendor` | Veto before | Veto after |
|---|---|---|---|---|
| Supertech Electronics `15274105699` | `hardware_vendor` | `true` | fires | fires |
| Simtech LED `18047161864` | `hardware_vendor` | *(null)* | does not fire | **fires** |

## `lv_is_gambling_operator`: ANSWERED, no work

Same shape, but **zero divergent records** — no company carries
`lv_org_type == "gambling_operator"` without the boolean — and gambling is a *graduated
deduction*, not a veto, with `graduated_deductions` currently empty (Phase 46 D-03 removed it),
so the deduction is zero either way. Recorded here so the question is not re-derived later.
**No code changed for it.**

## Scope of the change

Two engines carry the veto predicate, and they move in **one commit** per Phase 46's parity
rule:

| Engine | File |
|---|---|
| Python oracle | `src/icp_scoring.py` (hard-veto block) |
| n8n `Decide Company Action` | `scripts/build_cloud_workflows.py` → built `n8n/wf_enrichment_cloud.json` |

`n8n/wf_enrichment_cloud.json` is **built**, never hand-edited. No third engine carries this
predicate: `46-ENGINE-INVENTORY.md`'s three-engine count is about the org-type **weight table**
(oracle + HubSpot flow `4626124224`), a different inventory; the HubSpot flows only map an
already-written flag to a tier and never derive the veto (D-01). A grep for the reason string
`"Hardware/AV/LED vendor"` across the repo hits exactly `config/icp_scoring.yaml` (the source
of the string), the two engines above, and tests.
`scripts/remediate_veto_companies.py` also reads `lv_is_hardware_vendor`, but to *classify an
org type* from a research result — it is not a scoring engine and is out of scope.

The reason string is unchanged, byte for byte, and keeps its third position in the join.

## Consequence for the write window

Retroactivity is **not self-executing**: Simtech is a complete record, so its veto only
recomputes if something triggers the new recompute lane on it. It therefore joins **window
#2's** allowlist as a third id — `17317184159, 15860277364, 18047161864` — in plan 06, inside
that plan's stated cap. This plan writes no HubSpot record and arms nothing (D-07: the flag is
never PATCHed directly).

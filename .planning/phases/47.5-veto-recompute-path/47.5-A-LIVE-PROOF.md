neither can reload a newly-deployed graph. `set_active` is the named vehicle, and its verdict
comes from an INDEPENDENT second GET, never from the activate/deactivate call's own echo.

1. **`lv_org_type: "hardware_vendor"` and yet the derived veto is cleared.** §10.3 of CLAUDE.md
   lists hardware vendor as a hard veto, but the record's `lv_is_hardware_vendor` is `null`
   (its provenance blob carries `"value": "true"` at confidence 65 /
   `human_review_required`, which never promoted to the canonical property). The deployed
   `Decide Company Action` keys the hardware veto on the canonical boolean, not on
   `lv_org_type`, so it derives no veto. Out of scope for this plan — it changes no data here
   — but it is a live instance of exactly the question **RECOMP-04** already owns ("the
   hardware-vendor veto's trigger field is decided and recorded with reasoning"). Simtech LED
   is a concrete worked example for that plan: canonical `lv_is_hardware_vendor` is null while
   `lv_org_type` says hardware_vendor, and the two engines must agree on which one fires.
2. **POST 1's response `match.reason` is contact-shaped.** It reads "no searchable identity —
   the row has no email, object id, or name+company pair" on a row that plainly has an object
   id and a name. `identity_keys` is populated correctly and `Decide` received the right
   `hs_object_id`, so this is cosmetic response-envelope noise on the companies branch, not a
   routing fault. Recorded rather than fixed.

## 6. What this proves — and what it does not

**Proven.** A corrected input clears a veto **on demand**, end to end, live: a record that
the gate calls `skip` — complete, fresh, valid, i.e. exactly the frozen state that made
execution 11846's correction unrecomputable — is routed into `Decide Company Action` by the
recompute intent, re-derives its veto from `existingRecord`, and the PATCH lands. This is the
outcome the project has been unable to produce since Phase 40-07.

**The frozen-COMPLETE case is proven here, not merely by inheritance.** Execution 11857's
`Company Gate` output carries the verdict `skip` verbatim, with both `_verified_at` stamps
present on `existingRecord` at `2026-08-12T06:35:58.134Z`. The stamps landed — the
`datetime` format taken from `mergeCompanies.js` was accepted by HubSpot, and had it not
been, the gate would have said `stale` and this row would be silent about the frozen case.
Plan 02's Simtech LED execution (11852) remains the proof on a *real, pre-existing* frozen
record; 11857 is the proof on a purpose-built one. Both, not one instead of the other.

**Not proven: a live D → non-D tier transition.** `assert cleared.get("lv_icp_tier") != "D"`
passed, but the two legs are 5 seconds apart (`06:35:56.440Z` → `06:36:01.627Z`) and the
disarmed rehearsal on an identical disposable read `lv_icp_tier: "Unscored"` before any veto
write. The HubSpot flag→tier flow almost certainly never wrote `D` inside that window, so the
assertion held on a tier that was never `D` rather than on an observed transition. It is a
true assertion about the end state and it was not weakened — but it is not evidence that the
tier derivation reacts to a cleared flag. Reading it as such would overclaim.

**Zero cost.** No provider, research, judge or merge node ran in either execution.

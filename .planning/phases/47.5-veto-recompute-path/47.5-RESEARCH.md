## Summary

The defect is confirmed exactly as scoped, and the fix surface is smaller than it looks. `Company Gate`
emits `action:"skip"` for a complete record; `Normalize + Score Company` drops every skipped row on its
first line; everything downstream — including the sole veto writer — never runs. Three of the four
records workstream B wants to correct are in precisely that frozen state right now, verified live: all
three carry both required fields **and** both `_verified_at` stamps dated 2026-08-08, four days inside
the 180-day TTL. [VERIFIED: live HubSpot search, this session]

The mechanism that satisfies every constraint is a **request-level recompute lane**: one new `IF` node
between `Company Gate` and `Build Company Requests`, whose true lane runs straight into
`Decide Company Action`, skipping providers, research, judge and merge entirely. This works because
`Decide Company Action` already derives the veto from `row.existingRecord` when `merge` is absent
(`properties.lv_* ?? existing.lv_*`), and because all three veto inputs —
`lv_country_region_normalized`, `lv_produces_content`, `lv_is_hardware_vendor` — are already in
`ENRICH_COMPANY_SEARCH_PROPERTIES_CSV`, so the row reaching the gate is fully determined.
Decide stays the single writer, nothing is re-stamped (which also sidesteps the D-20 clobber race), and
the run costs one HubSpot search plus one PATCH.

Two landmines shape the design and must not be re-derived by the planner. **First: the recompute intent
must NOT be a value of `mode`.** `isReturnOnly(mode)` in `n8n/code/matchProposal.js:132-136` returns
`true` for *any* string that is not `"write"` — a `mode:"recompute"` request would set
`action:"proposed"` and silently write nothing. **Second: the intent flag must be read at
request level, by node name**, exactly as `_provider_enabled_expr` reads
`$('Parse HubSpot Event').item.json.provider_enabled.<name>`. That makes the new lane's two outputs
mutually exclusive *by construction* for a whole execution, which is the property every existing
multi-inbound convergence in this graph relies on and the reason none of them has ever mis-fired.

**Primary recommendation:** add a request-level `recompute` flag to the D-18 event, an
`IF Company Recompute` node after `Company Gate` routing true → `Decide Company Action`, and a
sibling `IF Company Skip` on the false lane terminating skipped rows at `Build Response` — which
simultaneously makes the silent skip observable and fixes a latent paired-index bug. Land A, prove it
on one disposable record, then run one small window for B and C together.

### Why a "skip" produces a silent 200 and no write [VERIFIED: build_cloud_workflows.py:1883, 4712]

Two independent facts stack:
1. `Normalize + Score Company` filters the row out, so zero items leave the node and every downstream node is unreached — including `Build Response` and `Respond to Webhook`. Execution `11846` ends at exactly this node, 19 nodes, 2.4 s.
2. Even if a skip row *did* reach `Decide`, `action:"skip"` falls through `IF Company Create` (false) and `IF Company Enrich` (false) with no PATCH. The build script says so in a comment: *"a 'skip' action falls through both IFs to end"*.

So a fix must do **both**: get the row to `Decide`, and give it `action:"enrich"` so the PATCH fires.

### The veto derivation is already existingRecord-driven [VERIFIED: build_cloud_workflows.py:2801-2815]

Quoted verbatim from `ENRICH_DECIDE_CO_CLOUD`:

```js
  const existing = row.existingRecord || {};
  const region = _regionKey(properties.lv_country_region_normalized ?? existing.lv_country_region_normalized);
  const producesContent = _boolish(properties.lv_produces_content ?? existing.lv_produces_content);
  const isHardwareVendor = _boolish(properties.lv_is_hardware_vendor ?? existing.lv_is_hardware_vendor);
```

### Candidate mechanisms, with trade-offs

| # | Mechanism | Blast radius | Decide stays sole writer? | Free (no provider/Anthropic call)? | Verdict |
|---|---|---|---|---|---|
| **1** | **Recompute lane** — request-level flag; `IF Company Recompute` after `Company Gate`, true → `Decide Company Action`; gate flips `skip`→`enrich` under the flag | 1 gate edit (~4 lines), 2 new IF nodes, 4 edges. Non-recompute traffic takes a byte-identical path | **Yes** — no new writer, Decide's veto block untouched | **Yes** — bypasses providers, research, judge and merge outright | **RECOMMENDED** |
| 2 | **Gate flip only** — `ENRICH_CO_GATE` turns `skip` into `enrich` when the flag is set; no topology change | Smallest diff (~3 lines), zero new nodes, zero new edges, no multi-inbound question | Yes | **No.** Runs the full enrich path: research fires for any evidence-gated org type (`content_producer`, `gambling_operator`, `governing_body_league`, `hardware_vendor` [VERIFIED: n8n/code/taxonomy.generated.js:68-73]) — which is **Simtech, Ironman and Entain**, i.e. the motivating records. Also re-runs Merge → re-stamps `_verified_at` → re-enters the D-20 clobber race | **RUNNER-UP** |
| 3 | Pass skipped rows through `Normalize + Score` with a marker | One-line filter change… but it changes behaviour for *every* complete record on *every* webhook and on the daily SJ-3 poller, turning today's cheap exit into a full merge + write. Unrequested, and expensive | Yes | No — same research/merge exposure as #2, on all traffic | Rejected |
| 4 | Dedicated recompute workflow | Largest. Either duplicates the veto predicate (a **second writer** — explicitly forbidden) or calls the same workflow, in which case it needs #1's wiring anyway | No, or no benefit | Yes | Rejected |

**Why #1 beats #2:** the constraint "recomputing a veto from properties already on the record costs
nothing and should stay free" is not decorative. Under #2, correcting Ironman's region would spend an
Anthropic web-research call *and* re-stamp its `_verified_at`, both of which this phase's out-of-scope
list is trying to avoid. #2's only advantage — no new topology — is bought back cheaply by the
request-level-flag design in #1, which removes the multi-inbound hazard by construction.

### Pattern: request-level flags are read BY NODE NAME, never bare `$json`

The established idiom, quoted verbatim [VERIFIED: scripts/build_cloud_workflows.py:2992-2996]:

```python
def _provider_enabled_expr(name):
    """The by-node-name provider_enabled read every gate uses — reads the ROOT
    `Parse HubSpot Event` node (never bare $json, which an upstream provider's HTTP
    response may have replaced by the time a later gate evaluates)."""
    return f"$('Parse HubSpot Event').item.json.provider_enabled.{name}"
```

Use `_if_bool_expr_node("IF Company Recompute", "$('Parse HubSpot Event').first().json.recompute === true", …)`.
`.first()` (not `.item`) makes it a **request-level** decision: every row in the batch goes the same
way, so the two output lanes are never both populated in one execution — the same property
`_provider_gate_bypass_chain`'s docstring relies on when it asserts *"Normalize + Score fires exactly
once"* [VERIFIED: scripts/build_cloud_workflows.py:2964-2967].

### Where the intent flag rides

The D-18 POST body is a bare **array**, not an envelope [VERIFIED: scripts/remediate_veto_companies.py:559-569]:

`parseWebhookBody` only lifts `providers` and `mode` from a non-array body

```js

  const events = Array.isArray(body)
    ? body
    : (body && Array.isArray(body.events) ? body.events : [body]);
  const providers = (body && !Array.isArray(body)) ? body.providers : undefined;

```

Two options for the planner, both viable:
- **Per-event** `"recompute": true` on each array element. Rides the existing `...event` spread in
  `ENRICH_PARSE_EVENT_CLOUD` (`build_cloud_workflows.py:3701`) with **zero** changes to
  `providerSelection.js`. Simplest.
- **Envelope-level** `{events:[…], recompute:true}` with a one-line `parseWebhookBody` addition mirroring
  `mode`, threaded at `:3693`. Cleaner semantically; costs a shared-module edit and its test updates.

Prefer per-event unless the planner wants envelope symmetry. Either way, thread it onto the row as an
explicit named property and have both the gate and the IF read the same source.

**Trust note:** the flag is caller-supplied. That is correct — it *is* an on-demand control — and the
webhook is header-authenticated (`X-Enrichment-Secret`). But note that `COMPANIES_TARGET` has
`entry_strip_markers=False`, so the companies chain does **not** strip caller-injected row properties
(only `CONTACTS_TARGET` does) [VERIFIED: scripts/build_cloud_workflows.py:1976, 2050-2051]. A recompute
flag is a deliberate, narrow addition to an already-injectable surface, not a new hole — but the plan
should say so rather than leave it implied.

### Anti-patterns to avoid

- **Do not use `mode` for the recompute intent.** `isReturnOnly` treats every non-`"write"` value as
  return-only, so `mode:"recompute"` writes nothing and reports success — the exact silent-success
  class this phase exists to remove. Quoted verbatim [VERIFIED: n8n/code/matchProposal.js:132-136]:
  ```js
  function isReturnOnly(mode) {
    if (mode === undefined || mode === null) return false;
    return String(mode).trim().toLowerCase() !== "write";
  }
  ```
- **Do not add a second node that writes `lv_anti_icp_flag`.** Hard constraint from the context doc.
- **Do not let a recompute row with `action:"create"` reach the write.** See Pitfall 2.
- **Do not hand-edit `n8n/wf_enrichment_cloud.json`.** Build it.

## Common Pitfalls

### Pitfall 1: the paired-index bug the filter creates (pre-existing, and the fix removes it)
**What goes wrong:** providers run for **every** gate row (companies has no skip lane —
`build_cloud_workflows.py:4649-4651` says so explicitly), but `Normalize + Score Company` indexes the
**filtered** rows against the **unfiltered** provider arrays:
```js
const rows = $('Company Gate').all().filter((it) => it.json.action !== "skip");
…
    lusha: lusha[i] && lusha[i].json,
```
In a 2-record batch where row 0 skips and row 1 enriches, `rows[0]` is row 1 but `lusha[0]` is row 0's
response — one company scored off another's provider data.
**Why it happens:** the filter was added to short-circuit the skip, not to re-index.
**How to avoid:** terminate skipped rows *before* `Build Company Requests` (recommended `IF Company Skip`),
which makes the arrays align by construction and reduces the filter to a no-op.
**Warning signs:** a 2-record POST where one record is complete; firmographics that belong to the sibling.
**Status:** latent today because the ceiling is 2 and Phase 47 posted one record at a time. Record it;
do not leave it unstated.

### Pitfall 2: recompute + `action:"create"`
**What goes wrong:** a recompute POST for a record the domain/id search does not find yields
`action:"create"`. Routed to Decide with `merge` absent, the create branch seeds `domain`/`name` and a
junk company is created carrying only veto fields — BUG-19's shape
[VERIFIED: scripts/build_cloud_workflows.py:2833-2843].
**How to avoid:** the recompute lane must be reachable **only** for rows that already have an
`existingRecord` with an `hs_object_id`. Make the gate refuse: under the recompute flag, `create` →
terminate as an observable refusal, never `enrich`.

### Pitfall 3: the write-safety gate applies to recompute too
`Decide` runs `_writeSafetyAllows(action, hs_object_id, domain)` and demotes to `write_blocked`
[VERIFIED: scripts/build_cloud_workflows.py:2854-2857]. A recompute PATCH therefore needs an **armed
window** with the target ids in `TEST_RECORD_IDS`, exactly like Phase 47. That is a feature — it is what
keeps workstream B's window small and bounded — but a plan that forgets it will read a clean 200 and
no write.

### Pitfall 4: a stored read-back proves nothing
Project memory (`n8n-stored-vs-running-content.md`) and `n8n_control`'s own docstring both say it: a GET
after a PUT reads stored content. The only proof the *running* graph changed is a live execution.

### Pitfall 5: n8n multi-inbound dispatch
`Decide Company Action` gains a second inbound edge. `Merge Company` already has three and
`Build Response` has many, and the codebase's comment on `Build Response` calls the semantics
*"honest per-batch first-arrival"* [VERIFIED: scripts/build_cloud_workflows.py:4933-4935]. Every existing
convergence is safe because exactly one lane carries data per execution. The request-level flag
preserves that property. **Do not** make the recompute predicate per-row.

### Pitfall 6: the D-20 clobber race is avoided, not solved
The recompute lane never runs Merge, so it writes no `cacheKeys` and no `_verified_at` — it cannot lose
the race because it does not enter it. Do not "improve" the lane by routing it through Merge.

Five of this phase's verifications are operator-driven by nature: two live-instance windows (one
disarmed, one armed against production CRM records), a deploy-and-bounce, and two decision
checkpoints. They are verified — by recorded, quoted, independently-read-back artifacts, and by
data assertions over those artifacts that were re-run green in this pass — but not by the suites,
and they should not be made suite-runnable. An offline fake of an armed HubSpot write would prove
the wrong thing, in exactly the way the `sweep-trigger-llm-free` record documents for the scheduler.

The phase's one genuine suite gap (G1) **is** now closed, so it is not a reason for this flag.
Setting `nyquist_compliant: true` would still claim every requirement has suite verification, which
is not true and should not be made true.

### G1 — nothing guarded "no scheduled path carries the recompute intent" — **RESOLVED**

CLAUDE.md §13.0 and §19.1 state as load-bearing operational facts that the recompute lane is
**on-demand only**: *"SJ-3 and every other scheduled path still hit `Company Gate` with no
`recompute` flag, so a complete record is still skipped on a poller tick."* §13.0.2 later
generalizes the same invariant to `async_ack`, `scale_up` and `source_by_field`.

**Verified true at HEAD, and verified unguarded.** `SJ-3 Build Dispatch Event` in
`n8n/wf_scheduled_maintenance_cloud.json` constructs its event from exactly five keys —
`objectId`, `objectType`, `subscriptionType`, `propertyName`, `occurredAt` — with no request-level
flag. No test in `tests/` or `tests/n8n/` referenced `recompute` in a scheduled-lane context.

**Why it matters:** SJ-3 dispatches into the enrichment workflow, whose `Parse HubSpot Event`
spreads each event and normalizes `recompute === true`. Had a future edit added `recompute: true`
to that construction, the **daily** poller would have flipped from enrich-only to
recompute-on-every-tick — silently re-deriving and, inside any armed window, re-writing
`lv_anti_icp_flag` across up to 100 companies per tick — and no test would have failed.

**The fix:** two tests appended to `tests/n8n/sj3DispatchGate.test.mjs`, the correct home since it
already loads this workflow and exercises this lane.

1. `G1: SJ-3's dispatch event carries no request-level flag, on any row (47.5)` — executes the
   node's **real** `jsCode` against fixture rows via `new Function("$input", …)` (a bare top-level
   `return` is exactly what an n8n Code node body is, so this is the faithful harness) and asserts
   that **no emitted event object carries a key** named `recompute`, `async_ack`, `scale_up` or
   `source_by_field`. It asserts the *absence of a key*, never an exact event shape, so a
   legitimate future event field does not trip it.
2. `G1 corollary: the enrichment lane's recompute intent is strictly boolean-true (47.5)` — the
   other half of the same invariant, asserted where the normalization actually lives: even a truthy
   non-boolean must never opt a request in.

**Why it executes the node instead of grepping the file — a correction to the audit's own first
account.** The auditor reported that the single `recompute` occurrence in
`wf_scheduled_maintenance_cloud.json` is a comment. That is **wrong**: there are **six**
occurrences, and they include live code — the shared `Company Gate` jsCode is copied into this
workflow and reads the flag through a `try { $('Parse HubSpot Event').first() } catch` that yields
`false` when there is no such node, which is the case here (independently confirmed: `Parse HubSpot
Event` is **not** among this workflow's nodes). The conclusion survives the correction and is
strengthened by it — a file-level grep is red today regardless, and any grep tuned to dodge those
six is one comment-rewrite away from vacuous.

**Independently confirmed to be a real guard, not a tautology.** `recompute: true` was injected
into `SJ-3 Build Dispatch Event`'s emitted object in a temporary perturbation of
`n8n/wf_scheduled_maintenance_cloud.json`; the suite went **19 pass / 1 fail** with the intended
message (*"SJ-3's dispatch event must not carry the request-level flag `recompute`…"*). The file
was restored via `git checkout` (`git status --porcelain n8n/` clean) and the suite returned
**20/20**. Full node suite after the addition: **864 pass / 0 fail**, up from 862.

No implementation file was modified by this gap-fill — only `tests/n8n/sj3DispatchGate.test.mjs`
was appended to.

### Note (not a gap): structural guards load only the cloud workflow

`tests/test_cloud_companies_branch.py::_load()` reads `n8n/wf_enrichment_cloud.json` only, so the
"exactly one veto writer" and single-edge assertions do not cover

catch first. Recorded as a WARNING, deliberately not counted as a second gap.

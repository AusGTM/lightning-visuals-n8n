<decisions>
Five decisions taken at planning time. Implement them; do not re-litigate them.

**Decision 1 — the diagnosis is allowed to find that no node drops an item.**
`62-UAT.md`'s `missing` list frames the diagnosis as "find the first node whose output count
is 1 where its input was 2". That framing presumes a node that swallows an item. There is a
second shape that fits every observation and in which **no node's total output is ever short**:
n8n runs a node ONCE PER INBOUND CONNECTION that delivers data, so items that split at an IF
and reconverge on a multi-edge node arrive as two separate RUNS of that node, each carrying
its own subset — and a reader that takes `runs[0]` sees one subset and silently discards the
other. Under that shape every node's summed-across-runs output is 2; only run 0 is 1.

Task 1 therefore reports, per node, **the number of runs and the item count of each run**, and
may return any one of exactly three terminal verdicts:

| Verdict token | Meaning |
|---|---|
| `reader_reads_run_0` | Every node's summed output is complete; the items are split across runs and the client's reader takes run 0 only. |
| `node_drops_item` | A named node's summed-across-ALL-runs output is genuinely short of its input. |
| `inconclusive` | The stored executions could not be read (retention, credentials) and the static leg alone cannot decide. |

**The lead hypothesis, stated as a lead and not as a cause.** `reader_reads_run_0` fits all
three executions and is code-visible at both ends: `Merge Winners` has three inbound edges on
`main[0]` (`IF Contact Research Needed` false, `IF Contact Needs Judge` false, `Apply Contact
Judge Verdict`) in the committed `n8n/wf_enrichment_cloud.json`, and
`report_enrichment._first_node_items` reads `runs[0]`. In `12096` and `12098` exactly one of
the two rows had a provider email — the row WITHOUT one needs research, so the pair split at
`IF Contact Research Needed`; in `12097` neither had an email, both took the same branch, and
both survived. That is a fit, not a finding. **The observed run counts are what upgrade it**
(CLAUDE.md §13.0.3: documented n8n semantics are not evidence of as-built behaviour). If the
run counts refute it, say so and follow the evidence.

**Decision 2 — fix scope: verdict-row readers, evidence-driven, one shared helper.**
`report._node_output_items` is read through several run-0-only call sites. They are not all
the same kind of read:

| Call site | Reads | In scope |
|---|---|---|
| `watch._build_response_rows` (via `report_enrichment._first_node_items`) | the round's VERDICT ROWS — the only channel an `async_ack` round has | **yes, mandatory** |
| `report_enrichment.enrichment_row_ledger` (`Decide Action` / `Decide Company Action`) | verdict rows | yes, IF the diagnosis evidences that node splitting in the observed executions |
| `report._decide_action_ledger`, `report._write_node_items` | verdict / "this landed" rows on the CONTACT INGEST workflow | yes, on the same evidence condition; otherwise recorded, untouched |
| `report_enrichment.remaining_credits_from_response`, `watch.token_usage_from_execution` | METADATA off item 0 of one run | no — leave alone; "first" is what they want |
| `watch`'s `Parse HubSpot Event` run_id read | a node with one inbound edge, so run 0 is all of it | no |
| `scheduled_arm._sj3_ids` | already loops every run | no — it is the precedent that runs can be plural |

Add **one** helper, `all_node_items(run_data, node_name)`, in `report.py` beside
`_node_output_items` (where the traversal already lives), and swap only the sites the table
above puts in scope. Do not fork a second traversal, and do not widen speculatively: a
sibling with no evidence of splitting is NAMED in the diagnosis artifact, not edited.

**Decision 3 — the credit question is answered, and its answer is a finding, not a fix.**
7 credits for 6 rows strongly suggests a lost row still cost money. Task 1 answers it from
`Lusha Enrich`'s own per-item `billing` block in the stored executions rather than from
arithmetic on a balance delta — `62-UAT.md`'s own cost-accounting note records that a single
before/after balance pair manufactured a phantom credit in round 1. If the answer is yes, the
diagnosis says so plainly: **a row that costs money and returns nothing is the worst available
shape**, and it is worth stating even though the fix is the same fix.

**Decision 4 — the synchronous path is recorded, not repaired here.**
`Respond to Webhook` also takes one run's items, so a SYNCHRONOUS (non-`async_ack`) caller
whose rows split is exposed to the same loss through a different channel. That is a real
exposure for `enrich-records` and `contact-upload`'s enrich pass. Repairing it means changing
the workflow's topology, which (a) must be regenerated through
`scripts/build_cloud_workflows.py` and never hand-edited, (b) requires a deploy, which is the
operator's action and belongs in the UAT, and (c) cannot be verified without a live run, which
this phase forbids. So: quantify it, name the proposed backend fix, implement none of it.

**Decision 5 — no throwaway script is committed, and nothing is reproduced live.**
62-10 deleted three `scripts/uat62_*.py` diagnostics for being committed and then unreferenced.
This plan commits **no** new script: both diagnostic legs run as one-shot inline invocations
and their OUTPUT is what becomes durable, in `62-11-DIAGNOSIS.md`. Reading the executions API
is read-only and allowed; dispatching a batch to reproduce the loss spends credit and is
forbidden. If the executions have aged out or credentials are unavailable, the static leg runs
alone and the verdict is `inconclusive` — never a live re-run.
</decisions>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| n8n executions API -> the diagnosis artifact | Stored execution payloads carry real contact data (names, emails, phone numbers) returned by providers. Anything copied out of them into a committed markdown file crosses from a credentialled API into the repo. |
| n8n executions API -> the client's verdict list | `recover_async_dispatch`'s output is what the operator is told happened. A reader that silently returns a subset makes the client under-report rather than error. |
| repo `.env` -> the diagnostic invocation | `N8N_API_KEY` is read into a short-lived process. It must never be echoed, interpolated into output, or written to the artifact. |

<objective>
Two narrow backend reads/writes that the plugin-side round cannot supply for itself: per-field
provenance for a suggested contact, and the associated-contact count that makes "nobody at this
company" answerable.

Purpose: D-62-17 (reuse the live Phase 15 provenance blob, parameterise the one `csv` hardcode) and
D-62-16 (zero associated contacts). Both are deliberately the smallest possible change to the
backend — the phase boundary excludes any change to how enrichment or the write path work, and
neither of these changes either.

**This plan REGENERATES the workflow JSON and does NOT deploy it.** Nothing is armed, nothing is
bounced. Deployment is a separate operator action outside this phase.

**Supersedes RESEARCH assumption A3.** The research pass assumed a per-company
`GET /crm/v4/objects/companies/{id}/associations/contacts` and recommended a human-verify
checkpoint before locking it in. That is no longer the mechanism: `num_associated_contacts` is a
native HubSpot company property present in all ten committed portal-schema baselines under
`config/hubspot_migration/baseline/`, so the count is a plain property read on a search this lane
already performs. No associations API call, no N calls, no checkpoint needed.

Output: `sourceByField` on `mergeContacts`, the `MERGE_CONTACTS` wrapper reading a round-level
source map, `num_associated_contacts` on the company search and on the response, regenerated
workflow JSON, and node tests for both.

Implements D-62-16, D-62-17.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| ingest webhook envelope → `Merge Contacts` | The round-level source map arrives over the authenticated webhook and decides what provenance a written contact carries. |
| HubSpot company search response → row → response projection | Portal data crossing into a value the plugin uses to decide where to spend. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-62-16 | Spoofing | a caller supplying a source map that mislabels provider data as `claude_web` (or the reverse) | medium | mitigate | The webhook is header-authenticated (the ingest `Webhook Trigger` uses `headerAuth` on the shared credential); the map only labels provenance and cannot change which fields promote — the merge gate is unchanged. |
| T-62-17 | Tampering | a suggestion source map leaking onto ordinary CSV uploads | high | mitigate | The map is read by node name from the envelope with a try/catch defaulting to an empty map, and a node test asserts the absent case produces a blob identical to today's flat-`csv` behaviour. |
| T-62-18 | Repudiation | an unread contact count read as a real zero, sending the round to spend on a company that already has people | high | mitigate | `Build Response` stamps `null` explicitly rather than omitting the key, and the plugin's `eligibility` tri-state (plan 62-01) branches on readability before magnitude; both halves are pinned by tests. |
| T-62-19 | Elevation of Privilege | a read-field addition becoming a write | high | mitigate | `num_associated_contacts` is a native read-only HubSpot rollup added only to a search `properties` list and a response projection; no PATCH body anywhere in this plan changes, and the acceptance criteria grep the search body and the response only. |
| T-62-20 | Denial of Service | a regenerated workflow deployed unreviewed | medium | accept | This plan regenerates and commits JSON only; deployment and arming are explicitly out of scope and remain an operator action, matching Phase 61's disarmed-only close. |
</threat_model>

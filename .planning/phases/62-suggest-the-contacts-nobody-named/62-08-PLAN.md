<decisions_recorded>
The UAT's `missing` list leaves three things open. They are decided here so no executor
re-litigates them mid-task.

## Decision 1 — WHERE `build_rows_spec` is called: ONCE, at the batch level, between stage 1 and stage 2

The round is per company (steps 5-6 loop), but ids must be minted once for the whole batch, and
`build_rows_spec` REFUSES a row that already carries one. So it cannot be called per company and
again for the batch. It is called **exactly once, after every eligible company's stage 1 has
finished and before the first stage-2 call** — the head of step 7.

Why there and nowhere else:

- **Not per company.** `build_rows_spec` mints `row-1`, `row-2`, … by position over the list it
  is given. Called per company, it would mint `row-1` for the first person at EVERY company, and
  `classify_matches`/`merge_enriched` would join two different people onto one id with no error.
  That is the exact failure `build_rows_spec`'s own docstring says it exists to prevent, and it
  is worse than the refusal being closed here: a wrong answer rather than a stop.
- **Not inside `synthesise_rows`.** That function asserts its rows carry only canonical props,
  and `row_id` is deliberately not canonical (`extraction.strip_row_id` exists precisely because
  it is a plugin-internal join key). Minting there would make the assertion a lie and would put
  the mint back inside a per-company call.
- **Not inside `extraction.validate`.** Step 8 places `validate` after stage 2, which is correct
  and stays — see Decision 3.

## Decision 2 — the round keeps a per-row provenance sidecar, so BOTH re-joins are code, not prose

`synthesise_rows` returns `records` (`record_type` / `row` / `provenance`). `build_rows_spec`
returns FRESH row dicts, and `merge_enriched` also returns FRESH rows ("Never mutates an input
row"). So there are TWO points where the round's `records` can silently fall out of step with
the rows the machinery is actually carrying:

1. after the mint — the records' rows have no `row_id`, so nothing can be joined back;
2. after the merge — the records' rows have no enriched email, so `partition_for_dispatch`
   would HOLD every row the waterfall had just filled, and the report would tell the operator
   nothing was found when everything was.

The second is a quiet wrong answer of exactly the class this phase keeps hitting, so both joins
become named, tested functions in `suggest_contacts.py` rather than two hand-written lines in a
worked example an LLM copies. Neither re-implements anything: `mint_row_ids` calls
`preingest.build_rows_spec` (D-62-01's call-it-never-rebuild-it discipline, applied to the mint
site the way it is already applied to the ladder), and `rejoin_enriched` joins on the `row_id`
`merge_enriched` already keyed its own walk on.

## Decision 3 — step 8's ordering claim is CORRECT and stays; the mint is what was missing

The UAT notes that step 8 places `extraction.validate()` after stage 2, "so even if validate did
mint an id it would arrive too late". Reconciled: `validate` was never going to mint one and must
not — the mint is `build_rows_spec`'s, at the batch level (Decision 1), and it now happens before
stage 2. With the mint inserted, `validate`'s position after stage 2 is right and unchanged: it
checks identity and provenance on the row as it finally stands, once per sendable row (D-62-10 —
the round has no second confirmation gate, so validate is a check, not a decision point).

One consequence to state rather than discover: `row_id` is not a canonical prop, so
`extraction.validate` reports it in `dropped_keys` and accepts the record. That is the existing,
intended treatment of a plugin-internal join key — `extraction.strip_row_id` is the boundary
strip, and it belongs before `write_dispatch_csv`, not before `validate`
(`enrich-before-ingest/SKILL.md` step 7 already places it there). Nothing about that changes
here.

## Decision 4 — the fenced block documents the spec handoff; it does NOT re-document the grant/arming dispatch

The block gains the mint, the ceiling and `plan_chunks`, and then hands `plan` to
`enrich-before-ingest/SKILL.md` step 5's dispatch block by reference — as step 7's prose already
says it does ("builds no second dispatch path"). Copying forty lines of grant, arming, ceiling
and closure machinery into this skill would be a SECOND copy of the send discipline, which this
repo refuses on principle (CLAUDE.md §13.0.1's one-implementation rule, the same reasoning behind
D-62-08). The composition test drives one call further than the block documents — through
`chunking.dispatch_plan` with a stub transport — because the ACCEPTED chunk is the property
G-62-4 is about, and more coverage than the census demands is never a problem.

| stage-2 provider response -> the round's own records | The merge back onto the round's records is a join, and a wrong join attributes one person's contact details to another. |

## Decision 1 — the equivalence rule, stated so it cannot over-match

Two URLs are on the same host when their **canonical authorities** are equal, where the canonical
authority is: the `netloc` from `urlsplit`, casefolded, with a single leading `www.` label removed
**only if what remains still contains a dot**.

Worked against the cases that matter:

| a | b | verdict | why |
|---|---|---|---|
| `www.gladstoneturfclub.com.au` | `gladstoneturfclub.com.au` | SAME | the measured case, both directions |
| `gladstoneturfclub.com.au` | `evil.gladstoneturfclub.com.au.attacker.tld` | DIFFERENT | stripping `www.` changes neither; the strings differ |
| `gladstoneturfclub.com.au` | `board.gladstoneturfclub.com.au` | DIFFERENT | a subdomain is not the apex; only the `www.` label is special |
| `www.x.com:8080` | `x.com:8080` | SAME | the port travels with the authority |
| `www.x.com:8080` | `x.com` | DIFFERENT | a different port is a different authority |
| `www.com` | `com` | DIFFERENT | stripping would leave a dotless authority, so nothing is stripped |
| `www.www.x.com` | `www.x.com` | DIFFERENT | exactly one label is stripped from each side; conservative on purpose |
| `https://x.com` | `http://x.com` | SAME | unchanged — scheme was never part of the comparison |

Deliberately NOT done: no public-suffix list, no registrable-domain computation, no other
"equivalent" label (`www2`, `m`, `web`), no host-variant retry, and no DNS. A public-suffix
library would be a new dependency and a new attack surface for a one-label problem; the
one-label rule is the whole of the operator's ruling.

**The refusal message is untouched.** It still names both raw hosts, which is what made this
diagnosable in one read — it simply stops firing for the apex/www pair.

**The change lands in `same_host` itself, not at either call site.** That is the one predicate
`filter_candidates` and every caller route through; a per-lane copy would be a second
implementation of a security rule, which is precisely what this repo refuses (CLAUDE.md §13.0.1,
D-62-01's called-never-rebuilt discipline for this very module). It therefore also fixes
`contact-upload`'s URL adapter, which has the identical problem for an operator who pastes an
apex link at a `www`-canonical site — an improvement on that lane, and its prose is updated to
say so rather than left silently stale.

## Decision 3 — what "redirects accepted" means, given `web_fetch` hands the redirect back

The native `web_fetch` returns a cross-host redirect to the caller rather than following it, so
"accept redirects" cannot mean "follow them" — nothing in this codebase follows anything. It
means: **a redirect target is treated as one more candidate URL and goes through the same guard.**

- A redirect from `www.` to the apex of the same host (or the reverse) now passes `same_host` and
  may be fetched. That IS the operator's ruling, and it needs no new code beyond Decision 1.
- A redirect to any other host is refused by the same guard, with the same both-hosts message,
  and is a result to report — never a prompt to try elsewhere (D-62-03; Phase 53's "escalating
  past a refusal turns a fence into a suggestion").
- One hop. A redirect target that itself redirects is offered back through the guard as a fresh
  candidate and spends one more of that company's five fetches
  (`url_fallback.MAX_FOLLOWUP_FETCHES`) — the budget is what bounds a chain, and no chain-follower
  is built.

This is documented in prose where the operator's agent reads it (SKILL.md step 5), not implemented
as a new mechanism.

## Known test-coverage gaps — recorded, deliberately NOT closed this round

Five adversarial host shapes are absent from this plan's test list. Each was checked against
Decision 1's rule at planning time and **none of them breaks it**, so this is a hardening gap for
a future pass, not a defect and not a reason to widen this round:

| Shape | Why it is safe under Decision 1 |
|---|---|
| trailing dot — `example.com.` | fails the equality test against `example.com`, so it falls through to REFUSED. Safe-by-default: a fetch is withheld, never granted. |
| uppercase — `WWW.example.com` | the authority is casefolded BEFORE the prefix test, so this is already handled and behaves identically to the lowercase form. |
| userinfo — `user@host` | `netloc` carries the userinfo, so the string does not start with `www.`, the prefix test fails and the pair is REFUSED unless byte-identical. |
| IPv6 literal — `[::1]:80` | never starts with `www.`, so nothing is stripped and the comparison degenerates to raw equality — the pre-existing behaviour. |
| bare IP — `203.0.113.10` | same: no `www.` prefix, raw equality, unchanged from today. |

Every one of them fails the `www.` prefix test and falls back to exact authority equality, which
is the behaviour that shipped before this plan. The gap is that none is PINNED, so a future
widening of `_canonical_authority` could change one without failing a test. Closing it is a
test-only task; add it to a hardening pass rather than to this round.

The UAT's `missing` list is deliberately not fully prescriptive. These three were decided here

## Decision 1 — WHERE the normalisation lives: at the seam, in ONE helper, used by TWO call sites

**`discovery_plan` is not the only broken caller.** `next_candidates` passes the same
`company_row["website"] or company_row["domain"]` into `url_fallback.filter_candidates`, whose
`same_host` compares `urlsplit(pasted_url).netloc` — empty for a bare domain — against each
sitemap-derived candidate's host. Every same-host sitemap URL is therefore refused as off-host.
That is the SECOND instance of the identical root cause, in the same module, and it is the rung
UAT test 1 exists to exercise: a fix to `discovery_plan` alone satisfies G-62-1's written
`missing` list and still fails the live sitting at exactly the sitemap step. One private helper
in `suggest_contacts.py`, called by both, fixes both with one rule that cannot drift between
them.

**Not inside `url_fallback` instead.** Normalising there would have to happen in `plan_ladder`
AND `filter_candidates` AND (transitively) `same_host` — three places each making the same
guess — inside a module whose whole documented character is "builds strings, guesses nothing,
host-bound in code, not by judgement". The guess belongs where the guessing is justified: at the
seam that knows the value came from a CRM property rather than from an operator's paste.

**AND `plan_ladder` refuses a host-less input** (Task 2) — see Decision 1b. After the seam fix
neither `discovery_plan` nor `next_candidates` ever trips that refusal; it exists for the future
third caller, which is precisely what G-62-1's second `missing` item asks for.

### Decision 1b — refusing does NOT break `contact-upload`, checked before deciding

`plan_ladder`'s only other caller is `contact-upload`'s URL adapter
(`skills/contact-upload/extraction.md` steps 1-4), which runs `url_fallback.py` as a subprocess
and reads its JSON. That CLI already prints `{"ok": false, "error": ...}` and exits 1 on any
exception. Today, an operator who pastes a schemeless address into that lane gets four
unfetchable candidates and a give-up message — the same quiet wrong answer, unreported. A loud,
actionable refusal is strictly better on that lane, so `extraction.md` needs no change.

## Decision 2 — the host to build: GUARD then PREFIX, never rebuild

This is a live-fetch decision, not a formatting one: every later rung is host-bound, so the host
chosen here determines every subsequent fetch. The rule is the least-inventive one that works,
and it is a **byte-identical no-op for every value that works today** (the UAT's own ground
truth labels the two scheme-bearing forms "fine today" — a fix that perturbs them is a second
change smuggled in beside the first):

| Recorded value | Ladder is built from | Why |
|---|---|---|
| `bunburyturfclub.com.au` | `https://bunburyturfclub.com.au` | prefix only — the whole recorded value moves into the authority |
| `www.alicespringsturfclub.org.au` | `https://www.alicespringsturfclub.org.au` | `www.` preserved EXACTLY as recorded |
| `https://bunburyturfclub.com.au` | itself, untouched | already usable |
| `https://www.bunburyturfclub.com.au/` | itself, untouched | already usable |
| `http://x.com.au/about` | itself, untouched | already usable; the scheme and the path are the record's, not ours to rewrite |
| `linkedin.com/company/x` | nothing — zero candidates + a reason | fails the shared company-domain guard |
| `unknown` / `n/a` / a dotless value | nothing — zero candidates + a reason | a host with no dot cannot be a public site |

**https, and only for a value that has no scheme.** A recorded `http://` is preserved, never
upgraded — and it costs nothing on the binding axis, because `same_host` ignores scheme by
design. A missing scheme becomes `https`, matching `plan_ladder`'s own existing
`parts.scheme or "https"` default rather than inventing a second convention.

**`www.` is preserved exactly as recorded — never added, never stripped.** `same_host` treats a
`www.` variant as a DIFFERENT host and refuses it, deliberately and by standing decision
(62-CONTEXT: "Host-bound in code, not by judgement — do not loosen it"). So rewriting the host
in either direction would silently retarget every subsequent fetch AND make the site's own
sitemap URLs off-host. Whoever recorded `www.` recorded what they saw in a browser; that is the
better evidence available here, and it is not ours to overrule.

**The path is preserved too** — dropping it would delete the WordPress-REST slug rungs, which
are the rungs that actually won UAT 2.4 (9/9 directors on `gctc.com.au/board-of-directors/`).
The bogus-slug half of the defect (`bunburyturfclub.com` derived from `bunburyturfclub.com.au`)
needs no path handling at all: once `https://` is prefixed, the whole recorded value sits in the
authority and the path is empty, so `slug_of` returns `None`, the WP-REST rungs are skipped with
their existing note, and the two SITEMAP rungs are what the company gets. That is D-62-01's
sitemap-first design landing exactly on the rung it was designed for.

**The validity guard is `enrichment._clean_domain`, reused and NOT re-implemented** — the one
guard (mirrored in `n8n/code/companyLink.js`) that already knows a LinkedIn/social/profile host
is never a company's own domain, closing the live 2026-08-25 poisoned-domain defect. It is used
here as a BOOLEAN test only: its return value is never the host that gets built (it strips
`www.`, which Decision 2 forbids). `company_domain.py` already imports `enrichment` and calls
`_clean_domain` — established precedent, not a new coupling.

**What this deliberately does NOT try to fix:** an apex-vs-`www` canonical mismatch (see
Decision 3); a redirect; a stale or defunct domain; a domain recorded for the wrong company (the
survey found one); a subdomain such as `country.racing.com`, which is accepted as recorded
because it IS a host and binding to it is the conservative reading.

**Sub-decision, recorded so it is not re-argued:** the existing `website or domain` precedence
is UNCHANGED — first non-empty wins, and if that value fails the guard the company gets the
no-candidates path. The helper does NOT fall through to `domain` when `website` fails. Falling
through would silently discover against a different host than the one recorded as the website —
the same class of quiet wrong answer this gap is about — and would have to be duplicated
identically in both call sites to stay coherent. The operator instead sees a reason naming the
recorded value, and can correct the CRM.

## Decision 3 — redirects and a wrong host are OUT of scope, and the existing refusal keeps that legible

No redirect following, no host variants tried, no second attempt elsewhere: `url_fallback.py`
performs no I/O by construction, 62-VALIDATION.md's manual-verification row 1 depends on that
property, and the hard constraint on this plan forbids introducing any — including a network
check of whether a host resolves. D-62-03 and Phase 53's rule are the same: "escalating past a
refusal turns a fence into a suggestion."

**The distinguishability G-62-1 requires is already held, with zero new code.** When a
`www`-canonical site's sitemap lists `www.` URLs and the CRM recorded the apex,
`filter_candidates` refuses them with its own existing reason, which names BOTH hosts
explicitly. That reads as a host mismatch, never as "no people page". The give-up path stays
distinct from the malformed path because the malformed path no longer exists.

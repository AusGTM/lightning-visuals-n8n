<objective>
Take the run off the synchronous response window. Submit returns a handle immediately, progress
is readable while the work runs, and an interrupted run resumes or fails loudly.

Purpose: RUN-01/03/04, absorbed from Phase 55 by D-61-08. Autonomy that still holds a connection
open for roughly 100 s per two-record chunk is not autonomy — a 40-record batch is twenty
sequential held connections, and a 300-record batch is not attemptable at all.

Output: an async run shape built on the substrate 61-01's operator decision selected, with the
n8n execution cost that decision was made on.

This plan is deliberately written against a verdict document rather than against assumptions.
Task 1 exists because the alternative — improvising a different mechanism mid-execution when a
premise turns out false — is how this phase's own risk register says it fails.
</objective>

    The failure this task must make impossible is a run that silently half-completes: RUN-03
    requires resume-or-fail-loudly, and the dangerous middle is a run that reports done over a
    batch it abandoned. Make "I do not know what completed" a loud failure, never an implicit
    success — `run_manifest.load()`'s existing degrade-to-empty is the right behaviour for
    resuming (degrading to a full run costs money; degrading to a partial skip costs a contact)
    and this task must not soften it into a partial trust.

    REVIEW-08 says those two sentences contradict each other, and it is half right, so resolve
    it precisely rather than by picking a side. `load()` returns `{}` for missing, malformed,
    unreadable AND schema-mismatched alike, and `rows_to_resume` over `{}` is a full rerun
    indistinguishable from a first run. THE RESOLUTION IS TWO CONSUMERS WITH TWO RULES over one
    load, not a new raise:

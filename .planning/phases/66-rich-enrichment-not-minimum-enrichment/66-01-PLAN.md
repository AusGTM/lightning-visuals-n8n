## Read this before PATTERNS.md — three of its findings are wrong or incomplete

Measured 2026-09-05 first-hand against the working tree, before this plan was written.

1. **PATTERNS.md has the D-66-03 key direction BACKWARDS.** It instructs a `_push` under the
   `lv_`-prefixed LinkedIn key. That is the silent no-op it warns about. `ENRICH_MERGE` in
   `scripts/build_cloud_workflows.py` (search for `canonicalizeLinkedin(winners.`) already
   reads the UNPREFIXED scoreCandidates winner key, runs it through `canonicalizeLinkedin()`,
   and assigns the `lv_`-prefixed merge candidate. Its own comment says that winner key
   "stays unprefixed on the READ side ... if a provider mapper ever populates it". This is the
   identical PN-1 rename `persona_group` already uses eight lines below. **The push key is the
   unprefixed one.** Task 3 states the full chain and proves it with a test.

2. **PATTERNS.md and 66-CONTEXT.md both overstate what `REQUIRED` controls at Lusha.**
   Widening `REQUIRED` does NOT widen Lusha's reveal by itself. `n8n/code/lushaRequest.js`'s
   `lushaReveal()` filters `missingFields` through a FROZEN two-entry map; anything not an
   exact key drops out. That module's own comment names the current three-member `REQUIRED`
   list as the reason the landline is absent. The ceiling for Lusha is that MAP, not `REQUIRED`.
   There is also a HAND-WRITTEN MIRROR of the map in an n8n expression in
   `scripts/build_cloud_workflows.py` (the `Lusha Enrich` node's `json_body`, search for
   `REVEAL_MAP`), kept in step by `tests/n8n/lushaRequestContract.test.mjs`. Both copies move
   together in one commit.

3. **`decideAction` returns an EMPTY `missingFields` on a CREATE row.** Measured directly:
   `decideAction({}, ["email","jobtitle","mobilephone","phone"], {}, now)` returns action
   `create` with an empty `missingFields`. So on the exact live scenario the brief cites — an
   all-blank CREATE row at Brisbane Roar FC — the reveal list falls back to its email-only
   default and widening `REQUIRED` changes nothing at all. Task 1 fixes this.

4. **Absent from both upstream artifacts, and the highest-severity item.**
   `ENRICH_CONTACT_SEARCH_PROPERTIES_CSV` in `scripts/build_cloud_workflows.py` does not fetch
   `lv_linkedin_url` or `lv_persona_group`. That constant's own comment states the hazard
   verbatim: a property never fetched "reads as blank regardless of what is actually stored
   live, silently turning non-clobber into clobber". Landing a LinkedIn producer without
   widening that list would let a provider URL overwrite a stored one, a direct D-66-08 and
   SAFE-01 breach. Task 2 fixes it, deliberately BEFORE Task 3 widens the chase.

5. **D-66-10's parity check comes up empty, as PATTERNS.md predicted.**
   `grep -nE "REQUIRED[[:space:]]*=" src/*.py` returns exactly one hit, `src/judge.py:41`
   `JUDGE_OUTPUT_REQUIRED`, which is the judge's output-key list read from
   `config/escalation_policy.yaml` and is unrelated to any chased-field gate. No Python oracle
   carries an equivalent contacts or companies `REQUIRED` list, so the Phase 46 parity rule is
   satisfied vacuously for this change. Do not fabricate a `src/` edit to satisfy it.

6. **No RESEARCH.md and no VALIDATION.md exist for this phase.** Both were deliberately skipped
   by operator decision. Verification below is derived from 66-CONTEXT.md's own test
   obligations, not from a Nyquist validation strategy.

7. **Measured test baseline, 2026-09-05:** `node --test tests/n8n/*.test.mjs` reports 894 pass,
   0 fail. The planning brief's figure of 867 is stale.

**RICH-04 is deliberately NOT in this phase.** `REQUIREMENTS.md` originally scoped RICH-04
(`merge_enriched`'s keep/replace rule on a CREATE row) to Phase 66, but `merge_enriched` lives in
`operator-claude-plugin/scripts/suggest_contacts.py`, which `66-CONTEXT.md`'s `<domain>` explicitly
excludes — this phase is the n8n lane only. **Operator ruling 2026-09-04: re-routed to Phase 65**,

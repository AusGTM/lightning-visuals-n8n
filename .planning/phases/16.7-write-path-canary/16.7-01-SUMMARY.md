**Fixed BUG 11 offline — both HubSpot update nodes moved from a native, patch-less hubspot node to a credential-bound httpRequest PATCH that actually carries the merge's computed patch, with a red-before-green oracle that writes down the exact live PATCH Plan 02 must confirm for contact 201.**

## Accomplishments

- Discovered and proved BUG 11 offline (reading the built `n8n/wf_enrichment_cloud.json` artifact): `HubSpot Update` / `HubSpot Company Update` were native `n8n-nodes-base.hubspot` nodes with `updateFields: {}` — a well-formed node that references `$json.properties` nowhere, documented in source as a placeholder "populated at deploy/operator-config time, not baked by this builder." No such deploy-time population exists anywhere in `scripts/deploy_n8n_workflows.py`.
- Fixed it: both nodes now emit a credential-bound `httpRequest` PATCH to the real CRM v3 object endpoint, carrying `{"properties": $json.properties}`, reusing the SAME provisioned `LV HubSpot` credential via `predefinedCredentialType`/`hubspotAppToken`. Node NAMES preserved so `NODE_CREDENTIAL_MAP` keeps binding them unchanged.
- The write node deliberately omits `onError` (every other httpRequest node in this builder carries `continueRegularOutput`) — a rejected PATCH now fails the execution instead of flowing on to `Build Response` as a healthy item, closing the exact swallowed-failure mechanism that hid ten prior live-only bugs.
- Wrote an end-to-end offline oracle (`tests/n8n/writePatchBodyFlow.test.mjs`) that drives a real merge-shaped row for contact 201 through the BUILT `Merge Winners`/`Decide Action` node bodies (disarmed, then armed via an in-test textual rewrite mirroring `enable_baked_flags()`), then evaluates the BUILT `HubSpot Update` node's own `url`/`jsonBody` expressions to produce the literal outbound request — captured failing RED before the fix, GREEN after.
- `HubSpot Create` / `HubSpot Company Create` are byte-identical to their pre-16.7 form and explicitly pinned as native with UNVERIFIED live status (`ALLOW_HUBSPOT_CREATE` stays `"false"` for the whole phase).
- Rewrote three pre-existing test pins this change invalidates (never deleted): `UNCHANGED_WRITE_NODES` + the contacts byte-identical guard in `test_bug10_company_search_transport.py`, the update-target assertion in `test_cloud_write_path.py`, the create/update split in `test_cloud_companies_branch.py`.
- Re-proved every 16.5-01 invariant on the rebuilt artifact and rehearsed the deploy-time write-safety overlay (pure functions, zero network calls) — rewrite counts and both fail-safe refusals match the CONTEXT's prior dry-run exactly.

## Decisions Made

- **BUG 11 is real and is caught the same way BUG 10 was: by reading the built artifact, not by burning an armed live window.** Running Plan 02's canary against the pre-fix nodes would have written nothing to HubSpot (an empty PATCH-equivalent), making a "protected field not overwritten" claim vacuously true. This plan closes that hole before any live call is made.
- **The fix mirrors BUG 10's `_hs_http_search_node` precedent deliberately** — same credential reuse, same node-name-preservation rationale — but diverges on one point: `onError` is omitted rather than set to `continueRegularOutput`, because a WRITE node's failure must be visible, whereas a search node's failure degrading gracefully to an empty result is the correct behavior for that node.
- **Creates stay untouched and explicitly unverified.** `ALLOW_HUBSPOT_CREATE` remains `"false"` for the whole of Phase 16.7 per CONTEXT Locked Decision 2; this plan does not claim or imply coverage for `company:create` or the contacts `HubSpot Create`.
- **No use of `gsd-tools query state.advance-plan` / `state.update-progress`** — per repo memory, these corrupt `STATE.md` here; STATE.md/ROADMAP.md updates are deferred to the orchestrator per this plan's explicit instruction.

## Predicted Live PATCH for Contact 201

The literal outbound request the oracle constructs from the BUILT `HubSpot Update` node's own expressions, for the plan's seed row (existing record: `hs_object_id "201"`, `email "brendan@lightningvisuals.com"`, `phone "+61399999999"` non-blank, `jobtitle`/`seniority` blank; candidates: `email`/`phone`/`jobtitle`/`seniority` at flat confidence 85):

```
METHOD: PATCH
URL:    https://api.hubapi.com/crm/v3/objects/contacts/201
BODY:
{
  "properties": {
    "jobtitle": "Head of Broadcast",
    "seniority": "Director",
    "lv_jobtitle_verified_at": "<ISO timestamp of the run>",
    "lv_contact_enrichment_provenance": "<stableStringify of the provenance blob — includes email/jobtitle/phone/seniority entries>"
  }
}
```

Non-clobber proof embedded in this prediction: **`email` and `phone` are absent from `properties`** — `email` because its 85 confidence sits below the `manual_protected` 95 threshold (and the hard email guard demotes it regardless of class); `phone` because it is `fill_blank_only` and the existing record already holds a value (`"+61399999999"`, the protected-field probe). `seniority` (`system_owned`) and `jobtitle` (`stale_refreshable`, existing value blank) promote as expected, and the promoted field's cache-key datetime (`lv_jobtitle_verified_at`) is present.

Plan 02's real live seed row and candidate values will differ from this synthetic fixture — the SHAPE of the prediction (method, URL pattern, single `properties` key) is what carries forward; the exact field values depend on what the live providers/existing record actually return.

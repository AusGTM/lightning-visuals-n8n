  <what-built>The contact lane's create decision now reads the deploy-time-overlayable write-safety constant (23-01), and the plugin can build and send the exact multipart request (23-04).</what-built>
  <how-to-verify>
    1. Choose a disposable canary contact — an email at a domain nobody else uses — and note the
       domain. Confirm no HubSpot contact with that email exists yet.
    2. Deploy armed, naming in one `ENABLE_BAKED_FLAGS` request: record writes, create, and a
       `TEST_RECORD_DOMAINS` value matching the canary's domain. The deploy refuses if the allowlist
       is missing; that refusal is a correct outcome to record, not an obstacle to route around.
    3. Confirm by read-back that the deployed workflow carries the enabled literals — a `200` from
       the deploy is not evidence.
    4. In a Claude session, run the plugin against a one-row CSV for that canary, approve the
       preview, arm the conversation with the plugin's arming phrase, and let it dispatch.
    5. In HubSpot, confirm a contact was CREATED with that email. A row landing in the review queue
       instead means the gate fix did not take effect — record that as a failure of 23-01, with the
       execution id.

       a complete per-record ledger; this phase claims only that the POST was accepted.
    7. Redeploy disarmed and verify by read-back that the constants are back to their disabled
       literals. Delete or mark the canary contact per the repo's existing canary cleanup practice.
  </how-to-verify>

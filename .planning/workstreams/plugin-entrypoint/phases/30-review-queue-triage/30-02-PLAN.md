<objective>
Tracer: one review decision travels the whole new path end to end — an authenticated POST carrying a
rejection reaches HubSpot as exactly one property write, and the same request unarmed returns the
exact write and performs none (D-03, D-10, REVIEW-03, REVIEW-05).

Rejection is the right first path: it touches every layer (webhook, payload validation, live refetch,
decision logic, write gate, PATCH, response) while writing exactly one property, so no non-clobber
question arises and nothing can be clobbered while the path is being proved. Approve, which needs the
existing `reviewApply` compare-and-set and the human provenance stamp, lands in 30-03 on top of this
proven skeleton. Contacts routing also lands in 30-03; this tracer is companies-only.

Purpose: the existing review apply path is a 15-minute poll, which cannot satisfy Phase 28's
confirm-then-verify pattern (D-13/D-14/D-15) — there is nothing to read back for up to 15 minutes
(D-08e). That poll stays untouched as a backstop; this is a second, synchronous path.

This plan also owns the **response contract** the whole phase reads back against (D-19). A written
decision is followed by an **independent refetch** of the record — not by HubSpot's PATCH echo, which
is the same response and therefore not evidence (Phase 28 D-14) — and both branches return one shape:
`{outcome, message, would_write, verified_properties, verified}`. 30-06's `verify_decision` consumes
exactly this, so it is designed and proved here rather than assumed there.

Output: `n8n/code/reviewDecision.js`, a new `n8n/wf_review_decision_cloud.json` serving
`hubspot/review/decision`, its credential and deployable-set registrations, and a flow test that runs
the committed node code.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin client → `hubspot/review/decision` | Untrusted request body crosses here; only headerAuth stands in front of it |
| n8n Code node → HubSpot PATCH | The only place a review decision becomes CRM state |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-05 | Tampering | `Parse Review Decision` | critical | mitigate | The endpoint accepts no field/value/patch from the caller — only the record id, the decision word, and free text; the value written always comes from the record's own stored state (Task 2, Task 3 case e) |
| T-30-06 | Elevation of Privilege | `Review Decision Update Write Gate` | high | mitigate | Gated on the `review` action plus the `TEST_RECORD_*` allowlist; committed artifact disarmed (Task 2, Task 3 cases b/c/d) |
| T-30-07 | Tampering / Repudiation | rejection path | high | mitigate | Rejection writes exactly one property and never clears a review flag; asserted by key-count (Task 1) |
| T-30-08 | Spoofing | webhook auth | high | mitigate | Native headerAuth on the webhook node, bound to the existing provisioned credential — no Code node ever reads the secret |
| T-30-09 | Information Disclosure | response body | low | accept | The response echoes the record's own properties back to an already-authenticated caller that is entitled to read them |
| T-30-10 | Denial of Service | unbounded reason text | low | mitigate | Operator text truncated at the HubSpot property ceiling before it enters a patch (Task 1) |
| T-30-10a | Repudiation | response body's `verified` claim | high | mitigate | `verified_properties` comes from `Review Verify Fetch`, an independent refetch, never from the PATCH's own echo; a written decision whose refetch is absent reports `null` rather than a default-true (Task 2, Task 3 case f, D-19) |
</threat_model>

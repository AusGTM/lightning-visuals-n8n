<objective>
Complete the write path: an approval applies the record's own stored candidate through the existing,
tested non-clobber engine and stamps the decision as a human's (D-05, D-08d, REVIEW-02, REVIEW-04),
and contact records — which the dedupe sweep flags — can be worked from the same endpoint.

The non-clobber engine already exists: `n8n/code/reviewApply.js` performs the compare-and-set
staleness check, applies all held decisions or none, and leaves a drifted record queued. It is wired
into the scheduled maintenance workflow's 15-minute `Review Trigger` loop and covered by
`tests/n8n/reviewLoop.test.mjs`. This plan reuses it and leaves that loop running as a backstop
(D-08d, D-08e). What it adds is the one thing that path never did: writing `source: "human"`.

The audit stamp targets the mechanism this repo actually built (D-08a): one JSON blob per object —
`lv_enrichment_provenance` on companies, `lv_contact_enrichment_provenance` on contacts — with one
entry per field. There is no flat per-field metadata property convention in this deployment and none
is invented here (D-08b: additive merge into the existing blob, never a replacement of it).

Output: the approve branch, the human provenance stamp, the contacts route, and the tests that pin
all three.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| stored candidate JSON → canonical CRM field | The only values a review decision can promote |
| existing provenance blob → re-serialized blob | A whole-object rewrite; a bug here silently erases audit history |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-11 | Tampering | approve path field set | critical | mitigate | `manual_protected`/`review_required` policy classes are dropped before the patch is built, so a stale or forged candidate cannot overwrite a protected value (Task 1) |
| T-30-12 | Tampering | stale record | high | mitigate | `reviewApply`'s all-or-nothing compare-and-set is reused verbatim; a drifted record writes nothing and stays queued (Task 1) |
| T-30-13 | Repudiation | provenance blob rewrite | high | mitigate | Additive field-keyed overlay with `stableStringify`; untouched entries asserted deep-equal, unparseable blob degrades to empty rather than throwing (Task 1) |
| T-30-14 | Repudiation | who decided | high | mitigate | Human source, human-approved status, timestamp, operator reason and superseded source recorded per approved field (Task 1, REVIEW-04) |
| T-30-15 | Elevation of Privilege | contacts PATCH node | high | mitigate | Spliced behind a `review`-action write gate identical to the companies one (Task 2) |
</threat_model>

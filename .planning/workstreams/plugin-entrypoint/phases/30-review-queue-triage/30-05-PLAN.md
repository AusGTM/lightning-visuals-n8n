<objective>
Turn the queue payload into something a non-technical operator can actually adjudicate (REVIEW-01).
This is the load-bearing half of the phase: the writeback plumbing is worthless if the conflict is
unreadable.

Two rules shape it. The client reads `config/field_policy.yaml` display-only, to say "this value is
protected — a review decision cannot overwrite it" before the operator invests in a decision (D-06);
it never refuses locally, because a second policy authority drifts from the backend's (D-07). And it
renders only what is stored — the resolved source, its confidence, the machine's held-back reason,
the evidence link — labelled as the resolved source rather than a provider-by-provider disagreement,
because that disagreement is computed transiently during scoring and never persisted (D-08f, D-11).

Output: a plugin module that fetches the queue through the n8n read endpoint, labels protected
fields, links each record back to HubSpot, and renders the whole thing in plain language.
</objective>

    Write `operator-claude-plugin/scripts/review_queue.py` with three responsibilities and no others:

    `fetch_queue(config, object_type, transport)` POSTs to the configured n8n base URL's
    `hubspot/review/queue` path with the same header-auth convention `dispatch.py` uses, takes the
    transport callable as an injectable parameter defaulting to the real one, and returns the parsed

    existing refusal path before any network call, and never shows a secret.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| n8n response → rendered chat output | CRM text, including operator- and model-written free text, is rendered to the operator |
| operator config file → outbound request | Holds the webhook secret the client must never display |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-20 | Information Disclosure | config handling | high | mitigate | The secret is only ever placed in a request header, never rendered, logged, or echoed in a refusal message (Task 1, inherited from Phase 23's refusal path) |
| T-30-21 | Tampering | policy lookup | medium | mitigate | The lookup is display-only by construction; the module docstring and tests forbid branching on it, so no second policy authority can drift from the backend (Task 1) |
| T-30-22 | Spoofing | rendered evidence links | low | mitigate | Evidence URLs come from CRM data and are rendered as text/links only; the client never fetches them |
| T-30-23 | Repudiation | single-source rendering | medium | mitigate | The rendering discloses that it shows the resolved source, so an operator cannot mistake it for provider consensus (Task 2, D-08f) |
</threat_model>

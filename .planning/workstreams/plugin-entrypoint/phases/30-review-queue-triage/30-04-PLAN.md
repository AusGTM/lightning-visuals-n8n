<objective>
Give the operator's client one read that returns the needs-review queue with each record's stored
conflict detail (REVIEW-01), through n8n because the client holds no HubSpot credential.

This is a deliberate divergence from 30-RESEARCH.md's Open Question 3, which suggested growing Phase
27's `hubspot/backend-status` endpoint with a detail mode. Phase 27 is not built yet, so extending it
from here would couple this phase to an undecided response shape; the queue read lives in this
phase's own workflow instead, and Phase 27's status surface keeps its count-only role.

What the queue can honestly show is bounded (D-08f): by the time a field is flagged, the pipeline has
resolved to a single source and a single reason. The multi-provider disagreement computed during
scoring is never persisted, so the payload carries the resolved source, and 30-05 says so in words.
Persisting the disagreement is recorded as deferred, not assumed.

Output: a second webhook path on the review workflow, returning per-record: identity, the held
candidate decisions, the provenance blob, the machine's review reason, the ICP narrative fields, and
the queue total.
</objective>

    Add a second webhook to `build_review_decision_cloud()`: `Review Queue Webhook`, httpMethod POST,
    path `hubspot/review/queue`, authentication headerAuth, responseMode responseNode — same auth
    convention as the decision webhook, since n8n Cloud webhooks in this repo are POST with header
    auth regardless of read or write intent.

    Chain: `Review Queue Webhook` → `Parse Review Queue Request` (Code; accepts only `object_type`,
    defaulting to companies, and an optional `limit` clamped to a sane maximum) → `Review Queue IF
    Contacts` → one of `Review Queue Search` (companies) / `Review Queue Contact Search` (contacts) →
    `Review Queue Rows` (Code) → `Respond Review Queue`.

    Both searches filter on the needs-review flag being true; the companies search adds a second
    filter GROUP on the ICP needs-review flag so either condition surfaces the record (groups are
    OR-ed). Companies request: identity (record id, name, domain), the held-candidate JSON, the
    provenance blob, the machine-written review reason, the review-approved flag, and the ICP
    narrative properties (tier, score breakdown, anti-ICP reason, ICP needs-review). Contacts request:
    record id, email, first and last name, company, the contacts provenance blob, the review reason
    and the review flags.

    `Review Queue Rows` adapts the search envelope the way `ENRICH_EXTRACT_SEARCH_ROWS` does but also
    carries the envelope's total onto every emitted row, and stamps `object_type`, so a truncated page
    is visibly a page. It parses nothing and computes nothing — the candidate JSON and provenance blob
    are passed through as the strings HubSpot returned, and the client parses them (D-11: the queue
    renders stored data, it does not recompute it).

    Register `Review Queue Webhook`, `Review Queue Search` and `Review Queue Contact Search` in
    `NODE_CREDENTIAL_MAP` — the webhook under the header-auth webhook credential, the searches under
    the provisioned HubSpot app-token credential.

    No node on this path may write. Do not splice a write gate here and do not connect this branch to
    either PATCH node.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin client → `hubspot/review/queue` | Untrusted request body; headerAuth is the only gate |
| HubSpot search results → response body | CRM data leaves the credential boundary here |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-16 | Elevation of Privilege | queue branch wiring | high | mitigate | Structural reachability test asserts no write node is reachable from the queue webhook (Task 2) |
| T-30-17 | Tampering | `Parse Review Queue Request` | medium | mitigate | Only `object_type` and a clamped `limit` are read from the body; no filter, property list or record id is caller-supplied |
| T-30-18 | Information Disclosure | response payload | medium | accept | The endpoint returns CRM fields to an authenticated caller that exists to read them; auth is the control, and no secret or credential material is in the payload |
| T-30-19 | Denial of Service | unbounded page size | low | mitigate | `limit` clamped server-side to the search node's maximum |
</threat_model>

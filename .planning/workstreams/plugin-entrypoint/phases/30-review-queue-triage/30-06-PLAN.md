<objective>
Give the operator the decision half of the loop: adjudicate a flagged record conversationally, see
exactly what would be written, and — only behind a review-specific session arm — write it and have
the result verified rather than assumed (REVIEW-03, REVIEW-04, REVIEW-05).

The exact-write display is not a client-side reconstruction of the merge. The endpoint computes the
patch and, unarmed, returns it without writing (D-03, D-05) — so what the operator approves is
literally what the backend would send, and no second copy of the merge rule exists in the plugin
(D-07). Arming is session-scoped and held in memory only, so a triage session of ten records is one
arming step rather than ten (D-04) and nothing survives the session (Phase 23 D-11's discipline).
The arm is its own switch: arming dispatch grants nothing here and arming here grants nothing there
(D-02), which 30-01 already made true at the backend.

Output: the decision module, its tests, and the skill that makes the whole loop reachable by asking.
</objective>

    Write `operator-claude-plugin/scripts/review_decision.py` with three functions:

    `preview_decision(config, object_type, record_id, decision, reason, transport)` POSTs the decision
    with the dry-run flag true and returns the backend's outcome plus its `would_write` map. This is
    the only source of the exact-write display — the module must not build a patch of its own.

    `submit_decision(config, object_type, record_id, decision, reason, reviewed_by, review_armed,
    transport)` refuses before any network call when `review_armed` is false, returning the preview's
    `would_write` and a plain-language statement that review writeback is off and how to turn it on
    for this conversation (D-03). When armed it sends the dry-run flag false. The armed state arrives
    as an argument from the conversation and is never read from or written to a file, an environment
    variable, or any cache — nothing about it may outlive the session.

    `verify_decision(intended, response)` compares the endpoint's post-write record properties against
    the `would_write` map the operator approved and returns verified, failed, or the endpoint's own
    non-writing outcome (stale, no candidate, not flagged, refused) with its message. A 2xx alone is
    never reported as success (Phase 28 D-14); a mismatch is reported as failed with the differing
    keys named.

    Every function takes the transport as an injectable parameter, as 30-05's fetch does, so tests
    drive them through the stub seam. `reviewed_by` comes from the operator label in config; when it
    is unset the module sends a neutral placeholder rather than an empty string, so the audit trail
    always names something.

    Tests: unarmed submit performs zero transport calls beyond the dry-run preview and returns the
    would-write map; armed submit sends the dry-run flag false exactly once; a response whose
    properties match reports verified; a response missing one approved key reports failed and names
    that key; each non-writing outcome is surfaced verbatim rather than translated into success; no
    module-level state persists an arm between two calls.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| conversation → armed request | The operator's arming intent becomes a real write authorization here |
| endpoint response → "verified" claim | Where an accepted response could be mistaken for a completed write |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-30-24 | Elevation of Privilege | client arming | high | mitigate | The review arm is a separate in-memory flag never persisted anywhere, and the backend's own review flag is the real gate a stray client call still cannot bypass (Task 1, plus 30-01) |
| T-30-25 | Repudiation | success reporting | high | mitigate | Verified is decided by comparing post-write properties to the approved write; a 2xx with mismatched properties reports failed and names the keys (Task 1) |
| T-30-26 | Tampering | exact-write display | medium | mitigate | The display is the backend's own dry-run patch, so the operator cannot approve one thing while another is sent (Task 1) |
| T-30-27 | Information Disclosure | skill and docs | medium | mitigate | No secret is displayed, requested in chat, or written into docs; refusals name what is unconfigured and who can fix it (Tasks 2 and 3) |
</threat_model>

<objective>
Turn a contact-upload dispatch into a per-record ledger the operator can act on, and make an
unfinished run say so. One report renderer, fed either by the synchronous webhook body or — when
that body is absent, thin, or the POST timed out — by `GET /api/v1/executions/{id}?includeData=true`
reading the decision node's own output.

Purpose: this is the whole architecture of the phase on one thin path. Correlate, fetch, parse the
right node, label the outcomes, and refuse to call an in-flight run finished. Every later plan in
this phase expands outward from these two modules, so an architectural mistake here is cheapest to
find now.

Output: `executions_client.py` (thin read-only n8n GETs plus best-effort run-handle correlation),
`report.py` (sufficiency check, contact ledger, reconciliation, summary counts, in-flight framing),
a redacted execution fixture, and the report step in the contact-upload skill.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| n8n executions API → plugin parser | Untrusted external input (arbitrary JSON shape, possibly truncated) crosses here |
| execution payload → conversation | Contact PII (email, phone, name) sits in `properties` and must not be dumped wholesale |
| config secret → conversation | The n8n API key must never cross this boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-26-01 | Repudiation | `reconcile()` in `report.py` | high | mitigate | A write is reported only when the terminal node produced output items; otherwise the row is downgraded to not-confirmed (Pattern 2). Unit-tested with a zero-item write node. |
| T-26-02 | Tampering (operator trust) | `build_contact_report()` in-flight framing | high | mitigate | Any status outside the settled set — including an absent or unrecognised one — renders as in flight. Unknown is never rendered as finished. |
| T-26-03 | Information Disclosure | skill report rendering | medium | mitigate | Summary counts by default; full per-row detail only for the failing subset or on explicit request; a raw execution payload is never pasted into chat. |
| T-26-04 | Information Disclosure | `executions_client.py` error paths | medium | mitigate | The `X-N8N-API-KEY` value is never interpolated into a message or repr; transport exceptions are translated rather than relayed, since a `requests` exception's text can echo request headers. |
| T-26-05 | Denial of Service | executions-API calls | low | mitigate | Exactly one fetch per call, an explicit finite timeout on every GET, and an AST guard forbidding sleep/loop constructs so no poll loop can be added without failing the suite. |
| T-26-06 | Spoofing | run-handle correlation | medium | accept | No execution id is returned by the webhook, so the handle is time-proximity matched and can name a neighbouring run. Accepted for this phase and surfaced in the report wording rather than hidden; a backend change to emit `$execution.id` would close it. |
| T-26-SC | Tampering | package installs | low | accept | No new dependency; `requests` is already declared and audited in `operator-claude-plugin/requirements.txt` (23-03). |
</threat_model>

<objective>
The enrichment lane's half of the report: per record, whether it needs human review, and what
provider credit is left — read from what the backend already hands back, with nothing invented and
nothing about ICP.

Purpose: REPORT-02 as amended. The enrichment response genuinely carries `remaining_credits`, and
the decision nodes genuinely carry the outcome and (for companies) the review flag. What it does not
carry is any ICP value, because Phase 15 deliberately moved those derived outputs to HubSpot. The
report reflects that split rather than papering over it with a placeholder.

Output: `report_enrichment.py` producing the same report object shape `report.py` already produces,
plus a redacted enrichment execution fixture and the tests that hold the two "unknown is not zero"
rules in place.
</objective>

  <action>
    Write `operator-claude-plugin/scripts/report_enrichment.py`, returning the same report object
    shape 26-01's `report.py` already produces so one renderer serves both lanes.

    Build the per-record ledger from the enrichment execution's own decision nodes —
    `Decide Company Action` for the company lane and `Decide Action` for the contact lane — using
    26-01's defensive `data.resultData.runData` traversal rather than a second implementation of it.
    Both the enrichment workflow and the contact-ingest workflow contain a node named `Decide Action`,
    so select the node **within the enrichment execution**, and pick the lane by which node is
    present in the run.

    Map the decision node's action onto operator-facing outcomes. The four values the deployed nodes
    emit are create, enrich, write-blocked and skip. Write-blocked means the write-safety gate
    refused the write, which is a distinct state from a failure and from a success — report it as
    blocked with the reason, never folded into either.

    Read the review flag correctly, because the two lanes differ and this is the trap: the **company**
    decision node emits a top-level review boolean derived from its merge decisions, while the
    **contact** decision node emits no such field. Do not infer false from its absence. An absent
    flag is unknown, and unknown renders as unknown — the same rule Phase 25 D-10 sets for credit
    balances. Where the row's own properties patch carries the backend's review status field, use it;
    where neither is present, say unknown.

    Read `remaining_credits` from the response body's items, appended by `Build Response` as a list of
    provider-and-credits pairs. A credits value of null is a genuine unknown, not a zero — Phase 25
    verified the Apollo key on this account is not a master key and its balance endpoint refuses, so
    null is the expected steady state for at least one provider. Render unknown and real-zero as
    distinguishable states. The client never calls a provider itself; if the response carries no
    credits block at all, render every requested provider as unknown rather than omitting the block,
    so a missing balance is visible rather than silent.

    **Report nothing about ICP.** The tier, the fit score and the anti-ICP flag are all owned by
    HubSpot by a deliberate Phase 15 decision, so the backend has nothing to hand back and the
    operator reads them in HubSpot. Do not add a field for them, and do not add a placeholder saying
    a value could not be retrieved — a placeholder would imply this plugin ought to have the value
    and would re-couple exactly what Phase 15 decoupled (D-10a, D-10b). Keep the rationale in this
    plan and in the phase context; the module itself simply has no such field.

    Hand-write `tests/fixtures/execution_enrichment.json`: a small redacted execution-shaped payload
    with a `Decide Company Action` entry carrying one row per action value, a `Decide Action` entry
    for the contact lane, and a `Build Response` entry whose items carry a credits list with one real
    number and one null. Allow-list the redaction the same way 26-01's fixture does — synthetic
    identifiers only, no real company or contact data, no secret.

    Write `tests/test_report_enrichment.py` covering every behaviour above.

<objective>
Make a partial dispatch actionable and a re-send safe: name the rows that did not land, say which of
them a re-send can actually fix, and route the re-send through the one dispatch path that already
exists, arming gate intact.

Purpose: DISPATCH-04. The safety property is the backend's, not the client's — n8n resolves identity
and routes update-versus-create on every row, so a re-sent row the first attempt already accepted is
updated in place. The client's job is to state that plainly, re-send without inventing a second
dedupe authority, and be honest about the one row shape a re-send can never fix.

Output: a retryability classifier over 26-01's ledger, the retry and re-check steps in the skill, and
a structural guard that keeps the plugin down to one dispatch entry point with no bookkeeping of its
own.
</objective>

    - A row belonging to a chunk that never got a response, or that returned a server error, is

  <action>
    Add `classify_retryability(row)` and a report-level roll-up to `report.py`, returning one of four
    states per row: nothing-to-retry, transport-failure, business-outcome, and permanently-stuck.

    The distinction that matters is the one 26-RESEARCH.md's fourth pitfall names. Phase 25's
    failed-chunk object is a **transport-level** unit — a chunk that timed out, never got a response,
    or returned a server error. Those rows never reached a business decision and re-sending them
    unchanged is exactly right. Rows that did reach a decision and came back for review or rejection
    failed for a **business** reason: the identity rule, an ambiguous match, a verifier verdict.
    Re-sending those unchanged reproduces the identical outcome, so the report says so instead of
    offering a retry that cannot work.

    Classify permanently-stuck from the decision node's own fields. The deployed workflow searches
    HubSpot by email and by nothing else — the name-plus-company branch of the identity function
    exists but is never exercised in this deployment, because nothing populates the weak-key search
    results it reads. A row that arrived with no usable address therefore can never resolve to an
    update and can never be treated as net-new; it lands in review on every attempt, forever. Detect
    it from the status marker `Apply Email` assigns for a missing address combined with an ambiguous
    identity outcome, and read that marker's literal value out of the node rather than assuming it.

    Say this plainly in the row's reason: this row will reach review on every attempt, and it needs an
    email address or handling directly in HubSpot. Do not present it as retryable, do not include it
    in the re-sendable set, and do not soften it into "may need review" — a row the operator retries
    three times before discovering it can never succeed is the failure this classification exists to
    prevent (D-14). This narrows D-04's retry-safety claim, which holds fully for the email path: the
    stuck row is still duplicate-safe, it is simply never resolvable.

    Roll the classification into the report object so the failing-rows section 26-01 already renders
    carries, per row, its identity or ordinal position, its reason, and which of the four states it
    is in. Naming the rows is criterion 4's actual requirement; the classification is what makes the
    naming actionable.

    Write `tests/test_retry_reuses_dispatch.py` covering every behaviour above, reusing 26-01's
    `contact_execution` fixture and adding a no-email row to it if one is not already present.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator retry request → armed dispatch path | A re-send crosses the same live-write boundary as an original send |
| failed-chunk object → dispatch payload | Data returned from a prior run re-enters the send path |

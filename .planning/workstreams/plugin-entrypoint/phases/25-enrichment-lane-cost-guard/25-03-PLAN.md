<objective>
The one genuinely new piece of backend work in this phase: teaching the enrichment webhook to turn a
list identifier into the record events it already knows how to process, using the HubSpot credential
that already lives in n8n.

Purpose: D-01 puts record resolution on the backend so exactly one system knows how to talk to
HubSpot. INGEST-04 is not met without it. The expansion is bounded by the same measured ceiling that
bounds client-side chunking, because a list the client cannot count is a list the client cannot split.

Output: an additive resolution branch in the enrichment workflow, its bound, its refusals, and
offline proof that the record-ID path is byte-for-byte unaffected.
</objective>

    Extend `build_enrichment_cloud()` with an additive branch off the webhook trigger. The trigger's
    existing single edge to `Parse HubSpot Event` becomes the false lane of a new IF node; nothing
    downstream of `Parse HubSpot Event` changes.

    New nodes, in order on the true lane:

    `IF List Input` — true when the incoming body carries a list identifier and no events array.
    Its false lane goes straight to `Parse HubSpot Event`, so the record-ID path is exactly what it is
    today.

    `HubSpot List By Name` — a credential-bound GET against the CRM v3 list-by-name endpoint, with the
    object-type id and the URL-encoded list name taken from the incoming body via an n8n expression.
    Built with the shared httpRequest helper in its GET form and the predefined HubSpot credential
    mode, never hand-written parameters.

    `HubSpot List Memberships` — a credential-bound GET against the memberships endpoint for the
    resolved list id, requesting one more than the recorded `max_records_per_chunk` so an oversize list
    is detectable rather than invisible.

    `Expand List To Events` — a Code node emitting the SAME envelope shape `Parse HubSpot Event`
    already accepts: the provider selection carried through from the original body unchanged, and an
    events array built from the returned record ids with the object type the caller named. This is the
    node the whole branch exists for and the only one that needs pure-function tests.

    Three refusals belong in that node, each producing a terminating item carrying a plain-language
    reason rather than an exception:
      - the membership response carried more ids than the ceiling, or carried a paging cursor. The
        client cannot split a list it cannot count (D-02), so an oversize list is refused with a
        sentence naming the ceiling and suggesting record ids instead. Truncating silently would
        enrich an arbitrary subset and report success.
      - the list name did not resolve. Say so; do not fall through to enriching nothing.
      - an input naming a saved view, handled exactly as `25-BLOCKERS.md` records. If the recorded
        decision was to refuse and redirect, use the exact operator-facing sentence recorded there. A
        view name must never be resolved against the list endpoint (Pitfall 2).

    Wire the expansion node's success output into `Parse HubSpot Event` and its refusal output into the
    same convergence the unsupported-object-type terminal already feeds, so a refusal reaches the
    caller as a response rather than a dangling execution.

    Extract the expansion node's pure logic into a module under `n8n/code/` and inline it the way every
    other Code node in this builder inlines its logic, so Task 2 can test it directly.

    Rebuild and confirm the diff under `n8n/` is confined to `wf_enrichment_cloud.json`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client → `hubspot/enrichment/event` | An untrusted list identifier crosses here |
| n8n → HubSpot Lists API | The HubSpot credential lives only on this side |
| membership response → enrichment chain | An unbounded record set crosses here into a timeout-bounded execution |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-25-07 | Denial of Service | `Expand List To Events` | high | mitigate | Membership fetch requests one more than the measured ceiling; over the ceiling or with a paging cursor present the branch refuses in plain language rather than expanding into an execution that cannot finish inside the response window |
| T-25-15 | Tampering | view-name resolution | high | mitigate | A view input is never resolved against the list endpoint; it takes the recorded refusal path, so a name collision cannot silently enrich the wrong record set (Pitfall 2) |
| T-25-16 | Repudiation | silent no-op on an unexpanded list body | high | mitigate | The branch sits upstream of `Parse HubSpot Event`, whose bare-event fallback would otherwise turn a list body into one unsupported event and report a clean 200; a structural test pins the IF node's placement |
| T-25-06 | Information Disclosure | list membership handling | medium | mitigate | The expansion carries record ids only; no HubSpot property value is read or emitted by this branch |
| T-25-02 | Repudiation | provider selection through expansion | high | mitigate | The incoming selection is carried onto the expanded envelope unchanged and asserted by test, including the empty-selection case, so an expanded batch cannot silently enable more providers than were approved |
| T-25-SC | Tampering | package installs | low | accept | This plan installs nothing |
</threat_model>

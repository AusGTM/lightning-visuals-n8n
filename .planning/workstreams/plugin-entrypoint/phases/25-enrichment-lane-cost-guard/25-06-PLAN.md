<objective>
The split and the sequence: turning a batch the operator approved into a bounded series of requests
that the enrichment webhook can actually finish inside its response window, and handing back the
failures as something Phase 26 can re-send rather than re-derive.

Purpose: the enrichment workflow has no internal batching node, so every record in a POST runs the
full provider and model chain before the response fires. Chunk size is therefore a correctness
property, not a preference — and because a failing chunk must not take the rest of the run with it,
skip-and-continue is what makes a partial success recoverable at all.

Output: a pure chunk planner, a sequential dispatcher with an explicit failure definition, and a
failed-chunk batch that is already a well-formed enrichment request by construction.
</objective>

  <behavior>
    - Dispatching a plan disarmed raises before any chunk is sent, and the stub transport records zero
      calls.
    - Dispatching with no armed argument at all raises a type error.
    - Dispatching an armed three-chunk plan calls the transport three times, in plan order, once per
      chunk.
    - Each call carries the provider selection the plan was built with, unchanged.
    - A chunk whose response status is not successful is recorded as failed and the following chunks are
      still sent.
    - A chunk whose transport raised — including a timeout — is recorded as failed with a reason
      distinguishing it from a status failure, and the following chunks are still sent.
    - A chunk whose response body is not parseable where a parseable body was expected is recorded as
      failed, and the following chunks are still sent.
    - A run in which every chunk fails still attempts every chunk.
    - A run with no failures returns no failed batch.
    - A run with failures returns a failed batch whose record ids are exactly the union of the failed
      chunks' ids, in original order, with no id from a successful chunk.
    - The failed batch is a record specification that the envelope builder accepts unmodified, so
      re-sending it is a dispatch rather than a reconstruction.
    - The per-chunk result records carry enough to report which chunk failed and why, without carrying
      the configured secret.
  </behavior>
  <action>
    Add the sequential dispatcher to `chunking.py`: it takes the plan, the resolved provider selection,
    the armed flag, the config and the transport, and iterates the plan's chunks in order, calling the
    25-04 dispatch entry point once per chunk.

    The armed parameter has no default here either. A whole batch sent by a caller who forgot the flag
    is strictly worse than a single record sent that way, so the same discipline applies.

    Define failure explicitly and in one place: an unsuccessful HTTP status, a transport exception
    including a timeout, or an unparseable body where a parseable one was expected. A timeout is a
    failure for the skip rule even though the backend may still be working — distinguishing those two is
    Phase 26's job, and conflating them here into a retry or an abort would either duplicate work or
    throw away the chunks that would have succeeded.

    Catch per chunk, record, and continue. The loop must not let one chunk's exception escape and end
    the run; that is the entire content of D-12. A run where every chunk fails still attempts every
    chunk.

    Collect the failed chunks' record ids, in original order, into one record specification of the same
    shape the envelope builder already takes. That object is the deliverable of D-13: Phase 26 re-sends
    it, it does not parse it out of log lines. Return it alongside the per-chunk results, and return no
    failed batch at all when nothing failed, so the caller branches on presence rather than on an empty
    container.

    Keep the per-chunk result records small and free of anything from the config: the chunk index, its
    row count, whether it succeeded, and a short reason. A relayed transport exception's text can echo
    request headers.

    Extend `test_chunking.py` with every behaviour above. The two that carry the weight: a run whose
    middle chunk fails must be asserted to have still called the transport for the third chunk, and the
    failed batch's ids must be asserted to exclude every id from a chunk that succeeded — a test that
    only counts failures passes against a dispatcher that hands back the whole batch.

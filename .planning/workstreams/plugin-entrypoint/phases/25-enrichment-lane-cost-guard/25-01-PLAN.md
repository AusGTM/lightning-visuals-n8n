<objective>
Settle the two facts every later plan in this phase is currently guessing at: whether the deployed
HubSpot credential can read the Lists API at all, and how many records fit in one enrichment POST
before n8n Cloud cuts the connection. Both are cheap to measure and expensive to discover
mid-implementation.

Purpose: 25-RESEARCH.md flags list/view resolution (D-02a) and chunk sizing (D-11a) as the phase's
two unresolved blockers. Planning around either without an answer produces work that has to be
thrown away. This plan is deliberately first, deliberately small, and deliberately mostly human.

Output: one live-only admin probe with offline tests, and a recorded decision file the later plans
read at implementation time.
</objective>

  <name>Task 1: One live-only probe that answers "can this credential read a HubSpot list?"</name>
  <files>scripts/check_hubspot_list_scope.py, tests/test_check_hubspot_list_scope.py</files>
  <read_first>
    - `scripts/check_provider_credits.py` in full — the repo's live-only-admin-script convention this
      probe mirrors exactly: lives in `scripts/`, has no `test_` prefix so pytest never collects it,
      gates on an env var, never prints a secret value, never raises on a refusal, and is unit-tested
      offline with mocked `requests` in a sibling `tests/test_*.py`.
    - `tests/test_check_provider_credits.py` — the mocking idiom to mirror (patch `requests` at the
      call site, assert the classification function, never touch the network).
    - `25-RESEARCH.md` §"List/view resolution — HubSpot API surface (D-01/D-02)" — the two endpoint
      shapes, the `crm.lists.read` scope requirement, and Assumption A2.
    - `25-CONTEXT.md` D-02a — why this probe exists and what happens to INGEST-04 if the answer is no.
  </read_first>
  <behavior>
    - Classifying a 200 response yields a granted verdict carrying the resolved list id.
    - Classifying a 404 response yields a granted verdict with no list id — the request was
      authorized, only the name failed to match.
    - Classifying a 403 response yields a denied verdict.
    - Classifying a 401 response yields a verdict distinct from both granted and denied — a bad or
      absent token is not evidence about scope either way.
    - A transport exception yields an inconclusive verdict and never propagates.
    - No verdict object and no printed line contains the token value.
    - With the token env var unset, the script prints a skipped banner and exits 0 without issuing
      any HTTP call.
  </behavior>
  <action>
    Write `scripts/check_hubspot_list_scope.py` as a read-only live-only CLI taking a list name and an
    optional object-type id (defaulting to the companies object type id) as arguments.

    Split it the way `check_provider_credits.py` splits: a pure classification function that turns an
    HTTP status code plus a parsed body into a verdict mapping, and a thin caller that performs the
    request and prints. Only the pure function is unit-tested; the caller is live-only.

    The probe issues `GET` against the CRM v3 list-by-name endpoint
    (`/crm/v3/lists/object-type-id/{objectTypeId}/name/{listName}`, URL-encoding the name) with a
    Bearer authorization header built from `HUBSPOT_PRIVATE_APP_TOKEN`, a finite timeout, and no
    retry. Encode the status classification described in the behaviour block — the 404-means-granted
    subtlety is the whole point of the probe and must be a named, tested branch, not an inline
    fallthrough.

    When the verdict is granted and a list id came back, issue one follow-up `GET` against the
    memberships endpoint for that list id and report ONLY the member count and whether the response
    carried a paging cursor. Report no record ids, no properties, no raw body — this is a scope probe
    and a size probe, not a data extract (T-25-06).

    Print one line per probe naming the verdict, the HTTP status, and — where relevant — the list id
    and member count. Never interpolate the token into any output, exception message, or repr.

    Write `tests/test_check_hubspot_list_scope.py` covering every behaviour above against the pure
    classifier plus the env-gate path, with `requests` patched so no test can reach the network.
  </action>
  <verify>

  </verify>

<task type="checkpoint:decision" gate="blocking">
  <name>Task 3: Decide how a HubSpot "view" input is handled</name>
  <decision>
    INGEST-04 names "list, view, or record IDs". Research found HubSpot saved views have no
    discoverable public API for resolving a view name to record ids — only an absence of evidence, but
    a thorough one. Decide what the enrichment lane does when an operator names a view.
  </decision>
  <context>
    Lists have a documented, scoped v3 API (Task 2 Probe A settles whether this credential can use it).
    Views are a different concept with no evidenced resolution path. Building against an API that may
    not exist risks a phase success criterion; refusing without saying so silently drops a stated
    requirement. D-02a explicitly requires this to be a recorded decision, and — if views are dropped —
    a recorded requirement amendment rather than a silent omission.
  </context>
  <options>
    <option id="refuse-and-redirect">
      <name>Refuse a view input with a message pointing at saving it as a list</name>
      <pros>Ships this phase on an API that demonstrably exists. The operator gets an actionable next
        step inside HubSpot's own UI (most views can be saved as a list). INGEST-04 scopes down to
        lists plus record ids, recorded as an amendment in 25-BLOCKERS.md and applied to
        REQUIREMENTS.md and ROADMAP criterion 1 by plan 25-07.</pros>
      <cons>INGEST-04 is not met as originally worded. A second requirement amendment in this
        milestone, after Phase 23 D-05 and this phase's D-05.</cons>
    </option>
    <option id="discovery-spike">
      <name>Budget a discovery spike inside this phase before committing to a view design</name>
      <pros>Might find a supportable path and meet INGEST-04 as written.</pros>
      <cons>Open-ended cost against an absence-of-evidence finding. Any endpoint found this way is
        likely internal/undocumented, so shipping on it trades a scope gap for a stability gap.</cons>
    </option>
    <option id="treat-view-as-list">
      <name>Accept a view name and resolve it against the Lists API anyway</name>
      <pros>No refusal path to build.</pros>

        list name enriches the wrong record set with no error. Listed only so it is visibly rejected.</cons>

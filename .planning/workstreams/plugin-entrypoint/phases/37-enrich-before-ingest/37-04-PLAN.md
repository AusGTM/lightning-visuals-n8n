<objective>
Turn proposals into decisions and responses into rows — both joined by id, both refusing rather
than guessing.

Purpose: this is where the flow's two most damaging silent failures live. A decision applied to
the wrong row merges one person onto another person's HubSpot record. An enrichment response
zipped by position shifts every subsequent row's data onto the wrong person, and nothing
downstream can detect it. Both are refused structurally rather than tested for afterwards.

Output: `apply_match_decisions`, `merge_enriched`, `rows_from_table`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator spreadsheet -> client | Untrusted file content becomes row values. |
| n8n response -> client rows | Backend-supplied `properties` maps are written onto rows that later become a HubSpot upload. |
| operator confirmation -> match decision | A typed or clicked confirmation selects a real HubSpot record. |

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |

| T-37-15 | Tampering | `merge_enriched` | high | mitigate | Join by `row_id` only; duplicate ids refused at index-build time; unknown ids reported not merged; missing responses marked. Red-checked against a positional zip so the failure mode is observed, not assumed. |

<objective>
Land the two independently-shippable live bug fixes 36-CONTEXT.md §13 sequences first, and
the pure match module they and the next plan both need.

Purpose: `Adapt Search` and `Adapt Fetch By Id` both open with the unfiltered
`const rows = $('Build Identity').all();` and index-align to their own HTTP node
(36-RESEARCH.md §A2). That is safe only while every batch is homogeneous. This phase makes
mixed batches ordinary, so the latent duplication becomes a live one — duplicated provider
calls, double credit burn, duplicate response items. Separately, the INGEST lane's
`HubSpot Search by Email` filter value is `undefined` for an emailless row, which drops the
key, 400s HubSpot, is swallowed by `onError`, and stamps a batch-wide `lookup_failed` that
demotes every sibling row's `create` to `review` (36-RESEARCH.md §A3) — that is this
feature's own re-upload path breaking.

Output: `n8n/code/matchProposal.js` (`laneOf`, `mediumCandidates`, `summarizeMatch`), a
`lane` stamp on every enrichment row, lane-filtered adapters, an `.invalid` sentinel on the
ingest search filter, and three regenerated workflow families.
</objective>

<assumption_delta_decision>
The detector fires on both `pluralization` (one search lane becomes three) and `chosen`
(request behaviour becomes an envelope parameter, `mode`).

**Primary noun: `lane`.** The enrichment row's identity model previously had exactly one
search key — `email` — so "how do we look this row up" was not modelled at all; it was
implied by the single `HubSpot Search` node. **Decision: `promote`.** `lane` becomes the
one field that names a row's identity-resolution strategy; `email` is demoted to one of its
values. Every routing IF and every adapter reads that one stamped field rather than
re-deriving its own predicate, so routing and filtering provably cannot disagree.

**`mode`: `add-alongside`, deliberately.** A `mode`-absent envelope keeps today's behaviour
byte-identically (36-CONTEXT.md §6), so `write` is not promoted to a required field. Accepted
debt: the predicate is two-state by design (`mode != null && lower(mode) !== "write"` →
return-only), which is a fail-safe, not an allow-list. What would force a promote: a THIRD
mode. At that point the two-state predicate must become an explicit dispatch, because a
typo would no longer have one safe destination.

**Invariant test (accepted, wired as Task 2's acceptance criterion):** every routing IF in
the contacts match cascade reads `lane` off `Build Identity`, and no adapter re-derives a
lane predicate of its own. It goes red the instant a second predicate is reintroduced.
</assumption_delta_decision>

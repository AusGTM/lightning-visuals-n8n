<objective>
**This plan is the phase's tracer.** One question — "what is workflow X doing?" — wired end to end
through every client layer this phase touches: the config gate, a read-only n8n Public API client,
the credential-boundary POST to the n8n-side status endpoint, the assembly step, and one
plain-language sentence out the other side. Wave 1's two plans are supply-side (a field added to an
existing endpoint, and a pure lookup table); this is the first plan with an architecture to prove.

Purpose: the credential split in D-01/D-02 is the architectural bet this whole phase rests on — the
client reading workflows and executions itself with the key it already holds, and asking the backend
only for what needs credentials it does not have. Proving that split on one workflow, with a real
runnable check, is what makes plan 27-04's breadth cheap and safe. If the split is wrong, it is
wrong after one plan rather than after four.

Deliberately one workflow, one execution, one line. Every workflow, stuck detection, per-node error
harvesting and the conversational surface are 27-04; the dashboard is 27-05. No stubs that would need
an architectural change to fill — the reads are the real reads, exercised against a stub transport.

Output: three thin modules plus a widened test guard, and a config gate that refuses the status read
in plain language when the n8n API key is not provisioned while still saying what does work.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| plugin → n8n Public API | The n8n API key crosses here; read-only calls only |
| plugin → n8n webhook endpoint | The webhook secret crosses here |
| fetched workflow body → plugin memory | Hundreds of kilobytes of backend internals cross here and must not cross onward |
| config file → conversation | No secret may cross this boundary |

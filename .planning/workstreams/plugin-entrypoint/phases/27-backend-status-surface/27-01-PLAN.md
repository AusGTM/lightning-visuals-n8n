<objective>
Grow the n8n-side status endpoint from the credit-only slice Phase 25 built into the full
credential-gated health picture: how many records are queued, how many are awaiting review, and
which credential-bearing sources are actually reachable. This is the half of the picture the client
cannot read for itself, because the HubSpot and provider credentials live in n8n (D-01/D-02).

Purpose: the client already holds the n8n API key and reads workflow and execution state directly.
Exactly two classes of fact require a credential the client does not have — provider balances
(already served) and HubSpot counts (added here) — plus the health of those credentials themselves.
Everything else stays out of this endpoint by design (D-02).

Scope correction this plan implements: STATUS-04's documented stuck-lock definition names a HubSpot
property that **does not exist in this portal's schema**, and nothing in the pipeline ever writes the
`running` status value that definition depends on. Per D-07a/D-07b, stuck detection moves entirely
to the executions API (plan 27-04, client-side) and this endpoint carries only the two counts that
are genuinely answerable today: requested-but-unresolved, and awaiting-review. Per D-07c, "queued"
is a bare count — no request timestamp is stored anywhere, so it can never be age-based. Per D-07d
this is a recorded requirement amendment, the third in this milestone: ROADMAP.md Phase 27
criterion 4 and REQUIREMENTS.md STATUS-04 were reworded to the execution-age definition at planning
time, so the phase is verified against what can actually be built.

Output: a pure, unit-tested JS module for the null-safe extraction and health derivation, wired into
the built enrichment workflow with four HubSpot count searches and their credential bindings.
</objective>

    - `extractSearchTotal()` on a well-formed search response returns the numeric total.
    - `extractSearchTotal()` returns null — never 0 — for: a non-object input, a missing total field,
      a non-numeric total, a boolean total, and an error-shaped response body.
    - `extractSearchTotal()` returns 0 only when the response genuinely carries a numeric zero.
    - `deriveSourceHealth()` maps a 2xx probe with usable data to an ok state.
    - `deriveSourceHealth()` maps any non-2xx probe to a refused state carrying the status code, and
      never to ok, including the 403 the provider whose key is not a master key returns.
    - `deriveSourceHealth()` maps an unconfigured or unreachable source to an unknown state distinct
      from both ok and refused.
    - `buildStatusBody()` round-trips a null count as JSON null, not as 0, not as an omitted key.
    - `buildStatusBody()` never throws on any malformed input — every branch degrades to unknown.
  </behavior>
  <action>
    Create `n8n/code/backendStatus.js` as a pure module in the same shape as `providerSelection.js`:
    no n8n globals, no `require` of siblings, every exported function total and non-throwing.

    Export three functions. `extractSearchTotal(raw)` reads the HubSpot search response's total field
    and returns a number or `null`; every shape mismatch yields `null`, and the numeric check
    excludes booleans, because a truthy-but-not-numeric total is a malformed response, not a count.
    `deriveSourceHealth(probe)` takes `{configured, status, value}` for one credential-bearing source
    and returns `{state, status, reason}` where `state` is one of three values meaning reachable,
    reachable-but-refused, and cannot-tell; a non-2xx status can never produce the reachable state,
    and an absent credential produces cannot-tell rather than refused (D-08). `buildStatusBody(parts)`
    assembles the response object from the per-source probes and the four counts, preserving `null`
    as `null` — the whole point of this module is that an absent datum survives serialization as an
    explicit absence rather than collapsing into a zero (STATUS-06).

    Keep the counts flat and named for what they measure on which object type: requested-unresolved
    and awaiting-review, each for companies and for contacts. Do not add an age or duration field to
    the queued count — no request timestamp exists on either object, so any age here would be
    fabricated (D-07c).

    Write `tests/n8n/backendStatus.test.mjs` covering every behaviour above, with the zero-versus-null
    distinction asserted on both sides: a genuine numeric zero stays 0, and every failure mode is
    `null` and is asserted `!== 0`.
  </action>

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-27-01 | Information Disclosure | status endpoint response | high | mitigate | The response carries counts, booleans and health states only — no record payload, no property values, no credential material. `limit: 1` on every search means row data is never even fetched |
| T-27-02 | Spoofing | `hubspot/backend-status` webhook | high | mitigate | Inherits the existing header-auth credential on the endpoint Phase 25 built; this plan adds no new entry point and no second auth mode |
| T-27-03 | Tampering | new HubSpot search nodes | medium | mitigate | Filter bodies are built from a fixed builder-side template; no caller-supplied string is interpolated into a filter value (V5) |
| T-27-04 | Repudiation / operator harm | a refused probe rendering as healthy | high | mitigate | `deriveSourceHealth` cannot produce the reachable state from a non-2xx status; asserted by unit test |
| T-27-05 | Elevation of Privilege | endpoint gaining a write path | critical | mitigate | The plan adds only search and code nodes; `tests/test_backend_status_wiring.py` asserts the chain contains no write node, and `tests/test_write_gate_coverage.py` still runs |
| T-27-SC | Tampering | package installs | low | accept | This plan installs nothing — no npm, pip or cargo operation |
</threat_model>

<objective>
Cadence in plain terms: read what a scheduled job does now, say it in a sentence, take a free-form
phrase, say back what it was understood to mean, and only after confirmation write the structured
interval. Plus the other half of CONTROL-03 — enabling and disabling an individual scheduled job,
via the one field D-25 added to the allowlist.

Purpose: D-09 is explicit that the confirmation step, not the parser's cleverness, is the safety
mechanism. A misparse that silently changes how often the backend burns provider credits is the
failure this guards against, and the operator confirms meaning rather than syntax — the same
principle as showing a preview before dispatch.

Output: `operator-claude-plugin/scripts/n8n_cadence.py` — read, describe, parse-or-refuse, the
per-job enable/disable toggle, and the one-node cadence mutation, all over 28-01's pipeline.
</objective>

    - `describe_cadence(interval)` renders each of the five deployed shapes as a plain sentence — a
      15-minute interval, an hourly interval, a monthly interval, a weekly interval.

    - `parse_cadence` on a phrase requiring the expression-based field returns a refusal, not an
      expression.
    - `parse_cadence` on an input that is already schedule-expression syntax returns a refusal.
    - `parse_cadence` on an ambiguous phrase returns a refusal carrying at least three worked example
      phrases the operator can use instead.
    - Every refusal carries a reason and examples; no refusal is a bare None.
  </behavior>
  <action>
    Write `operator-claude-plugin/scripts/n8n_cadence.py` with three pure functions and one refusal
    type — no network, no side effects, so the whole interpretation layer is testable without a
    transport.

    `read_cadence` looks the node up by name in the fetched workflow's node list and returns
    `parameters.rule.interval`. A missing name raises with the actual Schedule Trigger node names
    listed, because a typo in a node name is the most likely operator-facing failure here and a bare
    KeyError would tell them nothing.

    `describe_cadence` renders an interval array into plain language. Cover the six native field
    types and their companion keys per 28-RESEARCH.md's table. Render an array of several entries as
    several clauses. This function is the only thing the operator ever sees describing a schedule,
    so nothing it emits may contain schedule-expression syntax — that is D-09's binding constraint
    and the reason the module never round-trips through an expression internally either.

    `parse_cadence(phrase)` maps a free-form phrase to an interval array using the native field types
    only. Return a refusal rather than a best guess whenever the phrase is ambiguous, whenever it
    would need the expression-based field to express, or whenever it already is schedule-expression
    syntax. Each refusal carries a reason and at least three example phrases that would work.
    Reserving the expression-based field for nothing at all is deliberate: D-10 says a parse needing
    that fallback is exactly the low-confidence interpretation to refuse rather than emit as opaque
    syntax the operator never sees explained.

    The confirmation loop itself is not implemented here — 28-05 owns operator wording. This module
    supplies the two halves that make confirmation possible: the parse, and the description of what
    the parse means. The caller shows the description, waits, and only then writes.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| free-form operator phrase → schedule structure | An unvalidated interpretation silently changes how often the backend burns provider credits |
| cadence mutation → the other four triggers in the same workflow | A whole-workflow write could disturb schedules nobody asked to change |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-28-17 | Tampering | `parse_cadence` misinterpretation | high | mitigate | The parse is described back in plain language and confirmed before any write (D-08/D-09); an ambiguous phrase is refused with examples rather than guessed (D-10) |
| T-28-18 | Tampering | cadence PUT disturbing sibling triggers | high | mitigate | The allowed node set is the single named Schedule Trigger; `assert_only_allowlisted_change` refuses any other node, connections or settings difference before any network call |
| T-28-19 | Information Disclosure (comprehension) | schedule-expression syntax reaching the operator | medium | mitigate | The module never constructs the expression-based field at all; a test iterates the whole mapping table asserting no rendered description matches a field-expression regex |
| T-28-20 | Repudiation | a refusal object written as if it were an interval | medium | mitigate | `set_cadence` rejects a refusal object as input, asserted by a test |
| T-28-31 | Elevation of Privilege | the `disabled` widening used as a foothold to rewrite a trigger node | high | mitigate | D-25's widening is one boolean: reverting `disabled` must reproduce the original node byte for byte, and `set_cadence` may not touch `disabled` nor `set_schedule_enabled` the interval (Task 2, Task 3) |
</threat_model>

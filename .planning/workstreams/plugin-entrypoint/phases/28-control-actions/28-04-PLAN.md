<objective>
Cadence in plain terms: read what a scheduled job does now, say it in a sentence, take a free-form
phrase, say back what it was understood to mean, and only after confirmation write the structured
interval. Plus the half of CONTROL-03 that the deployed topology makes a genuine scope question —
enabling and disabling an individual scheduled job.

Purpose: D-09 is explicit that the confirmation step, not the parser's cleverness, is the safety
mechanism. A misparse that silently changes how often the backend burns provider credits is the
failure this guards against, and the operator confirms meaning rather than syntax — the same
principle as showing a preview before dispatch.

Output: `operator-claude-plugin/scripts/n8n_cadence.py` — read, describe, parse-or-refuse, and the
one-node cadence mutation over 28-01's pipeline.
</objective>

    - Every refusal carries a reason and examples; no refusal is a bare None.

  <action>
    Write `operator-claude-plugin/scripts/n8n_cadence.py` with three pure functions and one refusal
    type — no network, no side effects, so the whole interpretation layer is testable without a
    transport.

    `read_cadence` looks the node up by name in the fetched workflow's node list and returns
    `parameters.rule.interval`. A missing name raises with the actual Schedule Trigger node names
    listed, because a typo in a node name is the most likely operator-facing failure here and a bare
    KeyError would tell them nothing.

    `describe_cadence` renders an interval array into plain language. Cover the six native field
    types and their companion keys per 28-RESEARCH.md's table. Render an array of several entries as
    several clauses. This function is the only thing the operator ever sees describing a schedule,
    so nothing it emits may contain schedule-expression syntax — that is D-09's binding constraint
    and the reason the module never round-trips through an expression internally either.

    `parse_cadence(phrase)` maps a free-form phrase to an interval array using the native field types
    only. Return a refusal rather than a best guess whenever the phrase is ambiguous, whenever it
    would need the expression-based field to express, or whenever it already is schedule-expression
    syntax. Each refusal carries a reason and at least three example phrases that would work.
    Reserving the expression-based field for nothing at all is deliberate: D-10 says a parse needing
    that fallback is exactly the low-confidence interpretation to refuse rather than emit as opaque
    syntax the operator never sees explained.

    The confirmation loop itself is not implemented here — 28-05 owns operator wording. This module
    supplies the two halves that make confirmation possible: the parse, and the description of what
    the parse means. The caller shows the description, waits, and only then writes.

  <name>Task 2: Decision — how does "disable one scheduled job" work with five triggers in one workflow?</name>
  <decision>
    How does CONTROL-03's "enable or disable a scheduled job" work, given that
    `LV Scheduled Maintenance (Cloud)` carries five Schedule Trigger nodes in one workflow?
  </decision>
  <context>
    CONTROL-05's allowlist is written as three items: write-safety flag overlay, Schedule Trigger
    cadence, workflow active state. Workflow active state is workflow-wide — deactivating the
    maintenance workflow to disable one scheduled job would stop all five, including the review
    poller and the stuck-lock sweep. So the allowlist as written cannot express "disable this one
    job", which CONTROL-03 asks for in the same sentence as cadence.

    n8n's mechanism for disabling a single trigger is the node's own `disabled` field. Setting it on
    an already-allowlisted Schedule Trigger node is a one-field change to a node the allowlist
    already names — but it is not literally "cadence", and 28-CONTEXT.md's Deferred section says
    "widening the mutation allowlist is out of scope; any addition is a new requirement, not a
    planning decision." That sentence is why this is a checkpoint and not a planner's call.

    Whichever option is chosen, the structural diff still refuses every other node, every connection
    and every settings change, and the read-back verification is unchanged.
  </context>
  <options>
    <option id="widen-by-one-field">
      <name>Permit the `disabled` field on an already-allowlisted Schedule Trigger node</name>
      <pros>CONTROL-03 is satisfied as written. The change is one boolean on a node the allowlist already names, and is trivially reversible in one step. The field-level diff guard from 28-03 applies unchanged, so the permitted difference stays exactly two fields on one node.</pros>
      <cons>It is a widening of the allowlist, which CONTEXT says is a new requirement rather than a planning decision. REQUIREMENTS.md CONTROL-05's allowlist wording would need updating to name it.</cons>
    </option>
    <option id="refuse-per-job">
      <name>Refuse per-job disable; offer workflow-level on/off and re-timing only</name>
      <pros>The allowlist stays exactly as REQUIREMENTS.md and ROADMAP describe it, with no widening. Consistent with the milestone's refusal to accrete capability.</pros>
      <cons>CONTROL-03's "enable or disable a scheduled job" is only partly satisfied — the operator can re-time a job and turn a whole workflow off, but cannot turn one of the five maintenance jobs off. Requires a REQUIREMENTS.md amendment recording the narrowing, the fourth accepted amendment in this milestone.</cons>
    </option>
  </options>
  <resume-signal>Select: widen-by-one-field, or refuse-per-job.</resume-signal>

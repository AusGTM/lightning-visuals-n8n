  <action>
    Write `operator-claude-plugin/scripts/probe_n8n_semantics.py` as a small CLI with three
    subcommands, each driving 28-01's pipeline rather than its own HTTP.

    `roundtrip` implements D-20: fetch the target workflow, run it through `put_body` unchanged, PUT
    it straight back through `apply_mutation` with an empty allowed-node set (a genuine no-op passes
    the structural diff trivially — which is itself worth proving), then fetch again and report
    whether `settings` and `connections` survived identically. This is the first live PUT the phase
    performs and it changes nothing by construction.

    `execute_probe` implements research A2: POST to the workflow-execute path against a real workflow
    id and report the status code. Expect 404 or 405. A 2xx would mean this Cloud account has the
    unmerged upstream endpoint and D-05a's amendment could be reconsidered — report that as a
    finding, not a failure, and do not act on it in this phase.

    `cadence_reload` implements D-18 and research A1. Take a target workflow id and Schedule Trigger
    node name, capture the current interval, mutate that ONE node's `parameters.rule.interval` to a
    short interval through `apply_mutation` with that node as the only allowed name, wait a bounded
    number of minutes polling `GET /api/v1/executions` filtered to that workflow, and report the
    observed spacing between execution start times against the interval that was set. Then restore
    the captured interval through the same pipeline and report the restoring read-back verdict.
    Report the restore verdict separately and prominently — a probe that leaves a schedule changed
    is worse than a probe that answers nothing.

    **Credentials and gating — one source, named exactly.** The probe loads its credentials with
    `config_gate.load_config()` and calls `require_capability(cfg, "control")` before constructing
    any transport, exactly as every other plugin capability does. It does NOT read `N8N_URL` or
    `N8N_API_KEY` from the shell: those are the backend deploy script's variables, the plugin has
    never used them, and a guard that checked `os.getenv("N8N_URL")` while the request
    authenticated from `config["n8n_url"]` would be checking a value the request never sees — a
    guard that cannot fail is worse than no guard.

    Gate the whole module behind `ALLOW_N8N_PROBE`, defaulting off, refusing unless it reads exactly
    `true` — the same shape as the deploy script's `ALLOW_N8N_DEPLOY`, so the repo has one idiom for
    "this thing touches production" rather than two.

    Apply the wrong-instance check to the CONFIG's URL: if `N8N_EXPECTED_URL` is set,
    `config["n8n_url"]` must equal it exactly; if unset, refuse unless its host genuinely ends with
    `.n8n.cloud`. Never fail open. Do not import the deploy script for this — PLUGIN-04 forbids it;
    reimplement the check in ten lines against the config value and cite
    `deploy_n8n_workflows.py::_instance_ok()` (line 163) as the source of the shape.

    The module must contain no path that writes a write-safety constant. Arming is 28-03's job,
    behind a human gate; a diagnostic that could arm by accident defeats the point of running the
    diagnostic first.
  </action>

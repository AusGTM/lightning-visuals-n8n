<objective>
One armed window, executed by a human, closing the loop this phase exists to build: the plugin arms
live writes through the n8n API, one dispatch lands against one allowlisted test record, the plugin
disarms, and both directions are read-back verified. Then the documentation that tells an admin what
the plugin may and may not do.

Purpose: every automated test in plans 01–05 runs against a stubbed transport, because the plugin's
autouse network guard makes that mandatory and correct. The one thing no stub can establish is that
this account's n8n honors an API-side flag write the way the deploy-time overlay does. 28-02
observed the reload mechanism on a Schedule Trigger; this observes it on the write-safety constant,
which is the one where being wrong costs real data.

Output: `28-CANARY-LOG.md` recording what was run and what was observed, plus the plugin's README
control-surface section and CHANGELOG entry.
</objective>

<task type="checkpoint:human-verify" gate="blocking-human">
  <name>Task 1: The armed canary — one arm→dispatch→disarm cycle, bounded to one record</name>
  <precondition>`N8N_URL`, `N8N_API_KEY` and the plugin's operator config are all present in the executing shell, and a disposable HubSpot test record exists whose id or email domain will be the entire content of the arming allowlist.</precondition>
  <what-built>
    The full control surface: `control_actions.plan_action` composes the consequence and the
    before/after, `execute_action` runs it only on an explicit affirmative,
    `n8n_arming.armed_window` arms with a record-scoped allowlist, dispatches through the existing
    lane path, and disarms with an independent read-back in both directions. A failed disarm reports
    as its own loud state.

    Every automated test behind this ran against a stubbed transport. This is the first and only
    time in the phase that a real write-safety constant is set to its enabled literal on the live
    instance, and it is bounded by a `TEST_RECORD_*` allowlist to a single record.
  </what-built>
  <how-to-verify>
    Agent tooling in this repo is blocked from arming writes. A human runs every step below.

    1. Pick the lane. Prefer the enrichment lane with a single HubSpot object id in the record
       allowlist if Phase 25's enrichment dispatch is built; otherwise use the contact lane with a
       single disposable email domain in the domain allowlist. Note which was used.
    2. Record the backend's flag state BEFORE anything, read through Phase 27's status surface — not
       from local config (D-04). Every declaration in the target workflow must read disabled.
    3. Run the action conversationally through the skill, as an operator would. Confirm that before
       any confirmation is given, the consequence names what live writes permit AND names the single
       record the grant is bounded to. Decline once, and confirm nothing was sent — the decline path
       is as important as the accept path and is cheaper to test here than anywhere else.
    4. Run it again and confirm. Watch for three things: the arm read-back reporting verified, the
       dispatch landing, and the disarm read-back reporting verified. Note the wall-clock duration
       of the armed window — 25-RESEARCH.md's ~100s n8n Cloud webhook response ceiling bounds how
       long an arm→dispatch→disarm cycle can hold the flag open, and this is the measurement that
       says whether that bound is comfortable or tight.
    5. Confirm the write actually happened in HubSpot for the allowlisted record, and confirm no
       other record was touched. The record allowlist is the phase's strongest safety property and
       this is the only place it can be observed working.
    6. Confirm the plugin's API-side arm wrote the SAME literal shape the deploy script's overlay
       writes. Fetch the workflow and compare the declaration text against
       `_OVERLAY_FLAG_SPEC`'s enabled literal. A cosmetic difference here means two conventions
       exist and Phase 27's reader will eventually disagree with Phase 28's writer.
    7. Read the backend's flag state AFTER, through Phase 27's status surface again. Every
       declaration must read disabled. Then run a disarming redeploy from the committed templates as
       the belt-and-braces close-out this repo's armed windows always end with, and re-read once
       more.
    8. Write `28-CANARY-LOG.md`: the lane, the allowlist content, the before state, each verdict,
       the armed-window duration, the HubSpot outcome, the literal-shape comparison, and the after
       state. Record any step that did not behave as described, verbatim.
  </how-to-verify>
  <resume-signal>Type "approved" with the two read-back verdicts, the armed-window duration, confirmation that only the allowlisted record was written, and confirmation that the backend reads disarmed after the redeploy — or describe what failed.</resume-signal>
</task>

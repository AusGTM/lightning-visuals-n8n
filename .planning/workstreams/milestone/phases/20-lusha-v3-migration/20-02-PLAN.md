<objective>
Move both Lusha lanes off v2 onto the v3 combined search-and-enrich endpoints, with the contacts
lane's reveal list derived from the enrichment gate's missing-field set so the pipeline stops
paying for fields HubSpot already holds.

There are five emission sites across three build targets, all generated from string constants in
`scripts/build_cloud_workflows.py`, plus the standalone `scripts/dryrun_batch.mjs` harness. Today
those sites disagree about the identity set (the CLOUD contacts node sends only email/linkedin;
the LOCAL-LIVE node and the harness build a broader name+company query). That split predates this
migration and is carried forward deliberately rather than silently unified — see the task actions.

The measured baseline this attacks: ~4.65 credits per matched reveal, ~12.6k credits for a full
sweep against a ~3.9k balance. Selective reveal is the lever.

Purpose: one confirmed request shape per lane, built once and consumed by every target.
Output: `n8n/code/lushaRequest.js` as the single source of request-body truth, all five emission
sites rewired, contract tests re-pinned to v3, workflows rebuilt.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| enrichment gate output -> Lusha request body | Gate-derived field names cross into a request that costs money per revealed field. |
| n8n credential store / `$env` -> Lusha HTTP node | The `api_key` secret crosses here; it must stay bound to the credential (CLOUD) or `$env` expression (LOCAL-LIVE) and never enter a Code node or a body expression. |
| built workflow JSON -> live n8n deployment | A malformed body shape reaches production silently because provider nodes continue on error. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-02 | Elevation of resource consumption (cost abuse) | `lushaReveal()` and the CLOUD body expression | high | mitigate | Reveal list built from the frozen `LUSHA_REVEAL_BY_FIELD` literal map with `hasOwnProperty` lookups; unmapped and prototype-chain names drop out; unit-tested with a hostile-input case. A present-and-fresh mobile phone cannot produce a phone reveal because the gate never lists it as missing, and a fully populated contact never reaches the provider waterfall at all (the gate routes it to skip). |
| T-20-01 | Information Disclosure | Lusha HTTP nodes in all three targets | high | mitigate | `_http_node(auth="header")` on CLOUD keeps the key in the generic header-auth credential; `_live_http` keeps it in the `$env` expression. Neither the body expression nor `lushaRequest.js` reads, receives or logs the key — the module takes identity and missing-field arguments only, asserted by the module carrying no key-shaped identifier. |
| T-20-04 | Repudiation (malformed request indistinguishable from a clean no-match) | v3 request bodies | high | mitigate | Field names come from `docs/LUSHA-V3-CONTRACT.md`'s live 200, not from a guess; both contract tests evaluate the real committed expression rather than a reimplementation; the parity test forecloses drift between the CLOUD expression and the shared module. `onError: "continueRegularOutput"` is deliberately retained — a down provider must not fail an enrichment run — so a contract test, not runtime behaviour, is the guard. |
| T-20-05 | Tampering (silent divergence between three copies of one request shape) | LOCAL-LIVE builders, CLOUD expression, dry-run harness | medium | mitigate | One module, inlined into the Code-node targets and required by the harness; the one consumer that cannot import it (the n8n expression) is pinned by a deep-equality parity test against the module. |
| T-20-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task in this plan. `lushaRequest.js` is dependency-free by construction (asserted: zero `require`/`import` lines), the tests use the built-in `node:test` runner, and the builder change adds no Python dependency. No new supply-chain surface, so no legitimacy audit applies. |
</threat_model>

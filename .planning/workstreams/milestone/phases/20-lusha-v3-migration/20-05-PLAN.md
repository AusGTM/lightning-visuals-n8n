<objective>
Prove the migration landed everywhere and nowhere regressed: an offline guard against v2 URLs
returning, both suites green, the frozen fixture accounted for, and a disarmed redeploy whose
read-back shows v3 live and no v2 remaining.

The read-back is a distinct step from the redeploy on purpose. Phase 19's deployment-drift finding
(BUG 26) was exactly a case of the live deployment silently predating the committed build; trusting a
deploy script's exit code is what let that persist. The live artifact gets read back and inspected.

This plan arms nothing. Disarmed deploys, workflow activation and API read-backs are within the
executor's sanctioned envelope; arming any write flag is not, and no step here needs one.

Purpose: convert "we changed it" into "the live artifact proves it".
Output: a regression guard in the topology test file, a re-runnable live URL verifier, both suites
green, and a disarmed deployment with recorded read-back evidence.
</objective>

The verifier imports `_base_url()` and `_n8n_headers()` from `scripts/deploy_n8n_workflows.py` rather
than re-implementing auth or URL assembly — one place owns how this repo talks to the n8n API. It
GETs the deployed enrichment workflow, serializes its nodes, and reports counts: occurrences of the
retired Lusha major-version path prefix, occurrences of each v3 search-and-enrich URL, occurrences of
the v3 account usage URL, and the HTTP method plus body-presence of every node whose name identifies
a Lusha node. It exits non-zero if any retired URL is present or if either v3 endpoint is missing.
It prints only counts, node names, methods and URLs — never a credential value, never a token, and
never a node's full body. When `N8N_URL` or `N8N_API_KEY` is absent it prints a skip banner and exits

at all, not even an empty one:

```

```

Run from the repo root. `load_dotenv()` does not override shell-set variables, so the shell's values
win and `.env` fills in only the credentials.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| repo committed artifact -> live n8n deployment | A build artifact becomes running production behaviour here. |
| verifier -> n8n Cloud API | The n8n API key crosses here; the verifier reads and must never print it. |
| live workflow body -> local output | Deployed node bodies may contain expression text; printing them wholesale could surface configuration detail unnecessarily. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-20-11 | Repudiation (a deployment that silently predates the committed build) | the redeploy step | high | mitigate | The read-back is a separate step from the deploy and inspects the live artifact rather than trusting the deploy script's exit code. This is the direct lesson of Phase 19's BUG 26 deployment-drift finding, where the live deployment predated the committed build while every local check passed. |
| T-20-12 | Tampering (a regression reintroducing a retired provider URL after this phase closes) | built workflow artifacts | medium | mitigate | An offline test asserts zero occurrences of the retired path across four artifacts and builds the workflow in-process so an unrebuilt edit fails too; a positive assertion on each v3 endpoint prevents the negative assertion being satisfied by deleting the nodes. |
| T-20-01 | Information Disclosure | `scripts/verify_live_lusha_urls.py`, the deploy command | high | mitigate | Auth is delegated to the deploy script's existing helpers rather than reconstructed; the verifier prints only counts, node names, methods and URLs; credentials load in-process via `load_dotenv()` and no command in this plan reads or prints `.env`. |
| T-20-13 | Elevation of Privilege (an accidental armed write during the redeploy) | the deploy invocation | high | mitigate | The redeploy passes no flag-overlay argument at all, which is the documented disarmed form; the plan states arming is out of scope for every step and that needing a write flag is a signal the plan is being misread; an acceptance criterion asserts the recorded command carries no overlay. The deploy script additionally refuses to arm a write flag without an allowlist in the same invocation. |
| T-20-SC | Tampering | npm/pip/cargo installs | high | accept | No package-manager install task in this plan. The verifier uses `requests` via the deploy script's existing helpers plus `python-dotenv`, both already present and already used by the Phase 19 runbook. No new supply-chain surface, so no legitimacy audit applies. |
